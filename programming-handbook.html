The one habit

A program does exactly what it says, which is often not what you meant. Most of programming is closing the distance between the two, and you can only close what you can see.

So before you run code, predict what it will do, and when it surprises you, find out why before you change anything. A bug you understand is half fixed. A bug you made go away by changing things until it stopped is still there.

Chapter 1

Values, types and expressions

12 min read3 exercises

Everything a program works with is a value: a number, a piece of text, a list, the absence of a value. Every value has a type, and the type decides what operations mean, which is why "42" * 2 is "4242" and 42 * 2 is 84. Programs compute new values from old ones with expressions, which Python evaluates one operation at a time in a fixed order. This chapter watches that happen step by step, and then looks at the places where Python's numbers behave differently from the numbers you learned at school.

Values and their types

A value is a piece of data. 42 is a value, so is "hello", so is [4, 2]. A type is a kind of value, together with the operations that make sense on it. Integers can be added and divided. Strings can be joined and searched. Lists can be appended to and sorted. Python's built-in types cover most of what a program needs: int for whole numbers, float for numbers with a fractional part, str for text, bool for True and False, None for "no value", and the collections list, tuple, dict and set, which hold other values and have chapters of their own.

type(value) tells you a value's type, and you'll use it constantly while learning. The type matters because operators mean different things for different types. + adds numbers but joins strings. * multiplies numbers but repeats strings and lists. And some combinations have no meaning at all: Python won't guess whether "42" + 2 should be "422" or 44, so it raises a TypeError instead. That refusal is a feature. A language that guessed would sometimes guess wrong, silently.

Expressions

An expression is anything that produces a value: a literal like 7, a name like total, a calculation like 2 + 3 * 4, a function call like len(items). Expressions combine: the operands of an operator can themselves be expressions, to any depth. Python evaluates a compound expression one operation at a time. It first decides the structure, which operations apply to which operands, using precedence, the rule that * binds more tightly than +. Then it computes operations whose operands are already values, replacing each with its result, until one value is left.

The example's first part is a small program that performs those steps visibly. It uses Python's own parser, the ast module, to find the structure, then repeatedly evaluates the first operation whose operands are both values, and prints the expression after each step. The rest of the example looks at types, numbers and conversions.

The precedence rules you need to remember are few. From tightest to loosest: **; unary minus; *, /, // and %; + and -; comparisons such as < and ==; not; and; or. Operators on the same level are evaluated left to right, except **, which goes right to left, so 2 ** 3 ** 2 is 2 ** 9. When in doubt, add parentheses. They cost nothing, and they tell the next reader what you meant.

Integers and floating-point numbers

Python's integers have no upper limit: 2 ** 100 is computed exactly, using as much memory as the digits need. That's unusual. In C, Java and most other languages an integer is a fixed number of bits, typically 64, and arithmetic past the limit wraps around or is undefined. Python hides that, which is one less thing to go wrong.

Floats are different. A float is a binary fraction with about 16 significant decimal digits, stored in 64 bits under the IEEE 754 standard, which every modern processor implements in hardware. Most decimal fractions can't be written exactly in binary, just as 1/3 can't be written exactly in decimal. So 0.1 is stored as the nearest binary fraction, which the example prints in full: slightly more than one tenth. Adding two such approximations gives 0.30000000000000004, which isn't equal to the approximation of 0.3. This isn't a Python bug. Every language using hardware floats behaves the same way.

Three rules follow. Never compare floats with == after arithmetic; use math.isclose(a, b), which allows a small relative error. Never use floats for money, where every cent must be right; use integers counting the smallest unit, cents or pence, or the decimal module, which does decimal arithmetic exactly. And remember that floats have limits: 1e308 * 10 is inf, and nan, "not a number", is the result of undefined operations like inf - inf and is famously not equal even to itself.

Division and rounding

Python has three division operators, and the example shows why it needs them. / is true division and always gives a float: 7 / 2 is 3.5. // is floor division: the result rounded down to a whole number, so 7 // 2 is 3 but -7 // 2 is −4, because −4 is below −3.5. % is the remainder that goes with it, and in Python it takes the sign of the divisor, so -7 % 2 is 1. Together they always satisfy (a // b) * b + a % b == a. C and Java truncate toward zero instead, so -7 / 2 is −3 there and the remainder is −1. Code ported between languages breaks on exactly this.

Rounding has its own surprises. int(-3.7) truncates toward zero and gives −3, while math.floor gives −4. And round(2.5) is 2, not 3, because Python rounds halves to the nearest even number, a rule called banker's rounding that avoids a systematic upward bias when many values are rounded. If you need the schoolroom rule for money, the decimal module provides it.

Conversions and truthiness

Values change type only when you ask. int("42") parses a string into an integer and raises ValueError if the string isn't one. str(42) goes the other way. float("2.5") parses a float. Input from users, files and networks always arrives as text, so these conversions are where invalid data is first noticed, and chapter 10 is about what to do then.

Every value can also be used as a condition. A few values count as false: False, None, zero in any numeric type, and empty collections such as "", [] and {}. Everything else is true, including the string "0", the list [0] and the string "False". and and or use this truthiness, and they don't return True or False: they return one of their operands. a or b is a if a is true, otherwise b, and it doesn't evaluate b at all when it doesn't need to, which is called short-circuiting. That makes name or "anonymous" a common idiom, and also a common bug when a valid value, like 0, happens to be false.

Common traps
  • Comparing floats with == after any arithmetic. Use math.isclose.
  • Using floats for money. Count cents in an int, or use decimal.Decimal.
  • Assuming // and % work as in C or Java for negative numbers.
  • Writing x or default when 0, an empty string or an empty list is a legitimate value of x.
  • Expecting round(2.5) to be 3. It rounds halves to even.

Exercise 1.1Predict, then check

Without running them, write down the values of 2 ** 3 ** 2, -2 ** 2, 7 // -2, 7 % -2 and 10 / 4 * 2. Then check them in Python and explain any you got wrong.

Show solution

2 ** 3 ** 2 is 512: ** groups from the right, so it's 2 ** 9, not 8 ** 2. -2 ** 2 is −4, because ** binds more tightly than unary minus, so it means -(2 ** 2); write (-2) ** 2 for 4. 7 // -2 is −4: the exact quotient is −3.5, and floor division rounds down, toward minus infinity. 7 % -2 is −1, since the remainder takes the divisor's sign, and it checks out: (−4) × (−2) + (−1) = 7. 10 / 4 * 2 is 5.0: / and * share a level and go left to right, so it's (10 / 4) * 2, and / always produces a float. If you got the second one wrong, you're in good company, and it's a case where parentheses are worth writing even though they aren't needed.

Exercise 1.2Ten dimes

Add 0.1 to a total ten times, starting from 0, and compare the result with 1.0. What do you get, and why? Rewrite the calculation two ways so that it's exact.

Show solution

The total is 0.9999999999999999, and total == 1.0 is False. Each 0.1 is stored as a binary fraction slightly larger than one tenth, and each addition rounds its result to the nearest representable float; the ten small errors don't cancel exactly. The first exact version counts in whole cents: add the integer 10 ten times, get 100, and divide by 100 only when displaying. Integers are exact, so there's nothing to go wrong. The second uses decimals: from decimal import Decimal, then add Decimal("0.1") ten times to get exactly Decimal("1.0"). Note the string: Decimal(0.1), from a float, would faithfully copy the float's error, as the example shows. Financial code uses one of these two approaches, never floats.

Exercise 1.3When zero is an answer

A function receives quantity, which is a number or None when the user left the field blank. It does quantity = quantity or 1 to default blanks to 1. What goes wrong, and what's the correct version?

Show solution

The fix tests for the specific value meaning "missing": quantity = 1 if quantity is None else quantity. is None is the right test here, because there's only one None object, and it's what Python's style guide recommends for this comparison. Chapter 2

Names, assignment and scope

10 min read3 exercises

A variable in Python is not a box that holds a value. It's a name attached to a value, and two names can be attached to the same one. That single fact explains most of the surprises beginners meet, from a list that changes "by itself" to a counter that refuses to count. This chapter shows how assignment binds names, how mutating a value differs from rebinding a name, and where Python looks when you use a name: the rules called scope.

Assignment binds a name

A statement is an instruction that does something rather than producing a value, and the most common is assignment. scores = [70, 85] evaluates the right side, creating a list, and then binds the name scores to it. backup = scores evaluates the right side again, which is just the name scores, so it finds the same list, and binds a second name to it. Nothing was copied. There is one list with two names, and appending through either name changes the one list, which is visible through both.

Now assign backup = [0]. That creates a new list and moves the name backup to it. The original list is untouched, and scores still names it. So there are two quite different operations that both look like "changing a variable": mutating an object, through a method like append or an assignment to an element like xs[0] = 1, which every name for that object sees; and rebinding a name with =, which affects that name only.

Some types can't be mutated at all: integers, floats, strings, tuples and None are immutable. For them, an operation that looks like a change, such as count += 1, computes a new value and rebinds the name to it. That's why before = count; count += 1 leaves before alone. For a mutable list, += really does change the object in place, so it's seen through every other name, as the example shows. The same symbol does two different things depending on the type. Chapter 15 returns to this in detail, because it's the root of the aliasing bugs that experienced programmers still write.

Names have no types; values do

A name can be bound to an integer on one line and a string on the next. Python checks types when an operation runs, not when a name is assigned, so a name's "type" is just the type of whatever it's bound to at the moment. Type hints such as count: int = 0 document your intent and let checking tools catch mistakes, as chapter 6 of The Engineer's Press explains, but Python itself ignores them when running the program. Good names do more for correctness than you might expect: total_pence tells the reader the unit and the type, and x2 tells them nothing. Python's conventions, from the style guide PEP 8, are lower_case_with_underscores for variables and functions, CapitalisedWords for classes and UPPER_CASE for constants.

Scope: where Python looks for a name

A name's scope is the part of the program where it can be used. When Python meets a name, it looks in four places, in order, and uses the first match. That's the LEGB rule: the Local scope of the current function; the scopes of any Enclosing functions it's written inside; the Global scope of the module; and the Built-in scope, where len, print and list live. In the example, inner has no level of its own, so it finds the enclosing function's, which hides the global one.

The built-ins come last, so any name you define hides one. list = ["a", "b"] is legal, and afterwards list("xyz") fails, because list now means your list. This is called shadowing, and it's a common source of baffling errors when someone names a variable list, dict, str, sum, max or input. Linters such as Ruff warn about it.

The rule that surprises everyone is how Python decides a name is local. It doesn't look at the order of lines. If a function assigns to a name anywhere in its body, that name is local everywhere in the function, decided before the function runs. So visits += 1, which reads visits and then assigns it, makes visits local, and the read happens before any local value exists: UnboundLocalError. Declaring global visits tells Python the name means the module's variable, and nonlocal n does the same for an enclosing function's variable, which is how the example's counter keeps its count between calls.

Use those declarations sparingly. A function that changes a global is harder to test and reason about, because its behaviour depends on state outside it. Usually the better design is to pass the value in and return the new value, which chapter 4 develops. The counter built with nonlocal is a legitimate use, because the state is private to the function that owns it, and chapter 13 shows the same idea done with a class.

Blocks are not scopes

In many languages, a variable declared inside an if or a loop disappears at the end of it. In Python, only functions, classes, modules and comprehensions create scopes. A for loop's variable is an ordinary name in the surrounding scope and keeps its last value after the loop ends; a name first assigned inside an if exists afterwards, if that branch ran. A list comprehension is the exception: its variable lives in the comprehension's own scope and doesn't leak, as the example checks. Finally, the walrus operator :=, added in Python 3.8, is assignment inside an expression, useful in conditions such as if (n := len(items)) > 10:. Ordinary assignment with = is a statement and can't appear there.

Common traps
  • Thinking b = a copies a list. It names the same list; use a.copy() or list(a) for a copy.
  • Naming a variable list, str, sum or input, and then calling the built-in.
  • Incrementing a global inside a function without global, and getting UnboundLocalError.
  • Reaching for global when returning a value would be clearer.
  • Using a loop variable after the loop without noticing that it keeps its last value, or doesn't exist if the loop never ran.

Exercise 2.1Plus or plus-equals

After a = [1]; b = a; a = a + [2], what are a and b? After a = [1]; b = a; a += [2]? Draw the names and objects for each.

Show solution

In the first, a is [1, 2] and b is [1]. a + [2] builds a new list, and a = ... moves the name a to it; b still names the original. Two names, two lists. In the second, both are [1, 2]. For lists, += calls the list's in-place extend method, which changes the existing object, and then rebinds a to that same object. One list, two names. The difference only matters when another name refers to the list, which is exactly when it causes bugs: a function that does items += [x] on a list it was given changes the caller's list, while items = items + [x] doesn't.

Exercise 2.2A counter without global

Rewrite record_visit from the example so that it needs neither global nor nonlocal, and so that a test could check it without touching module state.

Show solution

Make the count an input and the new count an output: def record_visit(visits): return visits + 1, called as visits = record_visit(visits). The function now depends only on its argument, so a test is a single line, assert record_visit(4) == 5, and two parts of the program can keep separate counts without interfering. The caller decides where the state lives. If the state belongs with other related data, such as a visit count and the time of the last visit, the next step is a small class with a record_visit method, which chapter 13 covers. Exercise 2.3The vanishing built-in

A script contains sum = 0 near the top, and a hundred lines later average = sum(scores) / len(scores) fails with TypeError: 'int' object is not callable. Explain the error, and describe two ways a tool could have caught it before the script ran.

Show solution

sum = 0 created a global named sum, which comes before the built-ins in the LEGB order. From then on, sum means the integer 0, so sum(scores) tries to call 0 as a function. The message says exactly that, though it doesn't say why sum is an integer. The fix is to rename the variable, to total for instance. A linter catches it statically: Ruff's rule A001 and flake8's builtins plugin report any assignment that shadows a built-in. A type checker such as mypy or Pyright catches it too, by inferring that sum is an int and reporting that an int isn't callable. Both run in seconds and are worth running on every save.

Chapter 3

Control flow and loop invariants

10 min read3 exercises

A program becomes interesting when it decides and repeats: if chooses between paths, and loops do something once per item or until a condition changes. Loops are also where most off-by-one errors live, because a loop that is nearly right looks exactly like one that is right. The remedy is to know what your loop keeps true on every pass, its invariant, and why it must stop. This chapter writes two classic loops with their invariants checked, then tests three versions of binary search against every small input and finds the two bugs at once.

Choosing and repeating

if, elif and else run the first branch whose condition is true. Python has two loops. A for loop runs once for each item of something iterable: a list, a string, a file's lines, or range(n), which produces 0 up to n - 1. A while loop runs as long as its condition is true, and is for loops whose length you don't know in advance. Inside either, break leaves the loop at once and continue skips to the next pass. A for loop can also have an else clause, which runs only if the loop finished without a break; it's the natural shape for "search, and do something if nothing was found", as the end of the example shows.

Prefer for when you can. It can't run forever over a finite collection, and it can't skip or repeat an item through a mistake with an index. enumerate(items) gives you the index too, and zip(a, b) walks two sequences together. A while loop puts the burden of progress on you: something in the body must eventually make the condition false.

Invariants

A loop invariant is a statement about your variables that is true before the loop starts and stays true after every pass. It's the loop's purpose, stated so it can be checked. To show a loop is correct you show three things. Initialisation: the invariant is true before the first pass. Maintenance: if it's true before a pass, the pass keeps it true. Termination: when the loop stops, the invariant together with the reason it stopped gives the result you wanted.

Insertion sort is the standard example. Its invariant is "items[:i] is sorted". It starts true, because a list of one item is sorted. Each pass takes items[i], shifts the larger sorted items right by one and drops it into the gap, so items[:i + 1] is sorted: maintained. The loop stops when i reaches the length, so the whole list is sorted. The example asserts the invariant on every pass and prints the list as it grows, so you can watch it hold.

Binary search, and how nearly right goes wrong

Binary search finds a value in a sorted list by repeatedly halving the range that could contain it. It is famous for being easy to describe and hard to write: Jon Bentley reported that most professional programmers he asked couldn't write a correct version, and a bug in the version in Java's standard library went unnoticed for nine years. The invariant makes it manageable. Use a half-open range, lo included and hi excluded, as Python's slices and range do, and keep this true: if the target is in the list, it's in xs[lo:hi].

Each branch of the correct version preserves the invariant. If xs[mid] < target, the target can't be at mid or anywhere left of it, because the list is sorted, so lo = mid + 1. If xs[mid] > target, it can't be at mid or to its right, so hi = mid, which excludes mid because hi is excluded. When lo == hi, the range is empty, and the invariant says the target isn't present. Termination needs one more argument, a variant: a whole number that decreases on every pass and can't go below zero. Here it's hi - lo, and both branches shrink it by at least one, because mid is always inside the range.

The two buggy versions each break one of those arguments. Bug 1 starts with hi = len(xs) - 1 but keeps the half-open logic, so the last element is never inside the range: it fails exactly once per list length, 6 times in 56 cases, always on the last element. Bug 2 writes lo = mid, which doesn't shrink the range when mid == lo, so the variant stops decreasing and the loop spins forever; the example caps it and reports "stuck". Neither bug shows up on a typical hand-picked test. Testing every list of length 0 to 6 against every possible target, 56 cases, found both at once, which is a technique chapter 11 develops: small inputs, all of them.

The payoff for getting it right is large. Each look halves the range, so a million items take at most 20 looks, as the example measures, and a billion take 30. A loop that scanned item by item would take up to a million and a billion.

Common traps
  • Mixing inclusive and exclusive bounds in one loop. Pick half-open ranges, as Python does, and stick to them.
  • A while loop whose body doesn't always make progress, so some input makes it run forever.
  • Using indexes where for x in items, enumerate or zip would do.
  • Testing only the middle of the input space, when bugs live at the empty list, one item, and the last item.
  • Forgetting that else on a loop means "no break", not "the loop didn't run".
Exercises
Exercise 3.1The invariant of max

Write a loop that finds the largest number in a non-empty list without using max. State its invariant, and check initialisation, maintenance and termination.

Show solution
def largest(xs):
    best = xs[0]
    for i in range(1, len(xs)):
        # invariant: best == max(xs[:i])
        if xs[i] > best: best = xs[i]
    return best

The invariant is "best is the largest of xs[:i]". Initialisation: before the first pass, i is 1 and best is xs[0], the largest of the one-element slice. Maintenance: the pass compares xs[i] with the largest so far and keeps whichever is bigger, so afterwards best is the largest of xs[:i + 1]. Termination: the loop ends after i reaches len(xs) - 1, so best is the largest of the whole list. The precondition "non-empty" matters: on an empty list, xs[0] raises IndexError, which is a better outcome than returning a made-up value, and the docstring should say so.

Exercise 3.2Why bug 2 is stuck

Trace search_bug2([0], 1) from the example by hand. Which part of the correctness argument fails, and is the invariant itself still true?

Show solution

Start with lo = 0, hi = 1. mid = (0 + 1) // 2 = 0, and xs[0] = 0 < 1, so lo = mid = 0. Nothing changed, so the next pass computes the same mid and does the same thing, forever. The invariant still holds: 1 isn't in the list, so "if it's in the list, it's in xs[0:1]" is vacuously true, and in general lo = mid never excludes a position that could hold the target. What fails is termination. The variant hi - lo must decrease on every pass, and when mid == lo, which happens whenever the range has one element, lo = mid leaves it at 1. That's why correct code writes mid + 1: mid was just checked and found too small, so excluding it is both allowed by the invariant and needed for progress.

Exercise 3.3Counting digits

Write digits(n), which returns the number of decimal digits in a non-negative integer, using a while loop and no strings. Give the variant that proves it stops, and test it on every value from 0 to 1,000 against len(str(n)).

Show solution
def digits(n):
    count = 1
    while n >= 10:
        n //= 10
        count += 1
    return count

assert all(digits(n) == len(str(n)) for n in range(1001))

The variant is n itself: each pass replaces it with n // 10, which is strictly smaller for any n ≥ 10, and a non-negative whole number can't decrease forever. Starting count at 1 handles 0 correctly, which has one digit; a version that starts at 0 and loops while n > 0 returns 0 for 0, a bug that only the edge case reveals. The exhaustive check takes a moment and covers every one-, two-, three- and four-digit boundary, which is far more convincing than three hand-picked tests.

Chapter 4

Functions

9 min read3 exercises

A function gives a name to a computation, so you can use it without thinking about how it works. That's the most important tool in programming, because it's how a problem too big to hold in your head becomes several problems that each fit. This chapter breaks a small text-analysis problem into four functions, then covers what makes a function easy to use and test: returning results instead of changing things, the trap of mutable default arguments, the ways of passing arguments, and functions as values in their own right.

Breaking a problem into functions

"Find the most common interesting words in a passage" is one sentence, but the program has several steps: split the text into words, ignoring case and punctuation; count each word; drop the boring words and take the most frequent; format the result. Each step is a function: a named piece of code that takes arguments and returns a result. def words(text): declares a function with one parameter, text, which is bound to whatever argument the caller passes, and return sends a value back. A function that reaches the end without return returns None.

Decomposed like this, each function is small enough to get right by itself, and to test by itself, because its whole behaviour is "this input gives that output". When the program is wrong, you can check each stage's output separately and find the stage where it goes wrong. And the pieces are reusable: count works for anything you can iterate over, not just words. A useful test for whether a function is well chosen: can you say what it does in one sentence without the word "and"?

Pure functions and side effects

A pure function's result depends only on its arguments, and calling it changes nothing else: no printing, no modifying its arguments, no writing files or globals. The four pipeline functions are pure. Anything else a function does is a side effect. Programs need side effects, since a program that prints nothing and writes nothing is useless, but they're easiest to understand and test when they're kept at the edges, in a few functions whose job is input and output, with the logic in pure functions between them.

Python's standard library follows a convention that makes the distinction visible: a method that changes an object in place returns None. sorted(nums) is pure and returns a new list; nums.sort() sorts the list itself and returns None, so result = nums.sort() is a classic bug that leaves result as None. The same holds for list.append, list.reverse and dict.update. Following the same convention in your own code, a function either answers a question or makes a change, but not both, makes calls easier to read.

The mutable default argument

A default value makes a parameter optional: def add_tag(tag, tags=[]). The surprise is when the default is evaluated: once, when the def statement runs, not each time the function is called. So every call that uses the default gets the same list, and the example's second call returns ['a', 'b'], because the first call's tag is still in the shared list. Immutable defaults such as numbers, strings and None are safe, since they can't be changed. For a mutable default, the idiom is tags=None, then if tags is None: tags = [] inside the function, which makes a fresh list on every call. Linters flag the mistake, and it's worth letting them.

Passing arguments

Arguments can be passed by position, describe("Ada", 36), or by name, describe("Ada", age=36). Named arguments make calls readable when there are several of the same type: resize(img, width=640, height=480) can't be misread the way resize(img, 640, 480) can. A function can also accept any number of extra positional arguments with *args, collected as a tuple, and extra keyword arguments with **kwargs, collected as a dict. In the signature, a bare / makes the parameters before it positional-only, and a bare *, or *args, makes the ones after it keyword-only. The example's describe uses all of them, and the error messages for bad calls show Python checking the call against the signature before running a line of the body.

Keyword-only parameters are worth using deliberately. def connect(host, *, timeout=10, retries=3) forces callers to write timeout=, so a later reader never has to guess what connect("db", 5, 2) means, and you can add or reorder options later without breaking callers.

Functions are values

A function is an object like any other: it can be stored in a variable, kept in a dict, passed to another function and returned from one. sorted(words, key=len) passes the function len, and sorted calls it on each item to decide the order. A lambda is a small anonymous function written inline, lambda w: (len(w), w), for when a name would be overkill. And a function defined inside another can use the outer function's variables even after the outer one has returned, which is how make_scaler(2) returns a function that remembers its factor. That's a closure, and chapter 10 of The Engineer's Press explains how it's implemented.

Functions as values let you write code that's general over behaviour, not just data. A dict of functions replaces a long if-elif chain that dispatches on a name. A sort or search takes the comparison as an argument. Chapter 14 returns to this: often the right way to vary one behaviour is to pass a function, not to write a subclass.

Common traps
  • Using a mutable default argument such as [] or {}, shared between calls.
  • Assigning the result of an in-place method, as in xs = xs.sort(), and getting None.
  • Functions that both compute and print, which can't be reused or tested without capturing output.
  • Long positional argument lists where a swapped pair of numbers goes unnoticed. Use keywords.
  • Writing one long function because the parts "aren't reused". Small functions are for reading and testing, not only for reuse.

Chapter 5

Recursion and the call stack

9 min read3 exercises

A recursive function solves a problem by calling itself on a smaller version of the same problem, until the problem is small enough to answer directly. It's the natural way to handle anything that contains smaller things of the same kind: nested lists, folders inside folders, expressions inside expressions. Recursion seems like magic until you see the mechanism behind it, the call stack, after which it's just function calls. This chapter shows the stack growing and unwinding, counts the cost of solving the same subproblem twice, and shows what happens when the stack runs out.

Base case and recursive case

Every recursive function has two parts. The base case answers the smallest problems directly, without recursion: the factorial of 1 is 1, the total of a number is the number itself. The recursive case breaks a bigger problem into smaller ones of the same kind, solves those by calling the function, and combines the answers: the factorial of n is n times the factorial of n − 1. The recursion is correct if three things hold: the base case is right, the recursive case is right assuming the smaller calls return correct answers, and every chain of calls eventually reaches a base case.

That second point is the leap of faith that makes recursion manageable. When writing total(item) for nested lists, don't trace through every level. Assume total already works for each element, and ask only: given the totals of the elements, how do I get the total of the list? Sum them. The function is then correct by the same induction argument a mathematician would use.

The call stack

Each call to a function gets a frame: a record holding its parameters and local variables, and the place to return to when it finishes. Frames are kept on the call stack. A call pushes a new frame on top; a return pops it and resumes the frame below. Recursion needs nothing more. factorial(4) and the factorial(3) it calls are separate frames with separate values of n, so they don't interfere, and the first can't finish until the one above it returns.

The example's first part prints this happening, indented by depth: four calls going down, then four returns coming back up, each multiplying by its own n. Python Tutor, a free website, draws the frames for any short program as it runs, and stepping through a recursive function there once is the fastest way to make the mechanism concrete.

Recursive data

Recursion fits best when the data is recursive. A list that can contain lists, a folder that can contain folders, an HTML element that contains elements, a JSON value that contains JSON values: for each, the recursive function has one case for the "leaf" kind and one for the "container" kind, and the container case calls the function on each child. The example's total and depth are five lines each and handle any nesting. Writing them with loops alone is possible but harder, because a loop has to keep track by hand of where it is in the structure, which is exactly what the call stack does for free.

When recursion repeats itself

The obvious recursive definition of Fibonacci numbers, fib(n) = fib(n - 1) + fib(n - 2), is correct and disastrously slow. fib(25) made 242,785 calls, because fib(23) is computed twice, fib(22) three times, and smaller values thousands of times: the number of calls grows exponentially with n. The fix is memoisation: remember each answer the first time it's computed, and look it up afterwards. functools.cache does this with one line, and the call count fell to 26, one for each value from 0 to 25. Memoisation works for any pure function, which is one more reason to write functions without side effects. It's also the starting point of dynamic programming, which The Engineer's Workbench covers in depth.

When the stack runs out

Every frame takes memory, and Python limits the stack depth, to 1,000 frames by default, so that runaway recursion stops with a RecursionError instead of crashing the interpreter. sum_to(500) worked and sum_to(5000) didn't: a recursion as deep as its input is only safe for small inputs. You can raise the limit with sys.setrecursionlimit, but that only moves the problem, and too high a limit can crash Python outright when the real stack overflows.

The robust alternative is to manage a stack yourself. flatten_iterative keeps a list of items still to process, pops one, and pushes its children if it has any: the same work as the recursive version, with the pending items on a list on the heap instead of frames on the call stack. It flattened ten thousand levels of nesting that made the recursive version overflow. Any recursion can be converted this way, at some cost in clarity, so a good rule is to write recursion where depth is bounded by something small, like the nesting of a document, and loops where it's bounded by the size of the input. Some languages remove the problem for calls in tail position; Python deliberately doesn't, for reasons chapter 14 of The Engineer's Press describes.

Some problems are naturally recursive and stay that way. To move a tower of n discs in the towers of Hanoi, move the top n − 1 to the spare peg, move the biggest disc, then move the n − 1 back on top: three lines that would be very hard to write as a loop. The move counts the example prints, 1, 3, 7, 15 and so on, are 2n − 1, which exercise 5.3 proves.

Common traps
  • A recursive case that doesn't shrink the problem, or a missing base case: infinite recursion, then RecursionError.
  • Recursing once per element of a long list, which hits the depth limit at about a thousand elements.
  • Solving the same subproblem repeatedly. Memoise pure recursive functions with functools.cache.
  • Raising the recursion limit instead of converting deep recursion to a loop.
  • Tracing every level by hand instead of trusting the recursive call and checking the combine step.

Exercise 5.2How many calls

Show that the naive fib(n) makes 2 × fib(n + 1) − 1 calls, which checks against the example's 242,785 for n = 25. Why does the memoised version make exactly 26?

Show solution

Let C(n) be the number of calls fib(n) makes, itself included. C(0) = C(1) = 1, and for larger n, C(n) = 1 + C(n − 1) + C(n − 2). Adding 1 to both sides gives C(n) + 1 = (C(n − 1) + 1) + (C(n − 2) + 1), which is the Fibonacci recurrence, starting from 2 and 2. So C(n) + 1 = 2 × fib(n + 1), and for n = 25 that's 2 × 121,393 − 1 = 242,785. The memoised version computes each value from 0 to 25 once. Every later request is answered from the cache without running the function's body, and the example's counter is inside the body, so it counts only those 26. 26 values, 26 calls: the exponential tree has collapsed into a line.

Exercise 5.3Why Hanoi takes 2n − 1 moves

Prove that hanoi(n) makes exactly 2n − 1 moves. How long would 64 discs take at one move per second?

Show solution

Let M(n) be the number of moves. M(0) = 0. For n ≥ 1, the function moves n − 1 discs, then one disc, then n − 1 discs, so M(n) = 2M(n − 1) + 1. Suppose M(n − 1) = 2n−1 − 1. Then M(n) = 2(2n−1 − 1) + 1 = 2n − 1, and since it holds for 0, by induction it holds for all n. The proof has exactly the shape of the function: a base case and a step that assumes the smaller case. No better algorithm exists, either: the largest disc must move at least once, and before it can, all the others must be stacked on the spare peg, which gives the same recurrence as a lower bound.

Chapter 6

Lists and tuples

12 min read3 exercises

A list is an ordered collection you can change; a tuple is an ordered collection you can't. Both are sequences, so they share indexing, slicing and unpacking, and both are built on an array, a single block of memory with items side by side. That layout makes some operations instant and others slow in proportion to the length. This chapter covers the operations you'll use every day, then counts the work behind append, insert and in, so you can predict which code will still be fast with a million items.

Sequences

A list is written in square brackets, ["Mercury", "Venus", "Earth"], and holds any values, of any types, in order. Items are numbered from 0, and negative indexes count from the end, so planets[-1] is the last item. A slice, planets[1:3], is a new list of the items from index 1 up to, but not including, index 3: the same half-open convention as range and chapter 3's binary search, which makes xs[:k] and xs[k:] split a list cleanly with nothing lost or repeated. A third number in a slice is a step, so xs[::2] takes every other item and xs[::-1] is the list reversed.

Lists change in place. append adds to the end, extend adds several, insert(i, x) puts an item at position i, pop() removes and returns the last item, remove(x) removes the first item equal to x, and sort() sorts. A list comprehension builds a new list from an old one in one expression: [x * x for x in nums if x % 2 == 0] is the squares of the even numbers. Comprehensions are usually clearer than the equivalent loop with append, as long as they fit on a line or two.

A tuple, written with parentheses, (3, 4), is a sequence that can't be changed after it's made. Use one for a fixed group of values that belong together, like a point or a date, and a list for a collection of similar things whose length varies. Because tuples can't change, they can be dictionary keys and set members, which lists can't, as the example shows. Tuples also make unpacking natural: x, y = point splits a pair into two names, first, *middle, last = planets gathers the rest into a list, and a function can return several values as a tuple, return lowest, highest, that the caller unpacks.

What operations cost

A list stores references to its items in one contiguous array, so finding item i is a single calculation, the start of the array plus i slots, however long the list is. That's why xs[i] and xs[i] = v take the same time for a list of ten items or ten million. Programmers write this as O(1), constant time. Operations whose work grows in proportion to the length n are O(n), linear time, and ones that do a linear amount of work for each of n items are O(n2), which is fine for a hundred items and hopeless for a million.

Appending is the interesting case. The array has a fixed capacity; when it's full, the list allocates a bigger block and copies everything across. If it grew by one slot at a time, every append would copy the whole list, and the example's 100,000 appends would copy nearly five billion items. Instead it grows by a constant factor. With doubling, a copy of k items happens only after k cheap appends, so the copies add up to less than 2n in total: the example measured 1.31 copies per append. On average each append is O(1), which is called amortised constant time. CPython grows lists by about an eighth each time rather than doubling, which wastes less memory, and any constant growth factor gives the same O(1) average.

Inserting or removing at the front is the opposite: every other item must move one place, so insert(0, x) and pop(0) are O(n), and 10,000 front inserts shifted almost fifty million items. If you need to add and remove at both ends, as a queue does, use collections.deque, which does both in O(1). And x in xs must compare x with each item until it finds a match, so it's O(n): finding the last of 10,000 items took 10,000 comparisons. Doing that inside a loop over another list of 10,000 is 100 million comparisons, which is where programs that work in testing stall in production. Chapter 7's sets do the same test in O(1).

Sorting

sorted(xs) returns a new sorted list and xs.sort() sorts in place; both take key=, a function that computes what to compare, and reverse=True. Python's sort, Timsort, takes O(n log n) time, and it's stable: items whose keys are equal stay in their original order. Stability is what makes multi-level sorting simple. To sort people by age and then by name within an age, use a tuple key, key=lambda p: (p[1], p[0]), or sort by name first and then by age, and the second sort keeps the names in order. Negating a number in the key, as the example does, reverses that part of the order only.

Don't change a list while looping over it

The example's last part removes even numbers from [2, 4, 5, 6, 8] inside a for loop over the same list and is left with [4, 5, 8]. The loop keeps an index into the list. Removing an item shifts everything after it one place left, so the item that slides into the current position is skipped. Exercise 6.2 traces it. The reliable fix is to build a new list with a comprehension, or loop over a copy, for x in xs[:]. The same rule applies to dicts and sets, where Python detects the change and raises an error instead of silently skipping.

Common traps
  • Using a list as a queue with pop(0) or insert(0, x). Use collections.deque.
  • Testing membership in a big list inside a loop, turning an O(n) program into O(n2). Use a set.
  • Removing items from a list while iterating over it. Build a new list instead.
  • Writing xs = xs.sort() and losing the list to None.
  • Using a list where a tuple belongs, for a fixed record, and then being unable to use it as a dict key.

Exercise 6.2The skipped items

Trace the loop that removes evens from [2, 4, 5, 6, 8] while iterating, writing the list and the loop's position after each step, and explain why the result is [4, 5, 8].

The for loop keeps a hidden position, starting at 0. Position 0 holds 2, which is even, so it's removed, and the list becomes [4, 5, 6, 8]. Exercise 6.3Returning two values

Write span(nums), which returns the smallest and largest numbers in one pass, and call it with unpacking. Why is a tuple the right return type here, rather than a list or two separate functions?

Show solution
def span(nums):
    lo = hi = nums[0]
    for x in nums[1:]:
        if x < lo: lo = x
        elif x > hi: hi = x
    return lo, hi

low, high = span([4, -2, 9, 0])
assert (low, high) == (-2, 9)

The result is a fixed pair of two different things, a minimum and a maximum, whose positions have meanings, which is exactly what a tuple is for; a list would suggest a collection of similar items that might grow. One pass over the data does the work of two, which matters when the data is large or can only be read once, as with a file or a network stream. Unpacking at the call site names both parts immediately, and if the number of names doesn't match the tuple's length, Python raises an error instead of silently misassigning. For results with more than three parts, a named tuple or a dataclass, chapter 13, makes the fields self-describing.

Chapter 7

Dictionaries and sets

11 min read3 exercises

A dictionary finds a value by its key, and a set answers whether it contains something, and both do it in about the same time whether they hold ten items or ten million. That one property is behind a large share of all fast programs. The mechanism is a hash table: turn the key into a number, use the number to pick a slot, and look only there. This chapter shows dicts and sets at work, builds a small hash table to show where the speed comes from, and explains the rule that makes it work: equal keys must have equal hashes.

Dictionaries

A dict maps keys to values: {"apples": 12, "pears": 0}. stock["apples"] looks a value up, stock["figs"] = 7 adds or replaces one, and del stock["pears"] removes one. Looking up a missing key raises KeyError, which is what you want when the key should be there. When a missing key is normal, stock.get("kiwis", 0) returns a default instead. for key in d loops over the keys, and d.items() gives key-value pairs. Since Python 3.7, dicts keep their keys in the order they were first inserted, which makes output predictable and lets dict.fromkeys(items) remove duplicates while keeping the first occurrence of each.

Two variations from the collections module save a great deal of code. A Counter counts things: Counter(words).most_common(3) is a word-frequency table in one line. A defaultdict(list) creates an empty list the first time a key is used, so grouping items is groups[key].append(item) with no check for whether the key exists yet. Both are ordinary dicts underneath.

Sets

A set is a collection of unique values with no order: {1, 2, 3}, or set(items) to build one from a list. Its main job is fast membership testing, x in s, and it supports the operations of mathematics: a | b is the union, a & b the intersection, a - b the difference. Comparing sets ignores order and duplicates, so set("listen") == set("silent") is true. Use a set whenever the question is "have I seen this?" or "is this allowed?", and especially to replace x in some_list inside a loop.

How a hash table finds things

A dict is an array of slots. To store a key, Python computes the key's hash, an integer derived from its contents, and uses it to choose a slot, for instance the hash modulo the number of slots. To find the key later, it computes the same hash and goes to the same slot. No searching is needed, whatever the dict's size. When two keys land on the same slot, a collision, the second goes to another slot found by a fixed rule; the example's table uses the simplest rule, linear probing, which tries the next slot along. A lookup then checks a few slots, comparing keys, until it finds the key or an empty slot, which means the key isn't there.

Two things keep lookups short. The table must have room: the example's table grows when it's two-thirds full, so most slots near any key are empty and a probe sequence ends quickly. And the hash must spread keys evenly. The example compares two hash functions on 10,000 keys named user0 to user9999. The weak one, which multiplies by 31 and adds each character, gives similar keys similar hashes, so they land in neighbouring slots and form long clusters: 8.12 probes per lookup. FNV-1a mixes every character into every bit of the result, so similar keys land far apart: 1.18 probes. Either way, compare that with the 5,000 comparisons an average lookup in a list would need.

Python's real dict is more refined. It probes in a pseudo-random order rather than linearly, which avoids clusters even with imperfect hashes, and keeps a compact array of entries in insertion order alongside the slots, which is how dicts remember their order. Python also deliberately randomises the hashes of strings with a secret chosen when each program starts, so that an attacker can't craft thousands of keys that all collide and make a web server's dict lookups slow. That's why hash("tea") changes between runs, and why the example uses its own fixed hash functions to print the same numbers every time.

The rule for keys

A hash table only works if equal keys have equal hashes, since the hash decides where to look. Python enforces part of this. Built-in immutable types, numbers, strings and tuples of them, are hashable and follow the rule. Mutable built-ins such as lists and dicts aren't hashable at all, because a key whose contents changed after it was stored would have a different hash and be lost in the wrong slot. And a class that defines __eq__ to compare contents loses its default __hash__, so that it can't silently break the rule, which is the TypeError the example shows.

If you define __hash__ yourself, it must agree with __eq__. The example's BadPoint hashes by identity while comparing by contents, so two equal points usually hash to different slots, and BadPoint(1, 2) in places is false even though an equal point is right there. The correct version hashes the same tuple that __eq__ compares. In practice you rarely write either method by hand: a frozen dataclass, chapter 13, generates a matching pair.

Common traps
  • Searching a list in a loop when a set or dict lookup would be O(1).
  • Using d[key] where the key may be missing, or d.get where it must be present and a missing key is a bug.
  • Defining __eq__ without a matching __hash__, or hashing on fields that can change.
  • Relying on hash() of a string being the same between runs. It's randomised on purpose.
  • Expecting a set to keep order. Use dict.fromkeys to remove duplicates in order.

Chapter 8

Strings, Unicode and UTF-8

10 min read3 exercises

Inside a Python program, text is a sequence of characters. In a file or on a network, it's a sequence of bytes, and an encoding is the rule that converts one to the other. Most text bugs, the Ã© where an é should be, the crash on a customer's name, the emoji that counts as three characters, come from confusing the two or from guessing the encoding. This chapter separates characters from bytes, encodes UTF-8 by hand to show why it won, and covers the cases where what you see on screen isn't what len counts.

Code points

Unicode gives every character in every writing system a number, its code point, written U+ followed by hexadecimal: A is U+0041, é U+00E9, € U+20AC, 😀 U+1F600. There are nearly 160,000 assigned characters, out of a space of 1,114,112 possible code points. A Python str is a sequence of code points. ord("€") gives the number, chr(8364) gives the character back, and the unicodedata module knows each character's official name. Code points are abstract numbers. Nothing about them says how many bytes a character takes in a file; that's the encoding's job.

Encodings, and why UTF-8 won

For decades, each region used its own encoding. ASCII covered English in 7 bits, 128 characters. Latin-1 and Windows-1252 used the eighth bit for Western European accents; other code pages did the same for Greek, Cyrillic or Hebrew, using the same byte values for different letters. A file was only readable if you knew which one it used, and the file didn't say. Unicode replaced the character sets, and of its encodings, UTF-8 replaced the rest. It was designed by Ken Thompson and Rob Pike in 1992, and today it's used by about 98% of web pages.

UTF-8 uses one to four bytes per code point. Code points up to U+007F, which are exactly ASCII, take one byte with the same value, so every ASCII file is already valid UTF-8, which made adopting it painless. Larger code points are split into groups of bits spread across two, three or four bytes, each marked by its leading bits: the first byte of a multi-byte character says how many bytes follow, and every continuation byte starts with 10. That design means a program can find character boundaries anywhere in a stream, and no character's bytes can appear inside another's.

The example's utf8 function implements those rules with shifts and masks, and its output matches Python's own encode("utf-8") for all four sizes. It's worth reading slowly once: cp >> 6 drops the low six bits, & 0x3F keeps only the low six bits, and 0x80 | adds the continuation header. After that, you can read the bytes of any UTF-8 text by eye.

Decoding: the boundary where text goes wrong

Bytes become text only when decoded, and decoding needs the right encoding. Decode UTF-8 bytes as Latin-1 and each byte becomes its own character, so the two bytes of é turn into Ã©: this is mojibake, and its look, capital A with a tilde before an accented letter, is the signature of UTF-8 read as Latin-1 or Windows-1252. Decoding in the other direction usually fails outright, because Latin-1's single byte for é isn't a valid UTF-8 sequence, and Python raises UnicodeDecodeError. errors="replace" substitutes U+FFFD, the replacement character �, so a program can carry on and show where the damage is.

The rule that prevents nearly all of this: decode bytes to text as soon as they enter your program, work with str throughout, and encode only on the way out, naming the encoding every time. open(path, encoding="utf-8") is that rule for files. Without encoding=, Python uses the platform's default, which on many Windows machines isn't UTF-8, so a script that works on a Mac can fail on a colleague's PC. PEP 686 makes UTF-8 Python's default everywhere from version 3.15, but writing encoding="utf-8" costs nothing and works on every version.

What a "character" is

len counts code points, and a character on screen can be several. é can be the single code point U+00E9 or the letter e followed by U+0301, a combining accent; they look identical, but they aren't equal and have different lengths. Text from different sources mixes the two forms, so before comparing or using text as a key, normalise it: unicodedata.normalize("NFC", s) converts to the composed form wherever possible, and then the example's two és compare equal.

Some characters are always several code points. The emoji for a technologist is a woman, a zero-width joiner and a laptop, three code points drawn as one picture. A flag is two "regional indicator" letters. What a reader sees as one character is called a grapheme cluster, and slicing a string by code points can cut one in half. If you need to truncate user-visible text or count what a person would count, use a library that understands grapheme clusters, such as the third-party regex module's \X pattern.

Strings in Python can't be changed; every method returns a new string. That's why building a long string with += in a loop can be slow, since each step may copy everything so far, and why the idiom is to collect pieces in a list and "".join(pieces) once at the end. Case is subtler than it looks too: "Straße".upper() is "STRASSE", longer than the original, and for case-insensitive comparison casefold() is the correct method, since lower() leaves ß as it is.

Common traps
  • Opening files without encoding="utf-8", so the result depends on the machine.
  • Mixing bytes and str deep inside a program instead of decoding at the edge.
  • Comparing text from different sources without normalising it first.
  • Truncating to a byte or code-point length and cutting a character or an emoji in half.
  • Using lower() for case-insensitive matching instead of casefold().

Chapter 9

Files, CSV and JSON

10 min read3 exercises

Real data arrives in files, and real files are messy: names with stray spaces, two date formats in one column, a pound sign in a price, a quantity typed as a word, a blank line in the middle. This chapter reads such a file, turns each row into a clean record or rejects it with a reason, totals the results, and writes them out as CSV and JSON. On the way it covers opening and closing files safely, why the csv module exists, what JSON can and can't represent, and processing a file too big to load. It's a small version of one of the stage's four deliverables.

Opening and closing files

open(path, encoding="utf-8") returns a file object, which reads text; mode "w" writes, replacing what was there, "a" appends, and adding "b" reads or writes bytes instead of text. A file must be closed when you're done, which flushes anything still buffered and releases the operating system's handle. The with statement does that for you: with open(...) as f: closes the file when the block ends, whether it ends normally or because of an exception, and it's the only way you should open files. The same pattern manages other resources, and the example uses it for a temporary folder that's deleted, contents and all, when its block ends.

The pathlib module makes paths objects rather than strings. Path(folder) / "sales.csv" joins paths with the right separator for the operating system, path.read_text(encoding="utf-8") and write_text read or write a whole small file in one call, path.exists() and path.suffix answer questions, and folder.glob("*.csv") finds files. It's clearer than building paths by joining strings, and it avoids the classic bug of a missing or doubled slash.

Why CSV needs a module

A CSV file looks simple enough to parse with line.split(","), and that works until a field contains a comma. Then the field is quoted, "Smith, Jo", a quote inside a quoted field is doubled, and a quoted field may even contain a newline. The csv module handles all of it. csv.DictReader uses the first row as column names and yields each row as a dict, so code says row["Price"] instead of row[4], and it skips blank lines. When opening a file for csv, pass newline="", so that the module, not Python's line-ending translation, decides where records end. csv.writer quotes whatever needs quoting on the way out, as the report's "Smith, Jo" shows.

Cleaning: one clean record or one clear reason

The heart of the example is clean(row), which either returns a tidy record or raises ValueError saying exactly what's wrong. It trims and squeezes spaces and fixes the capitalisation of names, so " Ana Lima " and "ana lima" become the same customer; strips currency symbols; parses the two date formats the file actually uses; and converts quantities and prices to numbers, which fails, correctly, for "two". The loop around it collects the good records and, for every failure, the line number and the reason, using the reader's line_num rather than counting rows, since counting would be thrown off by the skipped blank line.

Two principles make this robust. Validate at the boundary: the rest of the program receives only records that are already correct, so it never has to check for a price with a pound sign in it. And never guess. The row with month 13 could be a typo for the 3rd of July or the 7th of March; the program can't know, so it rejects the row and says why, and a person decides. Guessing silently produces a report that looks fine and is wrong. The date 03/01/2026 shows the subtler version of the problem: it's the 3rd of January in Britain and March 1st in the United States. The example reads it day-first, the British convention, because it's a British shop's file. That's a decision about this particular source, and it belongs in a comment and a test, not in the reader's head.

JSON

JSON is the standard format for structured data between programs and in most web APIs. It has objects, arrays, strings, numbers, true, false and null, which correspond to Python's dicts, lists, strings, numbers, True, False and None; json.dumps converts a value to JSON text and json.loads converts back. The correspondence isn't exact, and the example shows the losses: a tuple comes back as a list, a dict key 7 comes back as the string "7", because JSON keys are always strings, and a date can't be written at all. The fix is to convert such values yourself, a date to date.isoformat(), and back after loading. json.dumps(data, indent=2, sort_keys=True) produces readable, stable output for files that people will read or compare in version control.

Python's pickle module can save almost any Python object, which makes it tempting. Don't use it for data that comes from outside your program: loading a pickle can run arbitrary code, so a malicious file can take over your machine. JSON, CSV and other plain formats can only describe data.

Files that don't fit in memory

A file object is an iterator over its lines: for line in f reads one line at a time, using memory for one line however big the file is. f.read() and read_text load everything at once, which is fine for small files and fails for a 50-gigabyte log. The example finds the longest line of the file by streaming it through max. The same applies to CSV: DictReader reads lazily, so a loop that updates running totals per customer needs memory proportional to the number of customers, not the number of rows.

Common traps
  • Splitting CSV lines on commas by hand, which breaks on the first quoted field.
  • Opening files without with, so an exception leaves them open and unflushed.
  • Silently skipping or "fixing" bad rows, so the report is wrong and nobody knows.
  • Assuming JSON round-trips Python values, and finding tuples turned to lists and int keys to strings.
  • Unpickling data from anywhere you don't control.

Getting it right

Chapter 10

Errors and exceptions

11 min read3 exercises

When something goes wrong, a Python operation raises an exception: it stops what it's doing and hands the problem to whoever called it, and so on up the call stack, until some code catches it or the program ends with a traceback. Used well, exceptions put each problem where it can be handled, and make bugs loud instead of silent. Used badly, with a catch-everything except or a function that returns None when it fails, they hide bugs until they surface somewhere unrelated. This chapter covers raising, catching and chaining, and the design question that matters most: at which boundary to fail.

What happens when an exception is raised

int("80a") can't produce a number, so it raises a ValueError. Execution doesn't continue to the next line. Python looks for a handler in the current function, a try block with a matching except; if there isn't one, the function's frame is abandoned and Python looks in its caller, and so on up the stack. The first matching except runs, and execution continues after its try statement. If nothing matches, the program stops and prints a traceback: the chain of calls, outermost first, and on the last line the exception's type and message.

Read tracebacks from the bottom. The last line says what went wrong, ValueError: invalid literal for int() with base 10: '80a', and the lines above it say where, innermost call last. The bug is usually in the deepest frame that's your own code rather than a library's, and often in what was passed to it. Python 3.11 and later also underline the exact expression on each line that raised, which settles questions like which of three indexes on one line was out of range.

Catching

try wraps code that might fail; except SomeError as e: handles that type of error and its subclasses; else runs only if nothing was raised; finally runs no matter what, even if the try block returned or the exception is still propagating, which makes it the place for cleanup. The example prints the order both ways. In practice, with blocks replace most finally clauses, since a file or lock used with with is released automatically.

Catch as narrowly as you can, in two senses. Name the specific exception type you expect, and put only the line that can raise it inside the try. The example's average_bad shows why: its bare except: was meant for an empty list, but it also caught the NameError from a typo, so the function returned 0 for a list that averages 3, with no sign of a problem. A bare except: even catches KeyboardInterrupt, so the program ignores Ctrl-C. The narrow version lets the typo crash immediately, with a message naming the misspelt variable. A crash you can see is a gift compared with a wrong answer you can't.

There is one place where catching broadly is right: the top of a long-running program, such as a web server's request loop or a batch job's loop over records, where one failure shouldn't stop everything. There, except Exception as e: logs the full traceback and moves on to the next item. Note Exception, not a bare except, so that Ctrl-C and sys.exit still work.

Raising, and the right boundary

Raise exceptions in your own code with raise ValueError("...") when a function is given something it can't work with. A good message says what was expected and shows what was received: "'port' must be 1 to 65535, got 70000" lets the reader fix the input without reading your code. Define your own exception class, a subclass of Exception, when callers will want to handle your errors separately from Python's, as the example's ConfigError lets a caller report configuration problems to the user while letting genuine bugs crash.

Where should errors be detected? At the boundary, where data enters your program from outside: user input, files, network responses, other people's code. Check everything there, convert it to the types and ranges the rest of the program expects, and raise one clear error if it doesn't fit. Code inside the boundary can then trust its data, which makes it simpler and faster, and an error message appears once, at the point where it can name the bad input, instead of as a mysterious failure three functions later. Chapter 9's clean function was a boundary; so is the example's read_config.

The opposite habit, returning None to signal failure, moves the error somewhere worse. The example's find_price_quiet returns None for a scone with no price, and the failure appears later, inside sum, as a TypeError about adding a float to None, which says nothing about scones. Raising KeyError("no price for 'scone'") at the lookup names the real problem. When "not found" is a normal outcome rather than an error, returning None is fine, as long as the function's name and docstring say so and every caller checks.

When you catch one exception and raise another, chain them with raise ConfigError(...) from e. The new exception keeps the original as its __cause__, and a traceback shows both, so the detail isn't lost. from None deliberately hides the original, for when it's just noise, as in the example's find_price.

Asking forgiveness or permission

Python style generally prefers EAFP, "easier to ask forgiveness than permission": try the operation and handle the exception, rather than LBYL, "look before you leap", checking first. The reason is that checks can be wrong or out of date. if path.exists(): open(path) fails anyway if the file is deleted between the check and the open, or if it exists but you lack permission to read it; try: open(path) except FileNotFoundError: handles exactly the case that happened. Use assert for a different purpose: to state things that must be true if your code is correct, such as a loop invariant. Assertions can be disabled with python -O, so they must never be used to validate input.

Common traps
  • A bare except: or except Exception: pass, which hides every bug in the block.
  • A try block around many lines, so you can't tell which one failed.
  • Returning None or -1 to mean "error" and leaving every caller to remember to check.
  • Error messages without the bad value, such as "invalid input".
  • Using assert to validate user input, which python -O removes.

Chapter 11

Testing

8 min read3 exercises

A test is a small program that runs part of your program and checks the result. A suite of them, run in seconds after every change, is what lets you change code without fear, because anything you break is reported at once, with its name. Tests belong in a project from the first week, not after it works, since writing them is also how you discover what "works" means. This chapter tests a pair of functions with a real test runner, finds three bugs, and then finds a fourth, which every unit test missed, by checking a property on two thousand random inputs.

A test is a claim you can run

Each test states one fact about the code: format_duration(5405) is "1h 30m 5s". It has three parts, often called arrange, act, assert: set up the input, call the code, check the result. A test passes silently and fails loudly, naming itself and showing what it got and what it expected. Give each test a name that states the behaviour it checks, such as test_zero_is_written_as_0s, because when it fails months from now, the name is the first thing anyone reads.

Python's standard library includes unittest, which the example uses so that it runs without installing anything. Most Python projects use pytest instead, and you should too: it finds test files named test_*.py by itself, lets tests be plain functions using plain assert, shows a detailed diff when an assertion fails, and has features such as @pytest.mark.parametrize for running one test with many inputs. The pytest version of the example's first test is two lines:

def test_formats_hours_minutes_seconds():
    assert format_duration(5405) == "1h 30m 5s"

Running pytest in the project folder runs every test and reports a summary. Run it after every change, and before every commit. A test suite that takes more than a few seconds stops being run, so keep unit tests fast: no network, no sleeping, no large files.

What the tests found

Version 1 failed three of six tests. format(0) returned an empty string instead of "0s", because every part was zero and the join had nothing to join; parse accepted "ninety minutes" and returned 0, because its regular expression simply found no matches; and format(-5) didn't complain at all. Each failure message names the test and shows the assertion, '' != '0s', so the fix is obvious. Version 2 handles all three, and all six tests pass.

Notice what kind of bugs these are. None is in the main path, formatting an ordinary duration like an hour and a half, which version 1 got right. They're all at edges: zero, invalid input, negative input. That's where bugs live, and so that's where tests should go. For any function, test the empty or zero case, a single item, a typical case, the boundaries of every range, and each kind of invalid input, which should raise an error. assertRaises in unittest, and with pytest.raises(ValueError): in pytest, check that an error is raised when it should be.

The bug the unit tests missed

Version 1 has a fourth bug, and all six unit tests passed it. Its hours are computed as seconds // 3600 % 24, the hours of a clock rather than of a duration, so anything longer than a day loses whole days. Every unit test used durations under a day, so none could see it. A different style of test can. A property is a statement that should hold for every input: here, "parsing what we formatted gives back the original number". The example checks it on 2,000 random durations up to 200,000 seconds, plus a list of edge values, and 1,087 of version 1's inputs fail. The smallest failure, 86,400 seconds, exactly one day, formats as an empty string.

Two details make property checks practical. The random generator is seeded, random.Random(7), so every run checks the same inputs and a failure can be reproduced exactly; an unseeded test that fails once and then passes is worse than none. And reporting the smallest failing input makes the failure easy to understand, since 86,400 says "one day" in a way that 173,962 doesn't. The Hypothesis library automates both, generating inputs of any type and shrinking every failure to a minimal example; it's well worth learning once you're comfortable with ordinary tests.

Habits that make tests worth having

Watch every new test fail before you make it pass. A test that has never failed might not be testing anything, if it calls the wrong function, say, or asserts something always true. Writing the test first and then the code, test-driven development, is one way to guarantee that, and it makes you decide what the function should do before deciding how. When you fix a bug, first write the test that reproduces it, a regression test, so the bug can never quietly come back.

Keep tests independent: each sets up what it needs, so they pass in any order and one failure doesn't cascade. Keep them deterministic: code that reads the clock, the network or an unseeded random generator should take those as arguments so a test can supply fixed ones, a design chapter 20 uses throughout. And treat coverage as a floor, not a goal. The coverage tool shows which lines your tests never ran, which is useful; but version 1's unit tests ran every one of its lines, and it was still wrong for every input over a day.

Common traps
  • Testing only the typical case, when bugs live at zero, empty, one, boundaries and invalid input.
  • Writing tests after the code is "finished", when they confirm what the code does rather than what it should do.
  • Tests that depend on the clock, the network or unseeded randomness, which fail sometimes and teach people to ignore failures.
  • Never seeing a test fail, so you don't know whether it can.
  • Reading 100% line coverage as "correct". Every line ran in version 1.

Chapter 12

Debugging

11 min read3 exercises

Debugging is finding the difference between what you think the program does and what it does. Guessing and changing things until the symptom goes away is the slow way, and it often leaves the bug in place. The fast way is to look: stop the program where the state goes wrong, inspect the variables, and compare them with what you expected. This chapter runs a real debugger session against a buggy function, shows what stepping through code reveals, and ends with bisection, the technique for when you don't even know where to look.

A method, not a mood

Every debugging session follows the same loop. Reproduce the failure reliably, ideally with the smallest input that shows it; a bug you can't reproduce, you can't confirm you've fixed. Observe what actually happens, rather than reasoning about what should. Form a hypothesis about the cause that would explain everything you've observed, and test it with one experiment, changing one thing at a time. When the hypothesis survives, fix the cause, not the symptom, then confirm the original failure is gone and write the test that would have caught it, as chapter 11 recommends.

The commonest mistake is skipping straight to the fix. A function returns 1.5 where 3 was expected; it's tempting to "fix" it by multiplying by 2, and the code is now wrong in two places. The example's mean_of_evens([1, 2, 3, 4]) is that situation: the total looks right, so the question is what it's being divided by.

The debugger

A debugger runs your program under your control. You set a breakpoint on a line, and when execution reaches it the program pauses, with every variable available to inspect. Python's built-in debugger is pdb. Put breakpoint() on any line of your code, run the program normally, and you get a (Pdb) prompt there; or start the whole program under it with python -m pdb script.py. Editors such as VS Code and PyCharm put the same operations behind buttons and show the variables in a panel, and everything below applies to them too.

A handful of commands do almost all the work. p expr prints the value of any expression, and pp pretty-prints large ones. n, next, runs the current line and stops at the next one; s, step, does the same but goes inside any function the line calls. c, continue, runs until the next breakpoint. b 9 sets a breakpoint at line 9, and b 9, n % 2 == 1 sets a conditional breakpoint that only stops when the condition is true, which is indispensable in a loop that runs a million times and goes wrong once. w, where, shows the call stack, and u and d move up and down it to inspect callers' variables. l lists the source around the current line, and q quits.

What the sessions show

The first session stops at the return and prints total, count: (6, 4). The total of the evens is right, 2 + 4, but four numbers were counted, not two. That's the observation that rules out half the code: the bug is in how count grows. The second session confirms the hypothesis with a conditional breakpoint that stops only for odd numbers: at n = 1, count is about to become 1, although 1 isn't even. The line-by-line trace shows the same thing without a debugger, for [1, 2]: after if n % 2 == 0: is false for 1, the next line run is count += 1, because it isn't indented under the if. The fix is one level of indentation.

That kind of bug, where the code is plausible and the output is wrong, is exactly what reading code finds slowly and running it under a debugger finds quickly. print statements can do the same job, and for a quick check they're fine, but they need editing the code, rerunning, and remembering to remove them, and you can only print what you thought to print in advance. At a breakpoint you can ask any question that occurs to you. Get comfortable with one debugger early; it's one of the highest-return skills in this stage.

When a program crashes, you can debug it after the fact. python -m pdb -c continue script.py runs the script and, if it raises an uncaught exception, drops into the debugger at the point of the crash, with all the variables still there, which is called post-mortem debugging. In an interactive session, import pdb; pdb.pm() does the same for the last exception.

When you don't know where to look: bisect

Sometimes you know a thing worked last month and doesn't now, and nothing about the symptom points to a cause. Then search the history instead of the code. Find a version that works and one that doesn't, test the version halfway between, and keep the half that contains the change. Each test halves the range, so 64 versions take 6 tests and a thousand commits take 10. Git automates this as git bisect: mark one commit good and one bad, and Git checks out the midpoints for you to test, or runs a test script on each one by itself with git bisect run. The result is the exact commit that introduced the bug, usually small enough that the cause is obvious from the diff.

Bisection works on more than history. If a 10,000-line input file crashes the program, try the first half, then the half of whichever half fails, and in about 14 steps you have the one line that causes it. If a change touches twenty files and breaks something, revert half. The principle is the same as chapter 3's binary search: an invariant, "the cause is in this range", and a range that halves with every test.

Finally, explaining the problem out loud, line by line, to anyone or anything, often reveals the bug before you finish. Programmers call it rubber duck debugging, after a story of one who kept a rubber duck on the desk for the purpose. It works because explaining forces you to state the assumptions you were skipping over, and the bug is usually in one of them.

Common traps
  • Changing code before you understand the bug, so the symptom moves and the cause stays.
  • Changing several things at once, so you can't tell which one mattered.
  • Debugging with a large input when a minimal reproduction would make the cause obvious.
  • Leaving print calls or breakpoint() in committed code. Search for them before committing.
  • Fixing a bug without adding a test for it, so it can return unnoticed.

Chapter 13

Objects and classes

8 min read3 exercises

A class defines a new type: what data its objects hold, and what operations they support. Its real value is that the operations can keep the data valid. A booking can refuse to end before it starts, and a calendar can refuse to double-book a room, so no other code has to remember those rules. This chapter builds a small booking system, shows what a method call really is, demonstrates the class-attribute trap that shares one list between every instance, and uses dataclasses for the many classes that are mostly data.

Classes, instances and methods

A class is a blueprint; an instance is an object made from it. class Booking: defines the type, and Booking("Oak", 540, 600) calls the class to make an instance, which runs the special method __init__ to set it up. Inside a method, self is the instance the method was called on, and self.room = room stores an attribute on it. A method is a function defined in the class, and calling it on an instance, b.overlaps(other), is exactly the same as calling the class's function with the instance as the first argument, Booking.overlaps(b, other). The example prints both. There's no magic in self; it's just the name, by convention, of that first parameter.

The example's Booking has an invariant, like chapter 3's loops: every booking's start is before its end, within one day. __init__ checks it and raises ValueError if it doesn't hold, so an invalid booking can't exist. minutes is a property, a method that's read like an attribute, b.minutes, without parentheses. It's computed from start and end each time, so it can never disagree with them, which a stored minutes attribute could after someone changed end. And __repr__ controls how the object prints, which matters more than it seems: Booking('Oak', 09:00-10:00) in a debugger or a log tells you something, and the default <Booking object at 0x104f...> doesn't.

Responsibilities

Notice how the work is divided. A Booking knows about itself: whether its times are valid and whether it overlaps another booking. A Calendar knows about the collection: it holds the bookings, refuses a new one that clashes, and answers questions about all of them, such as which room is busiest. Neither reaches into the other's data. That's the idea of encapsulation: each class owns its data and the rules for it, and other code goes through its methods. Python doesn't enforce privacy, but a leading underscore, self._bookings, is the universal signal that an attribute is internal and may change, so outside code should leave it alone.

When should you write a class instead of functions and dicts? When data and the rules for that data travel together, and you'd otherwise have to repeat the rules everywhere the data is used. A dict {"room": "Oak", "start": 600, "end": 540} is happy to hold an impossible booking; a Booking isn't. When you have no rules to enforce, only a few fields, a dataclass or even a plain tuple is enough, and a module of functions is often better than a class with no data at all.

Class attributes are shared

An attribute assigned in the class body, outside any method, belongs to the class, not to any instance. When you read blue.members, Python looks on the instance first and, finding nothing, looks on the class. So in the example's Team, where members = [] is written in the class body, every team shares one list, and adding a member to red adds it to blue. It's the same trap as chapter 4's mutable default argument, for the same reason: the list was created once, when the class was defined.

The fix is to create mutable attributes in __init__, so each instance gets its own. Class attributes are fine for constants that every instance should share and nobody changes, like a default rate or a table of valid values.

Dataclasses

Many classes are mostly data, and writing __init__, __repr__ and __eq__ for each is tedious and error-prone. The @dataclass decorator generates them from a list of annotated fields. With order=True it also generates comparisons, which compare the fields in order, so the example's Version objects sort correctly: 1.2.0, 1.2.3, 1.10.0, 2.0.0. Compared as strings, "1.10" would sort before "1.2", because string comparison goes character by character and "1" < "2". With frozen=True, assigning to a field raises an error, so a frozen dataclass is a value like a number or a string: safe to share, and usable as a dict key, because the generated __hash__ agrees with __eq__, as chapter 7 requires. Prefer frozen dataclasses unless the object genuinely needs to change.

Common traps
  • Mutable class attributes, such as members = [] in the class body, shared by every instance.
  • Storing a derived value that can drift out of date. Compute it with a property.
  • Constructors that accept invalid data and leave validation to every user of the class.
  • Reaching into another object's underscore attributes instead of asking it through a method.
  • Writing a class for something that has no data or no rules, where a function would do.

Chapter 14

Composition and interfaces

10 min read3 exercises

Inheritance looks like the natural way to reuse code: a counting bag is a bag that also counts, so subclass it. But a subclass depends on how its parent works inside, not just on what it does, and that dependency breaks in ways that are hard to see. Composition, an object that holds another and delegates to it, depends only on the public behaviour. This chapter shows a subclass that counts every item twice, a square that breaks code written for rectangles, and the alternatives: composition, interfaces defined by what callers need, and functions passed in where one behaviour varies.

Inheritance couples you to the inside

Inheritance makes a new class from an existing one: class CountingBag(Bag) gets all of Bag's methods, and can override some of them, calling the parent's version with super(). It's appealing because the subclass is short. The example's CountingBag overrides both add and add_all to count, and adding three items reports six. The reason is inside Bag: its add_all happens to call self.add for each item, and since self is the CountingBag, that's the counting add, so every item is counted once by add_all and again by add. Nothing in Bag's public behaviour said so; it's an implementation detail. If the author of Bag later changed add_all to append directly, the count would become correct, and a subclass that had been "fixed" to compensate would break.

This is called the fragile base class problem, and it's why the 1994 book Design Patterns advised "favour object composition over class inheritance". The composed version, CountingBagComposed, holds a Bag and forwards each call to it. Inside the bag, self is the bag, so its internal calls never reach the counter, and the count is right whatever Bag does inside. The cost is that every method you want to expose must be written out, one line each; the benefit is that you depend only on Bag's public methods, which its author has promised to keep working.

A subclass must be substitutable

A subclass is a promise: anywhere the program uses a Rectangle, a Square will do. That promise is the Liskov substitution principle, after Barbara Liskov, who stated it in 1987. The example's Square breaks it. Mathematically a square is a rectangle, so inheritance seems right, but Rectangle's set_width promises to change only the width, and a square can't keep that promise and stay square. Code written for rectangles, the example's stretch, doubles the width and expects double the area; with a square it gets four times the area. The lesson is that inheritance should model "behaves like", not "is a kind of" in everyday language. Here the trouble comes from mutation: if rectangles were immutable, with no set_width, a square would be a perfectly good one, which exercise 14.2 explores.

Interfaces: what callers need

An interface is the set of operations a caller relies on. Python doesn't require you to declare one. A function that calls shape.area() works with any object that has an area method, whatever its class, which is called duck typing: if it has the methods you need, it'll do. The example's Circle isn't related to Rectangle at all, and total_area happily mixes them. To make the interface explicit, for readers and for type checkers, write a Protocol: a class listing the methods required, which any class with those methods satisfies automatically, without inheriting from it. With @runtime_checkable, isinstance(x, HasArea) even checks it at run time, though only that the method exists, not its signature.

Sometimes you do want a family of classes with shared logic, and then an abstract base class states the contract. The example's Exporter marks write as abstract and implements export once on top of it; subclasses supply only write, and one that forgets can't even be instantiated, so the mistake appears at once instead of when export is first called. That's inheritance used well: the base class is designed for extension, with a documented hook, rather than a class someone happened to subclass. The standard library is full of these, and every exception class you define, chapter 10, is the same pattern.

Often, pass a function

When the only thing that varies between "kinds" of an object is one piece of behaviour, a class hierarchy is heavy machinery. The example's pricing has three rules, and rather than NoDiscountPrice, PercentOffPrice and ThresholdPrice subclasses, the rule is a function passed to price. Adding a fourth rule is one line, rules can be stored in a dict, chosen from configuration and tested alone. It's chapter 4's "functions are values" applied to design. Reach for a class when the behaviour needs its own data and several methods; reach for a function when it's one operation.

Common traps
  • Subclassing a class you don't control and depending on which of its methods call which.
  • Modelling "is a kind of" with inheritance when the subclass can't keep the parent's promises.
  • Deep hierarchies, where understanding one method means reading five classes.
  • Checking type(x) == Something instead of relying on the methods you need.
  • A class hierarchy for one varying behaviour, where passing a function would do.

Chapter 15

References, mutation and aliasing

11 min read3 exercises

Every Python object lives in one place in memory, and every name, list slot and attribute that refers to it holds a reference, a pointer to that place. When two references point to the same mutable object, a change through one is visible through the other. That's aliasing, and it's sometimes exactly what you want and sometimes the cause of a bug that seems impossible. This chapter draws what's actually in memory for the classic aliasing bugs, explains copying, identity and how Python decides an object is no longer needed, and connects it to the stack and the heap that CS50 shows you in C.

The stack, the heap and references

Chapter 5 described the call stack: each function call gets a frame holding its local variables. In Python, what a frame holds isn't the objects themselves but references to them. The objects live in the heap, a large region of memory where they're created and stay for as long as anything refers to them, independent of which function made them. That's why a function can create a list and return it: the frame disappears, but the list doesn't, because the caller now holds a reference. In C you handle these addresses directly, as pointers, which is why CS50's week on memory is worth doing even if you'll write Python: Python's references are pointers that the language manages for you.

Passing an argument copies the reference, not the object, so the function's parameter and the caller's variable refer to the same object. This is sometimes called call by sharing. The example's add_bonus mutates the list it's given, and the caller sees the change; reset rebinds its own parameter to a new list, which the caller never sees. That's chapter 2's distinction between mutating and rebinding, crossing a function call. A function that mutates its arguments should say so in its name or docstring, and most functions shouldn't do it at all.

Aliasing bugs

The best-known aliasing bug is building a grid with [[0] * 3] * 3. The inner expression makes one list of three zeros. Multiplying the outer list by 3 repeats its contents, which is a reference to that one list, so the grid holds three references to the same row. Setting grid[0][0] = 1 changes the only row there is, and all three "rows" show it. The example's picture helper labels each distinct object, and all three rows are object #1. A comprehension, [[0] * 3 for _ in range(3)], evaluates [0] * 3 three times and makes three separate rows.

The same mistake hides in other places. dict.fromkeys(keys, []) gives every key the same list. A mutable default argument, chapter 4, is one list shared by every call, and a mutable class attribute, chapter 13, is one list shared by every instance. Storing a list you were given in an object, self.items = items, means the caller can still change it behind the object's back. In every case the fix is the same: create a fresh object each time it's needed, or take a copy at the boundary.

Copies

There are two kinds of copy. A shallow copy, copy.copy(x), list(xs), xs[:] or d.copy(), makes a new outer container holding the same references as the original. A deep copy, copy.deepcopy(x), copies the container and, recursively, everything inside it. For a flat list of numbers or strings the difference doesn't matter, since the items are immutable. For nested data it does: the example's shallow copy of a team still shares the members list with the original, so appending to the original's members shows up in the copy, while the deep copy is fully independent.

Deep copies have costs: they take time and memory proportional to everything reachable, and they can copy things that should stay shared, such as an open file or a reference to a shared configuration. Often a better approach than copying defensively is not mutating in the first place: build new values from old ones, as chapter 4's pure functions do and chapter 19 of The Engineer's Press explores, and sharing becomes harmless.

Identity, and when objects are freed

a == b asks whether two objects have equal values; a is b asks whether they're the same object. Two lists built separately with the same contents are equal but not identical. Use is only to compare with None and with sentinel objects you created for the purpose. is on numbers or strings gives results that depend on interpreter details, since CPython reuses some small integers and strings and not others, so x is 5 is a bug even when it happens to work.

Python frees an object when nothing refers to it any more. CPython keeps a reference count on every object and frees it the moment the count reaches zero, which is why the example's lone node is gone as soon as its only name is deleted; a weakref lets you watch an object without keeping it alive. Objects that refer to each other in a cycle keep each other's counts above zero, so CPython also runs a cycle collector from time to time, and the example's cycle survives the deletion and is freed only when gc.collect() runs. Chapter 13 of The Engineer's Press explains these collectors in depth. For everyday code, the consequence is that Python programs leak memory not by forgetting to free but by remembering too much: a cache, a global list or a long-lived object that keeps references to things nobody needs.

The example ends with a puzzle that ties it together. A tuple can't change, so t[0] += [3] must fail, and it does, with a TypeError. But afterwards the list inside the tuple has grown anyway. += on a list first extends the list in place, which succeeds because lists are mutable, and then assigns the result back into t[0], which fails because tuples aren't. The tuple's immutability means its references can't change; the objects they point to can.

Common traps
  • Building nested lists with *, so every row is the same list.
  • Storing a caller's list or dict in an object without copying it.
  • Using a shallow copy of nested data and expecting it to be independent.
  • Using is to compare numbers or strings. Use ==.
  • Caches and registries that only grow, holding references that keep memory alive forever.

Chapter 16

Modules, packages and environments

11 min read3 exercises

A program of any size is split across files, and most programs also use code that other people wrote. Python's import system finds and loads your files, packages group them, and a virtual environment gives each project its own set of installed libraries so that one project's upgrade can't break another. On top of that, a dependency resolver has to choose versions that satisfy every library's requirements at once, and a lockfile records the choice so the program installs identically everywhere. This chapter builds a small package, runs into a circular import, creates an environment, and resolves a set of dependencies by search.

Modules and import

A module is a Python file, and import shop makes its contents available as shop.something. The first time a module is imported, Python finds the file, runs it from top to bottom, and stores the resulting module object in sys.modules. Every later import of the same module, from anywhere in the program, gets that stored object without running the file again, as the example shows: the second import printed nothing. So a module's top-level code runs once per program, which is why it should mostly define things, functions, classes and constants, rather than do things.

Python looks for modules in the folders listed in sys.path, in order, and the first entry is the folder of the script being run. That has a famous consequence: a script named random.py or json.py in your project hides the standard library module of the same name, for every program run from that folder, and the error it produces is baffling. Name your files after what they do, not after modules you use.

from shop.prices import price imports one name into the current module; import shop.prices keeps the module's name as a prefix. Prefer the second, or from imports of a few specific names. Avoid from module import *, which dumps every name into your module and makes it impossible to tell where a name came from.

Packages and running as a program

A package is a folder of modules with an __init__.py file, which runs when the package is first imported and can be empty. Inside a package, modules can import each other with relative imports, from .prices import price, where the dot means "this package", so the package keeps working if it's renamed or moved. Every module has a __name__: its module name when imported, and "__main__" when run as the program. The idiom if __name__ == "__main__": guards code that should run only when the file is used as a program, which lets the same file be both a library and a command. Run a module inside a package with python -m shop.cart, which sets up the import path correctly, rather than python shop/cart.py, which breaks relative imports.

Circular imports

The example's loop_a imports a name from loop_b, and loop_b imports a name from loop_a. Importing loop_a starts running it, and its first line starts importing loop_b, whose first line asks for loop_a.main. But loop_a is only partly run: it hasn't reached the def main line yet. Python reports exactly that, "cannot import name 'main' from partially initialized module 'loop_a' (most likely due to a circular import)". The cure is structural. Two modules that need each other usually contain a third concept that both depend on, which belongs in its own module; failing that, import inside the function that needs the name, so the import happens when the function runs, after both modules are loaded.

Environments, dependencies and lockfiles

Third-party libraries come from the Python Package Index, PyPI, and are installed with pip or a newer tool such as uv. Installing them into your one system Python mixes every project's libraries together, so upgrading a library for one project can break another, and nobody can tell which project needs what. A virtual environment solves this: a folder with its own Python interpreter and its own site-packages, created with python -m venv .venv and activated with source .venv/bin/activate, or .venv\Scripts\activate on Windows. Inside it, sys.prefix points at the environment, which is how the example's check confirms it's running in one. Make one per project, and never install project libraries globally.

A project declares what it needs in pyproject.toml, usually as ranges: requests >= 2.31, < 3. Libraries declare ranges too, and their requirements have requirements. Choosing one version of every package so that all the ranges hold at once is dependency resolution, and in general it's a search problem. The example's resolver tries the newest allowed version of each package first and backs up when a later constraint fails: web 2.4 needs util ≥ 1.5 but orm 1.3 needs util < 1.5, so no util fits, and it retreats to orm 1.2, which accepts util 1.8. pip's resolver works in the same spirit, backtracking through versions, at a much larger scale.

Because ranges allow many answers, the resolver's choice can change from one day to the next as new versions are published, and "it works on my machine" follows. A lockfile records the result: the exact version of every package, direct and indirect, with a hash of each package file, so that installing from the lockfile reproduces the environment exactly and a tampered download is rejected. Tools such as uv, Poetry and pip-tools generate them. The rule of thumb: applications commit a lockfile and install from it; libraries publish ranges, so that the applications using them can resolve compatible versions.

Common traps
  • Naming your file after a module you import, such as random.py, so it hides the real one.
  • Doing work at import time, such as connecting to a database, so importing the module has side effects.
  • Installing project libraries into the system Python instead of a virtual environment.
  • Unpinned dependencies in an application, so a new release of a library breaks a deploy.
  • Two modules importing each other at the top, and patching the symptom instead of moving the shared part out.

Chapter 17

Reading unfamiliar code

10 min read3 exercises

Most code you'll work on was written by someone else, often someone who has left, and changing it starts with understanding it well enough not to break it. Reading code is a skill with techniques of its own: map the structure before the details, find out what touches shared state, and use the running program to answer questions the text can't. Changing it safely has techniques too: record what the code does now, for many inputs, before you change a line. This chapter maps a small legacy module automatically, pins down its behaviour with 686 recorded answers, and shows those answers catching a refactoring mistake that looked harmless.

Map before you read

Reading a file top to bottom, line by line, is the slowest way to understand it. Start with the shape. What does the module define, and what's at module level? Which functions call which? Which ones read or change state that lives outside them, globals, attributes, files? Those last are where surprises come from, because their behaviour depends on more than their arguments. Then find the entry points, where the program starts or where other code calls in, and the tests, if there are any, which are often the best documentation of what the code is supposed to do.

Editors answer most of these questions directly: "go to definition", "find all references" and a call hierarchy view are worth learning thoroughly. On the command line, grep -rn "calc(" ., or the faster rg, finds every use of a name. git log -p file.py and git blame tell you when and why each line changed, which explains code that looks wrong but isn't. The example does the mapping with Python's ast module, which parses code into the same tree Python itself uses, so a dozen lines can list every function, what it calls, which module-level names it reads, and which it mutates.

What the map says

The legacy module is short, and still the map tells you things a quick read misses. calc calls disc and tax, reads SPECIAL, and mutates the global log: every call appends to it, so calling calc twice is not the same as calling it once, and any test that calls it leaves a trace for the next. SPECIAL is defined at the bottom of the file, after the function that uses it, which works only because it's looked up when calc runs, not when it's defined. And the names t, p and i carry no meaning, so the purpose of each line has to be reconstructed from arithmetic. None of this is a bug yet. All of it is a place where a change can go wrong.

Characterisation tests

Before changing code that has no tests, write tests that record what it does now, right or wrong. Michael Feathers, who named them characterisation tests in Working Effectively with Legacy Code, put the idea plainly: legacy code is code without tests, and the first job is to get it under test. The example runs calc on a grid of 686 orders, every combination of quantities for three products, with and without VIP status, and stores the answers. They aren't claims that the answers are correct, only that they're what the code produces, which is what existing users depend on. If a change makes any answer differ, you've changed behaviour, and you must decide whether you meant to.

The careful refactor renames everything, extracts line_total and vip_discount, names the magic numbers, and replaces the global log with an optional history parameter. Every one of the 686 answers is identical. (The history change does alter behaviour on purpose: callers that relied on the global log must now pass a list. A deliberate interface change like that belongs in its own step, announced to callers, not mixed in with a refactor.) The careless refactor changes one character, > to >=, which looks like a harmless tidy-up. One answer in 686 differs: a VIP order of exactly £100 now gets the £10 discount instead of 5%. No reviewer would reliably spot that; the recorded answers did in under a second.

Changing code in small steps

Refactoring means changing a program's structure without changing its behaviour, and it's done in small steps, each followed by running the tests: rename a variable, run; extract a function, run; replace a magic number with a named constant, run. If a step breaks something, the cause is the last small change, not one of fifty. Keep refactoring and behaviour changes in separate commits, so a reviewer can check the first for "nothing changed" and the second for "the right thing changed". Commit after each working step, so you can always go back. The habit feels slow and is the fastest way there is to change code you don't fully understand.

Common traps
  • Reading line by line from the top instead of mapping structure and state first.
  • Refactoring without tests, and relying on careful reading to spot behaviour changes.
  • Mixing a refactor with a bug fix or feature in one change, so neither can be reviewed.
  • "Fixing" code that looks wrong before finding out, with git blame and the tests, why it's like that.
  • Characterisation tests with too few inputs to reach the boundaries where behaviour changes.

Chapter 18

Command-line tools

9 min read3 exercises

A command-line program is used by people at a terminal and, just as often, by other programs: scripts, scheduled jobs, pipelines. Both depend on the same conventions. Arguments and a help screen, results on standard output and errors on standard error, standard input when no file is named, and an exit status that says whether it worked. A tool that follows them composes with every other tool; one that doesn't is a dead end. This chapter writes a word-counting tool with argparse and runs it as a real program, so you can see its help screen, its output, its errors and its exit statuses.

What a program reads and writes

A command-line program has three inputs and three outputs. Its arguments arrive as a list of strings, sys.argv, split by the shell. Standard input is a stream that a pipe, a redirected file or the keyboard can supply. The environment holds settings such as HOME, COLUMNS and NO_COLOR. On the way out, standard output carries results, standard error carries messages for people, and the exit status, a small number, tells the caller whether it worked: 0 for success, anything else for failure. Chapter 3 of The Engineer's Loom shows how a shell wires these together; here the point is to use each for its job.

The separation between the two output streams matters more than it looks. tally *.txt | sort -n sorts tally's results; if tally printed a warning to standard output, the warning would be sorted in with them. Written to standard error, it still appears on the terminal and stays out of the data. Likewise, exit statuses are how scripts decide what to do next: tally notes.txt && echo done prints "done" only if tally succeeded, and a scheduled job is marked failed when its status isn't 0.

Arguments with argparse

Parsing sys.argv by hand is tedious and always slightly wrong. The standard library's argparse does it properly. You declare each argument: a positional files taking any number of values, nargs="*"; an option -t or --top with type=int so it's converted and checked; a --version action. From that it generates the usage line and the --help screen, converts types, and rejects bad input with a usage message on standard error and exit status 2, as the example's --top lots shows, before any of your code runs. Add a sentence of help to every argument; the help screen is the first documentation most users read.

The conventions that make it composable

  • Read standard input when no file is given, and treat - as standard input. Then tally works at the end of a pipeline, curl -s https://example.com/page | tally --top 10, as well as on files.
  • Carry on past a bad file when it makes sense, report it on standard error, and exit non-zero at the end. The example counts poem.txt, reports missing.txt and returns 1, so the user gets the useful results and the script running it learns that something failed.
  • Use exit status 0 for success, 1 for failure, 2 for bad usage. argparse uses 2 already; shells report 128 plus the signal number for a program killed by a signal, such as 130 after Ctrl-C.
  • Print results as plain, regular lines, one record per line with consistent columns, so sort, grep, awk and spreadsheets can use them. If you also offer a human-friendly format, make machine-readable output, such as --json, available too.
  • Never prompt when standard input isn't a terminal, and respect NO_COLOR: a program run from a script has nobody to answer questions, and colour codes in a log file are noise.

Structure for testing and installing

The example's tool keeps all its logic in main(argv=None), which parses argv if given, or the real command line if not, and returns the exit status; the last lines, if __name__ == "__main__": sys.exit(main()), are the only part that runs when it's a program. That shape makes the tool testable without starting a process: a test calls main(["poem.txt", "--top", "2"]) and checks the return value, and pytest's capsys fixture captures what it printed. The example starts a real process with subprocess.run instead, which is slower but tests exactly what a user gets, including the exit status the shell sees.

To install the tool as a command, declare it in pyproject.toml under [project.scripts] as tally = "tally:main"; installing the package, for instance with uv tool install . or pipx install ., then puts a tally command on the path that calls main. For tools with many subcommands, like git, argparse supports them through add_subparsers, and third-party libraries such as Click and Typer build the same interfaces from decorators or type hints.

Common traps
  • Printing errors to standard output, where they corrupt the results another program is reading.
  • Exiting 0 after a failure, so scripts and schedulers think everything worked.
  • Requiring a file argument instead of reading standard input, so the tool can't be used in a pipe.
  • Parsing sys.argv by hand, and getting quoting, missing values or --help wrong.
  • Interactive prompts and colour codes when the output isn't a terminal.

Chapter 19

Programs with state

9 min read3 exercises

A game, an editor, a shopping basket and a server all remember things between one input and the next. That memory is their state, and programs with state go wrong in characteristic ways: a change made in one place and forgotten in another, a move applied twice, a bug that only appears after a particular sequence of actions. The cure is a design: keep the whole state in one value, and make every change a pure function from the old state and an action to the new state. This chapter builds the game of Nim that way, and the design pays for itself at once in testing, replay, saving, undo and a computer opponent.

State as a value

In Nim, players take turns removing any number of stones from one pile, and whoever takes the last stone wins. The example's whole state is a frozen dataclass, Game: the piles, whose turn it is, and the winner if there is one. Nothing about the game lives anywhere else, in globals or scattered across objects, so the question "what's the situation now?" always has a single, printable answer. Because the dataclass is frozen, a state can never change after it's made; each move makes a new one, which is what makes the rest of the chapter possible.

All the rules live in two functions. legal(game, pile, take) returns a reason a move isn't allowed, or None. step(game, pile, take) checks it, and returns the next state: the piles with stones removed, the turn passed to the other player, and the winner set if no stones remain. step is pure: the same state and move always give the same result, and nothing else changes. Everything else, reading what the player typed, printing the board, choosing the computer's move, is outside the rules, and talks to them only through those two functions.

What the design buys

Bad input can't break anything. The loop parses each line, and if it isn't two numbers, or names a pile that doesn't exist, or takes more stones than a pile has, it prints a specific message and asks again; the state is untouched, because nothing changes until step succeeds. The example feeds it three kinds of bad input, four times, and the game carries on.

The game can be replayed and tested. play reads moves from a list, so the same list always produces the same game. A real game passes lines typed at the keyboard, iter(input, "quit") for instance, through the same function. Tests don't need a person: call step on a state and check the result, or replay a whole game from a list and check the winner. The computer's random choices use a seeded generator, so even its play is reproducible, as chapter 11 requires.

Saving is one line, because the state is plain data: json.dumps(asdict(game)). Loading needs one detail, turning the JSON list back into a tuple, and the loaded state compares equal to the original, so the game continues exactly where it left off. Undo is a lookup: the loop appends every state to history, which costs almost nothing because states are small and never change, and stepping back two entries undoes your move and the computer's reply.

The opponent is a function of the state too. Nim has a complete strategy, found by Charles Bouton in 1901: XOR all the pile sizes together, and if the result isn't zero, there is always a move that makes it zero, which leaves your opponent in a losing position. best_move finds it in four lines. Your first move, taking 2 from pile 2, left a non-zero XOR, so the computer won from there; exercise 19.1 finds the move that would have won.

This shape, one immutable state, actions and a pure update function, is how many interactive programs are built. The Elm language and the Redux library for web interfaces are organised around exactly it, and the same idea appears in databases as an event log that can be replayed to rebuild any past state. When a program with state becomes hard to reason about, moving toward this design is usually the fix.

Common traps
  • State scattered across globals and objects, so no single place says what the situation is.
  • Rules mixed into input handling and display, so they can't be tested or reused.
  • Changing the state before validating the move, leaving it half-updated when validation fails.
  • Reading input straight from input() deep in the logic, so the program can't be replayed or tested.
  • Unseeded randomness, so a bug that appeared in one game can't be reproduced.

Exercise 19.3Undo and redo

Add undo and redo commands to the game: u undoes your last move and the computer's reply, r redoes them, and making a new move after an undo discards the redo history. Which data structure do you need?

Show solution

Two stacks of states, as every editor does it. Keep past, the states before the current one, and future, the states undone. Undo pops the current state onto future and takes the top of past as current, twice to cover both players' moves. Redo does the reverse. Any new move pushes the current state onto past, applies step, and clears future, because the undone moves no longer follow from where you are. All of this is possible only because states are immutable values: undo just means "go back to that value", with no need to reverse each change, which is what makes undo so hard to add to programs that mutate their state in place. The loop handles u and r before trying to parse a move, and refuses with a message when the relevant stack is empty.

  • Can you validate input with helpful messages without ever leaving the state half-changed?
  • Can you save and load state as JSON, and implement undo with a history of states?
  • Can you test the rules directly, and replay a session from a list of inputs?

Chapter 20

Talking to APIs

10 min read3 exercises

Calling a web API is one line of code, and making that line dependable takes the rest of the program. The network is slow sometimes and absent sometimes; servers fail briefly, refuse requests they consider too frequent, and return errors for things that don't exist. And asking again for data you already have wastes everyone's time. This chapter builds a client that sets timeouts, retries only what's worth retrying, honours rate limits, and caches answers on disk, revalidating them cheaply when they get old. It runs against a small API server started inside the example, so every run behaves the same without touching the internet.

Requests and responses

A web API speaks HTTP. The client sends a request: a method, usually GET to read and POST to create, a URL, and headers. The server sends a response: a status code, headers, and a body, which for most APIs is JSON. The status code's first digit is its class. 2xx means success: 200 OK. 3xx means look elsewhere, including 304 Not Modified, "your copy is still current". 4xx means the client's request was wrong: 404 Not Found, 401 for missing credentials, and 429 Too Many Requests. 5xx means the server failed: 500, or 503 Service Unavailable. That classification tells the client what to do next, and getting it right is most of what this chapter is about.

Python's standard library includes urllib.request, which the example uses so it runs without installing anything. Most Python projects use the third-party requests or httpx libraries instead, which have friendlier interfaces; everything below applies to them in the same way. One quirk of urllib is that it raises HTTPError for any status that isn't 2xx, even 304, which the example's client handles explicitly.

Failing well: timeouts, retries and rate limits

Always set a timeout. Without one, a request to a server that has stopped responding waits for minutes, or forever, and your program hangs with it. The example's /slow endpoint takes half a second and the client allows 0.2, so it gives up and reports "no answer within 0.2 s". Note in the server's log that the slow request still finished, with a 200 nobody received: a timeout means you stopped waiting, not that the server stopped working, which matters for requests that change things.

Retry only what might succeed next time. A 503 or 500 is often momentary: a server restarting, a database briefly overloaded. The client retries those up to three times, waiting 0.5, then 1, then 2 seconds, which is exponential backoff: each wait doubles, so a struggling server gets more breathing room, not a flood of retries. The example's /cities/lima fails twice and succeeds on the third attempt, and the waits recorded are 0.5 and 1.0. A 404 is different: asking again won't make Rome exist in the server's data, so the client raises an error at once. Retrying 4xx errors only adds load and delay. Retries are also only safe for requests that can be repeated without harm, like GET; a retried "charge the card" request can charge twice, which is why payment APIs use idempotency keys.

Honour rate limits. A server returning 429 is saying you've asked too often, and usually includes a Retry-After header saying how long to wait, here 2 seconds. The client waits exactly that and tries again. Ignoring it typically gets the client blocked. The example's client takes its sleep function as a parameter, so the run records the waits instead of actually sleeping, the same injection of dependencies as chapter 11, which is why the example runs in about a second.

Caching

The second request for Oslo, 30 seconds after the first, never reached the server: the cached answer was younger than the client's max_age of 60 seconds, so it was used as it was. That's freshness, and it's the biggest saving a cache offers. Choosing max_age is a judgement about the data: a city's weather can be a few minutes old, an exchange rate perhaps seconds, a country's name for ever.

After 91 seconds the cached copy was stale, but probably still correct, and downloading it again would waste bandwidth. So the client sends a conditional request: If-None-Match with the ETag, a fingerprint of the content that the server sent with the original response. If the content hasn't changed, the server replies 304 with no body, and the client reuses its copy and resets its age; that's revalidation. The server log shows it: the second request for Oslo got 304. The cache lives in a JSON file, so a new client, or the next run of the program, starts with everything the last one learned, as the line "a new client reads the saved cache" shows.

Two practical rules complete the picture. Keep credentials such as API keys out of your code and out of the cache: read them from an environment variable, os.environ["WEATHER_API_KEY"], and never print or log them. And in unit tests, never call the real API, which makes tests slow, flaky and dependent on someone else's server; run a local server as the example does, or pass the client a fake function in place of the network.

Common traps
  • No timeout, so one unresponsive server hangs the whole program.
  • Retrying every error, immediately and forever, including 4xx errors that will never succeed.
  • Retrying requests that aren't safe to repeat, such as payments, without an idempotency key.
  • Ignoring Retry-After and getting rate-limited further, or blocked.
  • API keys in source code, where they end up in version control and in logs.

Exercise 20.1Jitter

With fixed waits, all thousand clients retry at exactly 0.5 seconds, then all at 1.5, then all at 3.5: synchronised waves of a thousand requests each, which can knock a recovering server straight back over. That's called a thundering herd. Choosing each wait at random between 0 and the backoff limit spreads the retries evenly across the interval, so the server sees a steady trickle instead of spikes; AWS's architecture blog popularised this "full jitter" variant after measuring it against the alternatives. In tests, the random generator should be passed in and seeded, like the clock and sleep, so the waits are still reproducible.

Exercise 20.2How long to cache

Choose a max_age for each, and say whether revalidation with ETags is worth it: today's weather forecast, a currency exchange rate used to show prices, the list of countries, and a user's own profile that they just edited.

Show solution

A weather forecast changes a few times an hour, so 10 to 30 minutes is reasonable, and revalidation helps because unchanged forecasts are common. An exchange rate used for display tolerates seconds to a minute of staleness, but if it's used to charge someone, don't cache it at all, or fix the rate explicitly for that transaction. The list of countries changes almost never: cache it for a day or a week and revalidate, since it's large and nearly always unchanged. A user's own profile right after they edited it must not be served from a cache, or they'll see their change "fail": either bypass the cache for their own data, or update the cached copy with what they just saved, which is called write-through. There's no universal right answer; the question is always how wrong the data may be and for how long, and what that costs.

Exercise 20.3Testing without the network

Restructure the client so that tests can replace the HTTP call itself, without running any server. Show a test that checks a 503 is retried and a 404 isn't.

Show solution
class Client:
    """The retry logic, with the HTTP call passed in. (Caching works as before, and is left out.)"""
    def __init__(self, fetch, sleep=time.sleep):     # fetch(path, headers) -> (status, headers, body)
        self.fetch, self.sleep = fetch, sleep
    def get(self, path):
        for attempt in range(4):
            status, headers, body = self.fetch(path, {})
            if status == 200: return body, headers.get("ETag")
            if status == 429: self.sleep(float(headers["Retry-After"])); continue
            if status >= 500 and attempt < 3: self.sleep(0.5 * 2 ** attempt); continue
            raise RuntimeError(f"{path}: HTTP {status}")

def fake(responses):
    calls = []
    def fetch(path, headers):
        calls.append(path)
        return responses.pop(0)
    return fetch, calls

def test_retries_503_but_not_404():
    fetch, calls = fake([(503, {}, None), (200, {"ETag": '"x"'}, {"ok": 1})])
    assert Client(fetch, sleep=lambda s: None).get("/a")[0] == {"ok": 1} and calls == ["/a", "/a"]
    fetch, calls = fake([(404, {}, {"error": "no"})])
    with pytest.raises(RuntimeError):
        Client(fetch, sleep=lambda s: None).get("/b")
    assert calls == ["/b"]

Separating "make one HTTP request" from "decide what to do with the response" puts all the interesting logic, retries, backoff, caching, in code that a test can drive with a list of canned responses, in microseconds. The real fetch is a few lines wrapping urllib or httpx, tested once against a local server like the example's. The test checks behaviour by counting calls: one retry after the 503, none after the 404. This is the same design as chapter 19's pure step function, applied to I/O: keep decisions pure, push the side effects to the edges, and pass them in.

The deliverable

The stage asks for four programs, each a different shape, each with tests, a README and no framework doing the thinking for you. Chapters 18, 9, 19 and 20 build a small working version of each; the lists below say what the full versions need. Write them in that order or any other, but finish each one: a program that someone else has installed, run and used teaches more than four that nearly work.

1. A command-line tool

Pick something you'd use yourself: a to-do list, a unit converter, a tool that renames photos by date, a log summariser. Chapter 18 is the model.

  1. Arguments parsed with argparse, a --help screen with a sentence for every option, and --version.
  2. Reads standard input when no file is given, so it works in a pipeline.
  3. Results on standard output, errors on standard error, and exit statuses 0, 1 and 2 used as chapter 18 describes.
  4. All logic behind main(argv), with tests that call it directly and at least one that runs it as a process.
  5. Installable as a command through [project.scripts] in pyproject.toml.

2. Messy data to a clean report

Download a real public dataset in CSV, from a city's open-data portal or a national statistics office, and produce a report from it. Chapter 9 is the model.

  1. A cleaning function that returns a clean record or raises ValueError with a reason, and unit tests for each kind of mess the file contains.
  2. Rejected rows written to an errors file with their line numbers and reasons, and a check that clean rows plus rejected rows equals all rows.
  3. Explicit decisions, in comments and tests, about every ambiguity: date formats, units, duplicates, missing values.
  4. Streaming: memory use that doesn't grow with the number of rows.
  5. The report as CSV or JSON for programs, and as readable text for people.

3. A small game with state

Nim, noughts and crosses, hangman, Mastermind, a tiny text adventure. Chapter 19 is the model.

  1. The whole state in one immutable value, and every change through a pure step(state, action).
  2. Input validated with a specific message for each mistake, and no input that can crash the program.
  3. A game loop that reads from any iterable, so a test can replay a whole game from a list.
  4. Save and load as JSON, and undo.
  5. Randomness from a seeded generator passed in, and tests for every rule, including a property check over random games.

4. A script that talks to a public API

Choose a free API, such as Open-Meteo for weather, which needs no key, or the GitHub REST API, and build something useful on it: a forecast for your city, a summary of a repository's recent activity. Chapter 20 is the model.

  1. A timeout on every request, retries with exponential backoff and jitter for 5xx errors and timeouts only, and Retry-After honoured for 429.
  2. A disk cache with a max_age chosen and justified for the data, and ETag revalidation where the API supports it.
  3. Any API key read from an environment variable, never stored in the code, the cache or the logs.
  4. Tests that never touch the network, using a fake fetch function or a local server.
  5. Clear messages for the failures a user will actually meet: no network, a bad key, a rate limit.

For every program: a README that says what it does, how to install it, and how to run it, with an example; tests that run with one command; and a virtual environment with a lockfile. Then give each to someone else, watch them use it without your help, and fix whatever confused them.

The twenty rules

One per chapter, each linked back to it. Read them before you start a new program, and again when one surprises you.

  1. Predict what code will do before you run it, and know the type of every value.
  2. A name points to an object: know whether you're rebinding the name or mutating the object.
  3. Know each loop's invariant and why it stops, and use half-open ranges.
  4. One function, one job: return results, and keep printing and other side effects at the edges.
  5. Every recursion needs a base case and a shrinking step; memoise repeated work, and use a loop when it runs deep.
  6. Indexing and appending are cheap; inserting at the front and in are not. Choose the structure by its operations.
  7. Look things up in a dict or set, and make equal keys hash equally.
  8. Decode at the edge, work in str, encode at the edge, and always name the encoding.
  9. Open files with with and an encoding; reject bad rows with reasons, and never guess.
  10. Catch narrowly, validate at the boundary, and put the bad value in the message.
  11. Test from week one: edges first, seeded randomness, and watch every new test fail.
  12. Look, don't guess: reproduce, stop the program, inspect; bisect when you don't know where to look.
  13. A class owns its data and its invariants; compute derived values with properties.
  14. Prefer composition and narrow interfaces; inherit only from classes designed for it.
  15. Copy mutable data at boundaries, and never build nested lists with *.
  16. One virtual environment per project; ranges for libraries, lockfiles for applications.
  17. Map code before you read it, and record what it does before you change it.
  18. Results to standard output, messages to standard error, and an honest exit status.
  19. Keep state in one immutable value, and change it with a pure function.
  20. Set a timeout, retry only what might succeed, and cache what you've already been told.
