The Engineer's Loom

A loom weaves hundreds of threads into one cloth by passing each through the same narrow space in turn. An operating system does the same with programs. It gives every process the illusion of a machine of its own while one set of cores, one memory and one disk are shared between them all. This volume takes that illusion apart: processes and system calls, scheduling, the bugs that come from sharing, virtual memory, file systems that survive a crash, and the containers built from all of it. Every mechanism is shown working, in Python that makes real system calls or simulates what can't be shown directly.

The one habit

Everything an operating system manages is shared, and every kind of sharing needs a rule: who runs next, who may see which memory, and what happens if someone stops halfway through.

A thread can be interrupted between any two instructions, a process can be killed between any two system calls, and the power can fail between any two disk writes. So for every piece of shared state, ask what happens if this is interrupted at the worst possible moment. Most of this volume is the answer to that question for one resource after another.

Part I

The process

Three chapters on the unit an operating system manages: the process, a running program with an address space and an identity of its own; the system call, the one door through which a process asks the kernel for anything; and the signals and pipes with which a shell starts, connects and controls processes. By the end of this part you can build the core of a Unix shell.

Chapter 1

Processes and address spaces

10 min read3 exercises

A program is a file on disk. A process is that program running, together with everything the operating system keeps for it: its own memory, its open files, its saved registers and an identity. The first thing an operating system does is give every process the illusion of a machine to itself. This chapter shows what a process is made of, creates processes with fork and exec the way every Unix shell does, and follows one through its life until its parent collects its exit status.

What a process is

A process has three kinds of state. Its address space is the memory it can see: the program's code, its global data, a heap that grows as it allocates, a stack for each thread, and any files or libraries mapped in (chapter 17 of The Engineer's Mill). Its CPU state is the program counter, the stack pointer and the other registers; while the process isn't running, these are saved in the kernel. Its kernel state is the rest: a process ID, its parent's ID, the user and group it runs as, a table of open files, a current directory, how it handles each signal, and its resource limits. The kernel keeps all of this in one record per process, the process control block. On Linux it's a structure called task_struct, several kilobytes long.

On Linux you can read much of this directly. /proc/<pid>/maps lists a process's address space region by region, /proc/<pid>/fd lists its open files, and /proc/<pid>/status shows its state, memory use and owner. ps and top are mostly ways of reading /proc. On macOS, ps, lsof and vmmap show the same things.

Each process sees its own memory

Addresses in a program are virtual. When two processes both use address 0x601000, each reaches its own memory, because the kernel gives each process its own map from virtual addresses to physical memory. Part IV explains how that map works and what it costs. For now, the consequence is the one that matters: one process can't read or overwrite another's memory by accident, and a crash in one leaves the rest running.

fork, exec and wait

Unix creates processes in two steps. fork() makes a copy of the calling process. The copy, the child, has the same code, a copy of the same memory, the same open files and the same position in the program. It differs in its process ID and in one value: fork() returns 0 in the child and the child's ID in the parent, which is how each knows which it is. exec() then replaces the program running in a process with a new one, keeping the process ID and the open files. The parent calls wait() to learn when the child has finished, and how.

Splitting creation into two calls looks odd, but it's what makes the shell simple. Between fork and exec, the child is still running the shell's code, so it can rearrange its own file descriptors, change directory, set limits or drop privileges, and the program it then runs inherits the result. That's how ls > out.txt works (chapter 3). Windows takes the other approach: CreateProcess creates a process and starts a program in one call, with parameters for everything a Unix child would set up itself. POSIX also offers posix_spawn, which does the same.

The example forks a child that changes a value, shows that the parent's copy is untouched although the address is the same, and collects the child's exit status. It then runs echo through fork and exec, and reads the exit statuses of four commands, one of which doesn't exist.

Two details in the code matter in any language. The child ends with os._exit, which leaves at once, instead of returning into the parent's code or running the parent's clean-up handlers twice. And the parent empties Python's output buffer before each fork, for a reason exercise 1.2 explains.

fork has critics. Copying a process with a large address space is slow even with the tricks of chapter 13, and forking a process that runs several threads copies only the thread that called it, which can leave locks held forever by threads that don't exist in the child. Baumann and colleagues argued in 2019 that fork no longer belongs in operating systems. Python 3.14 stopped using it by default for multiprocessing on Linux for this reason. Shells and servers still use it everywhere, so it's worth understanding precisely.

The life of a process

A process moves between a few states. It's running while a core is executing it, ready while it could run but is waiting for a core, and blocked while it waits for something else: a disk read, a network packet, a timer, a lock. Chapters 4 to 6 are about the move from ready to running. A process that has exited but whose parent hasn't yet called wait is a zombie. Its memory and files are gone, but the kernel keeps its process ID and exit status until the parent collects them. In ps output these states appear as R, S (sleeping, blocked), D (blocked in a way signals can't interrupt, usually disk I/O), T (stopped) and Z.

Two rules follow. A parent should wait for every child, or tell the kernel it doesn't care, by setting SIGCHLD to be ignored, so that children are reaped automatically. Otherwise zombies accumulate until no process IDs are left. And if a parent exits first, its children are orphans: the kernel hands them to process 1, init or systemd, which waits for them. Exit statuses follow a convention shells rely on: 0 means success, small numbers are errors chosen by the program, 126 means a file couldn't be executed, 127 that the command wasn't found, and 128 plus n that the process was killed by signal n.

Common traps
  • Never calling wait, so finished children pile up as zombies.
  • Forking with unflushed output, which then appears twice.
  • Forking a multithreaded program and calling anything but exec in the child.
  • Treating a non-zero exit status as the only failure. A process killed by a signal has no exit status at all.
  • Assuming process IDs are unique forever. They're reused, so a stale PID file can name an unrelated process.
Exercises
Exercise 1.1Counting processes

A program runs for i in range(3): os.fork() and then prints one line. How many lines are printed? How many processes call fork in the third iteration?

Show solution

Every process that reaches a fork becomes two, so the number of processes doubles in each iteration: 2 after the first, 4 after the second and 8 after the third. Eight processes print, so there are 8 lines. In the third iteration all 4 existing processes call fork, the original included. In general n calls in a loop like this create 2n processes, which is why a loop that forks by mistake, a fork bomb, can exhaust a machine in seconds. Per-user process limits, ulimit -u, exist largely for that reason.

Exercise 1.2The line that appears twice

A program runs print("starting") and then os.fork(), and both processes then exit normally. Run in a terminal, it prints "starting" once. With its output redirected to a file, the file contains "starting" twice. Why?

Show solution

print doesn't make a system call straight away. It writes into a buffer inside the process, which is emptied when it fills, when the program exits, or, for a terminal, at the end of each line. On a terminal the line was written out before the fork, so only one copy exists. When output goes to a file, the buffer is flushed only when full or at exit, so at the moment of the fork "starting" is still in the buffer, part of the process's memory. The child gets a copy, and both processes flush their copies at exit. The fix is to flush before forking, as the example does, or to have the child end with os._exit, which exits without flushing. C's printf and exit behave the same way.

Exercise 1.3A server that never waits

A server forks a child to handle each request and never calls wait. Each child exits within a second. What builds up, what eventually goes wrong, and what are two ways to fix it?

Show solution

Every finished child stays a zombie, holding a process ID and a small kernel record, until the parent waits for it, and this parent never does. Zombies use almost no memory, but process IDs are limited: by the system-wide maximum, 32,768 by default on older Linux systems and over 4 million on newer ones, and by the per-user limit, which is usually much lower. When the limit is reached, fork fails with EAGAIN for the server and for every other process the same user runs. One fix is to handle SIGCHLD, which the kernel sends when a child exits, and call waitpid(-1, WNOHANG) in a loop until there are none left to collect. The other is to set SIGCHLD to be ignored, which on Linux and macOS tells the kernel to reap children automatically. If the server itself exits, its zombies are adopted by process 1 and reaped.

Chapter 2

System calls and the kernel boundary

9 min read3 exercises

A process can compute on its own at full speed, but anything that touches the world outside its memory goes through the kernel: reading a file, sending a packet, starting a process, allocating more memory. The processor enforces that boundary with privilege modes, and system calls are the one controlled way across it. This chapter follows a system call from a line of Python to a device driver and back, measures what the crossing costs, and draws the rule that follows: make fewer, bigger system calls.

Two modes

Every modern processor runs in at least two modes. In user mode, the mode programs run in, some instructions are forbidden: those that talk to devices, change the page tables, switch off interrupts or halt the machine. In kernel mode everything is allowed. On x86 the modes are called rings 3 and 0; on ARM they're exception levels EL0 and EL1. A user program that tries a privileged instruction doesn't get to run it. The processor traps into the kernel, which normally kills the program.

This is what lets the operating system run programs directly on the hardware, at full speed, and still stay in charge. OSTEP calls it limited direct execution. The program's instructions run on the real processor with no interpreter in the way, but there are only three ways back into the kernel: the program asks, with a system call; the program does something it can't, such as dividing by zero or touching unmapped memory, which raises an exception; or a device or the timer raises an interrupt. The timer interrupt is the one that guarantees the kernel can always take the processor back, even from a program stuck in a loop (chapter 5).

Crossing the boundary

From Python, os.write(fd, data) calls the C library's write function, which is a thin wrapper. On Linux on x86-64, it puts the system call's number, 1 for write, in the rax register and the three arguments in rdi, rsi and rdx, then executes the syscall instruction. On 64-bit ARM the instruction is svc #0 and the number goes in x8. The processor switches to kernel mode and jumps to an entry point the kernel registered at boot. Nothing else about the jump is up to the program.

The kernel's entry code saves the program's registers, switches to a stack that belongs to the kernel, and looks the number up in the system call table, about 450 entries on Linux. The handler checks its arguments before trusting them. A pointer from user space must point into the caller's own memory, and the kernel copies data in and out with special functions instead of following the pointer directly, because a malicious program could pass the address of kernel memory. When the work is done, the result goes back in a register and the processor returns to user mode. On failure the kernel returns a negative error number, and the C library turns it into a return value of −1 with the number in errno. Python turns it into an exception: ENOENT becomes FileNotFoundError, EACCES becomes PermissionError, EAGAIN becomes BlockingIOError.

What a crossing costs

A system call costs far more than a function call. The mode switch, saving and restoring registers, the checks, and on some processors the mitigations added after the Meltdown and Spectre attacks of 2018 (chapter 13 of The Engineer's Mill) all take time, and the kernel's code and data push the program's out of the caches. The example times the smallest system call there is, getppid, then one that does real work, and then writes a million bytes three ways. The timings are one recorded run on an Apple M1 Pro.

Even from Python, where an ordinary function call costs about 29 ns, the cheapest system call costs over five times as much, and from C the ratio is closer to a hundred. Writing a byte at a time made a million system calls and took over half a second. A buffered file object made 8, because Python collects bytes in a 128 KiB buffer and calls write only when it fills; its 39 ms are almost all the cost of a million calls to f.write in Python, not of the kernel. A single write of the whole megabyte took 0.04 ms. The per-call overhead, not the bytes, was the cost.

Fewer, bigger crossings

That result is behind a whole family of techniques. Buffering, in C's stdio and in every language's file objects, turns many small writes into a few large ones. readv and writev move several buffers in one call. sendfile and copy_file_range move data from one file descriptor to another without bringing it into the process at all. mmap maps a file into memory so that reading it needs no system calls, only page faults (chapter 13). epoll returns many ready connections from one call (chapter 18), and Linux's io_uring lets a program queue hundreds of operations and collect their results through memory shared with the kernel.

Some calls don't need the kernel at all. Reading the clock is so common that Linux maps a small read-only page of kernel data and code, the vDSO, into every process. clock_gettime runs there, in user mode, and costs about as much as a function call. macOS does the same with its commpage.

Watching system calls

On Linux, strace prints every system call a program makes, with its arguments and result. strace -c counts them and totals their time, and strace -e trace=openat shows only the files a program opens, which is often the fastest way to find out why it can't find its configuration. perf trace does the same with less overhead. On macOS, dtruss and Instruments do the same job, though system integrity protection limits what they can trace. A program that's slow without using much CPU is often blocked in a system call, and these tools show which one.

Common traps
  • Unbuffered output in a loop: one system call per byte or per line.
  • Ignoring short reads and writes. A read or write on a pipe or socket can move fewer bytes than asked.
  • Not retrying after EINTR in C, when a signal interrupts a slow call. Python retries for you.
  • Assuming a call that looks cheap is cheap. Each os.stat here cost over a microsecond.
  • Trusting pointers or lengths that come from user space, if you ever write kernel or driver code.
Exercises
Exercise 2.1The short write

os.write(sock_fd, data) is called with 10,000 bytes on a socket and returns 3,000. What happened, and what must the caller do? Write a function that writes all of data.

Show solution

The kernel accepted only what fit in the socket's send buffer and reported how much that was. That's not an error: write returns the number of bytes it actually took, and on pipes, sockets and terminals that can be fewer than asked. The caller must send the rest:

def write_all(fd, data):
    view = memoryview(data)
    while view:
        n = os.write(fd, view)     # may take only part of it
        view = view[n:]

Python's socket.sendall and buffered file objects do this loop for you; os.write and C's write don't. Reads behave the same way: read returns what's available, which may be less than requested even before the end of the data.

Exercise 2.2A logger's budget

A service logs 50,000 lines a second, 80 bytes each, with one unbuffered write per line costing 1.5 µs. What share of a core does that take? What if lines are collected in a 64 KiB buffer? What does buffering risk, and how do logging libraries limit the risk?

Show solution

Unbuffered: 50,000 × 1.5 µs is 75 ms of every second, 7.5% of a core spent on system calls alone. Buffered: the service produces 4 MB a second, so a 64 KiB buffer fills about 61 times a second, and 61 larger writes cost well under a millisecond. The risk is that lines still in the buffer are lost if the process crashes, which is exactly when you most want them. Logging libraries flush on a timer, every few hundred milliseconds, and flush immediately for errors, and many write logs from a separate thread or hand them to a local agent, so the service never waits for the disk.

Exercise 2.3Why the clock needs no kernel

Explain why reading the time can run entirely in user mode through the vDSO, while write can't.

Show solution

Reading the time needs no privileged instruction and changes nothing. The kernel publishes the clock's current parameters, such as a base time and a scale for the processor's cycle counter, in a page mapped read-only into every process, and updates them as needed. The vDSO code reads those values and the counter, which user mode is allowed to read, and computes the time. Nothing it does could harm another process. write is different: it must check that the process may write to that file, change shared state such as file contents, pipe buffers or a device, and possibly wake other processes. All of that needs kernel mode and the kernel's data structures, so it has to cross the boundary.

Chapter 3

Signals, pipes and the shell

10 min read3 exercises

A Unix shell is a short program built from about a dozen system calls: fork, exec and wait from chapter 1, plus pipe, dup2, open, setpgid and kill. Knowing how it uses them explains pipelines, redirection, exit statuses, Ctrl-C and Ctrl-Z, and why cmd > file 2>&1 and cmd 2>&1 > file do different things. This chapter builds the core of a shell in about forty lines and then controls a running pipeline with signals.

File descriptors 0, 1 and 2

Every process starts with three open file descriptors: 0 for standard input, 1 for standard output and 2 for standard error. A program writes to descriptor 1 without knowing whether it leads to a terminal, a file or another program. Whoever started the program decided that, and that's the trick behind redirection. open always returns the lowest free descriptor, and dup2(old, new) makes descriptor new refer to the same open file as old, closing whatever new referred to before. To run ls > out.txt, the shell forks, and the child opens out.txt, calls dup2 to put it on descriptor 1, closes the original descriptor, and execs ls. ls writes to descriptor 1 as always and never learns the difference.

Redirections are applied left to right, each one a dup2. 2>&1 means "make descriptor 2 a copy of whatever descriptor 1 is now". So cmd > file 2>&1 first points 1 at the file and then copies that to 2, sending both to the file. cmd 2>&1 > file copies 1, still the terminal, to 2 first, and only then points 1 at the file.

Pipes

pipe() creates a buffer in the kernel and returns two descriptors: bytes written to one can be read from the other, in order. The buffer is small, 64 KiB by default on Linux, so a fast writer blocks until the reader catches up, and a reader blocks until there's something to read. That keeps a pipeline's memory use bounded however much data flows through it. A read returns end-of-file only when every write end of the pipe is closed, and a write to a pipe with no readers left sends the writer SIGPIPE, which kills it by default. That's how yes | head -1 ends: head exits after one line and yes dies on its next write.

For a pipeline the shell creates one pipe between each pair of stages and forks one child per stage. Each child moves the right pipe ends onto its descriptors 0 and 1 with dup2, closes every other pipe descriptor it inherited, and execs its program. The parent closes its copies too. Each of those closes matters. A reader sees end-of-file only when every copy of the write end is closed, including copies left open by mistake in the parent or a sibling.

A shell in forty lines

The example's start function does what a real shell does for a pipeline with redirections, and wait_all waits for every stage and reports the status of the last, which is the status a shell reports for a pipeline. It runs the pipeline in the figure, writes a file through a redirection and reads it back through another, and shows that true | false fails while false | true succeeds. The second half starts sleep 30 | sleep 30, suspends it, resumes it and interrupts it, the way Ctrl-Z, fg and Ctrl-C would, and then catches a signal sent to itself.

One detail took longer to get right than the rest. The parent must not signal the pipeline until both children have called exec: a child interrupted while still running Python would handle the signal as Python, not as sleep. The example waits on an extra pipe that Python creates with the close-on-exec flag. Each child's copy closes automatically when that child execs, so the parent's read returns only when all of them have. Shells solve the same race in their own ways, and it's a good example of how much of systems programming is about the order in which things happen.

Signals

A signal is a small asynchronous notification sent to a process by the kernel or by another process. The common ones: SIGINT, sent by Ctrl-C; SIGTERM, the polite request to exit that kill sends by default; SIGKILL, which ends the process at once; SIGTSTP, sent by Ctrl-Z, and SIGSTOP, which suspend it; SIGCONT, which resumes it; SIGCHLD, sent to a parent when a child exits or stops; SIGPIPE; SIGSEGV, for an invalid memory access; and SIGHUP, sent when the terminal goes away and, by convention, used to ask a daemon to reload its configuration.

For each signal a process chooses the default action, which for most signals is to terminate, to ignore the signal, or to run a handler. SIGKILL and SIGSTOP can't be caught or ignored, which is what makes them reliable; the example's attempt to install a SIGKILL handler fails. A handler can run between any two instructions of the program, so in C it may only call functions that are safe at any moment: not malloc and not printf, which may be halfway through updating their own state. The usual pattern is for the handler to set a flag, or write a byte to a pipe that the main loop watches, and let the main program do the work. Python does this for you: its C-level handler only records the signal, and your Python handler runs in the main thread at the next safe point.

Job control

A shell puts each pipeline in its own process group, with setpgid, so the whole job can be signalled at once with killpg. The terminal driver tracks one foreground process group. When you press Ctrl-C, the terminal sends SIGINT to every process in that group, and the shell itself, which is in another group, is untouched. Ctrl-Z sends SIGTSTP; the shell notices that the job has stopped (through waitpid with the WUNTRACED flag), takes the terminal back, and prints a prompt. fg hands the terminal to the job again and sends SIGCONT; bg sends SIGCONT without handing the terminal over. The same mechanisms run production systems. When a container or a systemd service is stopped, its main process gets SIGTERM, a grace period, 10 seconds by default in Docker and 30 in Kubernetes, and then SIGKILL. A service that handles SIGTERM by finishing its current requests and exiting shuts down cleanly. One that doesn't is killed in the middle of them.

Common traps
  • Leaving a pipe's write end open in the parent or a sibling, so the reader never sees end-of-file.
  • Real work inside a C signal handler, which can deadlock in malloc or corrupt state.
  • A server killed by SIGPIPE when a client disconnects. Ignore the signal and handle EPIPE instead.
  • Writing 2>&1 > file and expecting errors in the file.
  • Trusting a pipeline's exit status: it's the last stage's. Use set -o pipefail in scripts.
  • A container's main process that ignores SIGTERM, so every stop waits out the grace period.
Exercises
Exercise 3.1Redirection, as system calls

Write the sequence of open and dup2 calls a shell's child makes for cmd > out.txt 2>&1 and for cmd 2>&1 > out.txt, and say where standard error ends up in each.

Show solution

For cmd > out.txt 2>&1: fd = open("out.txt", O_WRONLY|O_CREAT|O_TRUNC), dup2(fd, 1), close(fd), then dup2(1, 2). Descriptor 1 is the file when 2 is copied from it, so both go to the file. For cmd 2>&1 > out.txt: dup2(1, 2) first, while 1 is still the terminal, so 2 becomes the terminal; then open, dup2(fd, 1) and close(fd) point 1 at the file. Output goes to the file and errors to the terminal. Each redirection copies a descriptor's current value. It doesn't create a lasting link between descriptors.

Exercise 3.2The pipeline that never ends

A student's shell runs printf 'hi\n' | cat. cat prints "hi" and then the pipeline hangs forever. printf has exited. What's the most likely bug?

Show solution

cat reads until end-of-file, and a pipe reports end-of-file only when every descriptor for its write end is closed. printf's copy closed when it exited, so another copy must still be open: most likely the shell process never closed its own write end after forking, or the cat child inherited the write end and didn't close it before exec. cat holding a write end to its own input pipe is the subtlest case, because it can then never see end-of-file however long it waits. The fix is to close every pipe descriptor a process doesn't use, in the parent right after forking and in each child before exec. Creating pipes with the close-on-exec flag, as Python does by default, removes most chances to get this wrong.

Exercise 3.3The ten-second deploy

Every time a containerised service is stopped, it takes exactly 10 seconds, and its logs show it was killed rather than exiting. The Dockerfile ends with CMD python server.py. Explain the delay and give two fixes.

Show solution

Written that way, the "shell form", Docker runs /bin/sh -c "python server.py", so the shell is process 1 in the container and Python is its child. docker stop sends SIGTERM to process 1 only. Process 1 is also special: the kernel doesn't apply the default "terminate" action to it, so a signal it has no handler for is simply ignored. Either way the server never hears about the stop, and after the 10-second grace period Docker sends SIGKILL, which can't be ignored. Fixes: use the exec form, CMD ["python", "server.py"], so Python is process 1, and give it a SIGTERM handler that stops accepting work, finishes current requests and exits; or run a minimal init such as tini, with docker run --init, which forwards signals to the child and reaps zombies.

Part II

Sharing the CPU

Three chapters on how many programs share a few cores. Threads run several lines of execution inside one process's memory, and a context switch moves a core from one thread to another. The classic scheduling policies trade finishing work quickly against responding quickly. Real kernels add fair shares, weights and many cores to those policies.

Chapter 4

Threads and context switches

10 min read3 exercises

A thread is another line of execution inside the same process. It has its own registers and its own stack but shares everything else: the memory, the open files, the process ID. That makes sharing data between threads trivially easy, which is both why threads are useful and why Part III exists. This chapter compares threads with processes, shows what a context switch saves and restores, measures what creating each costs and how long a handover between them takes, and explains how runtimes from Go to Python map their own threads onto the kernel's.

Processes and threads

Each thread has its own program counter and registers, its own stack, its own thread-local variables (in C, errno is one) and its own signal mask. Everything else belongs to the process and is shared by all its threads: the code, the global variables, the heap, the open file descriptors, the current directory, the user ID and the process ID. A pointer created in one thread works in every other. On Linux a thread is simply a task, like a process, created with clone and flags that ask it to share the parent's memory, files and signal handlers. Each thread has its own thread ID, and ps -L or top -H lists them.

Threads are cheaper than processes to create and to switch between, because there's no address space to copy or change, and they communicate through ordinary memory. Processes are safer: a crash, a memory leak or a corrupted heap in one process leaves the others alone, while a bad pointer in any thread brings down the whole process. Browsers run each site in its own process for that reason, and databases such as PostgreSQL use a process per connection. Most servers written in Java, Go or C++ run many threads in one process.

What a context switch does

A context switch moves a core from one thread to another. It starts in the kernel, either because the running thread made a system call that blocks, such as a read with no data waiting, or because a timer interrupt fired and the scheduler decided the thread's turn was over. The kernel saves the running thread's registers and stack pointer, picks the next thread (chapters 5 and 6), loads that thread's stack pointer and registers, and returns to it as if from an interrupt. If the next thread belongs to a different process, the kernel also switches address spaces by loading a new page-table root, CR3 on x86 or TTBR0 on ARM. Tagging TLB entries with an address-space ID, PCID on x86 and ASID on ARM, means the switch doesn't have to throw away every cached translation (chapter 13).

The direct cost is a microsecond or two. The indirect cost is often larger: the new thread finds the caches and the TLB full of the old thread's data, and runs slowly until it has warmed them up again. That's why a scheduler doesn't switch as often as it could, and why a server that keeps thousands of threads busy can spend a surprising share of its time switching.

Measured

The example first shows the difference in sharing: four threads appending to one list fill it, while four forked processes each append to their own copy. It then times creating a thread against forking a process, and measures a handover with a ping-pong over two pipes, in which each side blocks until the other replies, so every round trip forces two wake-ups and two switches. The timings are one recorded run on an Apple M1 Pro.

Starting and joining a thread took about 42 µs, and forking and waiting for a process about 0.9 ms, over twenty times as long, because the kernel had to duplicate the page tables of a whole Python process. Each handover took about 2 µs, and that includes waking a thread blocked on a pipe, scheduling it, and the pipe read and write, so the switch itself is only part of it. Linux on a typical server gives similar orders of magnitude, with a faster fork. The practical lessons: create threads ahead of time and reuse them, which is what a thread pool does, and don't design a system that needs a context switch for every small piece of work.

Kernel threads and user threads

The threads above are kernel threads: the kernel knows about each one and schedules it. That's the model of POSIX threads in C, of Java's platform threads and of Rust's standard library, one language thread per kernel thread. Each needs a kernel stack and a user stack, 8 MiB of reserved address space by default on Linux, of which typically only tens of kilobytes are ever touched, and every switch between them goes through the kernel.

Many runtimes instead multiplex many lightweight user threads onto a few kernel threads, switching between them in user space for a few hundred nanoseconds. Go's goroutines start with 2 KiB stacks that grow as needed, and the Go runtime runs them on roughly one kernel thread per core. Java added virtual threads on the same model in JDK 21, and Erlang has always worked this way. The difficulty is blocking: when a user thread makes a system call that blocks, it blocks the kernel thread under it, and every user thread scheduled there. These runtimes therefore use non-blocking I/O internally (chapter 18) and hand blocking calls to spare kernel threads.

Python's threads

CPython's threads are real kernel threads, but in the standard build a global interpreter lock, the GIL, lets only one of them run Python code at a time. A thread releases it while waiting for I/O, so threads work well for programs that spend their time waiting on networks and disks, and do nothing for programs that spend it computing in Python. The example's thread handover includes passing the GIL. For CPU-bound work, use processes (multiprocessing or concurrent.futures.ProcessPoolExecutor), or libraries such as NumPy whose C code releases the lock. A free-threaded build without the GIL became an officially supported option in Python 3.14, which makes the data races of chapter 7 real for Python code too.

Common traps
  • One thread per request with no limit, until memory or the scheduler gives out under load.
  • Expecting Python threads to speed up CPU-bound code on a build with the GIL.
  • Creating threads in a hot path instead of reusing them from a pool.
  • Thread-local state left over in a pooled thread from the previous task.
  • Forgetting that one crashing thread kills the whole process, including every other thread's work.

Chapter 5

Scheduling

11 min read3 exercises

When more threads are ready to run than there are cores, the scheduler decides which run. Every policy trades one goal for another: finishing jobs soon, responding to them soon, using the processor fully, treating everyone fairly. This chapter simulates the classic policies on small workloads: first come first served, shortest job first, shortest time to completion and round robin. It then builds the multi-level feedback queue, which responds quickly to interactive programs without knowing in advance how long anything will run, and shows how a program can game it and how the scheduler stops that.

What a scheduler optimises

Chapters 2 and 4 covered the mechanism: the timer interrupt that hands control back to the kernel, and the context switch that moves a core to another thread. This chapter is about policy, the rule for which thread runs next. Two measures dominate. A job's turnaround time is how long it takes from arriving to finishing, which matters for batch work such as a build or a report. Its response time is how long it waits before it first runs, which is what a person at a keyboard or a client waiting on a request feels. Throughput, the work finished per second, and fairness, whether each job gets its share, complete the list. No policy wins on all of them.

First come, first served, and the convoy

The simplest policy runs jobs in the order they arrive, each to completion. Its weakness shows as soon as a long job arrives first. With A needing 100 ms and B and C 10 ms each, B and C wait behind A like cars behind a truck, the convoy effect, and the average turnaround is 110 ms. Running the shortest job first brings it down to 50 ms, and when all jobs arrive together, shortest job first is provably the best possible order for average turnaround.

Shortest job first has two problems. It needs to know how long each job will run, which a general-purpose operating system never does. And if it's non-preemptive, letting each job run until it finishes, it's helpless when short jobs arrive just after a long one has started: in the example's second workload B and C arrive 10 ms after A and wait 90 ms for it, and the average turnaround goes back up to 103 ms. The preemptive version, shortest time to completion first, interrupts A when they arrive and brings the average back to 50 ms.

Round robin and response time

Round robin gives each ready job a fixed time slice in turn and puts it at the back of the queue when the slice ends. It needs to know nothing about the jobs, and it's excellent for response time: with 1 ms slices every job runs within 2 ms of arriving. It's poor for turnaround, because it stretches every job out to near the end. The slice length is the dial between the two. Short slices give quick responses but spend more time switching, and with 20 CPU-bound threads ready, a 100 ms slice means each waits up to 1.9 seconds for its turn. Desktop and server kernels use slices of a few milliseconds.

Not knowing the future: the multi-level feedback queue

A real scheduler has to favour short, interactive jobs without being told which they are. The multi-level feedback queue (MLFQ), introduced by Fernando Corbató for MIT's CTSS time-sharing system in 1962, learns it from behaviour. There are several priority levels. A job at a higher level always runs before one at a lower level, and jobs at the same level share it round robin. Every new job starts at the top. A job that uses up its allotment of CPU time at a level moves down a level, so CPU-bound jobs sink, while a job that runs briefly and then waits for I/O stays near the top.

The example shows the effect. An interactive job that wants 1 ms of CPU every 10 ms competes with two CPU-bound batch jobs. Under plain round robin it waits about 11 ms every time it wakes, behind the batch jobs' slices, and gets only 4.8% of the CPU instead of the 10% it needs. Under MLFQ it waits 1.2 ms on average, because by then the batch jobs have sunk below it, and it gets 8.9%.

The rules need two refinements. The first version of the demotion rule reset a job's allotment whenever it gave up the CPU for I/O. A program that does a tiny I/O just before its allotment runs out then never sinks. The example's "gamer" yields after 9 ms of every 10 and takes 72.9% of the CPU from two jobs that should share it equally. Counting all the CPU a job uses at a level, however it's split up, demotes the gamer like anyone else, and the three jobs then get roughly equal shares. The second refinement fixes starvation. Five chatty jobs that together keep the top level busy leave a batch job at the bottom with 0.3% of the CPU and a wait of almost 3 seconds. A periodic priority boost that moves every job back to the top fixes that: with a boost every 100 ms, the batch job gets 10% and never waits more than 90 ms. The boost also helps a job whose behaviour changes, such as a compiler that turns into an editor.

Variants of MLFQ schedule Windows threads and macOS threads, and FreeBSD's ULE scheduler scores each thread's interactivity from how much it sleeps. Linux took a different path, fair queuing, which chapter 6 covers.

Common traps
  • Optimising the average when users feel the tail. Measure the 99th percentile of response time.
  • Lengthening time slices for throughput on a machine that also serves interactive requests.
  • Busy-waiting for something another thread will do, burning the slice that thread needs.
  • Using sleep(0) or sched_yield as synchronisation. They promise nothing about who runs next.
  • Measuring latency on an idle machine and expecting the same numbers under load.

Chapter 6

Fair shares and many cores

9 min read3 exercises

A multi-level feedback queue guesses which jobs deserve priority. A fair-share scheduler instead promises each thread a defined share of the processor, in proportion to a weight. This chapter builds weighted fair queueing the way Linux does it, with a virtual clock per thread that runs faster or slower according to its weight. It compares that with random lottery scheduling and deterministic stride scheduling. It then turns to machines with many cores, where the scheduler also decides where each thread runs, and to the priority inversion that once kept resetting a spacecraft on Mars.

Proportional share

In proportional-share scheduling each thread holds a weight, and when threads compete each gets CPU time in proportion to its weight. Carl Waldspurger and William Weihl's lottery scheduling (1994) did it with tickets and chance: at every time slice, draw a ticket at random, and the holder runs. A thread with 75 of 100 tickets wins 75% of the draws in the long run. Lottery is simple, needs no global state, and handles new threads instantly, but it's only fair on average. Over short windows the shares wander, which is exactly when a user notices. Waldspurger's stride scheduling (1995) removes the randomness. Each thread has a "pass" value that grows by a stride, inversely proportional to its tickets, every time it runs, and the scheduler always picks the thread with the smallest pass.

Virtual runtime

Linux's Completely Fair Scheduler, CFS, written by Ingo Molnar and in use from 2007, applies the stride idea to time itself. Each thread has a virtual runtime: a clock that advances while the thread runs, at a rate inversely proportional to its weight. The scheduler always runs the thread with the smallest virtual runtime, kept in a red-black tree so the smallest is quick to find. A thread at the default weight's virtual clock runs at real speed; a thread with a third of the weight has a clock that runs three times as fast, so it reaches the front of the queue a third as often.

Weights come from a thread's nice value, from −20 to 19, through a fixed table in the kernel: nice 0 is 1024, and each step changes the weight by about a quarter, so that each step moves about 10% of the CPU between two competing threads. One detail matters for interactive programs. A thread that has been asleep has a small virtual runtime, and if it kept it, it would monopolise the processor on waking until it caught up. So on waking, its virtual runtime is moved up to just below the smallest of the running threads, a few milliseconds of credit and no more. In Linux 6.6, in 2023, Peter Zijlstra replaced CFS's selection rule with EEVDF, earliest eligible virtual deadline first. It keeps the virtual clocks but also gives each thread a deadline based on how far it's behind and how long a slice it asks for, so latency-sensitive threads can request short slices and run sooner without getting more CPU in total.

The simulated shares match the weights to the decimal: 43.0%, 43.0% and 14.1% for nice 0, 0 and 5, and 99.5% to 0.5% for nice −5 against nice 19. The task that slept for a second got half the CPU once it woke, not a second of catch-up. The lottery's windows of 20 slices gave A anywhere from 55% to 80% of a share that should be 75%; stride gave exactly 75% every time.

Many cores

With several cores, the scheduler also decides where each thread runs. A single shared run queue would be fair but slow, because every core would contend for its lock, so kernels keep a run queue per core and balance them: periodically, and whenever a core goes idle and steals work from a busy one. Balancing fights with cache affinity. A thread that moves to another core leaves its warm caches behind, and on machines with several memory controllers, NUMA machines, it may end up far from its memory. The example's five equal jobs on four cores show what happens without balancing: the two jobs that share a core get 50% each while the other three get a whole core, and balancing gives all five 80%. Programs can restrict where a thread may run with sched_setaffinity or taskset, which helps for a latency-critical thread on a dedicated core and hurts when it overrides a balancer that knew better.

Priorities, real time and inversion

Above the fair classes, Linux has real-time classes. A SCHED_FIFO thread runs until it blocks or a higher-priority real-time thread wakes, and always ahead of every normal thread; SCHED_RR adds time slices among equals, and SCHED_DEADLINE schedules by declared runtimes and deadlines. A real-time thread stuck in a loop could freeze the machine, so by default Linux reserves 5% of each second for normal threads.

Strict priorities have a famous failure, priority inversion. In July 1997 the Mars Pathfinder lander began resetting itself every few days. A low-priority task held a mutex that a high-priority bus task needed. Medium-priority tasks, which needed neither, kept preempting the low-priority one, so it never released the mutex, and the high-priority task missed its deadline and a watchdog reset the system. The fix was priority inheritance: while a thread holds a lock that a higher-priority thread is waiting for, it runs at the waiter's priority. The engineers turned on the option, already in the operating system, VxWorks, by patching the software from Earth.

Containers apply the same ideas to groups of threads. A cgroup's cpu.weight divides CPU between groups in proportion, exactly like nice values between threads, and cpu.max sets a hard quota (chapter 20). In Kubernetes, a container's CPU request becomes its weight and its CPU limit becomes its quota.

Common traps
  • Expecting nice to slow a job on an idle machine. Weights only matter when threads compete.
  • Pinning threads to cores by hand and leaving some cores overloaded while others idle.
  • Giving real-time priority to code that can spin, which can starve the rest of the machine.
  • Sharing a mutex between high- and low-priority threads without priority inheritance.
  • Reading Linux's load average as CPU use. It also counts threads blocked on disk I/O.

Exercise 6.3Inversion, step by step

M can no longer preempt it, L finishes its critical section and releases the mutex, drops back to low priority, and H runs at once. POSIX mutexes offer this as the PTHREAD_PRIO_INHERIT protocol, and Linux's real-time mutexes use it.

Chapter 7

Race conditions and atomicity

9 min read3 exercises

Two threads that read and write the same memory without coordinating produce results that depend on timing. The trouble isn't that such code fails often. It fails rarely, differently each time, and almost never while you watch. This chapter makes races deterministic by trying every possible interleaving of tiny programs. It shows why count += 1 loses an update in 18 of 20 orders, and how checking a balance before debiting it lets two withdrawals overdraw an account. It then covers the atomic instructions that fix these races, and the hardware memory models that make plain variables unsafe for coordination.

A race in three instructions

count += 1 looks like one operation, but the processor does it in three: load count into a register, add one, store the register back. Each thread has its own registers, so if two threads both load before either stores, both store the same value and one increment is lost. Code that touches shared data and must not be interleaved with another thread's is a critical section, and a race condition is a bug whose outcome depends on how threads happen to interleave. When two threads access the same memory, at least one of them writes, and nothing orders the accesses, the program has a data race. In C and C++ that is undefined behaviour, so the compiler may assume it never happens and the program may do anything.

Every order at once

Running a racy program a thousand times proves little, because the bad interleavings are rare. The example instead treats each thread as a list of steps and tries every order in which the steps could run. Two threads of three steps each can interleave in 20 ways, and only the 2 that run one thread entirely before the other give the right answer. With two increments per thread there are 924 orders, and the count ends at 4 in only 6 of them. An atomic fetch-and-add, one indivisible instruction, gives 4 in every order. The last part of the example checks a balance before debiting it, and two withdrawals of 80 from 100 leave the account at −60 in 4 of the 6 orders.

In a real program the bad orders are rare because the window is tiny: a few nanoseconds between a load and a store, against time slices of milliseconds. A race can survive every test and still fire in production, under load, on more cores, or after an unrelated change shifts the timing. That's why races are found with tools, not luck. ThreadSanitizer, enabled with -fsanitize=thread in Clang and GCC, and Go's -race flag instrument memory accesses and report any two that aren't ordered, even when the run happened to produce the right answer. Model checkers go further and explore interleavings systematically, as the example does. Rust's loom crate does this for real concurrent code, and TLA+ does it for designs.

Check, then act

The withdrawal bug has a name, time of check to time of use (TOCTOU), and it's everywhere. "If the file doesn't exist, create it" races with another process creating it in between; open with O_CREAT | O_EXCL does both atomically and fails if the file exists. "If the user may access this path, open it" races with an attacker replacing the path with a symbolic link; open first and check the descriptor you got. In databases, reading a balance in one statement and updating it in another races with every other client; UPDATE accounts SET balance = balance - 80 WHERE id = 7 AND balance >= 80 makes the check and the change a single atomic step, and the number of rows it changed says whether it succeeded.

Atomic instructions

Processors provide instructions that read, modify and write a memory location as one indivisible step, even with many cores. Fetch-and-add (LOCK XADD on x86) increments and returns the old value. Compare-and-swap (LOCK CMPXCHG on x86, CAS on recent ARM) writes a new value only if the location still holds an expected one, and reports whether it did. With compare-and-swap you can make any update atomic: read the value, compute the new one, and retry if someone else changed it in between. Languages expose these as atomic types: std::atomic in C++, AtomicInteger in Java, sync/atomic in Go, AtomicU64 in Rust. Uncontended, an atomic operation costs a few tens of cycles. When many cores hammer the same location, its cache line bounces between them and each operation can take a hundred nanoseconds or more.

Memory models

There's a second reason plain variables can't coordinate threads: neither the compiler nor the processor promises to perform memory operations in program order. A compiler may keep a variable in a register and never reload it, or move a store past a load. Processors reorder too. On x86 a store can wait in a store buffer while later loads go ahead, so another core sees the store late. ARM, used in Apple silicon and AWS Graviton, allows much more reordering. The memory model of a language or processor says which reorderings are allowed, and atomic operations carry ordering guarantees, such as acquire, release or sequentially consistent, that rule them out where it matters. Chapter 8's model checker shows the consequence: Peterson's algorithm, provably correct with plain loads and stores, fails once store buffers are modelled, and a fence fixes it.

Python is not exempt. In the standard build, the GIL means only one thread runs Python code at a time, but count += 1 is several bytecodes and a thread switch can fall between them, so updates can still be lost. In the free-threaded build of Python 3.14 the threads really run in parallel. The rule is the same in every language: protect shared data with a lock, or use an operation documented to be atomic.

Common traps
  • Testing for races by running the program a few times. Use ThreadSanitizer or a race detector.
  • A plain boolean flag between threads. The compiler may never reload it, and the hardware may reorder it.
  • Two atomic steps treated as one, such as if key not in cache: cache[key] = value.
  • Code tested only on x86 that breaks on ARM's weaker ordering.
  • Hand-written lock-free code without a model checker or a proof.

Exercise 7.1Counting orders

Why do two threads of 3 steps have exactly 20 interleavings, and two threads of 6 steps 924? Why are only 2 of the 20 correct for count += 1?

Show solution

An interleaving is fixed by choosing which of the 6 positions belong to thread 1, since each thread's own steps stay in order. That's C(6, 3) = 20. In general, threads of m and n steps interleave in (m + n)! / (m! n!) ways, so two threads of 6 steps have C(12, 6) = 924, and the count explodes for more threads or longer code, which is why model checkers need clever pruning. For the increment, the result is right only if one thread's store happens before the other's load. If the second load comes before the first store, both threads computed from the same old value. That holds only when one thread runs all three steps before the other starts, which is 2 of the 20 orders.

Exercise 7.2Three fixes for the withdrawal

Fix the check-then-act withdrawal three ways: with a lock, with compare-and-swap, and in a SQL database. Say what each one costs.

Show solution

With compare-and-swap, loop: read the balance b; if b < 80, fail; otherwise attempt CAS(balance, b, b − 80), and if another thread changed the balance first, the CAS fails and you retry with the new value. No thread ever blocks, but under heavy contention the retries waste work. In SQL, the single statement UPDATE accounts SET balance = balance - 80 WHERE id = ? AND balance >= 80 lets the database do the check and the change atomically; a row count of 0 means insufficient funds. That's usually the best choice, because the database already serialises updates to the row.

Exercise 7.3The flag that doesn't work

In C, thread A runs data = compute(); ready = 1; and thread B runs while (!ready) {} use(data);, with both variables plain globals. Name two ways this can fail, and give a correct version.

Show solution

First, the compiler sees no write to ready inside B's loop, so it may load it once and spin forever. Second, the stores in A or the loads in B may be reordered, by the compiler or by an ARM processor, so B can see ready == 1 and still read the old data. It's also a data race and therefore undefined behaviour. A correct version makes ready an atomic: A does atomic_store_explicit(&ready, 1, memory_order_release) after writing data, and B loops on atomic_load_explicit(&ready, memory_order_acquire). Release and acquire guarantee that everything A wrote before the store is visible to B after the load. Better still, don't spin: use a condition variable (chapter 9), or threading.Event in Python.

Chapter 8

Locks

12 min read3 exercises

A lock lets only one thread at a time run a critical section. Building one correctly is harder than it looks. The obvious version doesn't work. A correct version using only ordinary loads and stores exists, and fails on real processors. The version everyone uses rests on an atomic instruction, plus help from the kernel for waiting. This chapter model-checks four lock algorithms, checks one of them again as real processors run it, explains why they need fences, and then covers spinning against sleeping, the futex, and how to stop a lock from becoming the bottleneck.

What a lock must do

A lock has two operations, acquire and release, and three requirements. Mutual exclusion: at most one thread is between acquire and release at any time. Progress: if the lock is free and threads want it, one of them gets it; they don't all wait forever. Bounded waiting: no thread is passed over indefinitely while others take the lock again and again. Then there's performance, which matters because locks sit on the hottest paths in a program. In code, the critical section should always be written so that the release can't be skipped: with lock: in Python, a scoped guard in C++ and Rust, defer mu.Unlock() in Go.

Building one from loads and stores

The obvious lock checks a variable and, if it's free, sets it. The example's model checker finds the flaw in four steps: both threads see the lock free before either sets it, and both walk in. Giving each thread its own flag, raised before waiting for the other's to drop, keeps them out of each other's way and introduces a new failure: if both raise their flags at once, each waits for the other forever. That's a deadlock. Gary Peterson's algorithm of 1981 adds one shared variable, turn. Each thread raises its flag, then gives the turn to the other, then waits while the other's flag is up and it's the other's turn. If both arrive together, whoever wrote turn last waits. The checker confirms it in all 26 reachable states: never two threads in the critical section, and never a state where neither can move.

Real hardware breaks it

Peterson's proof assumes that a store is visible to the other thread as soon as it happens. On a real multicore processor it isn't. Each core puts its stores in a store buffer and carries on, and the stores reach the shared cache, and so the other core, a little later (chapter 7). The example models that, and the checker finds a run in six steps with no store reaching memory at all. Each thread raises its flag and gives the turn away into its own buffer, then reads the other's flag from memory, sees 0, and enters.

The fix is a fence, an instruction that makes a core wait until its buffered stores are visible before it performs later loads: MFENCE on x86, DMB on ARM. With a fence between giving the turn away and reading the other's flag, the checker again finds no bad state. In practice nobody writes Peterson's algorithm; it handles only two threads, and the atomic instructions of chapter 7 make locks much simpler. The lesson is the method: reasoning about concurrent code means reasoning about every interleaving and about the memory model, and a model checker is the only reliable way to do either for anything beyond a few lines.

Test-and-set and spinning

An atomic test-and-set writes 1 to the lock and returns the old value in one indivisible step, so exactly one thread sees the old 0 and gets the lock. The checker confirms it in 5 states. A lock that loops on test-and-set until it succeeds is a spinlock. Two refinements are standard. Test and test-and-set spins on an ordinary read and attempts the atomic only when the lock looks free, because every atomic write steals the cache line from the other cores, while plain reads let every waiting core spin on its own cached copy. And a ticket lock gives each arriving thread a number from a fetch-and-add and serves them in order, which guarantees bounded waiting. Spinlocks make sense when critical sections are a few hundred nanoseconds and the lock holder can't be descheduled, which is why kernels use them with preemption disabled. In user space, the holder can be preempted at any moment, and every spinner then burns its entire time slice waiting for a thread that isn't running.

Sleeping instead of spinning: the futex

A lock that puts waiters to sleep needs the kernel, but going to the kernel for every acquire would cost a system call each time (chapter 2). Linux's futex, a "fast user-space mutex", added in 2002, avoids that. The lock is an ordinary integer in the process's memory. An uncontended acquire or release is a single atomic instruction in user space, about 20 ns, with no system call. Only when a thread finds the lock taken does it call futex(FUTEX_WAIT) to sleep until the value changes, and the releasing thread calls futex(FUTEX_WAKE) only if someone is waiting. glibc's pthread_mutex, Go's sync.Mutex, Rust's standard mutex and Python's threading.Lock all work this way on Linux; macOS has an equivalent primitive in os_unfair_lock. Most of them are adaptive: they spin briefly in case the holder is about to release, then sleep.

Locks at scale

A lock turns its critical section into serial code, and Amdahl's law (chapter 15 of The Engineer's Mill) then caps the speed-up. If 10% of the work happens under one lock, no number of cores makes the program more than 10 times faster, and contention makes it worse: the lock's cache line bounces between cores and waiters pile up in the kernel. The remedies are to hold locks for less time, never across I/O or calls into unknown code; to split one lock into many, such as one per hash bucket or per account, which is lock striping; to give each thread its own data and combine it only when needed, as per-thread counters do; and to choose structures built for concurrent reading, such as read-copy-update in the Linux kernel. Reader-writer locks look like an easy win and often aren't, because every reader still writes to the lock's shared counter. Finer locking also creates more ways to deadlock, the subject of chapter 10.

Common traps
  • A release skipped on an error path. Use with, a scoped guard or defer.
  • Holding a lock during I/O or a callback, which turns a nanosecond section into a millisecond one.
  • Spinlocks in user-space code, where the holder can be preempted.
  • Assuming a reader-writer lock is faster without measuring it.
  • Double-checked locking with plain variables, which the memory model doesn't make safe.

Exercise 8.1What the turn variable buys

Explain the two-flags deadlock the checker found, and how Peterson's turn variable prevents it without letting both threads in.

Show solution

With flags alone, each thread raises its own flag and then waits for the other's to drop. If both raise their flags before either checks, each sees the other's flag up and waits, and neither will ever lower its flag, because it's waiting: a deadlock. Peterson's algorithm lets a thread in if the other's flag is down or it's this thread's turn, and each thread gives the turn away before waiting. If both arrive together, both flags are up, and turn holds whichever value was written last. The thread that wrote last gave priority to the other, so it waits and the other enters. The value of turn breaks the tie exactly once, so one thread always goes ahead, which is progress, and the two can never both pass the wait at once, which is mutual exclusion.

Exercise 8.2Spin or sleep?

A critical section takes 50 ns. Sleeping on a futex and being woken costs about 5 µs in total. When should a waiting thread spin, and when should it sleep? What changes if the lock's holder can be preempted?

Show solution

If the expected wait is shorter than the cost of sleeping, spinning wins. With 50 ns sections a waiter is usually let in within a few hundred nanoseconds, so a short spin is far cheaper than 5 µs of sleeping and waking. But if the holder is preempted in the middle of its section, it won't run again for a whole time slice, milliseconds, and a spinner wastes all of that. That's why user-space mutexes are adaptive: spin for roughly the cost of a sleep, a few microseconds, and then sleep. The worst case is then about twice the optimal cost, whatever the holder does.

Exercise 8.3The hot counter

A service has 32 threads that increment one shared statistics counter, protected by a mutex, millions of times a second. Adding cores makes it slower. Why, and what are two better designs?

Show solution

Every increment needs the same lock and writes the same cache line, so the increments run one at a time, and each moves the line from one core's cache to another's, which takes far longer than the increment itself. More cores mean more contention, so throughput falls. Replacing the mutex with an atomic fetch-and-add helps but keeps the bouncing cache line. Better: give each thread its own counter, padded to a separate cache line so neighbours don't share one (false sharing, from chapter 11 of The Engineer's Mill), and add them up only when someone reads the statistic. Or have each thread count locally and add its total to the shared counter every thousand events. Both make the hot path free of sharing, at the cost of a read that's slightly stale or slightly slower.

Chapter 9

Condition variables and semaphores

10 min read3 exercises

A lock stops threads interfering with each other, but it can't make a thread wait until something becomes true: until a queue has an item, a buffer has room, or a count reaches zero. Condition variables and semaphores do that. This chapter model-checks the bounded buffer, the classic producer-and-consumer problem. The checker finds both classic bugs, an if where a while belongs and one condition variable where two are needed, before the correct version runs with real threads. It ends with semaphores and the higher-level tools built on both.

Waiting for a condition

A consumer that finds a queue empty has to wait. Spinning on the queue wastes a core; sleeping for 10 ms and checking again adds up to 10 ms of delay and still wastes wake-ups. A condition variable lets a thread sleep until another thread says the state may have changed. It's always used with a lock and a condition on shared state. A thread holding the lock checks the condition; if it's false, it calls wait, which atomically releases the lock and puts the thread to sleep, and reacquires the lock before returning. Another thread that changes the state, under the same lock, calls signal (notify in Python and Java) to wake one waiter, or broadcast (notify_all) to wake them all.

The atomic release-and-sleep is the whole point. If a thread checked the condition, released the lock and then went to sleep in three separate steps, another thread could change the state and signal in between, the signal would find no one waiting and be lost, and the first thread would sleep forever (exercise 9.1).

Mesa semantics, and why the check goes in a loop

When a waiting thread is signalled, it doesn't run immediately. It becomes ready, and it must win the lock back like any other thread. In between, another thread can take the lock and change the state again. This is called Mesa semantics, after the language in which Butler Lampson and David Redell described it in 1980, and it's what POSIX threads, Java, Python and Go all provide. The alternative, Hoare semantics, hands the lock straight to the woken thread, which is easier to reason about and slower to implement, and almost no real system uses it. Under Mesa semantics a signal is only a hint that the condition may now be true. POSIX even allows spurious wake-ups, from wait returning with no signal at all. So the condition must be checked again after every wake-up, in a loop: while not condition: cv.wait().

Checked, then run

The example models one producer that puts two items and two consumers that take one each, through a buffer that holds one item, with a mutex and condition variables that follow Mesa semantics. With if and one condition variable, the checker finds the trace in the figure in 14 steps. With while and one condition variable it finds a different bug: a deadlock with every thread asleep. With while and two condition variables it checks all 139 reachable states and finds nothing. The correct version then runs for real with Python's threading.Condition, 30,000 items through a four-slot buffer to three consumers, and every item arrives exactly once.

One condition variable or two

The deadlock is subtler than the if bug. Producers wait for space and consumers wait for items, and with only one condition variable they all wait on the same one. In the trace, both consumers wait, the producer puts an item, signals, and then waits itself because the buffer is full. Consumer 1 takes the item and signals, intending to wake the producer, but the signal wakes consumer 2 instead, which finds the buffer empty and goes back to sleep. Now all three are asleep and nobody will ever signal. A signal must wake a thread that can act on it, so threads waiting for different conditions need different condition variables: one for "there's space", one for "there's an item". notify_all also fixes it, because it wakes everyone, but it does so at the cost of waking every waiter for every change, the thundering herd.

Semaphores

Edsger Dijkstra introduced the semaphore in 1965: an integer with two atomic operations, P (wait, or down), which decrements it and blocks while it would go negative, and V (signal, or up), which increments it and wakes a waiter. A semaphore that starts at 1 is a lock. One that starts at n admits n threads at a time, which is a natural limit on a pool of resources, such as ten database connections or four concurrent downloads. Unlike a condition variable, a semaphore remembers: a V with no one waiting isn't lost but raises the count for the next P. A bounded buffer of n slots needs three semaphores: slots starting at n, items starting at 0, and a mutex starting at 1 for the buffer itself. The order of the waits matters, as exercise 9.2 shows.

In practice, write condition-variable code rarely, and reach for the tools built from these primitives: blocking queues such as Python's queue.Queue and Java's BlockingQueue; channels (chapter 11); barriers, which make a group of threads wait until all of them arrive, as chapter 10's example does; countdown latches; and futures. The thread pool in this stage's deliverable is a blocking queue of tasks and a fixed set of threads taking from it.

Common traps
  • if instead of while around wait.
  • Changing the state or signalling without the lock, which can lose a wake-up.
  • One condition variable for two conditions with notify, which can wake the wrong thread.
  • notify_all everywhere, waking every waiter for every change.
  • Taking the buffer's mutex before waiting on a semaphore, which deadlocks.
  • A hand-written queue where the standard library already has a correct one.

Thread A runs if not ready: cv.wait() without holding the lock while it checks ready, and thread B runs ready = True; cv.notify(). Describe an interleaving in which A sleeps forever, and explain how holding the lock prevents it.

A checks ready and finds it false. Before A has started waiting, B sets ready and calls notify, which finds no waiter and does nothing. Exercise 9.2A bounded buffer from semaphores

Write the producer and consumer for an n-slot buffer using semaphores slots (n), items (0) and mutex (1). Then show how putting the producer's P(mutex) before P(slots) can deadlock.

Producer: P(slots); P(mutex); put(x); V(mutex); V(items). Consumer: P(items); P(mutex); x = take(); V(mutex); V(slots). A producer first reserves a free slot, possibly waiting, then takes the mutex only for the moment it touches the buffer. Chapter 10

Deadlock, livelock and starvation

11 min read3 exercises

A deadlock is a set of threads, each waiting for something another one holds. Nothing moves, nothing fails, no error is logged: the program simply stops. This chapter model-checks the dining philosophers and finds their deadlock in a few dozen states. It sets out the four conditions every deadlock needs, with the fix that breaks each, detects a deadlock after the fact from the graph of who waits for whom, and reproduces one with real locks. It ends with livelock and starvation, the two ways a system can stay busy and still make no progress.

The dining philosophers

Dijkstra's puzzle from 1965: philosophers sit at a round table with one fork between each pair, and each needs both neighbouring forks to eat. If every philosopher picks up the left fork and then the right, there's a moment when all of them hold a left fork and wait for a right one that their neighbour is holding, and they wait forever. The example's checker explores every order in which the philosophers can act and finds that state after 14 states with three philosophers and 82 with five. Then it makes one change: every philosopher picks up the lower-numbered of their two forks first. Now the last philosopher, whose forks are numbered n − 1 and 0, reaches for fork 0 first, the circle is broken, and the checker finds no deadlock in any reachable state.

The four conditions

Edward Coffman and his colleagues showed in 1971 that a deadlock needs four conditions at once. Mutual exclusion: a resource can be held by only one thread. Hold and wait: a thread holds one resource while waiting for another. No preemption: a resource can't be taken away from the thread holding it. Circular wait: a cycle of threads, each waiting for a resource the next one holds. Remove any one and deadlock is impossible.

In practice, circular wait is the condition to break. Give every lock a place in one global order and always acquire locks in that order, as the philosophers did with fork numbers. When the locks belong to objects, order them by something stable such as an ID: a transfer between two accounts locks the account with the lower ID first, whichever direction the money flows. Hold and wait can be broken by acquiring every lock a task needs in one step, which is hard when the set isn't known in advance. No preemption can be broken by trying for a lock with a timeout, or with a non-blocking try-lock, and releasing everything held on failure before trying again. Dijkstra's banker's algorithm avoids deadlock by refusing any request that could lead to one, but it needs to know every thread's maximum demand in advance, so general-purpose systems don't use it.

Finding a deadlock

The alternative to preventing deadlocks is detecting them. Record which thread holds each lock and which lock each thread waits for, and look for a cycle, as the example's find_cycle does. Databases work this way, because transactions lock rows in whatever order the queries touch them. PostgreSQL waits a second, checks for a cycle, and aborts one transaction with "deadlock detected" so the others can continue. Runtimes help with diagnosis too: jstack reports a Java-level deadlock in a thread dump, Go's runtime stops with "all goroutines are asleep - deadlock!", and py-spy dump shows every Python thread's stack. The Linux kernel goes further with lockdep, which records the order in which locks are taken while the kernel runs and reports an order that could deadlock the first time it occurs, before any deadlock has happened.

The example also builds a real deadlock with two Python locks taken in opposite orders. A barrier makes sure each thread holds its first lock before either asks for its second, so the bad timing is certain instead of rare. Each thread asks for its second lock with a timeout and gives up after half a second, a simple form of detection. With both threads taking the locks in the same order, both finish.

Livelock and starvation

In a livelock the threads aren't blocked. They keep reacting to each other, and nothing gets done. Two threads that each take one lock, find the other taken, politely release theirs and retry at once can repeat that dance indefinitely if they stay in step, which the example's lockstep simulation does for 50 rounds. The fix is to break the symmetry with randomness: on a collision, each waits a random time before retrying, and doubles the range after each further collision. That's exponential backoff with jitter, the same rule Ethernet used for colliding transmissions and that well-behaved clients use for retrying failed requests. With it, one thread wins in the second round.

In starvation, the system makes progress but one thread never does, because the rules always favour someone else: readers that keep a reader-writer lock busy so a writer never gets in, an unfair lock that the same thread keeps winning, a low-priority job behind an endless stream of high-priority ones. The fixes are fairness and aging, such as serving waiters in order or boosting a waiter's priority as it waits, as the multi-level feedback queue's boost did in chapter 5.

Common traps
  • Lock order that depends on the arguments, such as transfer(a, b) locking a first.
  • Calling unknown code while holding a lock: callbacks, logging handlers, plugins.
  • Waiting with no timeout on locks and, especially, on network calls.
  • Retrying at once, or at fixed intervals, so colliding clients collide again. Add jitter.
  • Deadlocks across services, where each waits on the other's request; no local detector sees them.
Exercises
Exercise 10.1The transfer deadlock

transfer(a, b, amount) locks account a, then account b, and moves the money. Show how two concurrent transfers deadlock, and write a version that can't.

Show solution

transfer(x, y) and transfer(y, x) run at once: the first locks x, the second locks y, and each then waits for the lock the other holds. That's circular wait with two threads. Fix it by always locking in a global order:

def transfer(a, b, amount):
    first, second = (a, b) if a.id < b.id else (b, a)
    with first.lock, second.lock:      # lower ID first, whichever way the money moves
        a.balance -= amount
        b.balance += amount

Now both transfers try to lock the lower-ID account first, so one of them gets both locks and the other waits for it, and no cycle can form. A transfer from an account to itself would try to take the same lock twice, so either reject it or use a reentrant lock.

Exercise 10.2Which condition does it break?

For each design, say which of the four conditions it removes: one global lock around all shared state; a try-lock that releases everything and retries with backoff on failure; taking all the locks a task needs in sorted order before starting; giving each piece of data a single owner thread that other threads send requests to.

Show solution

One global lock: with only one lock there's never a second resource to wait for, so hold and wait, and with it circular wait, can't arise; the price is that nothing runs in parallel. Try-lock and back off: a thread that can't get a lock gives up the ones it has, which is preemption done voluntarily, so it breaks no preemption, at the risk of livelock without jitter. Sorted acquisition: a single global order makes circular wait impossible. A single owner per piece of data, the actor model of chapter 11, removes the locks, and mutual exclusion is guaranteed by the owner handling one request at a time. Actors can still deadlock if two of them each wait for a reply from the other, which is circular wait again at a higher level.

Exercise 10.3Why retries need jitter

A thousand clients lose their connection to a server at the same moment and all retry after exactly one second, then two, then four. What does the server see, and how does jitter change it?

Show solution

Doubling the delay isn't enough when everyone doubles in step. The server sees all thousand clients reconnect in the same instant at 1, 3 and 7 seconds, a thundering herd at each of which it may be overloaded again, so the retries keep failing together. With jitter, each client waits a random time between zero and the current delay ("full jitter"), so the thousand retries spread evenly across the whole interval: the first retry wave arrives at about a thousand per second instead of a thousand at once, and later waves spread further. The total work is the same; the peak is a small fraction of it.

Chapter 11

Event loops, actors and channels

11 min read3 exercises

Threads are one way to do many things at once. Another is to do them all on one thread that never waits. An event loop asks the kernel what's ready and runs only code that can make progress. This chapter builds an event loop from Python generators in a dozen lines, shows asyncio doing the same, and shows what happens when one coroutine blocks. It then turns to two models that avoid shared memory altogether: actors, which own their state and handle one message at a time, and channels, which connect stages that share nothing.

Concurrency without threads

A server handling ten thousand connections spends almost all its time waiting: for a request to arrive, for a database to answer, for a slow client to accept its reply. With a thread per connection, each wait holds a thread, with its stack and its share of context switches (chapter 4). An event loop handles all of them on one thread. It keeps a queue of work that's ready to run and a list of timers, asks the kernel which connections have data with a single call such as epoll_wait or kevent (chapter 18), and runs the code waiting for each. No code ever blocks; code that would wait instead registers interest and returns to the loop. nginx, Redis and Node.js are built this way.

Early event-driven code was written as callbacks, functions to run when an event happens, and deeply nested callbacks are hard to read and harder to debug. Promises, or futures, made them composable, and async/await made them look like ordinary sequential code: C# added it in 2012, Python in 2015, JavaScript in 2017 and Rust in 2019. An async function is a coroutine, and each await is a point where it can pause and hand control back to the loop until the thing it's waiting for is ready.

An event loop in a dozen lines

The example's loop is the idea with nothing else in the way. Each task is a Python generator. When it would wait, it yields a request to the loop, here "wake me in 0.3 seconds", and the loop keeps a heap of timers ordered by when they're due. The loop pops the earliest, advances its clock to that time, and resumes that task until it yields again. Three requests that wait 0.3, 0.1 and 0.2 seconds all start at once and finish in order of their waits, and the whole thing takes 0.3 seconds, not 0.6.

A real loop such as asyncio adds the other kind of waiting: instead of timers alone, it registers sockets with the kernel and asks which are readable or writable, then resumes the coroutines waiting on them. The example's second part runs a ticker and a worker under asyncio. When the worker waits with await asyncio.sleep, the ticker keeps ticking in between. When it calls time.sleep instead, which blocks the thread, nothing else runs until it returns.

The price: cooperation

An event loop is cooperative: a task runs until it chooses to yield, so one task that doesn't yield stops all the others. A blocking call, a slow library that does synchronous network or file I/O, or a long computation inside a coroutine freezes every connection on that loop, which is why Node.js documentation repeats "don't block the event loop". The fixes are to use asynchronous libraries throughout, and to move blocking or heavy work to a thread or process with asyncio.to_thread or run_in_executor. Async also spreads through a program: a function that awaits must itself be async, so its callers must be too. Bob Nystrom called this the problem of function colour.

In return, code between two awaits runs without interruption, so there are no data races within a single loop. But interleaving hasn't gone away; it's just confined to the await points. A check, then an await, then an act is the chapter 7 race again (exercise 11.1).

Actors

An actor is a unit of computation that owns its state outright and communicates only by messages. It has a mailbox, handles one message at a time, and may change its state, send messages and create other actors in response. Carl Hewitt proposed the model in 1973. Erlang, designed at Ericsson in 1986 for telephone switches, made it practical, and Akka brought it to the JVM. Because only the actor touches its state, no lock is needed: the example's account actor takes 40,000 deposits from four threads, one at a time, and ends with exactly 40,000. Erlang adds the other half of the idea: actors are isolated, so one that crashes takes nothing else with it, and a supervisor actor restarts it in a known state. That's how Erlang systems stay up for years.

Channels

A channel is a typed pipe between concurrent tasks. Tony Hoare described communicating sequential processes, CSP, in 1978, and Go made channels a core feature, with the advice "don't communicate by sharing memory; share memory by communicating". An unbuffered channel is a rendezvous: the sender waits until a receiver takes the value. A buffered channel is a bounded queue. Either way, a fast stage blocks when the next one falls behind, which is backpressure: the whole pipeline runs at the speed of its slowest stage, with bounded memory. The example's pipeline passes numbers through two channels with room for one item each, to a stage that squares them and on to one that keeps a running total. Go's select waits on several channels at once, and closing a channel tells its readers that no more values are coming, as the example's None does.

None of these models wins everywhere. Threads and locks suit shared in-memory structures and CPU-bound parallel work. Event loops suit many connections that mostly wait. Actors suit long-lived stateful entities that should fail independently, and channels suit pipelines. Real systems mix them: Go runs goroutines, which are threads, connected by channels; a Node.js server runs an event loop with a pool of worker threads behind it; a Python service runs asyncio with a thread pool for blocking calls.

Common traps
  • A blocking call inside async code, which stalls every task on the loop.
  • Check, then await, then act: the race is back at the await.
  • Calling a coroutine without awaiting it. It never runs, and Python only warns.
  • Unbounded queues and mailboxes, which hide a slow consumer until memory runs out.
  • Tasks started and forgotten, whose exceptions disappear. Keep a reference and await them.

That's backpressure, and the same mechanism appears throughout systems: a full pipe blocks its writer (chapter 3), TCP's flow control stops a fast sender, and a well-designed service rejects work it can't queue rather than accepting it all.

Memory

Four chapters on how an operating system shares physical memory between processes that each believe they have all of it. Page tables translate every address. Chapter 12

Virtual memory and paging

11 min read3 exercises

Every address a program uses is virtual. On every memory access the hardware translates it, through tables that only the kernel can change. Translation is what lets every process use the same addresses, keeps each process out of the others' memory, and lets the kernel share libraries, map files and hand out more memory than the machine has. This chapter splits an x86-64 address into its parts, walks the four-level page table by hand, triggers a page fault and a protection fault, and counts what the tables themselves cost.

Why translate

Translation solves several problems at once. Isolation: a process can reach only the memory its tables map, so it can't read or corrupt another's. Relocation: every program can be linked to run at the same addresses, wherever its memory physically is. Sparseness: a 64-bit address space is huge, and a process uses a few scattered regions of it, code at the bottom and stacks near the top, without paying for the gaps. Sharing: the same physical memory can appear in many processes, as a shared library's code does, or as a parent's pages do after fork (chapter 13). And overcommitment: the kernel can promise memory and supply it only when it's touched, or take it back by moving it to disk.

Early machines translated with a single base and limit per process, which was simple but required each process's memory to be one contiguous piece. Segmentation used several such pieces and suffered external fragmentation, chapter 15's problem. Paging, used by every modern system, cuts both virtual and physical memory into fixed-size pages, 4 KiB on x86, and lets any virtual page map to any physical frame. ARM processors support 4, 16 and 64 KiB pages, and Apple silicon uses 16 KiB.

Splitting an address

On x86-64, a virtual address has 48 significant bits; newer processors and kernels can enable a fifth level and 57 bits. The low 12 bits are the offset within a 4 KiB page and pass through translation unchanged. The 36 bits above them are the virtual page number, and the hardware uses them as four 9-bit indices, one per level of a tree of tables. Each table is exactly one page: 512 entries of 8 bytes. An entry holds the physical frame number of the next table, or, at the last level, of the page itself, plus permission and status bits: present, writable, accessible from user mode, no-execute, and the accessed and dirty bits that the hardware sets when the page is used or written.

Walking the tables

The kernel loads the physical address of a process's top-level table into CR3 (on ARM, TTBR0) when it switches to that process, which is how a context switch changes address spaces (chapter 4). The memory management unit then walks the tree on every access, four dependent memory reads before the program's own read can even start. That would make every load five times slower, so processors cache recent translations in the TLB, the subject of chapter 13. The example builds the tree as nested dictionaries that exist only where something is mapped, maps three pages with different permissions, and translates five accesses.

Faults

When the walk finds an entry that isn't present, the processor raises a page fault and the kernel takes over, with the faulting address in a register. The kernel then decides what the fault means. If the address belongs to a region the process is entitled to, such as heap memory it allocated but never touched, a file it mapped, or a page that was moved out to disk, the kernel supplies the page, fixes the entry and resumes the instruction, and the program never knows. If the address belongs to nothing, the kernel sends SIGSEGV, the segmentation fault. Page zero is left unmapped on purpose, so a null pointer is caught at once: the example's read of address 0 stops after three table reads, because no level 1 table exists for that region.

A protection fault is an access the entry forbids: a write to a read-only page, user-mode access to a kernel page, or an instruction fetch from a page marked no-execute. The example's write to its code page is one. Sometimes the kernel treats it as legitimate, which is how copy-on-write works (chapter 13), and otherwise the result is again SIGSEGV. Marking pages writable or executable but never both, a policy called W^X, is one of the defences against injected code from chapter 18 of The Engineer's Mill.

What the tables cost

A single flat table covering 48 bits would need 236 entries of 8 bytes, 512 GiB for every process, which is why the table is a tree. The example's process maps three pages and needs only 8 tables, 32 KiB in all, because a table exists only where something below it is mapped. A densely mapped gigabyte needs 516 tables, 2 MiB, which is 0.2% overhead. Larger pages shrink this further: a 2 MiB page is mapped by a level 2 entry directly, skipping the last level, and a 1 GiB page by a level 3 entry. Chapter 13 shows the bigger benefit, for the TLB.

Every process's address space has two halves. The lower half holds the program; the upper half, which user mode can't access, maps the kernel, so that a system call or interrupt doesn't need to switch tables. Since the Meltdown attack of 2018, kernels on affected processors keep most of that upper half unmapped while user code runs, a technique called kernel page-table isolation, which is one reason system calls got slower. On Linux, /proc/<pid>/maps lists every region of a process's lower half, and /proc/<pid>/smaps shows how much of each is actually in memory.

Common traps
  • Reading virtual size as memory use. Look at resident size (RSS), or proportional size (PSS) for shared pages.
  • Hard-coding 4096 as the page size. Apple silicon uses 16 KiB and some ARM servers 64 KiB; ask sysconf.
  • Trusting a successful allocation, when memory is only supplied on first touch and the out-of-memory killer may strike later.
  • Using memory after freeing it, which works until the page is reused or unmapped.
  • Turning on huge pages everywhere. Transparent huge pages can cause latency spikes, and some databases ask you to disable them.

Exercise 12.3Why not bigger pages?

Bigger pages mean smaller page tables and fewer translations to cache. Give three costs that keep the base page size at 4 or 16 KiB.

Third, paging in and out moves whole pages, so faults on sparse data read far more than was needed. That's why systems keep a small base page and offer large pages for regions that benefit, such as database buffer pools and big arrays, while Apple's 16 KiB is a middle point chosen for its own hardware.

Chapter 13

TLBs and page faults

10 min read3 exercises

A page walk on every access would make memory several times slower. Processors therefore cache recent translations in the translation lookaside buffer, and the kernel fills memory lazily, by handling page faults the first time each page is touched. This chapter simulates a TLB on four access patterns, with ordinary and huge pages. It shows copy-on-write reducing the copy that fork makes to almost nothing, and works out what a fault rate does to the average cost of a memory access.

The TLB

The translation lookaside buffer is a small cache of recent translations, each one a virtual page number, its physical frame and its permission bits. It's looked up on every memory access, in parallel with the first-level cache, and a hit costs about a cycle. Modern cores have two levels: a first-level data TLB of around 64 entries and a second-level TLB of 1,500 to 2,000 entries shared by code and data. A miss means a page walk. The processor does it in hardware on x86 and ARM, helped by caches of the upper levels of the tree, and it costs from a dozen cycles, when the tables are in cache, to hundreds, when they're not. How much memory the TLB can cover at once, its reach, is the number of entries times the page size.

Four access patterns

The example models a 1,536-entry TLB with least-recently-used replacement and runs 300,000 accesses in four patterns. Reading 8-byte values in order misses once per 512 accesses, 0.2%, because each 4 KiB page holds 512 of them. Touching one value every 4 KiB misses every time. Random reads in 64 MiB miss 91% of the time, because 64 MiB is 16,384 pages and the TLB holds 1,536; in 1 GiB, 99%. With 2 MiB pages every pattern misses at most 0.2% of the time, because the same TLB now reaches 3 GiB instead of 6 MiB.

Programs that jump around large amounts of memory, such as hash tables, graph algorithms, databases and garbage-collected heaps, can spend a large share of their time on TLB misses, and huge pages often speed them up by several to tens of percent. Linux offers them explicitly, through hugetlbfs or mmap with MAP_HUGETLB, and transparently, by promoting suitable regions automatically. Transparent huge pages have a cost of their own: assembling a 2 MiB physical region can require compacting memory at awkward moments, so latency-sensitive services such as Redis recommend turning them off.

The TLB across switches

TLB entries belong to one address space. When the kernel switches to another process, entries for the old one must not be used, so older processors flushed the whole TLB on every switch, and the new process started with every access missing. Tagging each entry with an address-space ID, called PCID on x86 and ASID on ARM, lets entries from several processes coexist and survive switches. The opposite problem arises when a mapping changes. If one thread unmaps memory, every core that might have cached the translation must drop it, so the kernel interrupts those cores with a TLB shootdown. Multithreaded programs that map and unmap memory constantly, as some allocators do, can spend real time on these.

Demand paging

malloc for a large block, and mmap of anonymous memory, only reserve virtual addresses. No physical memory is assigned until the program first touches each page. That first touch faults, and the kernel finds a free frame, zeroes it, maps it and resumes: a minor fault, costing around a microsecond. A file mapped with mmap works the same way. If the file's page is already in memory, in the kernel's page cache, the fault just maps it, another minor fault. If it isn't, the kernel reads it from storage, a major fault, which costs a disk access. This is why a process's resident size grows as it runs, why a freshly started program is slower than a warm one, and why /usr/bin/time -v and perf stat -e page-faults report fault counts.

Copy-on-write

fork would be ruinously slow if it copied a large process's memory, so it doesn't. It copies only the page tables, and marks every page in both parent and child read-only and shared. As long as both only read, they share the same physical pages. When either one writes to a page, the protection fault goes to the kernel, which sees a copy-on-write page, copies just that one, maps the copy writable for the writer, and resumes. In the example, a child that calls exec straight away copies none of a 100 MiB parent's 25,600 pages, and one that writes to 1% of them copies 256. Redis takes its snapshots this way: it forks, and the child writes the frozen view of memory to disk while the parent keeps serving. The memory cost depends on how many pages the parent writes during the snapshot (exercise 13.2).

What faults cost

The example's last table turns fault rates into an average memory access time, assuming memory takes 100 ns. One fault per million accesses costs almost nothing. One per ten thousand costs 10% when the faults are served from an SSD at 100 µs, and makes memory six times slower when they're served from a disk at 5 ms. One per thousand, from disk, makes it 51 times slower. A machine in that state is barely running, which is the subject of chapter 14.

Common traps
  • Random access over gigabytes with 4 KiB pages, where TLB misses dominate.
  • Benchmarking cold and counting first-touch faults as steady-state cost, or the reverse.
  • Forking a large process that keeps writing, which can nearly double its memory.
  • Constant mmap and munmap in multithreaded code, paying for TLB shootdowns.
  • Transparent huge pages on a latency-sensitive service without measuring.

Chapter 14

Swapping and page replacement

10 min read3 exercises

When memory is full and a process needs another page, the kernel must evict one, writing it to disk first if it has changed. Which page it chooses decides whether the machine runs at memory speed or disk speed. This chapter simulates the classic policies: first in first out, least recently used, the clock algorithm that approximates it, and the optimal policy no real system can implement. It meets Belady's anomaly, in which more memory causes more faults, and the looping access pattern that defeats recency completely. It ends with thrashing, and how modern systems avoid it.

Swapping

Physical memory is a cache for the pages processes have touched. When it's full, the kernel picks a victim page. A clean page, one that matches a copy on disk such as the code of a program or a file read through the page cache, can simply be dropped and read back if needed. A dirty page, such as modified heap memory, must first be written to swap space, a partition or file reserved for it, or for file data, back to its file. The entry for the page in the process's page table is then marked not present, and the next access faults and reads it back: a major fault (chapter 13). Linux reclaims memory in the background with a kernel thread, kswapd, which starts when free memory falls below a low watermark, so that most allocations find a free page without waiting.

Choosing a victim

The ideal policy, which László Belady described in 1966, evicts the page that won't be needed for the longest time. It's optimal and impossible, since it needs to know the future, but it's the yardstick: the example's OPT computes it from the whole reference string. FIFO evicts the page that has been in memory longest, which is simple and ignores how much the page is used. LRU, least recently used, evicts the page whose last use is furthest in the past, betting that the recent past predicts the near future. Exact LRU would mean updating an ordering on every memory access, far too expensive in hardware, so kernels approximate it.

The clock algorithm is the classic approximation. The processor sets a page's accessed bit in its page-table entry whenever the page is used. The kernel arranges the frames in a circle and moves a hand around it. If the page under the hand has its bit set, the kernel clears the bit and moves on, giving the page a second chance; the first page found with its bit clear is the victim. Pages in active use keep getting their bits set and survive, while pages nobody has touched since the last sweep go. Linux uses a refinement with two lists, active and inactive, and a page must be used twice to be promoted, so a single large scan doesn't flush everything useful.

Belady's anomaly, and the loop

Belady also found something stranger. On the reference string 1 2 3 4 1 2 5 1 2 3 4 5, FIFO makes 9 faults with three frames and 10 with four: giving it more memory makes it worse. LRU and OPT can't behave this way. They're stack algorithms: the pages they'd keep with n frames are always a subset of those they'd keep with n + 1, so more memory never hurts. FIFO's choice depends on arrival order, which changes in unrelated ways when memory grows.

The second part of the example is the access pattern that defeats recency. A program loops over 5 pages with room for 4. Each page is evicted just before it's needed again, so FIFO, LRU and CLOCK fault on every one of the 100 references, while OPT faults on 28. The same pattern hit chapter 10 of The Engineer's Mill in caches, and it's common in practice: a sequential scan of a file larger than memory evicts everything else and gains nothing from it. Databases defend against it with scan-resistant buffer pools, and Linux's two-list design exists for the same reason.

Working sets

Real programs have locality. At any moment they use a small working set of pages heavily, and it drifts slowly as the program moves through its work, an idea Peter Denning formalised in 1968. The example's last workload sends 90% of its references to a working set of 20 pages out of 1,000, replacing one of them now and then. The figure plots its fault rate against memory size for all four policies.

Two things stand out. The curves have a knee near the working-set size: memory below it is nearly useless, and memory beyond it buys little, because the remaining faults are the 10% of references to random pages, which no policy can avoid. And CLOCK, with one bit per page, stays close to exact LRU, while FIFO, which ignores use altogether, needs noticeably more memory for the same fault rate.

Thrashing

When the working sets of all running processes add up to more than physical memory, every process keeps faulting on pages another process's faults just evicted. The disk becomes the bottleneck, the processor sits idle waiting for it, and almost no work gets done. This is thrashing, and chapter 13's arithmetic shows why it's so severe: a fault per thousand accesses served from a disk makes memory 51 times slower. Early systems responded by reducing the number of programs running, suspending some until the rest fit, which is the right idea. Today, servers often run with little or no swap and let the out-of-memory killer end a process rather than letting the whole machine thrash. Linux's pressure stall information, in /proc/pressure/memory, reports how much time tasks spend waiting for memory, and tools such as systemd-oomd act on it before the machine locks up. Phones mostly avoid swapping to flash storage: iOS and Android compress memory instead, ask apps to release what they can, and then terminate background apps.

Common traps
  • Treating swap as extra memory. It's a slow overflow; a working set in swap means thrashing.
  • A large sequential scan through a cache that only knows recency, evicting everything useful.
  • Sizing memory by average use rather than by the working set at peak.
  • Reading "free memory" as unused capacity. Linux fills spare memory with the page cache on purpose; look at "available".
  • Containers without memory limits, so one process's growth pushes every other into swap.

Chapter 15

Memory allocation and garbage collection

10 min read3 exercises

The kernel hands a process memory in pages. Programs want objects of every size, created and destroyed millions of times a second, and the allocator in between decides where each one goes. Its choices determine how much memory is wasted, in holes between objects and in rounding inside them. This chapter runs a free-list allocator under three placement policies, compares the rounding of a buddy allocator with that of size classes, and then turns to garbage collection: reference counting, the cycles it can't free, and the mark-and-sweep collector that can.

From pages to objects

A process gets memory from the kernel in large pieces: brk to grow the heap, and mmap for big blocks and for allocators that manage their own regions. The C library's malloc and free, or a replacement such as jemalloc, tcmalloc or mimalloc, carve those pieces into objects. The allocator must find space for each request quickly, return freed space for reuse, and keep two kinds of waste low. External fragmentation is free memory broken into holes too small for the requests that arrive. Internal fragmentation is space wasted inside allocated blocks, because a request was rounded up.

Free lists and placement

A simple allocator keeps a list of free blocks. To allocate, it finds a free block large enough, splits off what's needed and keeps the rest on the list. To free, it returns the block and coalesces it with free neighbours, so that small holes merge back into large ones. The placement policy decides which free block to use. First fit takes the first one that's large enough, which is fast. Best fit takes the smallest that fits, to keep large blocks intact. Worst fit takes the largest, on the theory that the leftover piece will be big enough to be useful.

The example runs 4,000 random allocations and frees, in sizes from 16 bytes to 2 KiB, through a 64 KiB heap with each policy. First fit and best fit fill the heap almost completely; their failures come when it's full, with a few kilobytes left in holes. Worst fit fails more than twice as often, with more than half the heap still free, because it has broken that space into 83 holes of which the largest is 1,136 bytes. It splits the large blocks first, which leaves no room for the large requests. Studies of real programs' allocation traces agree: best fit and first fit waste similar, small amounts, and worst fit does badly.

Rounding: buddies and size classes

A buddy allocator manages blocks whose sizes are powers of two. A request is rounded up to the next power, and a block is split in halves, its "buddies", until one of the right size appears; when both halves are free again they merge. Finding a buddy is a single bit operation on the address, so splitting and merging are fast, and the Linux kernel allocates physical pages this way. The cost is rounding. In the example, 10,000 requests between 17 bytes and 4 KiB, with small sizes the most common, waste 39% of the memory they're given.

User-space allocators instead use size classes: a fixed list of sizes spaced roughly a quarter apart, and a separate pool of same-sized slots for each, carved out of pages. A request goes to the smallest class that fits, so rounding waste is bounded, 9% in the example with 28 classes, and since every slot in a pool is the same size, allocating and freeing are a pop and a push on a list, with no searching and no external fragmentation within a pool. jemalloc, tcmalloc and mimalloc all work this way, add per-thread caches so that most allocations take no lock, and hand very large requests straight to mmap. The Linux kernel does the same for its own objects with its slab allocator.

Garbage collection: reference counting

In C and C++ the programmer calls free, or a destructor does, and the bugs are leaks, double frees and use after free. Garbage-collected languages instead free an object automatically when the program can no longer reach it. The simplest way is reference counting: every object counts the references to it, and when the count drops to zero, it's freed immediately. CPython works this way, as do Swift and Objective-C, and C++'s shared_ptr and Rust's Rc. It's predictable, and memory is reclaimed promptly. It has two costs. Every assignment updates counts, which in multithreaded code must be atomic. And it can't free a cycle: in the example, two objects that refer to each other keep each other's count above zero after the program drops its own references, so neither is freed until CPython's separate cycle collector runs.

Tracing collectors

A tracing collector instead starts from the roots, which are global variables, the stacks of every thread and the registers, and follows every reference to find everything reachable. Mark and sweep marks each reachable object, then sweeps the heap and frees everything unmarked, cycles included, as the example's last part does. A copying collector moves the live objects into a fresh region instead, which compacts the heap and makes allocation a pointer increment, at the cost of needing space to copy into. Most programs follow the generational hypothesis: most objects die young. So collectors in the JVM, .NET and JavaScript engines collect a small young generation often and cheaply, and the old generation rarely.

The price of tracing is the pause, or the work needed to avoid it. A simple collector stops the program while it traces. Concurrent collectors such as Java's ZGC and Go's collector do most of the work while the program runs, using write barriers to track changes, and keep pauses to around a millisecond or less in exchange for some throughput and extra memory. Tracing collectors also typically need more memory than the live data, often twice as much, to run efficiently.

Common traps
  • Long-running services whose memory only grows because freed holes can't be reused. Measure fragmentation, not just leaks.
  • Cycles in reference-counted code, such as parent and child objects that point at each other. Use weak references for back-pointers.
  • Allocating in a hot loop what could be allocated once and reused.
  • Assuming free returns memory to the operating system. Allocators usually keep it for reuse.
  • Sizing a garbage-collected service by its live data without the collector's headroom.

Chapter 16

Files and file systems

10 min read3 exercises

A disk offers numbered blocks. A file system turns them into named files that grow and shrink, organised in directories, with owners and permissions. Its central idea is the inode, a record of a file's metadata and the location of its data, with the file's names kept separately in directories. This chapter traces open, read, link and unlink through real system calls and shows the three layers between a process and its data. It explains how an inode finds a file's blocks, why deleting a file frees no space while the file is open, and what extents and sparse files are.

Three layers

A file descriptor is a small integer, an index into the process's own table of open files. Each entry points to an open file description in the kernel, which holds the current offset and the mode the file was opened with. Each open file description points to an inode, the file itself. Two calls to open on the same file create two open file descriptions, each with its own offset. dup creates a second descriptor for the same description, and so does fork, for every descriptor the child inherits. Those share one offset, so a read through one moves the other.

The example opens one file twice and duplicates one of the descriptors. Reading 4 bytes through each gives "0123" twice, from the two independent offsets, and then "4567" through the duplicate, which shares the first offset. A forked child reads one more byte through the inherited descriptor, and the parent's next read starts after it.

Names and inodes

An inode holds everything about a file except its name: its type, size, owner, permissions, timestamps, link count, and where its data is. A directory is a special file whose contents map names to inode numbers. That separation explains links. A hard link is a second directory entry for the same inode, so after os.link the two names are equally real and the link count is 2; ls -i shows the shared inode number. A symbolic link is a separate small file whose content is a path, followed when the link is opened, so it can point across file systems or at nothing at all. unlink removes a name and decrements the link count. The inode and its data are freed only when the count reaches zero and no process has the file open.

That last condition explains a common incident. A disk fills up, someone deletes a huge log file, and no space comes back, because the process writing the log still has it open and keeps writing to an inode with no name. The example does the same: after unlinking the last name, the directory is empty of it, but the open descriptor still reads the whole file. lsof +L1 lists open files with no links left, and the space returns when the process closes the file or exits.

Finding the blocks

The classic Unix inode, used by ext2 and ext3, holds 12 direct block pointers, enough for the first 48 KiB of a file in 4 KiB blocks. After them come a single indirect pointer, to a block full of 1,024 further pointers, which adds 4 MiB; a double indirect pointer, adding 4 GiB; and a triple indirect pointer, adding 4 TiB. Small files, which are most files, need no extra blocks at all, and large files cost one extra read per level. Modern file systems, ext4, XFS, Btrfs and APFS, use extents instead: each entry describes a run of contiguous blocks with a start and a length, so a large file stored contiguously needs a handful of entries instead of millions of pointers.

Because an inode records where data is, not merely how big the file is, a file can have holes. The example seeks to just before 1 GiB and writes one byte. The file's size is 1 GiB, but the file system stores only the block that was written, and reads of the hole return zeros. Virtual machine images and database files are often sparse, which is why ls -l and du can disagree by gigabytes.

Layout, caching and the VFS

Where blocks go on the disk matters. The Berkeley Fast File System, in 1984, divided the disk into groups and placed each file's inode near its data and the files of a directory near each other, which multiplied throughput on spinning disks; ext4's block groups follow the same idea. Reads and writes don't go straight to the disk anyway. They go through the page cache, the kernel's cache of file data in otherwise unused memory: a read of cached data is a memory copy, and a write normally just updates the cache and marks the page dirty, to be written back seconds later. Chapter 17 is about what that delay means when the power fails.

On Linux, all of this sits behind the virtual file system layer, which gives ext4, XFS, Btrfs, network file systems and in-memory ones such as tmpfs the same open, read and write. It's also how files that aren't on any disk work: /proc and /sys generate their contents when read, which is what "everything is a file" means in practice.

Common traps
  • Deleting a file a process still has open and expecting the space back.
  • Running out of inodes with free blocks to spare, on a volume of millions of tiny files. Check df -i.
  • Assuming rename works across file systems. It fails with EXDEV, and a copy isn't atomic.
  • Two processes appending to one file through separate opens without O_APPEND, overwriting each other.
  • Checking a path and then opening it, when a symbolic link can be swapped in between (chapter 7).

Chapter 17

Crash consistency, journaling and fsync

11 min read3 exercises

Changing a file system means writing several blocks in different places, and the power can fail between any two of them; disks may even complete writes in a different order from the one they were issued in. This chapter tries every crash during a one-block append and classifies the damage. It shows how a journal makes the update all or nothing, and then moves up a level to applications: why overwriting a file in place can lose it, how writing a new file and renaming it fixes that, and what fsync does and doesn't promise.

One append, three writes

Appending one block to a file touches three structures on disk. The bitmap of free blocks must mark the new block used. The file's inode must record the new size and point to the block. And the data block itself must be written. They live in different places, so they're separate writes, and nothing guarantees that all three complete, or in which order. The example tries all eight combinations of which writes reached the disk before a crash, and asks what a file-system checker would conclude about each.

Only three outcomes are clean: all three writes, none of them, or only the data block, written into a block nobody points to. A bitmap update alone leaks a block that belongs to no file. An inode update without the bitmap points at a block the bitmap says is free, so a later allocation can give the same block to a second file, and the two files then overwrite each other. The bitmap and inode without the data leave a consistent file system with garbage at the end of the file: whatever was in that block before, possibly another user's deleted data. No checker can detect that last case, because the metadata is perfectly consistent.

Early Unix systems handled crashes by running fsck at boot: read every inode and bitmap, cross-check them, and repair what's inconsistent. It works, but it reads the whole file system, which on a large disk takes hours, and it can't recover data that was never written.

Journaling

A journal, or write-ahead log, makes the update atomic. Before touching the real structures, the file system writes everything it's about to change into a reserved log area, followed by a commit record. Only once the commit is on disk does it write the blocks to their home locations, the checkpoint, and finally it frees the log space. After a crash, recovery reads the log. A transaction with a commit record is replayed, which is safe to do twice, since replaying writes the same blocks again; a transaction without one is discarded. Either way the file system ends up entirely before or entirely after the update, which is what the example's second table shows for every crash point.

The order is enforced with write barriers, or cache flushes, because a disk with a write cache might otherwise write the commit before the blocks it describes. ext3, ext4, XFS and NTFS all journal. Writing every data block twice, once to the log and once home, halves write bandwidth, so ext4's default ordered mode journals only metadata, and writes a file's data blocks to their home locations before committing the metadata that points to them. That still rules out pointers to garbage. Copy-on-write file systems, ZFS, Btrfs and APFS, take another route: they never overwrite live blocks, write new versions elsewhere, and switch to them with a single atomic update of a root pointer.

What fsync promises

A write that returns has only copied the data into the page cache. Linux writes dirty pages back on its own schedule, typically within 30 seconds, and a crash before then loses them however consistent the file system stays. fsync(fd) blocks until the file's data and metadata are on stable storage, including telling the device to flush its own volatile cache; fdatasync skips metadata that isn't needed to read the data back, such as timestamps. On macOS, fsync does not force the drive to flush its cache, and durability across a power cut needs fcntl(fd, F_FULLFSYNC), which SQLite and other databases use there.

fsync is also where errors surface. In 2018 PostgreSQL's developers discovered that when Linux failed to write back dirty pages, fsync reported the error once and then marked the pages clean, so a retry would succeed and the data was simply gone. Since then PostgreSQL treats an fsync failure as fatal and recovers from its own log. The lesson for every program is that an fsync error means the data may be lost, not that it should try again. And fsync is slow: from around a hundred microseconds on a server SSD that can protect its cache against power loss, to several milliseconds on consumer drives and ten on spinning disks. That's why databases group commit, making many transactions durable with one fsync (exercise 17.2).

Saving a file safely

The same problem appears one level up. Opening a file with "w" truncates it first and then writes the new contents, so a crash in between leaves the old contents, an empty file, a partial one or the new one; the example lists all four. The safe pattern writes the new contents to a temporary file in the same directory, calls fsync on it, then uses rename to replace the original, and finally calls fsync on the directory so that the rename itself is durable. POSIX guarantees that rename replaces the target atomically, so every reader and every crash sees either the complete old file or the complete new one. The example's atomic_write does exactly this. When ext4 introduced delayed allocation in 2009, applications that skipped the fsync began leaving zero-length configuration files after crashes, and ext4 added a heuristic to protect them. Code that wants its data to survive shouldn't depend on heuristics.

Common traps
  • Treating a successful write as durable. Until fsync returns, it's in memory.
  • Overwriting important files in place. Write a new file and rename it over the old one.
  • Forgetting to fsync the directory after creating or renaming a file.
  • Retrying a failed fsync and believing the second success.
  • One fsync per record in a hot path, instead of batching.
  • Relying on plain fsync on macOS, or on drives and RAID controllers that ignore flushes.

Exercise 17.2Group commit

A database must make every committed transaction durable, and an fsync of its log takes 2 ms. At most how many transactions a second can it commit with one fsync each? How does group commit raise that, and what does it cost each transaction?

Show solution

With one fsync per transaction, run one after another, the limit is 1 / 2 ms = 500 commits a second, however fast the processor is. With group commit, transactions append their log records to a shared buffer, and one fsync makes everything in the buffer durable. All the transactions that committed during the previous fsync share the next one, so at 5,000 commits a second each fsync covers about 10 transactions, and 500 fsyncs a second suffice. The cost is latency: a transaction may wait for the fsync in progress to finish before its own starts, up to about two fsync times, 4 ms. Some systems also wait deliberately for a fraction of a millisecond to gather more commits into each group.

fsync on the file made its inode and data durable, but the file's name lives in a different file, the directory, which has its own dirty block in the page cache. If the crash came before that block was written back, the inode survived with no name pointing to it; after recovery it's an orphan, which fsck may move to lost+found or free. To make a new name durable, open the directory and call fsync on it after creating or renaming the file, as the example's atomic_write does. Some file systems happen to make this unnecessary in some modes, but portable code can't rely on that.

Chapter 18

I/O models: blocking, multiplexed and asynchronous

10 min read3 exercises

A read from a socket or a disk may have to wait, and how a program waits decides how many connections one thread can serve and how much processor time goes on waiting. This chapter compares four models: blocking calls, non-blocking calls with polling, readiness notification through select, epoll and kqueue, and completion-based I/O with io_uring. It runs a single-threaded server that handles a hundred connections by asking the kernel which ones are ready, and explains why regular files don't fit the readiness model.

Blocking

By default, a read on a socket with no data waiting puts the calling thread to sleep until data arrives. That's the simplest model to program: the code reads a request, handles it and writes a reply, in order, as if nothing else existed. To serve many clients, give each connection its own thread or process, which is how Apache's original servers and PostgreSQL work. Around 1999 Dan Kegel named the limit of that design the C10K problem: serving ten thousand connections at once with a thread each costs a great deal of memory, and every one of them needs scheduling. Most of those threads are idle, waiting for a slow client, and the waiting itself is what costs.

Non-blocking, and readiness

A descriptor in non-blocking mode, set with O_NONBLOCK, never sleeps: a read with nothing to read fails at once with EAGAIN, "try again". On its own that's only useful for checking, since a program that keeps retrying burns a core. Combined with a way to learn when a descriptor is ready, it becomes the basis of every high-performance server. select, from 4.2BSD in 1983, takes sets of descriptors and blocks until at least one is readable or writable. poll lifted select's limit of 1,024 descriptors, but both still pass the whole set to the kernel on every call and scan it, so their cost grows with the number of connections, not with the number that are active. Linux's epoll, from 2002, and FreeBSD's kqueue, from 2000 and also used by macOS, fix that: a program registers each descriptor once, and each wait returns only the ones that are ready.

The example uses Python's selectors module, which picks epoll on Linux and kqueue on macOS. A non-blocking read on an empty socket raises BlockingIOError, Python's name for EAGAIN. Then a hundred socket pairs stand in for a hundred client connections. When ten clients send a request, one call reports exactly those ten as ready and one thread answers them; when all hundred send, one call reports a hundred. A client that hangs up is reported as ready too, and its read returns an empty result, end-of-file, which tells the server to close and unregister it.

The details that bite

Readiness notification comes in two styles. Level-triggered, the default, reports a descriptor every time you ask, as long as it's readable. Edge-triggered, an option in epoll, reports it only when it becomes readable, which saves wake-ups but requires reading until EAGAIN every time, or the rest of the data sits unnoticed (exercise 18.1). Writes need the same care as reads: a send on a non-blocking socket can accept only part of the data when the buffer is full, so the server keeps the rest and asks to be told when the socket is writable again. It should ask only while it has something to write, because an idle socket is almost always writable, and waiting for writability on every connection turns the event loop into a busy loop.

Regular files don't fit this model at all. A file is always reported readable, because the kernel's notion of readiness doesn't cover waiting for the disk, so a read can still block on a page-cache miss (chapter 13). Event-loop runtimes such as libuv, behind Node.js, therefore send file operations to a small pool of threads.

Completion: io_uring

Readiness tells a program when an operation won't block, and the program then makes the system call itself. Completion-based I/O inverts that: the program describes the operation, the kernel performs it, and the program collects the result later. Windows has worked this way since its I/O completion ports in the 1990s. Linux's io_uring, by Jens Axboe, added in 2019, uses two rings in memory shared between process and kernel: the program writes requests into the submission ring and reads results from the completion ring, so a single system call can submit and collect hundreds of operations, and in polling mode none at all. It handles files and sockets alike, which solves the file problem above. It has also had a long series of security flaws, and some environments, including Docker's default security profile and Google's production servers, disable it.

Choosing

The example's last lines put rough numbers on the trade-off. An idle connection costs perhaps 64 KiB of stack and kernel state with a thread each, and a few kilobytes of buffers with an event loop, so at 100,000 connections the difference is about 6 GiB against a few hundred MiB. Under load, readiness-based servers also avoid most context switches. Few programs use these interfaces directly, though, because language runtimes build on them. Go's network poller runs goroutines over epoll or kqueue, so code that looks blocking is multiplexed underneath. Java has NIO and Netty, Rust has tokio, and Python has asyncio. Knowing what's underneath explains their behaviour: why a blocking call inside them hurts (chapter 11), why file I/O goes to a thread pool, and why a server can hold far more connections than it has threads.

Common traps
  • A blocking call inside a non-blocking server, which stalls every connection.
  • Edge-triggered epoll without reading to EAGAIN, leaving data unseen.
  • Asking for writability on every socket all the time, which spins at 100% CPU.
  • Using select with descriptor numbers of 1,024 or more, which overflows its fixed-size sets.
  • Assuming file reads never block because the file is "ready".
  • Closing a descriptor without unregistering it, when the number may be reused for a new connection.

Exercise 18.1Level and edge

A socket receives 10 KB at once. The handler reads 4 KB per event. What happens under level-triggered notification, and under edge-triggered notification?

Show solution

Level-triggered: after the first 4 KB read, the socket is still readable, so the next wait reports it again, and the handler gets all 10 KB in three events. It costs extra wake-ups but nothing is lost. Edge-triggered: the event fired once, when the socket went from empty to readable. After the handler reads 4 KB, 6 KB remain, but the socket hasn't become readable again, it simply stayed readable, so no new event comes. The 6 KB sits there until the client sends more, which may be never if it's waiting for a reply. With edge-triggered notification the handler must read in a loop until it gets EAGAIN.

Exercise 18.2Why not select?

A server holds 50,000 mostly idle connections, of which about 20 have data at any moment. Compare the work of one select call and one epoll_wait call.

Show solution

select can't even do it with the standard fixed set size of 1,024 descriptors. poll, which has no limit, copies an array of 50,000 entries into the kernel on every call, the kernel checks all 50,000, and the program scans all 50,000 results to find the 20 that are ready: work proportional to the number of connections, repeated on every call, thousands of times a second. epoll_wait copies nothing in, because the interest list was registered once, and returns only the 20 ready entries: work proportional to the number of active connections. That difference is most of why one machine can now hold hundreds of thousands of connections.

Exercise 18.3The slow client

A single-threaded event-loop server writes a 1 MB response to a client on a slow mobile connection. The socket's send buffer holds 256 KB. What happens if the server's write blocks? What should a non-blocking server do instead?

Show solution

A blocking write sleeps until the kernel has accepted the whole megabyte, which means until the slow client has drained most of it, possibly many seconds. The loop's only thread is stuck in that write, so every other connection waits. A non-blocking server writes what fits, 256 KB at first, keeps the remaining 768 KB in a per-connection buffer, asks to be told when the socket becomes writable, and goes back to serving others. Each writable event sends a little more, and when the buffer is empty it stops asking. It should also cap how much output it will buffer per connection, or many slow clients could exhaust its memory.

Chapter 19

Interprocess communication

10 min read3 exercises

Processes share no memory by default, which is the point of having them. When they need to cooperate, the kernel offers several ways to talk, and this chapter runs most of them for real. It covers pipes and named pipes; stream and datagram sockets, and the framing a byte stream needs; shared memory, and the difference between shared and private mappings; and passing an open file descriptor from one process to another. It ends with how to choose between them.

Pipes and named pipes

A pipe (chapter 3) is a one-way byte stream through a kernel buffer, and a read returns end-of-file once every writer has closed its end. An anonymous pipe exists only as two descriptors, so it can connect only processes that inherited them from a common ancestor. A named pipe, or FIFO, created with mkfifo, has a name in the file system, so unrelated processes can find it, and permissions decide who may open it. Opening a FIFO blocks until the other end is opened too, which makes it a simple rendezvous between two programs.

Sockets

Unix domain sockets use the same API as network sockets, socket, bind, connect, send and recv, with an address that's a path in the file system instead of a host and port. They're bidirectional, faster than TCP over the loopback interface because they skip the network stack, and protected by file permissions; a server can also ask the kernel for the user ID of the process at the other end. The Docker daemon, PostgreSQL's local connections, systemd and the display servers of Linux desktops all listen on them.

A socket comes in kinds. A stream socket, SOCK_STREAM, carries bytes with no message boundaries: three sends can arrive as one read, as in the example, or one send as three reads. A datagram socket, SOCK_DGRAM, keeps each send as a separate message; for Unix sockets it's reliable and ordered, unlike UDP. A protocol on a stream must therefore mark where each message ends, which is framing. The example prefixes each message with its length in four bytes and reads exactly that many back, the method used by many binary protocols; text protocols such as HTTP and Redis's use delimiters instead (exercise 19.1).

Shared memory

Every message through a pipe or socket is copied twice: from the sender into the kernel, and from the kernel into the receiver. Shared memory avoids both copies by mapping the same physical pages into both processes. A mapping created with mmap and MAP_SHARED before a fork is shared with the child; unrelated processes can share a named object from shm_open or a file mapped by both. In the example, the child writes into a shared mapping and the parent reads the child's words straight out of memory, while the same write to a MAP_PRIVATE mapping lands in the child's copy-on-write copy (chapter 13) and the parent sees nothing.

Shared memory is the fastest form of communication and the most dangerous, because it brings back every race of chapters 7 to 10, now between processes. The usual answer is a structure designed for it, such as a ring buffer with atomic head and tail indices, or a mutex created as process-shared, which on Linux is a futex in the shared page. Databases put their buffer caches in shared memory, as PostgreSQL does, and browsers use it to pass rendered frames between processes. Python's multiprocessing.shared_memory wraps the same mechanism.

Passing descriptors

A Unix socket can carry more than bytes. With an SCM_RIGHTS message, a process sends open file descriptors, and the receiver gets new descriptors for the same open files, sharing their offsets, as if it had inherited them. In the example the child opens a file and sends the descriptor, and the parent reads the file through it without ever opening it. The kernel checked permissions when the child opened the file, not when the parent used it, which makes this a tool for privilege separation: a small privileged helper opens what's needed and hands the descriptors to an unprivileged worker. It's also how servers restart without dropping connections. The old process passes its listening socket to the new one, which starts accepting while the old one finishes its current requests, and systemd's socket activation passes listening sockets to services in the same way.

Choosing

Other mechanisms fill the gaps: POSIX message queues, which keep message boundaries and priorities; the older System V IPC calls; eventfd for one process to wake another; and on Linux desktops, D-Bus, a message bus built on Unix sockets. In practice, the choice usually comes down to a few questions. A one-way stream between a parent and a child is a pipe. A local service with requests and replies is a Unix socket, or local TCP or HTTP if it may move to another machine one day, at a cost of tens of microseconds per request. Large volumes of data at a high rate, such as video frames or tensors, go in shared memory with a carefully designed queue. And the kernel's permission checks apply to all of them, so a socket that's writable by everyone is an open door: access to Docker's socket is equivalent to root.

Common traps
  • Treating a stream socket as a stream of messages, with no framing and no handling of partial reads.
  • Shared memory without synchronisation, which reintroduces every race in Part III between processes.
  • Two processes that both write large amounts before reading, deadlocking on full buffers.
  • Named FIFOs, sockets and shared-memory objects left behind after a crash.
  • A sent descriptor not closed by the sender, which keeps the file open longer than intended.
  • Sockets with permissions wider than their power, such as Docker's.

Exercise 19.1Two ways to frame

Compare length-prefix framing with delimiter framing, such as one message per line. Give an advantage and a cost of each, and a protocol that uses each.

Show solution

A length prefix tells the receiver exactly how many bytes to read, so messages can contain any bytes and the reader never scans the data. It's compact and fast, and used by most binary protocols, such as PostgreSQL's wire protocol and gRPC. Its costs are that the sender must know the length before it starts sending, and that a corrupted length desynchronises everything after it. A delimiter, such as a newline, lets the sender stream without knowing the length, and is easy to read and debug by hand; HTTP/1.1 headers, Redis's protocol for commands, and JSON Lines use delimiters. Its cost is that the delimiter can't appear inside a message unless it's escaped, and the reader must scan every byte to find it. Many protocols mix the two: HTTP ends its headers with a blank line and gives the body's length in a header.

Exercise 19.2The pipe deadlock

A parent starts a child with pipes to its standard input and output, writes 1 MB into the child's input, and then reads the child's output. The child echoes everything it reads. The program hangs. Why, and how do you fix it?

Show solution

The child reads input and writes output as it goes, but nobody reads its output until the parent has finished writing. The output pipe fills after 64 KiB, so the child blocks in write and stops reading its input. The input pipe then fills, so the parent blocks in its write too. Each waits for the other: a deadlock with two pipes. Fix it by writing and reading at the same time, with a thread for one direction or with readiness notification on both pipes. In Python, subprocess.run(input=...) and Popen.communicate() do exactly this, and the subprocess documentation warns against writing to stdin and reading stdout in sequence.

Exercise 19.3Restarting without refusing anyone

Describe how a server can be replaced by a new version without refusing a single connection, using descriptor passing. What does the old process do with its existing connections?

Show solution

The listening socket is the key: as long as some process holds it open, the kernel keeps queueing incoming connections. The old process starts the new version and passes it the listening socket's descriptor over a Unix socket, or simply leaves it open across fork and exec. The new process starts calling accept on it. The old process then stops accepting, closes its copy of the listener, finishes the requests on its existing connections, and exits. Connections that arrived in between waited in the kernel's queue and are accepted by the new process, so none is refused. nginx and HAProxy reload this way. An alternative on Linux is SO_REUSEPORT, which lets both processes bind the same port for the overlap.

Chapter 20

Virtual machines and containers

11 min read3 exercises

Virtual machines and containers both let many workloads share one machine as if each had it to itself, and both are built from the mechanisms of this volume. A virtual machine gives each guest its own kernel, running on virtual hardware with the processor's help. A container shares one kernel among all its guests and gives each group of processes its own view of it. This chapter explains how a hypervisor traps and emulates, and what nested paging adds to a TLB miss. It then takes a container apart: namespaces for what it sees, cgroups for what it may use, and layered images for its files. The example simulates an overlay file system and a CPU quota.

Virtual machines

A hypervisor, or virtual machine monitor, runs operating systems as guests, each believing it controls real hardware. The classic technique is trap and emulate: run the guest kernel in user mode, so that every privileged instruction it executes traps to the hypervisor, which performs the instruction's effect on the guest's virtual state and resumes it. Gerald Popek and Robert Goldberg showed in 1974 that this works if every instruction that could reveal or change the machine's privileged state traps. For a long time x86 failed that test: a few instructions behaved differently in user mode without trapping. VMware worked around it in 1999 by rewriting guest kernel code on the fly, and Xen in 2003 by modifying guest kernels to call the hypervisor directly, which is paravirtualisation.

Since Intel's VT-x and AMD-V, in 2005 and 2006, the processor supports virtualisation directly. A guest runs in a special mode at full speed, kernel and all, and certain events cause a VM exit to the hypervisor: some privileged instructions, accesses to emulated devices, and interrupts. Linux's KVM, added to the kernel in 2007, turns Linux itself into a hypervisor, with QEMU emulating devices; most clouds run KVM or a close relative. A VM exit saves the guest's state, runs the hypervisor and resumes the guest, about a microsecond or two, and the example's last table shows why exits must be kept rare: 500,000 a second would take three quarters of a core. Paravirtual devices such as virtio, which batch requests through shared memory rings, and direct assignment of hardware devices to guests are the usual cures.

Memory for guests

A guest kernel has page tables that map its virtual addresses to what it believes are physical addresses. Those are really guest-physical addresses, which the hypervisor maps to the host's real memory with page tables of its own. With nested paging, Intel's EPT and AMD's NPT, the hardware walks both. Each of the guest's table pointers is itself a guest-physical address that needs a host walk, so a TLB miss walks a two-dimensional grid: up to (4 + 1) × (4 + 1) − 1 = 24 memory reads with four-level tables in both, against 4 natively, and 35 with five levels. TLBs and huge pages in the host matter even more for virtual machines than for processes, and hypervisors back guest memory with large pages whenever they can.

A container is a process

The Linux kernel has no "container" object. A container is an ordinary set of processes that the kernel shows a restricted view and holds to limits, using features added separately over a decade. Namespaces give a group of processes its own instance of a global resource: a PID namespace with its own process 1, which the host sees under some other number; a mount namespace with its own file-system tree; a network namespace with its own interfaces, addresses and ports; and namespaces for host name, users, IPC and cgroups. Cgroups limit and account for what the group uses: CPU, memory, I/O and the number of processes. On top of these come dropped capabilities, so that root inside the container lacks most of root's powers, and a seccomp filter that blocks system calls the workload shouldn't need. Docker, containerd and Kubernetes assemble all this from a container image, following the Open Container Initiative's specifications.

Images and layers

A container image is a stack of file-system layers, each a set of changes on top of the one below: a base distribution, then installed packages, then the application. overlayfs presents them as one directory tree. Looking up a path takes the topmost layer that has it, so a container sees its image's files without any of them being copied. The layers are read-only and shared by every container started from the image, and each container adds one thin writable layer on top. Writing to a file from a lower layer first copies the whole file up into the writable layer, copy-up, and deleting one leaves a whiteout entry that hides it. In the example, a container changes a configuration file and deletes the shell, and its neighbour, started from the same image, still sees both untouched.

Limits: CPU quotas and throttling

Cgroups offer two kinds of CPU control. cpu.weight shares the processor in proportion when groups compete, like nice values (chapter 6). cpu.max sets a hard quota per period, such as 50 ms of CPU time every 100 ms, half a core. A quota counts CPU time across all of a container's threads, so a parallel burst can use the whole quota early in a period and then sit throttled until the next one starts. In the example, a request that needs 120 ms of CPU finishes in 220 ms on one thread, and still takes 205 ms on four threads, although four idle cores could finish it in 30. Throttling like this shows up as unexplained latency spikes on services that are nowhere near their average limit, which is why many teams running Kubernetes set CPU requests, which become weights, and leave CPU limits off. A related trap is a runtime that sizes its thread pool from the host's core count rather than the container's limit; the JVM has read cgroup limits since Java 10, and Go's GOMAXPROCS since Go 1.25. Memory limits are harder still: a container that exceeds memory.max is killed by the out-of-memory killer.

How strong is the wall?

A virtual machine's guest reaches the host only through the hypervisor and its virtual devices, a small and heavily scrutinised interface. A container's processes call straight into the host kernel, with its hundreds of system calls, and a single kernel bug can let one escape. Containers are therefore excellent for packaging and for running trusted workloads side by side, and need more care for untrusted code. Two families of projects bridge the gap. gVisor intercepts a container's system calls and serves them from its own user-space kernel. Kata Containers and Firecracker run each container in a lightweight virtual machine: Firecracker, built for AWS Lambda, boots a microVM in about 125 ms with under 5 MiB of overhead, which gives virtual-machine isolation with container-like speed.

Common traps
  • Treating a container as a VM-strength boundary for untrusted code, especially a privileged one or one with Docker's socket mounted.
  • CPU limits on latency-sensitive services, which throttle bursts even when the machine is idle.
  • Runtimes that size thread pools or heaps from the host rather than the container's limits.
  • Heavy writes into the container's writable layer instead of a volume.
  • A main process that neither handles signals nor reaps zombies (chapter 3).

Exercise 20.1Quota arithmetic

A container has cpu.max set to "200000 100000", two CPUs' worth. A request runs 16 threads in parallel and needs 1.6 s of CPU in total. How long does it take on an idle 16-core host with no limit, and with the limit? What would you change?

Exercise 20.2Appending one byte

A container's image includes a 2 GB data file in its base layer. The application appends one byte to it. What does overlayfs do, and what does it cost? What should the application do instead?

Show solution

Data that changes belongs in a volume, a directory mounted from the host or from network storage, which bypasses the overlay entirely, is shared or persisted as needed, and doesn't depend on the container's lifetime. The thread pool

A thread pool is a bounded blocking queue (chapter 9) and a fixed set of threads that take tasks from it. Build it in any language with threads and condition variables, without the standard library's executor, and then compare it with that executor. It should provide:

  1. A fixed number of worker threads, created once (chapter 4), and a way to choose that number from the workload.
  2. A queue with a capacity, so that submit blocks or fails when it's full rather than growing without limit.
  3. submit returning a future whose result, or exception, the caller can wait for.
  4. Shutdown in two forms: finish everything queued, or stop now and cancel what hasn't started.
  5. No busy-waiting anywhere, and every wait on a condition inside a while loop.
  6. A stress test with many submitters and tiny tasks, run under ThreadSanitizer or a race detector (chapter 7).

The twenty rules

One per chapter, each linked back to it. Read them before you write concurrent code, chase a memory problem, or trust that data has reached the disk.

  1. Wait for every child you create, and flush your output before you fork.
  2. Cross into the kernel as rarely as you can: buffer and batch, and count the system calls.
  3. Close every pipe end you don't use, and answer SIGTERM by finishing your work and exiting.
  4. Create threads once and reuse them, and size the pool with Little's law, not by guesswork.
  5. Decide whether you need short turnaround or quick response before you choose a scheduling policy.
  6. Weights share a contended processor and quotas cap it; set hard limits only where you can afford the stalls.
  7. Shared data needs a lock or an atomic; running a test proves nothing about races, and a race detector does.
  8. Hold locks briefly and never across I/O, and let the library's mutex decide when to spin.
  9. Wait on a condition in a while loop, with the lock held, with one condition variable per condition.
  10. Take locks in one global order, and give every wait that can fail a timeout and jittered retries.
  11. Never block an event loop, and remember that every await is a point where the world can change.
  12. Every address is virtual: judge memory by what's resident, not by what's reserved.
  13. Mind the TLB and the first touch: huge pages for large random-access data, and warm up before you time.
  14. Size memory to the working set, and treat swapping as an alarm, not as capacity.
  15. Fragmentation wastes memory as surely as leaks do; use pools and size classes, and weak references for back-pointers.
  16. Names point to inodes, and a deleted file lives on until its last descriptor closes.
  17. Nothing is durable until fsync returns: write a new file, sync it, rename it, sync the directory.
  18. Wait for many things at once with epoll or kqueue, and read until EAGAIN.
  19. A byte stream needs framing, and shared memory needs synchronisation.
  20. A container is a set of processes with a restricted view of one shared kernel; trust it accordingly.
