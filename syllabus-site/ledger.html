The Engineer's Ledger

A ledger is the oldest database there is: a book you only ever add to, kept so carefully that a business trusts it over anyone's memory. Every serious database still has one at its core, the write-ahead log, and everything else in it, the pages, the indexes, the planner, the locks, exists to make that record fast to search and safe to share. You already know how to ask a database questions. This volume is about what it does with them.

How to use this volume

The chapters follow the shape of the rest of the series: the idea in one sentence, worked examples, the traps, then exercises with folded solutions, a checklist and further reading. Run the examples. A database is a machine you understand by watching it work, and every example here prints what it did.

This volume assumes you can write SQL. Joins, subqueries, CTEs, window functions and the interview patterns are taught in SELECT Again, and this volume starts where that course stops: what the database does with your query once it has it. You will meet SQL on every page, but you won't be taught it. The other prerequisite is a little computer architecture (stage 04): what a page of memory is, why a disk read costs so much more than a memory read, and what a cache does.

The examples run on a real database, or build a small working one. Python's standard library ships SQLite, so where an example needs a real engine it uses one: real query plans, real constraints, real locks, and a real million-row table. Where an example needs to show the inside of an engine, a B-tree splitting a page or a log being replayed after a crash, it builds a small version in plain Python. Every example was run before publication, and the output printed under it is what it actually printed.

Engines differ; the mechanisms don't. PostgreSQL, MySQL, SQLite and the rest make different choices: different default isolation levels, different index structures, different ways of keeping old versions of rows. This volume names those differences where they bite, but it teaches the mechanisms underneath, because those are what transfer. The stage's deliverable tests both halves. First, build a key-value store with a write-ahead log, crash recovery and a B-tree or LSM index (chapters 5 to 7 and 15 build the parts). Then take a slow query over a million rows and bring it under fifty milliseconds, documenting every plan change (chapter 11 does exactly that).

The one question

When a query is slow or a write is unsafe, the instinct is to reach for a setting, an index or a different database. Most of the time the answer is already visible if you know where to look.

So before you change anything, ask: what does the database have to read to answer this, and what does it have to write to the log before it can say "done"? Reads are measured in pages, and a query that touches a million pages to return ten rows is slow no matter how fast the server is. Writes are measured in log records and the locks held while they're made. Every chapter in this book is a way of answering that question more precisely.

Part I

The model

Four chapters on what you store before how it's stored. What a database promises that a file can't, the keys and constraints that let it refuse bad data, the designs for the shapes that don't fit neatly into tables, and the ORM layer that sits between your objects and its rows.

Chapter 01

What a database promises

10 min read3 exercises4 flashcards

A file is a place to put data; a database is a set of promises about it. It promises that a change happens completely or not at all, even if the power fails halfway. It promises that many people can change data at once without losing each other's work. And it promises that you can find any part of it without reading all of it. Every chapter in this volume is one of those promises and the machinery that keeps it.

Three promises a file can't keep

Most programs start by saving data to a file, and for a while that works. Then three things happen. The machine loses power while the file is being written, and the next start finds half a file. Two requests arrive at the same moment, both read the file, both change it, and one change disappears. And the file grows until finding one record means reading all of them. Those are the three promises a database exists to keep: atomic, durable writes, safe concurrency, and finding without scanning.

The first accident is the torn write. Opening a file for writing truncates it, so a crash between the truncate and the last byte leaves a file that is neither the old version nor the new one. The usual fix, writing a temporary file, flushing it to disk with fsync and renaming it over the original, does keep the old version safe, because a rename is atomic on POSIX file systems. But it only works for one file, it rewrites the whole file for every change, and it does nothing for the second accident.

The second accident is the lost update. Both clients read 0, both write 1, and two visits are recorded as one. Nothing crashed and nothing reported an error: the data is simply wrong. The database turns the same two increments into 2 because it won't let the second writer act on stale data. Client B is told to wait while A holds the write lock, then its update runs against A's committed value. That waiting is concurrency control, and a whole part of this book (chapters 12 to 15) is about doing it without making everyone wait all the time.

The third promise isn't in the example because it's the subject of Parts II and III: a database keeps its data in fixed-size pages and builds indexes over them, so that finding one customer among ten million means reading three or four pages instead of all of them.

What's inside

Almost every relational database has the same parts, arranged the same way. Your SQL is parsed into a tree, the planner turns the tree into a plan, and the executor runs the plan as a pipeline of operators. The operators read through access methods, B-trees and their relatives, which ask the buffer pool for pages, which reads them from disk only when they aren't already in memory. Alongside, a transaction manager decides who may see and change what, and a log manager records every change before it is allowed to count.

The detail worth noticing now is the two arrows to disk. When you commit, the database does not rush your changed rows into the data files. It appends a description of the change to the log and flushes the log, a fast sequential write, and only then tells you the transaction is done. The data pages are written back later, in the background, in whatever order is efficient. If the machine crashes in between, the log holds everything needed to redo the work. The log is the ledger, and the data files are a convenient, searchable copy of what it says. Chapter 15 builds one.

Choosing an engine is choosing trade-offs

Databases differ in where they sit and what they optimise. Embedded databases such as SQLite run inside your process and store everything in one file. They are the most widely deployed database engine there is, in every phone and browser, and the right default for local and single-writer data. Client-server databases such as PostgreSQL and MySQL run as their own service, accept many concurrent writers over the network, and add replication, roles and online maintenance. Transactional (OLTP) systems are built for many small reads and writes; analytical (OLAP) systems are built for scans over billions of rows, and store data in columns instead of rows (chapter 20). Non-relational stores trade the query language for a particular access pattern or scale (chapter 18). None of these is better in general. The useful question is always which promises you need, and how much each one costs.

This volume uses SQLite for its real examples because it ships with Python, so every example runs anywhere without setup. Its mechanisms, pages, B-trees, a write-ahead log, locks, a cost-based planner, are the same ones the server databases use, at a smaller scale.

Common traps
  • Using files where you need a database, then rediscovering torn writes and lost updates one incident at a time.
  • Renaming without fsync, so the rename survives a crash but the bytes it points at don't. Durable atomic replace needs a flush of the file and, strictly, of its directory too.
  • Assuming promises you never asked for. A database keeps them per transaction, and many client libraries run in autocommit mode, where every statement is its own transaction.
  • Confusing durability with backups. Durability survives a crash; it does nothing for a mistaken DELETE or a lost disk (chapter 16).
  • Choosing an engine by popularity rather than by the promises and the access patterns you need.
Exercises
Exercise 1.1Which promise broke?

Name the promise each incident breaks.

  1. After a power cut, the app's settings file is empty and the app won't start.
  2. Two warehouse workers both see one item left, both sell it, and the stock count reads zero.
  3. "Find customer by email" took 5 ms at launch and takes 4 seconds a year later.
Show solution
  1. Atomic, durable writes. The file was truncated and only partly rewritten when the power went. Write to a temporary file, flush it, and rename it over the original, or use a database.
  2. Safe concurrency. A lost update: both read 1 and both wrote 0, so one sale was never subtracted. The fix is to make the read and the write one atomic step, for example UPDATE stock SET n = n - 1 WHERE id = ? AND n > 0, and check that one row changed.
  3. Finding without scanning. With no index on email, every lookup reads the whole table, and the table grew. An index turns the scan into a few page reads (chapters 6 and 8).
Exercise 1.2The limits of the rename trick

The atomic rename protected the file in the example. Name three things it does not solve, and say which part of a database solves each.

Show solution

First, concurrent writers: two processes can each write a temporary file and rename it, and the second rename silently discards the first one's change, the same lost update as before. A database solves that with locks or version checks (chapters 13 and 14). Second, changes that span more than one file: debiting one account file and crediting another can't be made atomic with renames, because a crash between the two renames leaves money missing. A database makes the whole transaction atomic through its log (chapter 15). Third, cost: every change rewrites the whole file, so a one-byte update to a gigabyte of data writes a gigabyte. A database writes a small log record and updates one page in memory. A fourth, if you found it: the rename is only durable once the directory entry is flushed too, which the example glosses over.

Exercise 1.3What is on disk when COMMIT returns?

Using the diagram, trace UPDATE accounts SET balance = balance - 30 WHERE id = 7; COMMIT;. When COMMIT returns, which of these are guaranteed to be on disk: the log record for the change, the changed data page, or the index page for id = 7? What happens to the others if the power fails one second later?

Show solution

Only the log record (and the commit record after it) is guaranteed to be on disk. That is the whole point of the write-ahead log: a sequential append plus one flush is cheap, so the database pays for it on every commit. The changed data page is in the buffer pool and may not reach the data file for seconds or minutes. The index page is untouched here, because balance isn't indexed; if it were, its change would be logged too. If the power fails one second later, recovery reads the log, finds the committed change whose page never made it to disk, and redoes it. A committed transaction is never lost, and the data files catch up from the log.

Checklist
  • Can you name the three promises and the incident that breaks each?
  • Do you know why an atomic rename isn't a substitute for a transaction?
  • Can you trace a query and a commit through the parts of a database?
  • Do you know what is guaranteed to be on disk when COMMIT returns?
  • Can you say which promises your application actually needs?

Chapter 02

Keys, constraints and normal forms

9 min read3 exercises4 flashcards

The cheapest bug fix is the row the database refused to store. Keys and constraints let the database enforce the facts your code assumes, for every client and every code path at once. Normalisation is the discipline of storing each fact exactly once, so that the data can't disagree with itself. Denormalise later, on purpose, with a plan for keeping the copies honest.

Constraints are rules nobody can skip

Every application has rules about its data: emails are unique, an order belongs to a customer who exists, a total is never negative. You can check them in application code, and you should, to give users friendly errors. But application checks only cover the code paths that remember to run them. They miss the admin script, the batch import, the second service written by another team next year, and, as exercise 2.2 shows, two requests racing each other. A constraint declared in the schema is checked by the database on every write, from every client, inside the same transaction as the write. It is the only check that can't be bypassed.

Each refusal names the rule that stopped it. UNIQUE blocks the duplicate email, CHECK rejects the malformed email and the negative total, and the foreign key blocks both the order for a customer who doesn't exist and the deletion of a customer who still has orders. ON DELETE RESTRICT is a choice: CASCADE would delete the orders too, and SET NULL would orphan them on purpose. Pick the one that matches what deleting a customer means in your business.

The last line is the trap. SQLite, for backward compatibility, enforces foreign keys only when the connection turns them on, and turning them on (or off) silently does nothing inside an open transaction. MySQL's old MyISAM engine accepted foreign key syntax and ignored it entirely. Never assume a constraint is enforced: write a test that tries to violate it.

Keys

A key is a set of columns whose values identify one row. A table can have several candidate keys (a customer might be identified by an internal id and also by an email); one is chosen as the primary key and the others should still be declared UNIQUE, or the database won't know they are keys. A surrogate key, an auto-incrementing integer or a UUID, carries no meaning and never needs to change; a natural key, like an ISBN, carries meaning and sometimes does change. SELECT Again's schema-design module covers that choice. The rule that matters here is simpler: every fact you believe is unique deserves a UNIQUE constraint, whichever key you pick.

One fact, one place

Normalisation sounds academic and is entirely practical. When the same fact is stored in many rows, an update that changes some copies and misses others leaves the database contradicting itself, and no query can tell you which copy is right. The tool for spotting this is the functional dependency: X → Y means that knowing X tells you Y. An order id tells you the customer; a customer id tells you the email. A table is in good shape, formally Boyce-Codd normal form, when the left side of every dependency is a key. When it isn't, that dependency's facts repeat.

The wide table's only key is (order_id, product_id), one row per line item. Every other dependency has a smaller left side, and each one means a fact repeated across rows. The customer's email is copied onto every line of every order they place, so changing it means updating hundreds of rows and getting all of them. The product name is copied onto every line that ever sold it. The classic names describe the two shapes: order_id → customer_id depends on part of the key (a second normal form violation), and customer_id → customer_email depends on a non-key column (a third normal form violation). The fix is the same for both: give each dependency a table of its own, keyed by its left side.

The output hides one deliberate trap. The tool treats unit_price as a fact about the product, and if it means the product's current price, it is. But on an order line, the price usually means the price this customer paid, which must not change when the catalogue price does. That's a different fact with a different key: it belongs on the order line. Normalisation can only be as right as the dependencies you write down, so the real work is asking what each column actually means.

Denormalising on purpose

A normalised schema is the right default for data you write. Sometimes you deliberately copy a fact anyway: an order count kept on the customer row so a list page doesn't count orders on every view, a materialised summary for a dashboard, a search document that flattens five tables. That's fine if you treat the copy as derived data, with one owner and a way to rebuild it. Update the copy in the same transaction as the source, or with a trigger, or rebuild it on a schedule and accept the lag, and keep a reconciliation query that finds copies that have drifted. The failure mode is the copy nobody owns, updated by some code paths and not others, quietly diverging for a year.

Common traps
  • Rules enforced only in application code, which the next script, service or race walks straight past.
  • Constraints that silently aren't on: SQLite foreign keys without the pragma, engines that parse CHECK and ignore it.
  • Forgetting that UNIQUE allows many NULLs in most databases, because NULL never equals NULL.
  • Declaring only the primary key and leaving the other candidate keys unenforced.
  • Denormalising without an owner or a reconciliation check for the copies.
Exercises
Exercise 2.1Find the repeated facts

A timesheet table has columns (emp_id, emp_name, dept_id, dept_name, project_id, hours), one row per employee per project. Write down the functional dependencies, the key, and the tables you'd split it into.

Show solution

Dependencies: emp_id → emp_name, dept_id; dept_id → dept_name; emp_id, project_id → hours. The key is (emp_id, project_id). emp_id → emp_name, dept_id depends on part of the key, so an employee's name and department repeat on every project row. dept_id → dept_name is transitive, so a department's name repeats for every employee in it. Split into employees(emp_id, emp_name, dept_id), departments(dept_id, dept_name) and timesheet(emp_id, project_id, hours), with foreign keys from employees.dept_id and timesheet.emp_id. Renaming a department is now one update to one row.

Exercise 2.2The check that races

A sign-up handler runs SELECT 1 FROM users WHERE email = ? and inserts the user only if no row comes back. There's no UNIQUE constraint. Explain how duplicate accounts still appear, and what the fix is.

Show solution

Two sign-ups with the same email arrive together (a double-clicked button is enough). Both run the SELECT before either has inserted, both see no row, and both insert. Check-then-act in application code is a race, and wrapping it in a transaction doesn't help at the default isolation level of most databases, because neither transaction can see the other's uncommitted insert (chapter 13). The fix is a UNIQUE constraint on email, ideally on a normalised form such as lower case: the database serialises the two inserts, the second fails with a constraint violation, and the handler turns that error into a friendly "this email is already registered". Keep the SELECT for a good user experience if you like, but the constraint is the check that actually holds.

Exercise 2.3Is this a copy?

A reviewer flags order_lines.product_name and order_lines.unit_price as normalisation violations, because both are in products. Are they right about both columns?

Show solution

It depends on what each column means, which is the real lesson. unit_price on an order line is almost always the price paid at the time of sale. That's a fact about the line, keyed by the line, and it must stay fixed when the catalogue price changes, so it isn't a violation. product_name is less clear. If it's there so that invoices show the name the customer saw at the time, it's also a historical fact about the line and should stay. If it's there only to save a join, it's a copy of products.name that will drift when a product is renamed, and the reviewer is right. Decide which it is, write it down in a comment on the column, and if it's a copy, give it an owner or remove it.

Checklist
  • Is every rule your code assumes also a constraint in the schema?
  • Have you tested that each constraint is actually enforced?
  • Is every candidate key declared, not just the primary key?
  • Can you find the functional dependencies of a table and spot the repeated facts?
  • Does every denormalised copy have an owner and a reconciliation check?

Chapter 03

Modelling the hard shapes

8 min read3 exercises4 flashcards

Most schemas are easy until they have to hold a tree, a history, an amount of money, or a thing that can be several kinds of thing. Each of those shapes has a handful of known designs with known costs. Picking one deliberately, on day one, is far cheaper than discovering its trade-off in production with ten million rows already written.

Trees

Categories, comment threads, org charts and folders are all trees, and a table is flat. The obvious design is the adjacency list: each row stores its parent's id. It's easy to write and to move a subtree (change one parent_id), but reading a whole subtree needs a recursive query that walks one level at a time. The closure table stores every ancestor-descendant pair, with its depth, in a second table. Reading a subtree, all ancestors, or the depth of any node becomes one indexed lookup, at the cost of more rows and more work when the tree changes. Two other designs are worth knowing by name: the materialised path stores '/1/2/3/' on each row and finds a subtree with a prefix search, and nested sets store left and right numbers that make subtree reads fast and every insert expensive.

Both tree designs return the same subtree. The closure table pays for it in storage, 18 path rows for 7 categories, because every node is also paired with itself and with each of its ancestors. In return, its subtree query has no recursion, and its (ancestor, descendant) primary key is an index the planner can use directly. Choose by the workload: an adjacency list for trees that change often and are read a level at a time, a closure table or materialised path for trees read whole far more often than they change.

Money

The last lines of the example are the reason money is never a binary float. A float stores most decimal fractions as the nearest binary fraction, so a running total of 1,000 prices of 19.99 drifts off by a few billionths. Rounding 2.675 to two places gives 2.67, because 2.675 is actually stored as 2.67499999.... Each error is tiny, and an accounting system that is off by a cent in a few thousand invoices fails its audit anyway. Store money either as an integer number of the currency's minor unit (cents, pence) or as an exact DECIMAL(19, 4). Always store the currency next to the amount, and decide explicitly where rounding happens, because tax and currency conversion force it somewhere.

Things that are several kinds of thing

A payment might be a card payment, a bank transfer or a voucher, each with its own fields. Single-table inheritance puts them all in one table with a type column and nullable columns for every kind: simple to query, but the database can't enforce that a card payment has a card number. Class-table inheritance keeps the shared columns in a payments table and each kind's columns in its own table, keyed by the payment id: the constraints work, at the cost of a join. The design to avoid is the polymorphic foreign key, a pair like (commentable_type, commentable_id) that might point at a post or a photo. It can't be a real foreign key, so the database can no longer guarantee that the thing it points at exists. Where you need that shape, use one nullable foreign key column per target, with a CHECK that exactly one is set.

Time and history

Store timestamps in UTC, as a timestamp type rather than text, and convert to local time only for display. Daylight-saving shifts make local times ambiguous for one hour every autumn. When you need history, don't overwrite and hope: give the row valid_from and valid_to columns so you can ask what was true on a given date, or append changes to an event or audit table so you can ask what happened. Soft deletes, a deleted_at column instead of a real delete, preserve history but cost more than they look. Every query must remember to filter them, and unique constraints break, because the deleted row still holds the email a new user wants (exercise 3.3).

Semi-structured data

Modern relational databases store JSON well, and a JSON column is the right home for data whose shape genuinely varies: a webhook payload you keep for debugging, product attributes that differ by category, user preferences. It's the wrong home for data you filter, join or constrain, because the schema can no longer enforce types, keys or references inside it, and indexing it takes expression indexes you must remember to create. A useful rule: any field you query by gets promoted to a real column.

Common traps
  • Polymorphic foreign keys, which give up referential integrity for convenience.
  • Money as a float, or an amount stored without its currency.
  • Local timestamps, ambiguous for an hour every year and wrong across time zones.
  • Soft deletes everywhere, with queries that forget the filter and unique constraints that block re-registration.
  • JSON as an escape from design: fields you filter on, hidden where the schema can't check them.
Exercises
Exercise 3.1Pick a tree design

Choose a design for each and say why: (a) comment threads, read whole on every page view and almost never moved; (b) an org chart that is reorganised every quarter; (c) a file system whose most common query is "everything under this folder".

Show solution
  1. A closure table or materialised path. Reads dominate overwhelmingly and moves are rare, so pay at write time to make "the whole thread" one indexed query.
  2. An adjacency list. Moving a team is one parent_id update; in a closure table it means deleting and reinserting every path through the moved subtree. The recursive query for a subtree is fine at org-chart sizes.
  3. A materialised path such as /home/ana/projects/. "Everything under this folder" becomes a prefix search that a normal B-tree index serves directly, and the path is also what users see. Renaming a folder rewrites the paths beneath it, an acceptable cost for a rare operation.
Exercise 3.2What did it cost on March 3rd?

Prices change over time, and support needs to answer "what was this product's price on a given date". Design the table and the query, and say how to stop two prices being valid at the same moment.

Show solution

Use product_prices(product_id, price_cents, currency, valid_from, valid_to), with valid_to NULL for the current price, and treat the range as half-open, [valid_from, valid_to), so that consecutive prices meet without overlapping. The query is WHERE product_id = ? AND valid_from <= :d AND (valid_to IS NULL OR valid_to > :d), served by an index on (product_id, valid_from). To prevent overlaps, PostgreSQL can enforce it with an exclusion constraint on a range column (EXCLUDE USING gist (product_id WITH =, valid_period WITH &&)). Elsewhere, change prices only through one transaction that closes the old row and opens the new one, with a uniqueness rule such as one open row per product.

Exercise 3.3Soft deletes and unique emails

Users are soft-deleted with deleted_at, and email is UNIQUE. A deleted user's email can now never be registered again. Fix it without dropping the uniqueness rule.

Show solution

Make the uniqueness apply only to live rows, with a partial unique index: CREATE UNIQUE INDEX users_live_email ON users(email) WHERE deleted_at IS NULL, supported by PostgreSQL and SQLite. Any number of deleted rows may share an email, but only one live row can hold it. In MySQL, which lacks partial indexes, the usual workaround is a generated column that is the email for live rows and NULL for deleted ones, made unique. The broader lesson: before adopting soft deletes, list the constraints and queries that will need to know about them, and consider moving deleted rows to an archive table instead.

Checklist
  • Did you choose a tree design by its read and write pattern?
  • Is money stored as integer minor units or exact decimals, with its currency?
  • Are timestamps UTC, stored as timestamps?
  • Does every reference to another row use a real foreign key?
  • Are fields you query by real columns rather than keys inside JSON?

Chapter 04

Objects meet tables: ORMs and the N+1 query

7 min read3 exercises4 flashcards

An object-relational mapper turns rows into objects and saves you hundreds of lines of plumbing, but it hides the one number you most need to see: how many queries your code sends. Use the ORM for the many simple reads and writes it handles well, count queries the way you'd assert on any other output, and write SQL where the object model and the relational model disagree.

Two models of the same data

Your code thinks in objects: an author has a list of books, you follow references from one object to the next, and identity means "the same object in memory". The database thinks in relations: sets of rows, related by matching values, combined by joins, where identity means "the same key". The gap between the two is called the object-relational mismatch, and an ORM such as Django's, SQLAlchemy, Hibernate or ActiveRecord bridges it. It does a lot well. It maps rows to objects and back, always parameterises queries (which prevents SQL injection), tracks which objects changed and writes them in one transaction, and generates migrations. The trouble is that following a reference in object code looks free, and in an ORM it can be a network round trip.

All three functions produce the same page. The lazy version sends 101 queries: one for the authors, then one for each author's books the moment the loop touches a.books. This is the N+1 query problem, and it is invisible in the code, because a.books reads like an attribute. Each query is fast, so it doesn't show up in a profiler either. What shows up is the page: at one millisecond per round trip to a database on another machine, the round trips alone cost a tenth of a second, and on a page with a thousand rows, a full second.

The fixes

There are two good fixes, and the example shows both. A join fetches parents and children in one query. For a count, as here, it's exact and minimal. The ORM's eager loading (select_related in Django, joinedload in SQLAlchemy) does the same for related objects. Prefetching fetches all the parents, then all their children in one IN (...) query, and stitches them together in memory: two queries regardless of N (prefetch_related, selectinload). Prefetching is often the better default for one-to-many relations, because a join repeats each parent's columns on every child row, and joining two collections at once multiplies them (exercise 4.2). Services built on GraphQL get the same effect from a batching loader that collects every id requested in one tick and fetches them together.

Other things the ORM hides

N+1 is the famous one, but not the only one. Loading full objects to change one field reads every column and writes them all back. Iterating over a query that returns a million rows can load them all into memory before the first iteration. Transaction boundaries are set by the framework's defaults, often one per request or one per statement, rather than by what the business operation needs. And the ORM writes whatever SQL its query builder produces, which may wrap an indexed column in a function and quietly defeat the index (chapter 8). None of this means avoiding ORMs. It means looking at the SQL they generate, which every ORM can log, and treating the number of queries per request as a quantity to test.

Write SQL directly where the relational model is the natural one: reports and aggregates, bulk updates (UPDATE ... WHERE touching a million rows should be one statement, not a million objects), window functions, and anything performance-critical you want to read in an EXPLAIN. Most ORMs make raw SQL easy and still map the results.

Common traps
  • Lazy loading inside loops, especially in templates, where the query is invisible.
  • Joining several collections at once, multiplying rows into a cartesian product.
  • Loading whole objects for bulk changes instead of one set-based UPDATE.
  • Never looking at the generated SQL, so the missing index or the wrapped column goes unnoticed.
  • Framework-default transactions standing in for the boundaries the business logic needs.

Exercise 4.1Count the queries

An order list page shows 50 orders. For each it prints order.customer.name and len(order.items), with lazy loading for both relations. How many queries does it send, and how do you get it down to a constant?

Show solution

One query for the orders, plus 50 for customers and 50 for items: 101 queries, or 2N+1. Make it constant by loading customer eagerly with a join (each order has exactly one customer, so the join adds columns without multiplying rows) and prefetching items with one IN query, for three queries total whatever the page size. If the page only needs the item count, as here, better still is to ask for COUNT(*) grouped by order in the same query and never load item objects at all.

Exercise 4.2When the join is worse

An author has on average 10 books and 20 reviews. Why does eagerly loading both relations with joins in one query go badly, and what should you do instead?

Show solution

Joining author to books and author to reviews in one query produces every combination of a book and a review for each author: about 10 × 20 = 200 rows per author instead of 30, each repeating the author's columns. With a hundred authors that's 20,000 rows to send and de-duplicate in memory. Load each collection with its own query instead, which is what prefetching does: one query for authors, one IN query for their books, one for their reviews. Three queries, 3,100 rows, no multiplication.

Exercise 4.3Catch it in CI

Design a test that fails when someone reintroduces an N+1 query into the order list page.

Show solution

Most frameworks provide the counter: Django's assertNumQueries, SQLAlchemy event listeners on before_cursor_execute, Rails' notifications. The key detail is to run the test with enough rows that N+1 can't hide, say 20 orders rather than 1, because with one order, 2N+1 and a constant 3 are the same number. Assert queries <= 3, so the test fails the day someone touches a lazy relation inside the loop.

Chapter 05

Pages, records and the buffer pool

9 min read3 exercises4 flashcards

A database doesn't read rows; it reads pages. Every table and index is a file cut into fixed-size pages, usually 4 to 16 KB, and the cost of almost any query is the number of pages it has to bring into memory. Inside each page, a slotted layout fits variable-length rows; above them, the buffer pool decides which pages stay in memory and which go back to disk.

Why pages

Storage hardware doesn't hand out single bytes. Disks and SSDs transfer blocks, the operating system caches pages, and a read of one byte costs the same as a read of the four or eight kilobytes around it. So databases organise everything in pages of a fixed size they choose: 4 KB by default in SQLite, 8 KB in PostgreSQL, 16 KB in MySQL's InnoDB. A table is a file of pages holding rows; an index is a file of pages holding keys. When a query needs a row, the database works out which page holds it, reads that page if it isn't already in memory, and looks inside.

Rows are placed in pages one of two ways. In a heap, PostgreSQL's default, rows go wherever there is room, in no particular order, and every index points at a row's physical location. In a clustered layout, InnoDB's primary key and SQLite's rowid tables, the rows themselves live in the leaves of the primary key's B-tree, sorted by key. Chapter 6 shows why that difference matters for lookups.

Inside a page

Rows vary in length, and the database needs to find any one of them quickly and move them around without breaking the indexes that point at them. The standard answer is the slotted page. A small header records how many slots exist and where free space ends. A slot directory grows forward from the front of the page, one fixed-size entry per row holding that row's offset and length. The rows themselves are packed backwards from the end. Free space is the gap in the middle, and the page is full when the two meet.

Thirty-nine records of 100 bytes fill the page, with 36 bytes too few for a fortieth. Deleting every other record frees nothing: a delete only zeroes the slot's length, leaving the bytes where they were, because moving data on every delete would be expensive. The space comes back when the page is compacted, all at once, and 2,036 bytes reappear. The slot numbers survive compaction, so a record's id, its page and slot, stays valid. PostgreSQL calls that id the ctid, and every index entry stores one. A value too large for a page goes to separate overflow pages, which PostgreSQL calls TOAST, and the page keeps a pointer.

The buffer pool

The buffer pool is the database's own page cache: a large region of memory divided into page-sized frames. Every page access goes through it. A hit costs a memory read; a miss costs a disk read, which is roughly a thousand times slower on an SSD and a hundred thousand times slower on a spinning disk. Changed pages are marked dirty and written back later (chapter 15 explains why that's safe). When the pool is full, a page has to be evicted, and which one is the whole game. The natural choice, least recently used, has a famous weakness.

Eighty hot pages, the indexes and busy tables the application touches constantly, sit comfortably in a 100-page pool. Then one report scans a 10,000-page table. Under plain LRU, each scanned page is the most recently used, so the scan pushes every hot page out. Afterwards, the next thousand ordinary lookups need 80 disk reads to warm the cache back up. That is sequential flooding, and it explains the classic complaint that "the app is slow every morning after the overnight report". With a scan ring, large sequential scans recycle a handful of private buffers and leave the shared cache alone. PostgreSQL does exactly this for big sequential scans; InnoDB instead inserts new pages at the midpoint of its LRU list, so a page must be touched twice before it can push out the hot ones.

What this means for your schema and queries

Because pages are the unit of cost, row width matters. A table of 200-byte rows fits about forty rows in an 8 KB page; at 2,000 bytes, four. The same million-row scan reads ten times as many pages. Keep large, rarely read columns in a separate table or let the database move them out of line, select only the columns you need, and size the buffer pool so the working set, the pages your hot queries touch, fits in memory. A database whose working set fits in RAM behaves like a different machine from one whose working set doesn't.

Common traps
  • Thinking in rows instead of pages when estimating what a query costs.
  • Wide rows, with large text or JSON stored inline, so fewer rows fit per page and every scan reads more.
  • Expecting deletes to shrink files. The space is reused by later inserts but returned to the operating system only by a rewrite (VACUUM FULL, OPTIMIZE TABLE, SQLite's VACUUM).
  • Running big reports on the primary, flooding the cache the application depends on.
  • Benchmarking with a warm cache and promising production numbers from a cold one, or the reverse.

Exercise 5.1Rows per page

A table has 10 million rows and 8 KB pages. Roughly how many pages, and how many gigabytes, does a full scan read if rows are 200 bytes? If they're 2,000 bytes?

Show solution

At 200 bytes, about 40 rows fit per page after headers and slots, so 10 million rows take about 250,000 pages, roughly 2 GB. At 2,000 bytes only 4 rows fit, so it's 2.5 million pages, about 20 GB, and the scan reads ten times as much. If the wide column is a description that most queries never read, moving it to a separate table keyed by the row's id makes the common scans ten times cheaper, and only the queries that need the description pay for the extra join.

Exercise 5.2Where did the space go?

You delete half the rows of a 50 GB table, and the file is still 50 GB. Explain why, and what would make it smaller.

Show solution

As in the example, a delete marks space as free inside each page without moving anything; in PostgreSQL the dead rows also stay until VACUUM confirms no transaction can still see them (chapter 14). The free space is reused by later inserts, so the file stops growing, but it doesn't shrink, because returning space to the operating system means moving every live row so the empty pages end up at the end of the file. Tools that rewrite the table do that: VACUUM FULL or pg_repack in PostgreSQL, OPTIMIZE TABLE in MySQL, VACUUM in SQLite. Most of them need extra space and lock or slow the table while they run. Often the right answer is to leave the space for future growth.

Exercise 5.3Slow every morning

Every morning from 06:00 to about 06:20, the application's queries are three times slower than usual. A nightly export finishes at 05:58. What's happening, and what are three fixes?

Show solution

The export scans large tables, and the pages it reads evict the hot working set from the buffer pool and the operating system's cache. For the next twenty minutes, ordinary queries miss and go to disk until the cache warms up again. Fixes: run the export against a read replica, so the primary's cache is never touched (the usual answer); make sure the engine treats the scan as a scan, using ring buffers or midpoint insertion as in the example, and avoid scan patterns that defeat them; and pre-warm the hot pages after the export (PostgreSQL's pg_prewarm). Checking the buffer cache hit ratio over time would confirm the diagnosis before you change anything.

Chapter 06

B-trees

8 min read3 exercises4 flashcards

The B-tree is why a database can find one row among a billion by reading four pages. It is a search tree designed for disks: each node is a whole page holding hundreds of keys, so the tree is wide and shallow. It stays balanced by splitting full nodes upwards, and its leaves are chained together so a range query reads sideways instead of climbing back up.

Wide and shallow

A binary search tree over a billion keys is about 30 levels deep, and if every level is a separate disk read, a lookup costs 30 reads. A B-tree puts as many keys in a node as fit in a page. With 8-byte keys and 8 KB pages, that's around 500 children per node, so each level multiplies the reach by 500: 500 rows at one level, 250,000 at two, 125 million at three, 60 billion at four. Better still, the root and the next level are touched by every lookup, so they stay in the buffer pool permanently. In practice a lookup in a huge table costs one or two real disk reads.

Search, insert and split

A search starts at the root, picks the child whose range contains the key, and repeats until it reaches a leaf. An insert finds the leaf the key belongs in and adds it. If the leaf overflows, it splits in two and a separator key goes up to the parent; if the parent overflows, it splits too. When the root splits, a new root is created above it, so the tree only ever grows at the top and every leaf stays at the same depth. That is what keeps a B-tree balanced without any rebalancing pass.

The small tree shows the shape after ten sequential inserts: a root of separators over four leaves. It also shows a real-world quirk. Because each new key was larger than everything before it, the splits always happened at the right edge, leaving half-full leaves behind and a full one at the end. Real engines detect ascending inserts and split unevenly so that pages stay full. Random keys are worse: they land in a random leaf, so they cause splits everywhere, leave pages around 70% full, and touch a different page on every insert. That's why random UUIDs make poor clustered primary keys, and why time-ordered ids such as UUIDv7 or ULIDs exist.

The large tree holds 100,000 random keys in just three levels, with 1,458 splits along the way, and every lookup visits exactly three nodes. The range scan finds its first leaf with one descent, then walks the leaf chain, returning 6,021 keys already in order. That chain is why ORDER BY on an indexed column can cost nothing: the index is already sorted. The capacity lines are the arithmetic that matters. With 8-byte keys, a billion rows need four levels; wider keys mean fewer per page and an extra level.

Clustered and secondary indexes

Databases use the B+tree variant shown here, where inner nodes hold only separators and the data lives in the leaves. What a leaf holds depends on the index. In a clustered index, the leaf holds the row itself: InnoDB stores every table this way, ordered by primary key, and SQLite does the same by rowid. A secondary index leaf holds the indexed value plus a way to find the row. In PostgreSQL that's the row's physical location, the ctid from chapter 5. In InnoDB it's the primary key, so a secondary lookup is two descents, one through the secondary index and one through the clustered one. That design keeps secondary indexes valid when rows move, at the cost of the second descent.

Every index costs writes. An insert adds an entry to every index on the table, and an update to an indexed column deletes the old entry and inserts a new one. Deleted entries leave space that is reused later rather than immediately, so heavily churned indexes grow larger than their contents. The right number of indexes is the smallest number that serves your queries, which chapter 8 makes precise.

Common traps
  • Random UUIDs as clustered keys, scattering every insert across the tree.
  • Long composite or text keys that cut the fanout and add a level to every lookup.
  • Indexes nobody queries, each adding write cost to every insert and update.
  • Forgetting the second lookup behind every secondary-index read, which a covering index avoids (chapter 8).
  • Assuming deletes shrink an index; heavy churn calls for an occasional rebuild.

Exercise 6.1How many reads?

A table has 50 million rows with an 8-byte primary key and 8 KB pages. How many levels does its B-tree have, and how many disk reads does a primary-key lookup cost with a cold cache, and with a warm one?

Show solution

With a fanout of about 500 at 70% fill (an effective 350), three levels reach 3503 ≈ 43 million, just short, so it takes four levels, though the root will hold only a couple of keys. With a cold cache, a lookup reads one page per level: four reads. With a warm cache, the root and the second level (a few hundred pages) are permanently in memory, and often the third level too, so a lookup costs one or two disk reads: the leaf, and perhaps its parent. That's why a primary-key lookup in a table of tens of millions of rows takes well under a millisecond on an SSD.

Exercise 6.2The UUID slowdown

A team switches InnoDB primary keys from auto-increment integers to random UUIDv4, and insert throughput drops sharply once the table outgrows memory. Explain why, using the example's observations.

Show solution

With increasing integers, every insert goes to the rightmost leaf, which is always in the buffer pool. Splits happen only at the edge, and pages fill completely. With random UUIDs, each insert lands in a random leaf. Once the table is larger than memory, that leaf usually isn't cached, so every insert costs a disk read before it can write. Splits happen all over the tree, leaving pages around 70% full, so the table and every secondary index (which store the primary key in InnoDB) grow larger and the cache holds a smaller fraction of them. Time-ordered identifiers (UUIDv7, ULID, or an integer with a separate public UUID column) keep the global uniqueness and restore the sequential insert pattern.

Exercise 6.3A range of ten thousand rows

SELECT * FROM events WHERE created_at BETWEEN :a AND :b returns 10,000 rows using a secondary index on created_at. Describe the reads, and explain why the same query can be ten times faster with a different index.

Show solution

One descent finds the leaf holding :a, and the scan follows the leaf chain until it passes :b. With hundreds of entries per leaf, that's a few dozen leaf pages. But each entry only points at its row, so fetching the rows means 10,000 lookups into the table, scattered randomly across perhaps thousands of pages: that's where the time goes. If the query only needs a few columns, an index that includes them all (a covering index, chapter 8) answers it from the leaves alone. Alternatively, if events is clustered by created_at, the rows are stored in that order and the range becomes a few consecutive pages. Either way the random fetches disappear.

Chapter 07

LSM trees and the price of fast writes

8 min read3 exercises4 flashcards

A B-tree updates data in place, which means random writes to pages all over the disk. A log-structured merge tree never updates anything: it collects writes in memory, flushes them as sorted, immutable runs, and merges the runs in the background. Writes become fast and sequential. The cost moves elsewhere, into compaction work and into reads that may have to look in several places, and every LSM design is a choice about where to pay it.

Writes go to memory first

In an LSM tree, a write is appended to a log for durability (the same idea as chapter 15) and inserted into the memtable, a sorted structure in memory. Nothing on disk is touched. When the memtable fills, it is written out in one sequential pass as a sorted, immutable file, usually called an SSTable (sorted string table), and a fresh memtable takes its place. Updates and deletes are writes too: an update is just a newer value for the key, and a delete writes a marker called a tombstone. Old values aren't removed; they're shadowed by newer ones.

Reads look everywhere a key could be

A read checks the memtable, then each run from newest to oldest, and stops at the first version it finds, which is by construction the newest. A tombstone means the key was deleted. Each run is sorted, so finding a key within one is a binary search over a small index of its pages. The problem is the number of runs: a key that was never written, or was written long ago, means checking every run. Two tools keep this under control. Bloom filters, one per run, answer "definitely not here" for most runs a key isn't in, using about ten bits per key. Compaction merges runs so there are fewer of them to check.

The table holds the whole trade-off in three rows. Without compaction, writes are as cheap as they can be: each entry is written to disk exactly once, a write amplification of 1.0. But all 20,000 versions of 5,000 keys stay on disk, a space amplification of 4.0, and reads are dreadful: finding a present key checks 48 runs on average, and proving a key absent checks all 198. Bloom filters rescue the reads without changing anything else, down to 1.4 and 2.0 runs. Compaction rescues the space too, down to 1.0, with about one run read per lookup, but it pays by rewriting live data again and again: every entry was written 13.4 times. This is the RUM conjecture in miniature: you can optimise for reads, updates or memory (space), and improving one costs at least one of the others.

Compaction strategies

Real systems compact more cleverly than "merge everything at four runs", but they choose between the same costs. Size-tiered compaction, Cassandra's long-time default, merges runs of similar size: it rewrites data fewer times, but may hold several versions of a key for a while, and needs free disk space as large as the runs being merged. Leveled compaction, used by LevelDB and RocksDB, keeps data in levels that each grow about ten times larger, with no overlapping keys within a level. Space and read costs stay tightly bounded, and data gets rewritten more often. Tombstones are their own hazard. A tombstone can only be dropped once compaction reaches the oldest run that might hold the key, so a workload that deletes heavily can leave reads wading through tombstones in the meantime.

B-tree or LSM tree?

B-trees suit read-heavy workloads that want predictable latency: every read is a fixed number of page reads, and no background process competes for the disk. LSM trees suit write-heavy workloads: event logs, metrics, messaging, anything that ingests far more than it updates. They also compress well, because runs are immutable and sorted, and they write sequentially. They power RocksDB (and through it MyRocks, CockroachDB's Pebble and TiKV), Cassandra, ScyllaDB and most time-series stores. Discord stores its message history this way: it moved it to Cassandra in 2017 and to ScyllaDB in 2023. B-trees have write amplification too, which is easy to forget: changing 100 bytes rewrites an 8 KB page, and if the change touches five indexes, five pages.

Common traps
  • Benchmarking before compaction reaches a steady state, measuring cheap writes and ignoring the debt they create.
  • Running out of disk during compaction, which writes the new run before deleting the old ones.
  • Delete-heavy workloads that leave reads scanning past piles of tombstones.
  • Long range scans across many runs, which can't use Bloom filters and must merge every run.
  • Write stalls: when compaction falls behind, LSM engines deliberately slow or stop writes.

Exercise 7.1The worst lookup

Why is looking up a key that doesn't exist the worst case for an LSM tree, and what exactly do Bloom filters change? Use the example's numbers.

Show solution

A read stops at the first run that holds the key, so a present key, especially a recently written one, is often found early. An absent key can only be proven absent by checking every run: 198 of them without compaction. A Bloom filter for each run answers "definitely not here" for almost all of those runs without reading them, with a false-positive rate of about 1% at ten bits per key, so the cost dropped from 198 run reads to 2.0. Exercise 7.2Full disk, stopped writes

A Cassandra node with a disk at 70% full stops accepting writes during a large compaction. Explain how a disk at 70% can run out of space.

Show solution

Compaction writes the merged run before it can delete the runs it merged. With size-tiered compaction, merging the four largest runs, which may together be most of the node's data, needs free space roughly equal to their total size while both copies exist. At 70% full, a compaction over runs totalling more than the remaining 30% runs out of disk midway; the node can neither finish compaction nor accept more writes. That's why size-tiered deployments keep up to half the disk free, and why leveled compaction, which merges small pieces at a time, needs far less headroom.

Exercise 7.3Choose the structure

Choose a B-tree engine or an LSM engine for each, and say why: (a) sensor readings at 200,000 writes a second, queried by device and recent time range; (b) a bank ledger read ten times more often than it's written, with strict latency targets; (c) a chat application's message history.

Show solution
  1. LSM. Ingest dominates, writes arrive roughly in time order (which compacts cheaply), old data is rarely updated, and immutable sorted runs compress repetitive readings well.
  2. B-tree. Reads dominate and must be predictable. A B-tree reads a fixed number of pages and has no compaction competing for disk at unpredictable moments. A relational engine also gives the ledger the transactions and constraints it needs.
  3. Usually LSM. Messages are written constantly, almost never edited, and read in recent-first ranges per channel, which is why Discord runs on Cassandra and ScyllaDB. A B-tree engine also works at moderate scale, and many products start there; the switch becomes worthwhile when write volume makes page-level random writes the bottleneck.

  • Would you choose an LSM or a B-tree engine for your workload, and why?

Chapter 08

Indexes the planner will use

9 min read3 exercises4 flashcards

An index only helps a query that can use it, and whether it can is decided by a few mechanical rules: the column must appear bare, not inside a function; the index's leading columns must be constrained; and equality columns must come before range columns. Learn the rules, check every important query's plan, and keep the fewest indexes that serve your real queries.

Reading the plan

Every database will tell you how it intends to run a query. SQLite's EXPLAIN QUERY PLAN prints one line per step; PostgreSQL and MySQL's EXPLAIN print a tree, and their EXPLAIN ANALYZE actually runs the query and adds real row counts and timings to each step. The words to look for are few. A scan reads a whole table or index (SCAN in SQLite, Seq Scan in PostgreSQL). A search descends an index to the matching entries (SEARCH ... USING INDEX, Index Scan). A covering or index-only scan answers from the index without touching the table at all. The example below runs four index lessons against SQLite's real planner, on a 200,000-row orders table, and measures the work as the number of instructions SQLite's engine executes, a count that comes out identical on every run.

Rule 1: an index turns a scan into a search

Without an index, finding one customer's orders means reading all 200,000 rows: 600,070 steps. With one, it's a descent and a few entries: 120 steps, five thousand times less work. That ratio grows with the table, because a scan is linear and a B-tree descent is logarithmic.

Rule 2: equality columns first, then range

A composite index is sorted by its first column, then by its second within equal first values, like a phone book sorted by surname, then first name. That ordering decides what the index can find. With (status, created_at), all the 'pending' entries sit together, sorted by date, so "pending since September" is one contiguous slice: 3,730 steps. With (created_at, status), the index can only use the date range, and must read every entry from September 1st onwards, of every status, checking each one: 29,800 steps for the same answer. The general rule: put columns compared with = first and the one range column last. An index on (a, b, c) serves queries on a, on a and b, and on all three, but not on b alone. This is the leftmost prefix rule.

Rule 3: keep the column bare

An index on created_at is sorted by created_at, not by substr(created_at, 1, 7). Wrap the column in a function and the planner has no ordering to search, so it falls back to reading every entry and computing the function for each: 818,630 steps. The same rows, asked for as a range on the bare column, cost 37,250. This catches out WHERE date(created_at) = ..., WHERE lower(email) = ..., WHERE total_cents / 100 > 50, and implicit conversions, such as comparing a text column to a number. Rewrite the condition so the bare column is compared to a value, or, when you genuinely query by the expression, index the expression itself: CREATE INDEX ON users(lower(email)).

Rule 4: a covering index never touches the table

An ordinary index finds the matching entries and then fetches each row from the table to get the other columns: one more lookup per row, often to a random page. If the index contains every column the query uses, the plan says COVERING INDEX (PostgreSQL: Index Only Scan) and the table is never read. The instruction count can't show the saving, because each table lookup is a single instruction however many pages it reads, so chapter 11 measures it with a stopwatch instead. On a million rows, making the index covering cut the report from 31.3 ms to 3.1. PostgreSQL lets you add columns to an index purely for covering, without sorting by them: CREATE INDEX ON orders(customer_id) INCLUDE (total_cents).

Selectivity, and what indexes cost

An index pays off when it narrows the rows to a small fraction. An index on status, where 85% of rows are 'shipped', narrows almost nothing, and following it to 170,000 scattered rows is slower than reading the table in order: chapter 11 shows exactly that. If a small subset is what you query, a partial index indexes just that subset: CREATE INDEX ON orders(created_at) WHERE status = 'pending'. And every index has a price: space, cache, and work on every insert and update. Find the unused ones (PostgreSQL's pg_stat_user_indexes counts scans per index) and the redundant ones, since (a) is already served by (a, b), and drop them.

Common traps
  • One index per column, instead of composite indexes shaped like your queries.
  • Range column first in a composite index, so equality conditions after it can't narrow the search.
  • Functions and implicit casts on the indexed column, silently turning a search into a scan.
  • Leading wildcards such as LIKE '%son', which no ordinary B-tree index can serve.
  • Low-selectivity indexes that the planner may use and regret.

Exercise 8.1Design the index

A multi-tenant app's busiest query is WHERE tenant_id = ? AND created_at > ? ORDER BY created_at LIMIT 50. Which index serves it best, and why not (created_at, tenant_id)?

(tenant_id, created_at). The equality column comes first, so one tenant's entries are contiguous and sorted by date; the range then selects a slice of them, already in the order the query wants, so ORDER BY ... LIMIT 50 reads 50 entries and stops, with no sort. With (created_at, tenant_id), the index can only use the date range, so it reads every tenant's rows after that date, checking each one's tenant. For a big tenant that may work out fine; for a small tenant in a busy system it reads thousands of entries to find fifty.

Exercise 8.2Make it sargable

Rewrite each condition so an ordinary index on the column can be used: (a) date(created_at) = '2026-09-14'; (b) total_cents / 100 > 50; (c) lower(email) = 'ana@example.com'.

Show solution
  1. created_at >= '2026-09-14' AND created_at < '2026-09-15': a half-open range on the bare column.
  2. total_cents > 5000: move the arithmetic to the constant side.
  3. This one can't be rewritten on the bare column, because case-insensitive matching genuinely depends on the expression. Either store a normalised copy (lower-case the email on write) or create an expression index, CREATE INDEX ON users(lower(email)), which the planner uses when the query's expression matches the index's exactly.
Exercise 8.3Prune the indexes

A table has indexes on (a), (a, b), (b) and (a, b, c). The queries are WHERE a = ?, WHERE a = ? AND b = ?, WHERE b = ?, and WHERE a = ? AND b = ? AND c > ?. Which indexes can you drop?

Show solution

Drop (a) and (a, b). By the leftmost prefix rule, (a, b, c) serves a = ?, a = ? AND b = ? and the full query, so both shorter indexes are redundant. Keep (b), because no index starting with a can serve a query constraining only b. That's two indexes instead of four, which halves the index maintenance on every write. The one caveat: a narrower index is slightly smaller and faster to scan, which matters only if a query reads a large share of it.

  • Do composite indexes put equality columns before the range column?

Chapter 09

How a query executes: operators and joins

8 min read3 exercises4 flashcards

A plan is a tree of operators, each doing one simple job: scan, filter, join, sort, aggregate. Rows flow up the tree one at a time, so a query can start returning results before it has read everything, unless some operator has to see all of its input first. And for every join, the algorithm the planner picks is often the biggest single factor in what the query costs.

The iterator model

Most databases execute a plan with the iterator or Volcano model, named after the research system that formalised it. Every operator has the same three methods: open, next and close. Calling next() on the top operator makes it call next() on its children until it has a row to return. A filter pulls rows from the scan below until one passes; a projection pulls one row and trims its columns. Rows stream upwards, one at a time, through the whole tree, without the intermediate results ever being stored. This is pipelining, and it's why LIMIT 10 can return after reading a few dozen rows of a huge table.

Some operators can't pipeline. A sort can't return its first row until it has seen every row, because the last one might sort first. A hash join must read its whole build side before it can probe it, and a grouping aggregate must see every row of a group. These blocking operators break the stream: everything below them runs to completion first. Spotting them in a plan explains most "why didn't LIMIT help?" mysteries.

Four ways to join

A join combines rows from two inputs where a condition holds, and there are four basic algorithms. A nested loop compares every row of one input with every row of the other: simple, and fine when one side has a handful of rows. An index nested loop looks each outer row's key up in an index on the inner side; it's the workhorse of transactional queries, where the outer side is small and the inner side is indexed. A hash join builds a hash table on the smaller input and streams the larger one past it; it suits large inputs with no useful index, works only for equality conditions, and needs memory for the table. A sort-merge join sorts both inputs on the key and walks them together once; it's cheapest when both inputs already arrive sorted, from an index for instance, and it also handles range conditions.

All four produce the same 20,000 rows; the work differs by a factor of a thousand. The plain nested loop does 20 million comparisons, one for every pair. The index nested loop needs about ten binary-search steps per order, 199,578 in all. The sort-merge join spends most of its 277,244 units sorting, and would be nearly free if both inputs arrived sorted. The hash join wins at 21,000: one pass to build a table of 1,000 customers, one pass to stream 20,000 orders past it. The last two lines show the iterator model at work. LIMIT 10 over a filter read just 77 rows before it had its ten and stopped pulling. Add ORDER BY, and the sort, a blocking operator, read all 20,000 first.

Which join, and who decides

The planner chooses the algorithm for each join, along with the order in which tables are joined, from its estimates of how many rows each side will produce (chapter 10). Engines differ in what they offer. PostgreSQL and SQL Server implement all of them. MySQL relied on nested loops until it added hash joins in version 8.0.18. SQLite implements only nested loops, and when no index fits, it builds a temporary one just for the query, which its plans report as an automatic index. In PostgreSQL plans, look for Nested Loop, Hash Join with a Hash node beneath it, and Merge Join, usually above a Sort. A hash join whose build side exceeds its memory budget (work_mem) spills to disk in batches and slows sharply; EXPLAIN ANALYZE reports the batch count.

Common traps
  • Assuming tables are joined in the order you wrote them. The planner reorders joins freely.
  • No index on a foreign key column, so every join from the parent becomes a scan of the child.
  • ORDER BY ... LIMIT without a supporting index, which forces a full blocking sort.
  • Joining on expressions or mismatched types, which hides the indexes on both sides.
  • Hash joins spilling to disk because the memory budget is smaller than the build side.

Exercise 9.1Pick the algorithm

Which join algorithm fits each case? (a) one customer's 5 orders joined to products, which has a primary-key index; (b) a nightly report joining two 50-million-row tables on customer_id, neither sorted; (c) two inputs that both arrive sorted by date from index scans, joined on date.

Exercise 9.2The slow LIMIT

The index already holds rows in total order, so the planner reads it backwards from the highest value, filters as it goes, and stops after ten: the sort disappears from the plan and the query pipelines again.

Exercise 9.3Count the work

That's the same ratio the example shows between its nested loop and its index nested loop, and why a missing index on a join column is the most common cause of a query that "suddenly" got slow as a table grew.

Chapter 10

The planner and its statistics

8 min read3 exercises4 flashcards

The planner chooses between plans by estimating how many rows each step will produce and what each step will cost. It can't run the query to find out, so it estimates from statistics: row counts, distinct values, the most common values, histograms. When a plan is bad, the estimate behind it is almost always wrong, and the fix is usually better statistics, not a hint that overrules the planner.

Cost-based optimisation

For any non-trivial query there are many correct plans: which index to use for each table, which order to join the tables in, which algorithm for each join. A cost-based optimiser, an idea that dates back to IBM's System R in the 1970s, enumerates candidate plans, estimates each one's cost with a model that charges for page reads and CPU work, and picks the cheapest. The search space grows explosively with the number of tables, so planners use dynamic programming for small joins and heuristics beyond that; PostgreSQL switches to a genetic search above twelve tables. All of this rests on one input that's easy to forget: the estimated number of rows flowing out of each step. Get that wrong and the cheapest-looking plan can be the slowest.

What the planner knows

Statistics are gathered by ANALYZE, run manually or by a background process (PostgreSQL's autovacuum, MySQL's persistent statistics). For each table they record the row count. For each column, typically: the fraction of NULLs, the number of distinct values, a list of the most common values with their frequencies, and a histogram of the rest. To estimate WHERE country = 'US', the planner checks the common-values list; to estimate a range, it reads the histogram. For combinations of conditions, it usually assumes they're independent and multiplies their selectivities. Each of those steps can go wrong.

The first case is skew. Seventy percent of customers are in one country, but a planner that only knows the number of distinct values assumes they're spread evenly and guesses 3,225 rows where there are 70,117, an error of more than twenty times. A most-common-values list fixes it exactly, which is why databases keep one.

The second case is correlation. Every Paris row is in country C07, so the second condition adds no filtering at all. The planner, multiplying the two selectivities as if they were independent, estimates 3 rows; there are 308. The third block shows why that matters. At 3 rows, an index nested loop costs 12 page reads and looks far cheaper than a hash join's 600, so the planner picks it. At the real 308 rows, the nested loop costs 1,232 and the hash join would have cost 631. The plan was the right choice for the wrong number, and errors like this compound: in a query with five joins, a tenfold error at the bottom can become a millionfold error at the top.

The last block is a real planner changing its mind. Without statistics, SQLite assumes an equality condition is selective and uses the index on status. After ANALYZE, it knows the index has about 33,000 rows per distinct value, so following it would mean tens of thousands of scattered row lookups, and it switches to a plain scan. Chapter 11 measures both plans and confirms the planner is right to switch.

Why estimates go wrong

Beyond skew and correlation, the usual causes are stale statistics after a bulk load or a big delete, conditions the statistics can't see into (functions, expressions, LIKE patterns, values from a subquery), and parameter sensitivity. A prepared statement may be planned once for a generic parameter and reused for a value that matches a million rows instead of ten. Joins make all of these worse, because the error in each input's estimate multiplies through every join above it.

Fixing a bad plan

Start with EXPLAIN ANALYZE and compare each step's estimated rows with its actual rows. The step where they first diverge badly is where the plan went wrong, and everything above it inherited the error. Then work through the fixes in order of how well they age. Run ANALYZE, and make it the last step of every bulk load. Raise the statistics detail for skewed columns (PostgreSQL's per-column STATISTICS target). Tell the planner about correlated columns: PostgreSQL's CREATE STATISTICS ... (dependencies) exists for exactly the Paris case. If none of that works, rewrite the query: split it, or materialise an intermediate result whose size is then known. Hints and forced indexes come last. They fix today's plan by freezing it, and they keep forcing it after the data has changed so much that it's wrong.

Common traps
  • Stale statistics after a bulk load, so the planner plans for a table a fraction of its real size.
  • Reading EXPLAIN without ANALYZE, which shows the estimates but not how wrong they are.
  • Correlated columns treated as independent, making combined conditions look far more selective than they are.
  • Generic plans for skewed parameters, fast for most values and disastrous for the big one.
  • Hints that outlive the data they were written for.

Queries filter on both country and city, which are strongly correlated, and their estimates are consistently far too low. Give two fixes.

Chapter 11

A million rows under fifty milliseconds

8 min read3 exercises4 flashcards

Tuning a query is an experiment, not an act of inspiration: measure, read the plan, change one thing, measure again, and write down what happened. This chapter does the stage's deliverable on a real million-row table, including the change that made things slower, because that's the one that teaches the most.

The method

Start with data that resembles production: the same row count, or close to it, and the same distributions. A query tuned on ten thousand evenly spread rows tells you nothing about ten million skewed ones. Measure each version several times and take the median, so one slow run doesn't mislead you, and note whether the cache was warm. Read the plan before changing anything, form a hypothesis about what it's doing badly, and change one thing. Then measure again, check the result is identical, and record the plan and the time. The record matters as much as the speed-up: it's how you explain the change in review, and how the next person learns why the index exists.

The query

The table holds a million orders spread over 21 months, 85% of them shipped. The report wants daily shipped revenue for September 2026, about 4.7% of the table. Here is the whole session, run against a real SQLite database. The output is one recorded run on a laptop; your timings will differ, but the ratios and the plans won't.

Reading the session

Step 0, 68.2 ms. With no index, the plan is a scan of all million rows followed by a temporary B-tree to group the results by day. That's not terrible for a scan, but it reads every page to use one row in twenty.

Step 1, 82.4 ms: slower. An index on status looks like the obvious move, since the query filters on it, and with no statistics the planner assumes an equality condition is selective and uses it. But 85% of rows match. Following the index means about 850,000 row lookups in index order, each landing on a scattered page, instead of one sequential pass through the table. A low-selectivity index can be worse than none, and this is what it looks like.

Step 2, 68.3 ms. ANALYZE tells the planner what step 1 found out the hard way: status barely filters. With the statistics, it abandons the index and goes back to the scan, and the time returns to the baseline. The useless index is still costing every insert and update, so the next step drops it.

Step 3, 31.3 ms. An index on created_at, the selective column, narrows the read to September's 47,000 or so rows. Two things changed in the plan. The SEARCH ... (created_at>? AND created_at<?) line shows the index is used for the range, and the temporary B-tree for grouping has disappeared: the index delivers rows already in date order, so each day's group arrives together and no sort is needed. What's left is a table lookup per row, to check status and read total_cents.

Step 4, 3.1 ms. A covering index on (status, created_at, total_cents) follows all of chapter 8's rules at once. The equality column comes first, so the shipped orders are contiguous; the range column comes second, so September's shipped orders are one slice; and the summed column is included, so the plan says COVERING INDEX and never touches the table. The answer is identical at every step, the final time is 22 times faster than the scan, and it is comfortably under the fifty-millisecond target.

Writing it down

The covering index isn't free. It is a second copy of three columns for every row, and every insert, and every update to those columns, now maintains another B-tree. Common traps
  • Tuning on a toy dataset, a thousand times smaller and evenly distributed.
  • Measuring once, so a cold cache or a background job decides the result.
  • Changing several things at once, so you can't tell which change helped and which hurt.
  • Adding an index on the column in the WHERE clause without checking how selective it is.
  • Never checking the results are identical after a rewrite.

Chapter 12

What ACID really promises

7 min read3 exercises4 flashcards

ACID names four promises a transaction makes, and they're less uniform than the acronym suggests. Atomicity and durability are the database's job, and it does them well. Isolation comes in weaker forms than its name implies (chapter 13). And consistency is mostly your job, done with constraints and with transactions drawn around the right operations.

A transaction is the unit of every promise

A transaction is a group of statements between BEGIN and COMMIT that the database treats as one indivisible unit. Every ACID promise is made per transaction, which makes it important to know where your transactions actually begin and end. Many drivers default to autocommit, where every statement is its own transaction, so a two-statement operation is two separate promises, not one. Others open transactions implicitly and leave them open until you commit, as chapter 2's foreign-key trap showed. The example runs the classic test, a transfer that dies halfway, both ways.

Atomicity: all or nothing

Case A is the bug every financial system fears. Without a transaction, the debit committed on its own and the credit never happened, so 30 left the system. Case B runs the same crash inside a transaction: the rollback undoes the debit and the books still balance. The database delivers this by recording how to undo each change until the commit. SQLite keeps a rollback journal or, in WAL mode, doesn't touch the main file until commit; PostgreSQL keeps old row versions; InnoDB writes undo records. However it's done, the promise is the same: a failed transaction leaves no trace.

Consistency: the rules the database knows

Case C is consistency as the database understands it: the transfer would have made Bob's balance negative, the CHECK constraint refused it, and the whole transaction rolled back. That's the limit of the database's version of consistency: it enforces the constraints you declared and nothing else. The rule that the total of all balances never changes in a transfer is consistency too, but no constraint expresses it. It holds only because the debit and credit are in one transaction. That's why the C in ACID is the application's responsibility, and why chapter 2 pushed so hard on declaring constraints.

Isolation, briefly

Isolation promises that concurrent transactions don't see each other's half-finished work. Fully honoured, it means they behave as if they ran one at a time, a level called serializable. Most databases default to weaker levels that are faster and allow specific anomalies, and chapter 13 shows exactly which. The savepoint in case D is a smaller tool: a named point inside a transaction you can roll back to without abandoning the whole thing, which is useful when one step of a larger operation may fail and be skipped.

Durability: committed means committed

Case E reopens the database file: the committed transfer and the savepoint result are there, because a commit isn't acknowledged until its log record is flushed to disk (chapter 15). Durability can be weakened deliberately for speed. PostgreSQL's synchronous_commit = off, MySQL's innodb_flush_log_at_trx_commit = 2 and SQLite's synchronous = NORMAL each acknowledge commits before the flush, risking the last fraction of a second of commits in a crash, without corrupting anything. Hardware can weaken it accidentally: a disk with a volatile write cache that reports a flush as done before it is. Servers use drives with power-loss protection for exactly this reason.

Drawing the boundaries

Draw a transaction around one business operation: everything that must happen together, and nothing else. Keep it short. A transaction holds locks and an old snapshot for its whole life, and a long one blocks other writers and holds back the cleanup chapter 14 describes. Above all, never make a network call to another service inside a transaction. The call may take seconds while every lock waits, and if the transaction rolls back afterwards, the other service's action can't be undone with it. Make the external call outside, with an idempotency key so a retry can't do it twice. Across services there is no ACID at all; Fleet's sagas and outbox pattern take over there.

Common traps
  • Autocommit for multi-step operations, turning one promise into several that can fail independently.
  • Calling external APIs inside a transaction, holding locks during the call and leaving actions that can't be rolled back.
  • Catching an exception and committing anyway, keeping half of the work.
  • Long or idle transactions that hold locks and old snapshots for minutes.
  • Retrying without idempotency, so a transaction that actually committed runs twice.

Exercise 12.1Draw the boundaries

A checkout inserts an order, decrements stock, charges the card through a payment API, and marks the order paid. Where should the transaction boundaries go?

Show solution

Not around all four steps, because the payment call would sit inside the transaction. Use two short transactions with the call between them. Exercise 12.2Name the letter

Which ACID property failed? (a) After a crash between two statements, the sum of all balances changed. (b) An order confirmed to the customer is missing after a power cut. (c) A report shows money that has left one account but not yet arrived in the other. (d) Stock went negative because of an application bug.

Exercise 12.3Trading durability for speed

Turning on PostgreSQL's synchronous_commit = off triples write throughput in your benchmark. What exactly can you lose, and for which data is it acceptable?

Show solution

Commits are acknowledged before their log records are flushed; the flush happens shortly afterwards in the background (within about three times wal_writer_delay, well under a second by default). If the server crashes in that window, the most recent acknowledged transactions are lost, but the database stays consistent, because no transaction is ever half-applied. That's acceptable for data you can afford to lose a second of: analytics events, view counters, logs, caches. It isn't acceptable for money, orders or anything a user was told was saved. PostgreSQL lets you set it per transaction, so you can relax it for the event stream and keep it on for payments in the same database.

  • Is every multi-step business operation inside one transaction?
  • Are transactions short, with no external calls inside them?
  • Are invariants beyond constraints protected by transaction boundaries?
  • Do you know your durability settings and what they risk?

Chapter 13

Isolation levels and their anomalies

8 min read3 exercises4 flashcards

Almost no database gives you full isolation by default. Each weaker level lets through specific anomalies, and the bugs they cause look like ordinary logic errors that only appear under load. Know which level you're running, which anomalies it allows, and which of your operations can't tolerate them.

Levels defined by what goes wrong

Serializable isolation means concurrent transactions produce the same result as running them one at a time in some order. It's the only level at which you can reason about each transaction alone. The weaker levels exist because serializability costs throughput, and the SQL standard defines them by the anomalies they forbid. Read uncommitted allows dirty reads of another transaction's uncommitted changes. Read committed forbids those, but allows a value to change between two reads in the same transaction. Repeatable read keeps such values stable, but in the standard's definition allows phantom rows to appear. A famous 1995 paper by Berenson and colleagues showed these definitions miss two anomalies that matter in practice: the lost update and write skew.

Defaults vary, and the names don't mean the same thing everywhere. PostgreSQL, Oracle and SQL Server default to read committed; MySQL's InnoDB defaults to repeatable read. PostgreSQL's repeatable read is really snapshot isolation: each transaction reads from a snapshot taken when it starts. Its serializable level adds conflict detection on top of snapshots (serializable snapshot isolation, since version 9.1). SQLite is serializable because it allows only one writer at a time. The example implements three levels in a small multi-version engine and runs the three classic scenarios against each.

The lost update

Two transactions each read a counter, add one in application code and write it back. At read committed, both read 0, both write 1, and both commit: one increment is gone and nothing reported an error. Snapshot isolation catches it, because the second transaction tries to write a row that someone else changed since its snapshot, and it aborts with an error the application can retry. Note the shape of the bug: a read, then a write computed from it. UPDATE counters SET n = n + 1 is a single atomic statement, and every common database executes it safely at read committed. The lost update lives in read-modify-write code, which is exactly what ORMs generate when you load an object, change a field and save it.

Write skew

The on-call rule says at least one doctor must stay on call. Alice and Bob both feel unwell at the same moment, and each transaction checks the rule: two doctors on call, so it's safe for me to go. Alice's transaction updates Alice's row; Bob's updates Bob's. Neither writes a row the other wrote, so snapshot isolation sees no conflict, both commit, and nobody is on call. Each transaction was correct on its own; together they broke the rule. Only serializable catches it here, by noticing that Bob's transaction read a row (Alice's) that changed before it committed.

The non-repeatable read is the mildest of the three: at read committed, a transaction that reads the price twice sees 100 and then 70, because another transaction committed in between. A report that sums one table and then another can be inconsistent this way. Snapshot isolation and serializable both read from the transaction's starting snapshot, so the price stays 100 until the transaction ends.

Defences short of serializable

You don't have to switch the whole database to serializable to be safe; you have to protect the operations that can't tolerate an anomaly. Replace read-modify-write with a single atomic statement where you can. Lock what you read with SELECT ... FOR UPDATE, so concurrent transactions queue: in the on-call case, locking both doctors' rows before checking makes the second transaction wait and then see the first one's change. Use optimistic version checks (chapter 14). Turn the rule into a constraint where it fits one, or materialise the conflict: give the rule a row of its own, such as one row per shift, that every transaction touching the rule must update, so they conflict on it. Or run serializable for those transactions and retry when they abort, as exercise 13.3 describes.

Isolation is subtle enough that database implementations get it wrong too. Kyle Kingsbury's Jepsen analyses test databases against their documented guarantees and have found real violations in many of them, including a serializable-isolation bug in PostgreSQL in 2020, fixed promptly after the report.

Common traps
  • Assuming you're running serializable when the default is read committed or snapshot.
  • Read-modify-write in application code, the source of lost updates at read committed.
  • Check-then-act on a rule spanning several rows, which snapshot isolation lets break through write skew.
  • Raising the isolation level without retry logic, so serialization failures become user-facing errors.
  • Trusting a level's name without reading what your engine means by it.

Chapter 14

Locks, MVCC and deadlocks

9 min read3 exercises4 flashcards

There are two ways to stop concurrent transactions trampling each other: make them wait, with locks, or let them work on different versions of the data, with multi-version concurrency control (MVCC). Every major database uses both: versions so that readers and writers never block each other, locks so that two writers can't overwrite each other. Each has a failure mode worth knowing in advance. Versions pile up, and locks deadlock.

Locks and two-phase locking

A lock is permission to use a piece of data. A shared lock lets you read and lets others read too; an exclusive lock lets you write and keeps everyone else out. The classic protocol for serializability is two-phase locking: a transaction acquires locks as it goes and releases none until it is done with all of them. The strict form, holding every lock until commit, is the one databases use, because it also prevents others from reading uncommitted data. It works, and it's expensive: a long report holding shared locks blocks every writer, and every writer blocks the report. Locks can cover a row, a page or a whole table. Some engines escalate many row locks into one table lock to save memory, which can suddenly block unrelated work.

MVCC: readers don't wait

MVCC removes the reader-writer conflict by never overwriting a row in place. An update creates a new version and marks the old one as ended, and each transaction reads whichever version was committed as of its snapshot. PostgreSQL stores every version in the table, stamped with the id of the transaction that created it (xmin) and the one that ended it (xmax). InnoDB and Oracle keep only the newest version in the table and reconstruct older ones from their undo logs on demand. Either way, the result is the snapshot isolation of chapter 13: a reader sees a consistent picture and never waits for a writer.

The first half is PostgreSQL's design in miniature. Transaction 3 updates the balance but hasn't committed: it sees its own 70, while the long report, transaction 2, sees the committed 100, without waiting. After the commit, the report still sees 100, because its snapshot predates transaction 3. A transaction that starts afterwards sees 70. The version list shows how: the old version wasn't erased, only ended (xmax=3), and the new one carries xmin=3.

The cost of keeping versions

Old versions must eventually be removed, by PostgreSQL's VACUUM or InnoDB's purge thread, and they can only be removed once no running transaction might still need them. The example's first vacuum, run while the report is open, removes nothing; after it finishes, the dead version goes. That's why a single long transaction is dangerous on a busy database. A report running for six hours, or a session left "idle in transaction", holds back cleanup for the whole database, and tables bloat with versions nobody can see. PostgreSQL has a sharper version of the same problem. Transaction ids are 32-bit counters, and if old rows aren't vacuumed in time, the counter approaches wraparound, at which point the database stops accepting writes rather than risk data appearing to come from the future. Sentry in 2015 and Mailchimp's Mandrill in 2019 both had outages for exactly this reason.

Version design also shapes write costs. Because PostgreSQL writes a new version for every update, the new version needs new entries in every index on the table, unless the update qualifies as a "heap-only tuple" update that stays on the same page and touches no indexed column. Uber cited that write amplification, among other reasons, when it moved from PostgreSQL to MySQL in 2016.

Deadlocks

MVCC handles readers; writers still lock. Transaction 1 locks account A and transaction 2 locks account B. Then 1 asks for B and waits for 2, and 2 asks for A and waits for 1. Neither can ever proceed. The second half of the example catches this the way databases do: it keeps a wait-for graph of who is waiting for whom, and a cycle in that graph is a deadlock. The database aborts one transaction, usually the youngest or the one that has done the least work, and the other proceeds. PostgreSQL checks for cycles after a transaction has waited for deadlock_timeout (one second by default); InnoDB checks as each lock wait begins. The aborted transaction gets an error, and the application should retry it. Prevention is cheaper than detection: acquire locks in a consistent order, such as always locking the lower account id first, and the cycle can't form.

Optimistic concurrency

When conflicts are rare, it's cheaper to check than to lock. Give the row a version column, read it with the data, and write with UPDATE ... SET ..., version = version + 1 WHERE id = ? AND version = ?. If another writer got there first, the version won't match, the update changes zero rows, and the application reloads and retries or asks the user. This is the right tool for edits that span human time, such as a form open for ten minutes, where holding a database lock is impossible.

Common traps
  • Long or idle-in-transaction sessions that hold back vacuum for the whole database.
  • Ignoring transaction-id wraparound warnings until the database stops accepting writes.
  • Locking rows in inconsistent orders across code paths, the recipe for deadlocks.
  • Treating a deadlock error as a bug report instead of retrying the transaction.
  • Holding database locks across user think time instead of using optimistic version checks.

Chapter 15

The write-ahead log and crash recovery

9 min read3 exercises4 flashcards

The write-ahead log is the ledger at the heart of a database: every change is described in the log, and the log is forced to disk, before the change is allowed to count. That one rule makes commits fast, makes crashes survivable, and makes replication and point-in-time recovery possible. This chapter builds a key-value store around it, the first half of the stage's deliverable.

The rule

Writing a changed page back to its place in a data file is a random write, and a transaction may change dozens of pages scattered across many files. Making all of them durable before acknowledging a commit would be slow, and a crash partway through would leave some pages old and some new. The write-ahead log solves both problems with one rule: before any change reaches the data files, a record describing it must be on disk in the log. A commit then needs only one sequential append and one flush. The changed pages stay in the buffer pool and are written back later, at leisure, as chapter 1's diagram showed. After a crash, recovery replays the log: committed changes whose pages never reached disk are redone, and changes from transactions that never committed, which may have reached disk early, are undone. Production databases implement this with the ARIES algorithm, published by IBM in 1992. The store below needs only the redo half, because it never writes uncommitted data anywhere but the log.

Five ways to test a log

Crash and restart. The store is dropped without any shutdown, as if the process were killed. On restart it replays four records and reaches exactly the state it had acknowledged, with the delete of carol applied in order. Nothing in the dictionary itself was ever saved; the log was enough.

A torn final write. Power can fail while a record is being written, leaving only part of it on disk. Each record carries its length and a CRC-32 checksum of its contents, so recovery can tell a complete record from a fragment. It replays the four good records and discards the 22 bytes of the partial fifth. That's correct, not lossy: the fifth write never finished, so its put never returned, and no one was ever told it succeeded.

A corrupted record. A flipped bit in the second record fails its checksum, and recovery stops there, keeping only the first record and discarding everything after it. That looks harsh, since records three and four might be fine, but a log is only trustworthy as an unbroken prefix. Once one record is bad, recovery can't be sure where the next one starts, and replaying later changes without an earlier one could produce a state that never existed. PostgreSQL treats the first invalid record as the end of the log for the same reason. Real corruption in the middle of a log is a job for backups and replicas (chapter 16), not for recovery.

Checkpoints. A log that grows forever makes recovery slower every day. A checkpoint writes the current state durably (here, a snapshot file replaced atomically, the trick from chapter 1) and then discards the log before it. After a thousand writes, the log shrank from 29,780 bytes to nothing, and a restart loaded the snapshot and replayed just the two records written since. Real databases checkpoint by flushing dirty pages and noting the log position from which recovery must start, trading I/O spikes during checkpoints against shorter recovery.

Group commit. The flush is the expensive step: fsync takes anywhere from about a tenth of a millisecond on a good SSD to several milliseconds on a disk, and it caps how many commits per second one log can make. Batching commits that arrive together into one flush, called group commit, turned 200 flushes into 4 here. Databases do it automatically: when several transactions commit at once, one flush makes all of them durable.

When fsync lies, and when pages tear

The whole scheme rests on fsync meaning what it says. Disks with volatile write caches can acknowledge a flush before the data is safe, which is why servers use drives with power-loss protection. The operating system can fail too. In 2018, PostgreSQL's developers discovered that on Linux, a failed fsync could clear the error, so a retry would report success while the data was gone; PostgreSQL now stops with a panic on any fsync failure rather than retry. Data pages have their own torn-write problem. An 8 KB page written as two 4 KB halves can be half old and half new after a crash. PostgreSQL logs the full page image the first time a page changes after each checkpoint (full_page_writes), and InnoDB writes pages to a doublewrite buffer first.

The log is the database

The log turns out to be useful far beyond recovery. Ship it to another machine and replay it there, and you have a replica (chapter 16). Archive it next to a base backup, and you can restore the database to any moment, a minute before the bad DELETE: point-in-time recovery. Stream it to other systems, and every change becomes an event: change data capture, which is how tools like Debezium feed search indexes and warehouses. Seen this way, the log is the source of truth, and the tables are just a convenient, indexed copy of its latest state.

To finish the deliverable, swap the store's dictionary for chapter 6's B+tree, which adds ordered range scans, or put this log in front of chapter 7's memtable, which makes the LSM tree durable. Then test it the way this chapter did, but harder: kill the process at random moments thousands of times and check that every acknowledged write survives and no unacknowledged one appears.

Common traps
  • Never testing recovery, so the first real crash is also the first test.
  • Retrying a failed fsync and believing the second answer.
  • Trusting consumer disks' write caches on a database server.
  • Deleting log files by hand to free space, which can make the database unrecoverable.
  • Checkpoints tuned badly: too rare means long recoveries, too frequent means constant I/O spikes.

Exercise 15.2Why stop at the first bad record?

A colleague proposes that recovery skip a record with a bad checksum and carry on with the ones after it, to lose less data. What can go wrong?

Show solution

Replaying them creates a state that never existed, which is worse than a clean loss, because nobody can tell it's wrong. Third, a bad record in the middle of the log means the disk or file system is damaged, so the right response is to stop, alert, and restore from a backup or replica rather than paper over it.

Chapter 16

Replication, backups and recovery points

8 min read3 exercises4 flashcards

Replication copies the log to other machines, so you can survive losing one and spread reads across several. It is not a backup: a replica faithfully copies every mistake, including the DELETE with the wrong WHERE. Decide how much data you can afford to lose and how long you can afford to be down, then build replication for one and backups for the other.

Copying the log

Chapter 15 ended with the observation that the log is the database. Replication is that idea in practice: the primary streams its log to replicas, and each replica replays it to keep an identical copy. Physical replication ships the log's bytes and produces an exact copy of the primary's files, page for page. It's simple and complete, but the replica must run the same major version. Logical replication ships row changes, which can cross versions, replicate selected tables, and feed other systems, at the cost of more moving parts. PostgreSQL offers both; MySQL replicates its binary log, preferably in row format. The other choice is timing. With asynchronous replication, the primary acknowledges a commit without waiting for any replica. With synchronous replication it waits for at least one, which adds a network round trip to every commit. Semi-synchronous schemes wait for the replica to receive the record but not to apply it.

What lag does to users

An asynchronous replica is always a little behind, usually milliseconds and sometimes much more. Part 1 shows the classic consequence: a user saves a new display name, the next page reads from a replica that hasn't replayed the change yet, and the save looks lost. The fix is read-your-writes consistency. The primary returns the log position (LSN) of each write, the client keeps it, and a read is served by a replica only if that replica has replayed at least that far; otherwise it goes to the primary, or waits. PostgreSQL exposes a replica's position with pg_last_wal_replay_lsn(), and MySQL uses global transaction ids for the same purpose. A cruder fix sends a user's reads to the primary for a few seconds after any write. Part 2 is the subtler monotonic reads problem: two replicas with different lag, and a user whose reads alternate between them sees data go forward and then back in time. Pinning each user to one replica, or using the same position tokens, prevents it.

Failover, and what it can lose

When the primary dies, a replica is promoted to take its place. With asynchronous replication, whatever the replica hadn't received is gone: in part 3, three orders that customers were told had succeeded. Two numbers make this a decision instead of a surprise. The recovery point objective (RPO) is how much data you can afford to lose, and the recovery time objective (RTO) is how long you can afford to be down. An RPO of zero requires synchronous replication to at least one other machine, and pays a round trip on every commit; a few seconds of RPO allows asynchronous. Failover also has to make sure the old primary is truly dead, or fenced, before the new one accepts writes, or both accept writes at once. In October 2018, a 43-second network partition led GitHub's failover tooling to promote primaries in a different region while the original side kept writing too. Reconciling the two sets of writes took 24 hours of degraded service.

Backups are for mistakes

Part 4 is the case replication can't help with. Someone runs a DELETE with the wrong condition, and the replica, doing its job, deletes the row too. The defence is point-in-time recovery: a base backup, plus every log record archived since, replayed to the moment just before the mistake. The restore brings back the deleted row and keeps the legitimate change made just before it. Backups must also live somewhere a mistake or an attacker can't reach at the same time: another account, another region. And they must be tested, because a backup you've never restored is a hope, not a backup. In January 2017, an engineer at GitLab, fighting a replication problem late at night, deleted the primary's data directory instead of the replica's. The team then found that their regular backups had been failing silently. They restored from a snapshot taken six hours earlier for another purpose, and lost six hours of users' issues, merge requests and comments.

Common traps
  • Treating replicas as backups, when they copy every mistake within milliseconds.
  • Never restoring a backup until the day you need it.
  • Reading from replicas with no lag handling, so saves look lost and data goes back in time.
  • Asynchronous failover without an agreed RPO, so lost writes come as a surprise.
  • Failover without fencing, leaving two primaries accepting writes.

Exercise 16.2The disappearing save

After users save their profile, they sometimes see the old values for about a second. Reads go to replicas. Give two fixes and their trade-offs.

Exercise 16.3A backup plan you can trust

Then prove it works: every month, an automated job restores the latest backup to a fresh instance, replays the log to a chosen time, runs verification queries (row counts, recent records, a checksum of a key table), and reports how long it took. That duration is your real RTO. Alert if the restore fails or the newest archived log is older than a few minutes.

Chapter 17

Changing the schema under live traffic

7 min read3 exercises4 flashcards

Every schema change on a live system happens while two versions of the application are running at once, and the database has to work for both. The safe pattern is expand and contract: add the new shape alongside the old one, move code and data across in small steps that can each be undone, and remove the old shape only when nothing uses it any more.

Why it's hard

On a laptop, renaming a column is one statement. In production, three things get in the way. The first is two versions of the code: a rolling deploy replaces servers one at a time, so for minutes or hours the old code and the new code run side by side against the same tables, and a rollback brings the old code back. Rename the column in one step and whichever version doesn't know the new name breaks. The second is locks. Many ALTER TABLE forms take an exclusive lock, and some rewrite the whole table while holding it. Even a change that needs the lock only for a moment must first wait for every running query on the table, and in PostgreSQL every query that arrives after it waits behind it, so a two-second change can stall the table for minutes behind one slow report. The third is the data: copying values into a new column across a hundred million rows takes time and can't be one transaction.

Expand and contract

The pattern breaks a change into steps, each compatible with both the code running before it and the code after it, and each reversible until the last.

The order is the whole trick

The first run backfills while the old code, v1, is still deployed. v1 knows nothing about display_name, so every rename it performs after a batch has passed that row updates fullname and leaves display_name holding the old value. The backfill finishes, everything looks done, and 262 rows are silently wrong, waiting to show users their old names the day v3 starts reading the new column. The second run deploys the dual-writing v2 everywhere first, so every rename keeps both columns in step, and only then backfills: zero mismatches. The batches matter too. Each one is its own short transaction of at most 1,000 rows, so no lock is held for long and replicas never fall far behind. A single UPDATE of the whole table would be one enormous transaction, holding locks and an old snapshot for its whole duration (chapter 14). Before switching reads, verify, as the example's mismatch count does, and only drop the old column once v1 and v2 are gone.

Engine features that help

Databases have steadily made more changes cheap. In PostgreSQL, adding a column with a constant default has been instant since version 11. CREATE INDEX CONCURRENTLY builds an index without blocking writes, and a constraint can be added NOT VALID, which checks new rows immediately, then validated against old rows later without a long lock. Setting lock_timeout before any DDL makes a change give up and retry rather than queue the whole table behind it. MySQL supports ALGORITHM=INSTANT for many column changes. For the rest, tools such as gh-ost and pt-online-schema-change build a shadow copy of the table, keep it in sync, and swap it in. SQLite supports adding, renaming and, since version 3.35, dropping columns. Whatever the engine, rehearse every migration on a copy of production-sized data before running it for real.

Common traps
  • Renaming or dropping a column in one step while the old code may still be running or be rolled back to.
  • Backfilling before dual writes are fully deployed, leaving silently stale rows.
  • DDL without a lock timeout, so one long query turns a quick change into an outage.
  • Building indexes without the concurrent option on a busy table.
  • One giant backfill transaction instead of small batches.

In the wrong-order run, which writes produced the 262 stale rows, and why didn't renames by v1 before a row's batch cause problems?

Show solution

The stale rows are exactly those that v1 renamed after the backfill had already copied them. So the danger window is any old-code write that lands after the copy, which is why dual writes have to be deployed everywhere before the backfill starts.

Exercise 17.3The two-second outage that lasted three minutes

Show solution

The ALTER needed an exclusive lock on orders, so it waited for the report's query, which held a shared lock. In PostgreSQL, the waiting ALTER sits in the lock queue ahead of every later request, so every ordinary read and write on orders queued behind it. The table was effectively locked until the report finished three minutes later and the ALTER ran. Prevent it by setting SET lock_timeout = '2s' before the DDL, so it gives up quickly instead of blocking everyone, and retrying with backoff until it gets the lock in a quiet moment. Schedule DDL away from long batch jobs, and check for long-running queries before starting.

Chapter 18

NoSQL: choosing by access pattern

9 min read3 exercises4 flashcards

Non-relational databases aren't a newer, faster kind of relational database. Each family gives up something general, usually ad-hoc queries, joins or transactions across many rows, to make one access pattern cheap at large scale. Choose one when you know your access patterns and they fit its shape; choose relational when you don't, or when they'll change.

The families

Key-value stores (Redis, DynamoDB used by key) do one thing: get and put a value by its key, extremely fast. Document databases (MongoDB, Couchbase) store a nested JSON-like document per key and can index fields inside it. Wide-column stores (Cassandra, ScyllaDB, Bigtable, HBase) group rows into partitions by a partition key and keep the rows within a partition sorted by a clustering key, on LSM storage (chapter 7) that is built for writes. Graph databases (Neo4j, Amazon Neptune) store relationships as first-class links, so a query that follows them many hops deep doesn't become a pile of joins. Time-series databases (TimescaleDB, InfluxDB) are tuned for appending timestamped measurements and querying recent ranges. Search engines (Elasticsearch, OpenSearch) are the subject of the next chapter. What they share is a bargain: decide your queries up front, and the database makes those queries cheap at a scale where one relational server would struggle.

Reading the table

The example models the same 20,000 orders three ways and asks three questions. The relational column comes from SQLite's own plans, and with the right indexes every answer is an index search. The document model, one document per customer with orders embedded, is perfect for question A: one read returns the customer and every order. The key-value model was designed for A and B: the customer's partition holds its orders sorted by date, and each order has a partition of its own.

Then the questions go off-script. Finding one order in the document model means scanning every customer document, because nothing leads from an order id to the customer who placed it; a real document database would need a secondary index on the embedded field, which is fine, as long as someone planned it. Question C, every order containing a product, is the one nobody planned. The relational database answers it with an index that can be added in a minute at any time. Both NoSQL models must scan everything, or have their data reorganised around the new question: a secondary index, or a copy of every order line keyed by product, kept in sync by every write. That is the trade in one table. NoSQL makes the anticipated access patterns cheap and the unanticipated ones expensive.

Designing for a NoSQL store

The method is the reverse of relational design. Start from the list of access patterns, not from the entities, and design keys so that each pattern is a lookup by key or a range within one partition. That is the single-table design style used with DynamoDB, where keys like CUST#77 and ORDER#2026-09-01#4242 encode the queries they serve. Denormalise on purpose and accept duplication. Watch the sizes: a partition or document that grows without bound, such as every comment on a viral post, becomes a hot spot or hits a hard limit (MongoDB documents are capped at 16 MB). And know what you're giving up. Joins move into application code, multi-record transactions are limited or missing (MongoDB and DynamoDB both added them later, with restrictions), and the schema is enforced, if at all, by your code reading the data.

When to choose one

NoSQL earns its place for enormous scale with simple, known patterns (Discord's message history, chapter 7), for records whose shape genuinely varies, for caching and sessions, for deep relationship traversals, and for high-rate time-series ingestion. Two developments have narrowed the gap. Relational databases absorbed the most useful NoSQL features: PostgreSQL's jsonb, with indexes inside documents, covers many document-store use cases. And distributed SQL databases such as Google Spanner and CockroachDB offer SQL and transactions across many machines. A sound default for a new product is a relational database, adding a specialised store when a specific access pattern demands it and you can name which one.

Common traps
  • Choosing NoSQL "for scale" years before having the scale, and paying in lost flexibility meanwhile.
  • Modelling relationally in a document database, with references everywhere and joins done in application code.
  • Unbounded documents or partitions that become hot spots or hit size limits.
  • Forgetting the unplanned question, the report or admin screen that nobody listed as an access pattern.
  • Assuming strong consistency where the store defaults to eventual consistency for reads.

Chapter 19

Caches and search indexes beside the database

9 min read3 exercises4 flashcards

Two kinds of system sit beside almost every database: a cache that answers repeated questions from memory, and a search index that answers questions the database's indexes can't. Both are copies of data the database owns, which is what makes them fast and what makes them stale. Design them as derived data, with a clear answer to the question of what happens when the copy is wrong.

Cache-aside

The most common pattern is cache-aside, or lazy loading. To read, the application asks the cache first. On a hit it's done. On a miss it queries the database, stores the result in the cache with a time-to-live (TTL), and returns it. To write, it updates the database and deletes the cached entry, so the next read reloads it. Redis and Memcached are the usual caches. Alternatives exist: write-through updates the cache and the database together, and write-behind updates the cache and writes to the database later, which is fast and can lose data. Whatever the pattern, the TTL is the safety net: however the cache goes wrong, the error expires.

The stampede

A cache can hide a database's limits so well that nobody notices until it fails. When a popular entry expires, every request that arrives before it's refilled misses at once, and in part 1 a thousand of them query the database at the same moment for the same answer. That's a cache stampede, also called a thundering herd, and it can take down a database that handles the steady load easily. Three fixes appear in the example and in practice. Single flight lets the first request refresh the entry while the others wait for its result: one query, 999 short waits. Serve stale while revalidating returns the old value to everyone and refreshes it once in the background: one query, nobody waits. Early or jittered expiry refreshes a hot entry slightly before its TTL ends, at a random moment, so entries don't all expire together. A restart has the same effect at a larger scale: an empty cache sends every request to the database, so warm the cache, or let traffic back in gradually.

The invalidation race

Part 2 shows why "delete the cache entry after writing" isn't the end of the story. A reader misses and reads 100 from the database. Before it stores that value, a writer updates the database to 120 and deletes the cache entry. Then the reader stores the 100 it read. The cache now contradicts the database, and will until the TTL expires. Every step was correct in isolation; the order made it wrong. Facebook's memcache paper describes the fix it adopted: leases. A miss hands the reader a token, a delete invalidates outstanding tokens, and the cache refuses a set with an invalidated token. Simpler defences are a short TTL, which bounds how long the staleness lasts, and versioned keys that include the row's version or update time, so a stale value is stored under a key nobody reads any more.

Search indexes

A B-tree finds rows whose value starts with something; it can't find documents that contain a word somewhere in the middle, so LIKE '%stale%' scans every row. Search needs an inverted index: for every word, the list of documents that contain it, called its postings. A query for two words intersects two posting lists. In part 3, the search read 6,000 postings to find its 2,000 matches, where the scan read all 12,000 documents; the gap grows with the size of the collection and the rarity of the words. Real search engines add tokenisation, stemming (so lagging matches lag), and ranking, usually by BM25, which weighs rare words more heavily and rewards documents where the query's words are prominent. SQLite's FTS5, run at the end of the example, does exactly this inside the database.

Start with your database's built-in search, such as PostgreSQL's tsvector with a GIN index, SQLite's FTS5 or MySQL's FULLTEXT: it stays transactionally consistent with the data and needs nothing new to run. Move to a dedicated engine such as Elasticsearch or OpenSearch when you need typo tolerance, faceting, relevance tuning, or scale beyond one server. Feed it from the database's change stream (chapter 15) and accept that it lags slightly behind. Keep a way to rebuild it from scratch, because a derived index that drifts needs a reindex, and a reindex is only possible if the database is the source of truth.

Common traps
  • Cache entries with no TTL, so any invalidation bug lasts forever.
  • Caching errors or empty results with the same TTL as real answers.
  • No stampede protection on the few keys that carry most of the traffic.
  • Treating the cache as the source of truth, so a cache restart loses data.
  • A search index with no rebuild path, drifting further from the database every week.

Exercise 19.2Close the race

Fix part 2's race using versioned keys, and explain why it works.

Show solution

Give the row a version that changes on every write (an integer, or the update timestamp), and include it in the cache key: price:42:v7. The reader learns the current version when it reads from the database, so it caches 100 under price:42:v7. The writer's update makes the version 8, and subsequent readers look up price:42:v8, miss, and load 120. The reader's late write of the stale 100 lands under the old v7 key, which nobody reads any more and which expires on its own. The cost: finding the current version needs a cheap lookup of its own, or the version must travel with whatever references the item.

  2. A dedicated engine built for logs (OpenSearch, Elasticsearch, or a log-specific store). The volume is far beyond one database server, the data is append-only, and the queries are time-bounded searches.
  3. A dedicated engine. Typo tolerance, faceted counts and relevance tuning are what search engines are built for, and doing them well inside a relational database is a project of its own. Feed it from the catalogue's change stream and keep a full reindex job.

  • Can you rebuild the search index from scratch?

Chapter 20

Analytical data: columns, stars and pipelines

9 min read3 exercises4 flashcards

Transactional databases are built to touch a few rows at a time; analysis touches millions of rows and only a few of their columns. Analytical systems flip the storage layout to keep each column together, which lets them read a fraction of the data and compress it dramatically, and they model data as facts surrounded by dimensions. Keep the two workloads apart, and move data between them deliberately.

Two workloads

An online shop's database spends its day on transactional (OLTP) work: show this order, add that item, update this stock count. Each query touches a handful of rows, by key, and needs an answer in milliseconds. The finance team's questions are analytical (OLAP): revenue by month and category for two years, the average basket size by region. Each query touches millions of rows but only a few columns, runs for seconds, and is asked by a few people. Run the second kind on a database built for the first and you get chapter 5's flooded cache and chapter 14's held-back vacuum, on the system your customers depend on. Analytical work belongs in a system built for it, fed from the transactional one.

Store columns, not rows

A row store keeps each row's values together in a page, which is ideal for fetching a whole row by key. A column store keeps each column's values together, so a query reads only the columns it mentions. Columns also compress far better than rows, because each holds one kind of value with lots of repetition.

Reading the numbers

For a sum of one column filtered by another, the row store reads all five columns of every row, 8.2 MB, while the column store reads two, 3.0 MB. That's before compression, which is where columns pull far ahead. The status column, 1.4 MB of repeated words, shrinks to 200,000 one-byte codes with dictionary encoding, and to three runs, 15 bytes, with run-length encoding once the table is sorted by status. Dates sorted in order become small day-to-day differences, which delta encoding plus a general compressor squeezes from 2 MB to under 800 bytes. A table can only be sorted one way, so column stores let you choose a sort key, and the leading columns of that key compress best. Engines then process compressed values in batches of thousands at a time (vectorised execution), which is how DuckDB on a laptop, or ClickHouse, BigQuery, Snowflake and Redshift at scale, scan billions of rows in seconds. Parquet files bring the same layout to data that lives in object storage.

Facts and dimensions

Analytical schemas are usually star schemas, the design Ralph Kimball popularised. A central fact table records events at a chosen grain, such as one row per order line, with numeric measures like quantity and revenue, plus keys to the dimension tables around it: date, product, customer, store. Dimensions are wide and denormalised on purpose, with month and quarter stored on the date row and category stored on the product row, because analytical data is loaded in bulk and read far more than it's changed, so chapter 2's arguments for normalisation weigh much less. History matters here: when a product changes category, a type 2 slowly changing dimension adds a new dimension row with validity dates rather than overwriting, so last year's sales stay in last year's category, the same idea as chapter 3's history tables.

The example's third part runs a typical star-schema query on SQLite: revenue by month and category, joined from the fact table to two dimensions, with a subtotal row per month. Databases that support it write the subtotals with GROUP BY ROLLUP (month, category), or more generally GROUPING SETS and CUBE, which compute several groupings in one pass; MySQL offers WITH ROLLUP. SQLite has none of these, so the example writes the rollup out as a UNION ALL of two groupings.

Pipelines

Data reaches the analytical store through a pipeline. Classic ETL extracts from the source, transforms in a separate system, and loads the result. Modern ELT loads raw data into the warehouse first and transforms it there with SQL, often managed with dbt, which keeps the raw data available for new questions and makes transformations versioned and testable. Batch loads run on a schedule; streaming loads follow the source's change log (chapter 15) for fresher data. Whichever you choose, treat the pipeline like production code: loads that are idempotent, so a rerun doesn't double-count; tests for row counts, nulls and uniqueness at each step; and a stated freshness target that someone is alerted about when it's missed.

Common traps
  • Running analytics on the production primary, competing with customers for cache and I/O.
  • An unclear grain, so some rows mean an order and others an order line, and every sum is wrong.
  • Overwriting dimension history when reports need to see the past as it was.
  • Pipelines that aren't idempotent, double-counting a day's data whenever a job is retried.
  • Using a column store for point lookups and frequent updates, the workload it's worst at.

ELT suits a startup because the warehouse's compute does the heavy lifting, the transformations live in version control, and the team needs SQL rather than a separate transformation platform.

The twenty rules

One per chapter, each linked back to it. Read them before you design a schema, and against every change that touches a query, an index, a transaction or a migration.

  1. Know which promises you need: writes that are atomic and durable, concurrency that loses nothing, and finding without scanning. A file keeps none of them.
  2. Declare every rule your code assumes as a constraint, test that it is enforced, and store each fact in one place.
  3. Design trees, money, history and polymorphism on purpose: integer cents, UTC timestamps and real foreign keys.
  4. Count the queries each page sends, load what loops touch eagerly, and write SQL where the ORM fights the relational model.
  5. Estimate cost in pages, keep the working set in memory, and keep big scans away from the primary's cache.
  6. Keep keys short and sequential, so B-trees stay shallow, dense and cache-friendly.
  7. Choose B-trees for predictable reads and LSM trees for heavy writes, and know which amplification you are paying.
  8. Put equality columns before the range column, keep indexed columns bare, and drop the indexes nobody uses.
  9. Read plans as operator trees, spot the blocking operators, and index the columns you join and sort on.
  10. When a plan is bad, compare estimated rows with actual rows and fix the statistics before reaching for hints.
  11. Tune by experiment: realistic data, one change at a time, median timings, identical results, and every plan written down.
  12. Put each business operation in one short transaction, and never call another service from inside it.
  13. Know your isolation level and the anomalies it allows; make read-modify-write atomic and retry serialization failures.
  14. Watch for long transactions, lock rows in a consistent order, and use version checks for edits that span human time.
  15. Log before you apply, checksum every record, stop recovery at the first bad one, and test recovery by crashing on purpose.
  16. Agree an RPO and an RTO; replicate for one, back up for the other, and restore a backup on a schedule.
  17. Change schemas by expand and contract, backfill in small batches after dual writes are deployed, and run DDL with a lock timeout.
  18. Choose a non-relational store only for an access pattern you can name, and plan for the question nobody listed.
  19. Give every cached value a TTL and every hot key stampede protection, and keep the database as the source of truth.
  20. Keep analytics off the transactional primary: columns for scans, stars with a clear grain, and pipelines you can rerun safely.
