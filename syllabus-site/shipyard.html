The Engineer's Shipyard

The previous volume taught you to write code a team can change. This one is about assembling it into a product that strangers use and pay for: the API, the sign-in, the interface, the work behind each request, the money, and the discipline of shipping it and learning from what happens next.

How to use this volume

Each chapter has the same shape as in The Engineer's Craft. It opens with its idea in one sentence, works through examples, lists the traps, and ends with exercises, a checklist and further reading. Every exercise has a solution folded underneath it. Try first, then open it.

Build one product while you read. Stage 10's deliverable is a real product with real users, maintained for at least three months. Wherever an exercise can be done against your own product instead of the example, do it there. The chapters are ordered roughly as you'll need them, but Part VI is worth reading early, before you decide what to build.

The running example is a small invoicing app for freelancers and studios. Teams send invoices to their clients, clients pay by card, and the app chases late payers. It needs almost everything in this volume: accounts and teams, an API and a web interface, PDFs and email, payments and webhooks, and a launch.

Code is in Python on the server, TypeScript and React in the browser, SQL for PostgreSQL, and raw HTTP where the protocol itself is the point. The self-contained examples were run before publication to confirm they behave as described. Every idea transfers to other stacks.

The one question

Tutorials stop at the moment code works on the author's machine. Products begin at the moment it meets the world.

A client retries a payment request because the network blinked. A user pastes an emoji into a name field. Someone navigates by screen reader, or on a mid-range phone on a slow train. A bank asks the cardholder to confirm a payment. An email lands in spam. And someone, within days of launch, deliberately tries to break it.

Every chapter here is about one of those meetings. Before you ship anything, ask what happens when this meets a real user? Then ask what happens when it meets an attacker.

Part I

The API

An API is a promise to everyone who calls it, and it's the hardest part of a product to change later. These four chapters cover designing that promise, making it safe to page through and retry, evolving it without breaking anyone, and choosing its shape.

Chapter 01

Designing HTTP APIs

7 min read3 exercises4 flashcards

A good API is predictable: resources named as nouns, methods that mean what HTTP says they mean, status codes a client can act on, and errors that tell the caller exactly what to fix.

Resources, not actions

Model the nouns of your domain as resources with stable URLs, and let HTTP's methods be the verbs. The URL says what; the method says what to do with it.

Some operations don't fit create, read, update and delete. Sending an invoice is an action with consequences: an email, a status change, an audit record. Don't contort it into PATCH /invoices/7 {"status": "sent"}, which hides the side effects behind what looks like a field edit. POST /invoices/7/send is honest, widely understood, and easy to authorise separately. Google's API guidelines call these custom methods. Use them sparingly, and only for genuine actions.

Conventions worth adopting from day one: plural nouns, lower case, hyphens or underscores used consistently, nesting no deeper than one level, and identifiers that are opaque strings such as inv_8f3k2 rather than sequential integers, which leak your volume and invite people to guess neighbours.

Methods mean what HTTP says they mean

MethodMeaningSafeIdempotentTypical success
GETRead a resource or collectionYesYes200
POSTCreate a resource, or perform an actionNoNo201 with a Location header, or 200 or 202
PUTReplace a resource entirelyNoYes200 or 204
PATCHChange part of a resourceNoNot necessarily200
DELETERemove a resourceNoYes204

Safe means the request has no side effects the client asked for. Idempotent means sending it twice has the same effect as sending it once. RFC 9110 defines both, and browsers, proxies, crawlers and retry libraries all rely on them. A GET link that deletes something will eventually be followed by a link prefetcher or a search engine, and your data will quietly disappear.

Status codes a client can act on

The most useful property of a status code is that a client can decide what to do from it alone. A 4xx says "your request is wrong; sending it again unchanged won't help". A 5xx, or a 429, says "try again later".

Errors that explain themselves

RFC 9457, Problem Details for HTTP APIs, which replaced RFC 7807 in 2023, defines a standard error format with the media type application/problem+json. Use it rather than inventing your own. A machine-readable type lets code branch on the error; title and detail are for people; and you can add fields, such as a list of every invalid field.

Report all the problems in one response, not one per round trip. Never return a stack trace or a database error message, which leaks internals to anyone probing your API. And never return 200 OK with an error in the body: every retry library, monitoring tool and cache will believe it succeeded.

Consistency is a feature

Pick conventions once and apply them everywhere. Clients learn one endpoint and can guess the next.

  • Field names: one case style, such as snake_case, across every endpoint.
  • Timestamps: RFC 3339 strings in UTC, such as "2026-09-18T14:30:00Z". Dates without times as "2026-09-18".
  • Money: an integer in minor units with its currency, or a decimal string. Never a floating-point number (chapter 15).
  • Enums: lower-case strings, such as "overdue", never magic integers.
  • Nulls: decide whether an empty value is null or absent, and document it.

Write your conventions down in a short API style guide, describe the API in an OpenAPI file, and lint it in CI with a tool such as Spectral. Consistency that isn't checked by a machine erodes one endpoint at a time.

Design from the client's side

Before building an endpoint, write the client code that will call it: the screen that lists invoices, or the integration that syncs them. This is test-first development applied to API design. It exposes chatty designs that need five calls to draw one screen, and it stops you publishing your database schema as your API. Tables are an implementation detail you'll want to change; the API is a contract you'll have to keep.

Common traps
  • Verbs in every URL. /getAllInvoices is a function call wearing a URL.
  • 200 with an error body. Every tool between you and the client will think it worked.
  • Leaking the database. Internal column names, auto-increment IDs and table structure, all now frozen into a public contract.
  • Inconsistent shapes. The same invoice returned with different fields by different endpoints.
  • 401 and 403 confused. 401 means "who are you?"; 403 means "I know who you are, and no".

Chapter 02

Pagination, filtering and safe retries

8 min read3 exercises4 flashcards

Lists must be paged in a way that stays fast and correct while the data changes, and every write must be safe to retry, because on a real network every write eventually will be retried.

Offset pagination, and why it breaks

The obvious design is ?page=3&per_page=50, which becomes OFFSET 100 LIMIT 50 in SQL. It's simple, and it lets a user jump straight to page 37. It has two problems that appear only once a product is real.

  • It gets slower the deeper you go. The database must find and discard every skipped row. Page 1,000 at 50 per page processes 50,000 rows to return 50.
  • It's wrong when data changes. If a new invoice is created while someone pages through a list sorted newest-first, every row shifts down by one. The last row of page 1 reappears at the top of page 2. Delete a row instead, and one is silently skipped.

Cursor pagination

Instead of "skip N rows", say "continue after this row". This is keyset pagination: the query filters on the sort key of the last row the client saw, so the database seeks straight to it through an index. The sort order must be total, meaning no two rows can tie, so always add a unique column, usually the id, as a tiebreaker.

Hide the key inside an opaque cursor string. If clients could read the cursor's structure, they would start depending on it, and you could never change it.

The query is fast only with a matching index, here on (team_id, created_at DESC, id DESC). The row comparison (created_at, id) < (…) compares both columns in order, which is exactly what a total sort needs. The trade-off is that users can't jump to page 37. For feeds, infinite scroll, exports and sync, nobody wants to. For a small admin table where they do, offset pagination is fine.

Filtering and sorting

Accept filters and sort orders as query parameters, such as ?status=overdue&client_id=cl_12&sort=-due_date, and allowlist both. Passing a client-chosen column name into ORDER BY invites SQL injection, and even when it's safe, it lets a client pick a sort with no index and run a full table scan on every request. Document the default order, cap the page size, and return 400 for unknown parameters rather than silently ignoring them.

Why every write needs to be retryable

A client sends POST /invoices/inv_8f3k2/payments. The server charges the card. The response is lost on the way back, because a phone switched networks. From the client's side, the request simply timed out. Did it work? It can't know. Retrying might charge the card twice; not retrying might lose the payment.

The standard answer is an idempotency key. The client generates a unique key for each logical operation, once, when the user clicks "Pay", and sends it with every attempt in an Idempotency-Key header. The server stores the key with a fingerprint of the request and the response it produced. A repeated key gets the stored response back instead of a second charge. Stripe popularised the pattern, an IETF draft describes the header, and Stripe discards keys after at least 24 hours, comfortably longer than any sensible retry window.

Two details matter in production. Run the handler's writes and the final update in one transaction, and delete the started row if the handler fails, so a retry can try again. And scope keys to the caller, so one customer's key can never collide with another's.

Concurrent edits: lost updates and ETags

Two people open the same invoice. Both edit the notes and save. The second save silently overwrites the first, and nobody is told. This is a lost update, and "last write wins" is its polite name. HTTP's fix is optimistic concurrency with ETag and If-Match.

On the server, a version column does the work: UPDATE invoices SET notes = %s, version = version + 1 WHERE id = %s AND version = %s. If no row was updated, the version moved on, so return 412. The client can then show "this invoice changed since you opened it" and offer to reload, instead of destroying a colleague's work.

What PATCH means

JSON Merge Patch (RFC 7396) is the common choice: send only the fields to change, and null means "clear this field". It's simple, but it can't say "remove the third line item". JSON Patch (RFC 6902) sends a list of operations and can, at the cost of complexity. Whichever you choose, state it with the request's media type, and document the difference between a field that's absent (leave it alone) and one that's null (clear it).

Common traps
  • Unbounded lists. An endpoint with no maximum page size will one day return two million rows.
  • Sorting on a column that ties. Rows with equal timestamps come back in any order, so pages skip and repeat.
  • Readable cursors. Clients start constructing them, and you can never change the format.
  • Retrying POST without a key. Duplicate invoices, double charges, repeated emails.
  • Keys without fingerprints. A reused key with a different body silently returns the wrong response.
  • Last write wins on shared data. Somebody's work disappears, and nobody finds out.

Exercise 2.3Prevent the lost update

Two browser tabs are editing the same invoice's notes. Write the SQL for the save and describe what the second tab sees when it saves.

Show solution
UPDATE invoices
SET notes = $1, version = version + 1, updated_at = now()
WHERE id = $2 AND version = $3;     -- $3 is the version this tab loaded

The first save updates one row, and the version becomes 8. The second save matches no rows, because the version is no longer 7. The server returns 412 Precondition Failed, and the second tab shows "This invoice was changed by someone else", with the other version and an option to reload or copy their text. Nobody's work vanishes silently.

Checklist
  • Is every list paginated, with a maximum page size?
  • Is every sort order total, with a unique tiebreaker and a matching index?
  • Can every non-idempotent write be retried safely with an idempotency key?
  • Do concurrent edits fail loudly instead of silently overwriting?
  • Are filter and sort fields allowlisted?

Chapter 03

Evolving an API without breaking clients

7 min read3 exercises4 flashcards

Once someone depends on your API, every change is a negotiation. Most changes can be made additively. For the rest, version deliberately, deprecate loudly, and give people time.

What counts as breaking

A change is breaking if a client that worked yesterday stops working today without changing anything. That's a broader category than most people assume.

ChangeBreaking?Why
Add an optional request fieldNoOld clients don't send it
Add a new endpointNoNobody calls it yet
Add a field to a responseUsually notTolerant clients ignore it; strictly generated clients may not
Add a value to a response enumOftenA client's switch meets "disputed" and falls over
Remove or rename a fieldYesCode reading it gets nothing
Make an optional field requiredYesExisting requests start failing
Change a type or formatYesCents to decimal, integer to string
Tighten validationYesRequests that were valid now return 422
Change a default order, page size or rate limitIn practice, yesSomebody relied on it

That last row is Hyrum's law, from The Engineer's Craft: with enough users, every observable behaviour is depended on by somebody, whatever your documentation promises. Assume undocumented behaviour is load-bearing until you've checked.

Be strict early, tolerant as a client

Postel's robustness principle says to be conservative in what you send and liberal in what you accept. RFC 9413, published in 2023, argues that liberal acceptance entrenches bugs: once you accept a malformed input, clients depend on it, and you can never stop. For API design the lesson splits in two.

  • As a server, validate strictly from day one. Loosening validation later is easy and never breaks anyone. Tightening it always breaks someone.
  • As a client, read tolerantly. Ignore fields you don't recognise, and handle enum values you've never seen with a sensible default. Martin Fowler calls this the tolerant reader. Your own frontend and SDKs should be tolerant readers of your API.

Versioning strategies

StrategyExampleStrengthsCosts
URL path/v2/invoicesObvious, cacheable, easy to route and testEvery break bumps the whole API; clients must change URLs
Media type or headerAccept: application/vnd.example.v2+jsonClean URLs, per-resource versionsInvisible in logs and browsers; easy to get wrong
Date-pinned versionsStripe-Version: 2024-06-20Small, frequent changes; each customer upgrades on their own scheduleThe server must translate between every supported version

Stripe's approach is the benchmark for public APIs. Each account is pinned to the API version current when it first made a request, and the server keeps a chain of small transformations that turn today's responses into each older shape. It's elegant and it costs real engineering. For most products, a better default is to evolve additively almost always, and reserve a new URL version for the rare, genuinely incompatible redesign.

Expand and contract

Most "breaking" changes can be made as a series of non-breaking ones. Suppose you want to replace an invoice's flat client_name field with a nested client object.

  1. Expand. Add client alongside client_name, and return both. Nothing breaks.
  2. Migrate. Update your documentation, examples and SDKs to use the new field. Mark the old one as deprecated in the OpenAPI description.
  3. Measure. Find out who still uses the old field. For request fields, you can log it per API key. For response fields you usually can't see reads, so rely on SDK versions, surveys and direct contact.
  4. Announce a sunset date, with deprecation headers and emails to the affected developers.
  5. Contract. Remove the old field in the next major version, after the date has passed.

It's the same pattern as the database migrations of chapter 17, and as branch by abstraction in The Engineer's Craft: never change a contract in one step when you can change it in several reversible ones.

Deprecating out loud

Two standard response headers tell clients about deprecation. RFC 9745, published in 2025, defines Deprecation, whose value is the moment the endpoint became deprecated. RFC 8594 defines Sunset, the date it will stop working, which must not be earlier than the deprecation date. A Link header with rel="deprecation" points at the migration guide.

Headers alone aren't enough, because few clients read them. Email the developers behind every API key that still calls the old endpoint, which is one reason every key should be tied to a real contact. Put the change in your changelog. Before the sunset date, run scheduled brownouts: switch the old endpoint off for an announced hour or two, so hidden dependencies break while there's still time to fix them. After the sunset, return 410 Gone with problem details pointing at the migration guide, not a bare 404.

The contract as a file

Describe the API in an OpenAPI document and treat it as the source of truth. It generates reference documentation, client SDKs and mock servers. More importantly, it can be diffed: a CI step comparing the new specification with the last release, using a tool such as oasdiff, flags removed fields, new required parameters and narrowed types before they reach a customer.

Note the description on status. Telling clients up front that the enum may grow, and how to treat unknown values, turns a future breaking change into a non-event.

Common traps
  • "We only added a field." New enum values and strict deserialisers make additions break things too.
  • A new version for every change. Version 14 after two years means fourteen APIs to maintain.
  • Deprecating blind. If you can't name who uses an endpoint, you can't warn them.
  • Removing on the date, unannounced. Without brownouts, the first sign of trouble is a customer's outage.
  • Internal models as the API. When the API mirrors your tables, every refactor becomes a breaking change.

Chapter 04

REST, GraphQL, gRPC and real time

6 min read3 exercises4 flashcards

Each API style optimises for a different constraint. Choose by who your clients are and how they fetch data, not by fashion. Most products need plain HTTP plus, at most, one real-time channel.

JSON over HTTP

The style of chapters 1 to 3, usually called REST, whether or not it meets every one of Roy Fielding's constraints. Its strengths are that it's universal: every language and tool speaks it, curl can debug it, HTTP caching and CDNs work with it unmodified, and OpenAPI gives it a schema. Its weaknesses show on complex screens. A client may over-fetch, receiving fifty fields to show three, or under-fetch, needing five requests to draw one dashboard.

GraphQL

Facebook open-sourced GraphQL in 2015. The client sends a query naming exactly the fields it needs, across related objects, to a single endpoint, and a strongly typed schema describes everything available. It shines when many different clients, such as web, iOS, Android and partners, need different slices of the same data, and when a frontend team wants to move without waiting for new endpoints.

The costs are real, and they land on the server.

  • N+1 queries. A naive resolver for client runs once per invoice: twenty invoices, twenty-one queries. The fix is a DataLoader, which collects every key requested during one tick and fetches them in a single batch.
  • Hostile queries. A deeply nested query can ask for invoices, their clients, the clients' invoices, and so on, until the server falls over. Limit depth, compute a cost for each query, and consider allowing only pre-registered persisted queries in production.
  • Caching. Every query is a POST to one URL, so HTTP caches and CDNs can't help without persisted queries.
  • Authorisation per field. Because a client can reach any field through any path, checks must live in the resolvers, not in a handful of endpoints.
  • Errors. A GraphQL response is usually 200 OK with an errors array, so monitoring by status code sees nothing.

gRPC

gRPC sends Protocol Buffers over HTTP/2. You define services and messages in .proto files, and code generators produce typed clients and servers for many languages. It's compact, fast, supports streaming in both directions, and makes breaking changes visible at compile time. That makes it an excellent choice between your own services. It's a poor choice for public or browser-facing APIs: browsers can't speak it natively and need gRPC-Web or a proxy, and binary payloads can't be read by a human with curl.

In an all-TypeScript codebase, typed remote procedure call libraries such as tRPC offer similar end-to-end type safety without a schema language, at the cost of tying the client and server tightly together.

How to choose

  • A public API for other developers: JSON over HTTP, described in OpenAPI, with webhooks (chapter 14) for events.
  • Your own web and mobile apps, with varied, data-heavy screens and a dedicated frontend team: GraphQL can pay for itself. So can a backend-for-frontend that exposes screen-shaped endpoints.
  • High-volume calls between your own services: gRPC.
  • The server needs to push to a browser: server-sent events first; WebSockets only if the browser must talk back continuously.
  • A new product with one web client: plain JSON over HTTP. You can add the others when a real need appears. Removing them is much harder.
Common traps
  • GraphQL without limits. No depth or cost limits means any client can take the server down.
  • WebSockets for one-way updates. All of the operational cost, none of the benefit.
  • gRPC at the browser edge. You'll spend your time on proxies and tooling.
  • Real time without recovery. Connections drop; if nothing refetches on reconnect, users see stale data and never know.
  • Choosing by fashion. The API style your favourite company uses solved their problem, not yours.

Part II

Identity and access

Who is this, and what may they do? Getting either question wrong is the most common way real products leak data. Three chapters: proving identity, delegating it with OAuth, and deciding what each identity may touch.

Chapter 05

Authentication

9 min read3 exercises4 flashcards

Authentication proves who someone is. Store as little as you can, hash what you must, keep sessions in locked-down cookies, and treat account recovery as part of the login, because attackers do.

Build or buy?

For most products, use your framework's built-in authentication or a managed identity provider rather than writing your own. Authentication is full of subtle, security-critical details, and the maintained options have already fixed the bugs you haven't met yet. But you still need everything in this chapter, because you have to configure those tools correctly, judge whether they're any good, and debug them when a user can't log in.

Passwords, if you have them

Never store a password. Store a hash made by a deliberately slow, memory-hard algorithm, so that a stolen database is expensive to crack. OWASP's current guidance is Argon2id with at least 19 MiB of memory, 2 iterations and a parallelism of 1. Fall back to scrypt if Argon2id isn't available, and use bcrypt, with a cost of at least 10, only in legacy systems, remembering that it ignores everything after 72 bytes. Fast hashes such as SHA-256 on their own are wrong for passwords, and encryption is wrong too, because it's reversible.

What to demand of the password itself changed in 2025, when NIST finalised SP 800-63B-4.

  • Length over complexity. At least 15 characters when a password is the only factor, and at least 8 when it's one factor of several.
  • No composition rules. Stop requiring a symbol, a digit and a capital letter. They produce Password1!.
  • Screen against breached and common passwords instead, for example with the k-anonymity range lookup of Have I Been Pwned, which never sends the password itself.
  • Allow long passwords, spaces and Unicode, at least 64 characters, and never block pasting. Password managers depend on it.
  • No forced periodic changes. Require a change only when there's evidence of compromise.

Sessions and cookies

After a successful login, create a session: a long random identifier, at least 128 bits from a cryptographically secure source, stored on the server with the user it belongs to. Send only that identifier to the browser, in a cookie with every protective attribute set.

  • HttpOnly stops JavaScript reading the cookie, so a cross-site scripting bug can't simply steal the session.
  • Secure sends it only over HTTPS.
  • SameSite=Lax withholds it from cross-site form posts and embedded requests, which blunts cross-site request forgery.
  • The __Host- prefix makes the browser refuse the cookie unless it's secure, has Path=/, and has no Domain, so a subdomain can't overwrite it.

Issue a new session identifier at login, and again whenever privileges change, which defeats session fixation. On logout, delete the session on the server, not just the cookie. Give sessions an idle timeout and an absolute lifetime, and let users see their active sessions and sign out of all of them.

For a web app talking to its own backend, server-side sessions in HttpOnly cookies are simpler and safer. A JWT is a token format, not a session strategy. If you do use JWTs, verify the signature with an algorithm you choose, never the one named in the token, and check issuer, audience and expiry every time. Never keep them in localStorage, where any script on the page can read them.

Cross-site request forgery

Browsers attach cookies automatically, so another site can try to make your user's browser submit a form to your app. SameSite=Lax blocks cookies on cross-site POSTs but still sends them on ordinary top-level links, which is one more reason a GET must never change anything. Add a second layer for every state-changing request: a CSRF token tied to the session, or a check that the Origin or Sec-Fetch-Site request header says the request came from your own site.

Multi-factor authentication and passkeys

A second factor stops most account takeovers that start with a leaked password. The options differ a lot in strength.

  • Passkeys are public-key credentials created by the user's device and bound to your site's domain. There is no shared secret to steal from your database, and a phishing page on a lookalike domain simply can't use them. Synced passkeys are backed up by the platform across the user's devices, and NIST's 2025 guidance recognises them. Offer them as a primary sign-in method, and make them appear in the browser's autofill so people actually find them.
  • Authenticator apps generate time-based one-time codes. Good, but a convincing phishing page can relay them in real time.
  • SMS codes are the weakest: SIM-swap fraud and message interception defeat them. Better than nothing, but not a foundation.

Whatever you offer, issue single-use recovery codes when a user enrols, and store them hashed, like passwords.

Account recovery is part of the login

An attacker doesn't need to defeat your login if your "forgot password" flow is weaker. The rules:

  • Reset tokens are long and random, single-use, and expire within about an hour.
  • Store only a hash of the token, so a leaked database doesn't hold working reset links. A fast hash is fine here, because the token is random rather than chosen by a person.
  • Say the same thing whether or not the email exists: "If an account exists for that address, we've sent a link."
  • Rate-limit reset requests, and notify the user by email whenever their password or second factor changes.
  • After a reset, end every other session.
  • Recovery must not be weaker than sign-in. A passkey protected by an SMS fallback is only as strong as SMS.

Throttling and enumeration

Limit login attempts per account and per IP address (chapter 16), with growing delays rather than permanent lockouts, which an attacker could use to lock real users out. Return the same message, taking about the same time, for "no such user" and "wrong password", so attackers can't discover which emails have accounts. Sign-up is the hard case: "this email is already registered" leaks the same fact. One answer is to accept the sign-up form either way and email the address, telling an existing user that someone tried to register with it.

Common traps
  • Home-made crypto. Your own session format, token scheme or hashing. Use maintained libraries.
  • Tokens in localStorage. Readable by every script on the page, including third-party ones.
  • Account existence leaks through login, reset and sign-up messages or timings.
  • Hostile password rules. Blocking paste, demanding symbols, forcing rotation.
  • Recovery weaker than login. The attacker walks around the front door.
  • Sessions that survive a password change. The attacker stays logged in.

Chapter 06

OAuth 2.0 and OpenID Connect

8 min read3 exercises4 flashcards

OAuth lets one application act on a user's behalf at another without ever seeing their password. OpenID Connect adds a standard way to learn who the user is. Use the authorization code flow with PKCE, keep tokens out of the browser, and validate everything you receive.

The problem OAuth solves

Before OAuth, an app that wanted your contacts asked for your email password, and then had full, permanent access to your account. OAuth replaces that with a limited, revocable grant: the user approves specific permissions, called scopes, at the provider, and your app receives an access token that can do only those things.

Four parties are involved. The user owns the data. The client is your app. The authorization server authenticates the user and issues tokens; think of Google's or Microsoft's sign-in. The resource server is the API holding the data. OAuth on its own is about delegated access, not about who the user is. OpenID Connect (OIDC) adds an ID token, a signed statement of who signed in, and that's what "Sign in with Google" actually uses.

The authorization code flow, with PKCE

  1. Start. Your server generates a random state and a random PKCE code_verifier, keeps both in the user's pre-login session, and redirects the browser to the authorization server with the verifier's SHA-256 hash, the code_challenge.
  2. Sign in. The user authenticates at the provider and approves the requested scopes. Your app never sees their credentials.
  3. Return. The provider redirects to your registered redirect_uri with a one-time code and the same state.
  4. Check and exchange. Your server confirms state matches, then sends the code, the original verifier and its own client credentials straight to the provider's token endpoint.
  5. Validate. It receives the tokens and validates the ID token's signature, issuer, audience, expiry and nonce.
  6. Sign in locally. It creates its own session (chapter 5) and gives the browser only a session cookie.

Each ingredient blocks a specific attack. state stops an attacker completing a login in your user's browser with the attacker's own code. PKCE stops a stolen code being redeemed by anyone who doesn't also hold the verifier. The nonce ties an ID token to one login attempt so it can't be replayed. Exact matching of redirect URIs, with no wildcards, stops codes being delivered to an attacker's page.

Note how the user is identified: by the pair of issuer and subject, iss and sub, which the provider guarantees are stable and unique. Never identify users by the email claim. Some providers let users set an email address they haven't verified, and some allow it to change. Apps that matched accounts by email have been taken over by attackers who simply registered a victim's address at a provider. Link a provider identity to an existing account by email only when the provider marks the email as verified, and preferably only after the user has also signed in to the existing account.

The tokens

TokenWhat it isTypical lifetimeWho uses it
Authorization codeA single-use voucherSeconds to a minuteYour server, to exchange for tokens
Access tokenPermission to call an API, within its scopesMinutes to an hourThe resource server
Refresh tokenGets new access tokens without asking the user againDays to months; rotated on each useThe authorization server

Never send an ID token to an API as if it were an access token, and never accept an access token issued for a different audience. With refresh-token rotation, each refresh returns a new refresh token and invalidates the old one; if an old one is ever presented again, someone has copied it, so revoke the whole family.

What's deprecated, and why

RFC 9700, the OAuth 2.0 Security Best Current Practice published in January 2025, retired two flows you'll still find in old tutorials. The implicit grant returned access tokens directly in the redirect URL, where browser history, logs and referrer headers could leak them. The resource owner password grant had the app collect the user's password, defeating the point of OAuth. It also requires PKCE for every authorization code flow. The in-progress OAuth 2.1 consolidates these rules into one document.

Tokens in browser apps

The IETF's guidance for browser-based applications, now published as RFC 10017, prefers a backend-for-frontend: your own server runs the flow, holds the tokens, and gives the browser nothing but an HttpOnly session cookie, exactly as in the diagram. If a single-page app must hold tokens itself, keep them in memory only, never in localStorage or sessionStorage, where every script on the page, including third-party ones, can read them.

When you're the provider

If your product offers an API to other companies, you become the authorization server. Use a proven implementation rather than writing one. Design scopes around what integrations actually need, such as invoices:read and payments:write, and show them plainly on the consent screen. Let customers see and revoke every connected app.

For server-to-server customers, API keys are often simpler than OAuth. Treat them like passwords: show a key once, store only its hash, allow several per account so they can be rotated without downtime, scope them, and give them a recognisable prefix such as ik_live_. That lets secret-scanning tools, including those run by code hosts, spot a key accidentally committed to a public repository.

Common traps
  • OAuth as login without OIDC. An access token proves access, not identity. Validate an ID token.
  • Users matched by email. Key them by issuer and subject.
  • Skipping state or PKCE. Each blocks a real attack.
  • Loose redirect URI matching. Wildcards and prefix matching deliver codes to attackers.
  • Tokens in localStorage. Readable by any script on the page.
  • Long-lived access tokens with no rotation and no way to revoke them.

Chapter 07

Authorisation and multi-tenancy

7 min read3 exercises4 flashcards

Authentication says who someone is; authorisation says what they may do, and to which object. Check it on every request, for every object, in one place, and make it impossible to query across customers by accident.

The most common serious bug in APIs

The OWASP API Security Top 10 has ranked the same flaw first since its first edition in 2019: broken object level authorisation, often called IDOR, for insecure direct object reference. The handler checks that someone is logged in, but not that the object they asked for is theirs. An attacker signs up, notices their invoice is inv_1043, and asks for inv_1042.

Two relatives appear in the same list. Broken object property level authorisation is a user sending a field they shouldn't control, such as {"role": "owner"} or {"team_id": "…"}, and the server saving it; this is also called mass assignment. Broken function level authorisation is an admin-only endpoint that a regular user can call because only the admin screen, not the endpoint, was protected.

Three models

Role-based (RBAC)The user's role"Admins can delete invoices."Most products, most of the time

Relationship-based (ReBAC)A graph of who relates to what"You can view a document if you belong to a team that owns its folder."Sharing, nested workspaces, documents

Most products need roles plus a few attribute rules. Relationship-based systems, modelled on Google's Zanzibar paper and available as open-source and hosted services, earn their complexity when users share individual objects with each other across a hierarchy.

One policy, in one place

Checks such as if user.role == "admin" scattered through handlers drift apart, and one endpoint always gets forgotten. Put every decision in a single policy module, deny by default, and test it exhaustively.

Your interface should hide the buttons a user can't use, because that's good design. But the interface is never the check. Every request is checked again on the server, because anyone can send any request with curl.

Multi-tenancy

In a business product, each customer organisation is a tenant: a team, a workspace, a studio. Every row belongs to one tenant, and one customer seeing another's data is the kind of incident that ends companies. There are four ways to isolate tenants.

If the setting has never been set on a connection, current_setting(…, true) returns null, the comparison fails, and the query sees no rows. On a pooled connection where an earlier request set it, the setting goes back to an empty string when that transaction ends, and casting it to uuid raises an error instead. Both are safe failures: no request sees another team's rows. SET LOCAL lasts only until the end of the transaction, which is what stops one request's team from carrying over to the next request on the same pooled connection. The application must connect as a role that doesn't own the tables and doesn't have the BYPASSRLS attribute. And background jobs, admin tools and reports need the tenant context too; they're where scoping is most often forgotten.

Mass assignment

Never copy a request body straight onto a model. Define an explicit input schema for each action, listing the only fields a caller may set, and reject anything else.

Audit logs and impersonation

In any product used by teams, record who did what, to which object, and when: actor, tenant, action, object type and id, timestamp, and a little context. Keep the log append-only. Customers will ask for it, support needs it to answer "who deleted this?", and security needs it after an incident.

Support staff will eventually need to see what a customer sees. Build impersonation deliberately: explicit, time-limited, read-only by default, recorded in the audit log, and ideally visible to the customer. A hidden "log in as anyone" switch is a breach waiting for an insider.

Common traps
  • Logged in, therefore allowed. Authentication without object-level checks.
  • Checks only in the interface. The API is the real front door.
  • 403 that confirms existence. For private objects, "not yours" should look like "not found".
  • Request bodies bound to models. Mass assignment of roles, owners and prices.
  • Jobs and reports without tenant scope. The code path nobody reviews for authorisation.
  • Unaudited god mode. Admin powers with no record of their use.

Chapter 08

The web platform

6 min read3 exercises4 flashcards

Frameworks come and go; HTML, CSS, the DOM and the event loop are what all of them compile down to. Learn the platform first, and every framework becomes easier to use well.

Semantic HTML does work for you

Use each element for its meaning: <button> for actions, <a href> for navigation, <form> and <label> for input, <nav> and <main> for landmarks, headings in order, <table> for tabular data. The browser attaches behaviour to meaning. A native button is focusable, activates with Enter and Space, announces itself to screen readers, supports a disabled state, and submits its form, all for free. A div with a click handler does none of it.

The rule of thumb: if it changes something, it's a button; if it goes somewhere, it's a link.

Forms: the most important interface you'll build

Sign-up, sign-in, checkout, settings: the moments that matter most in a product are forms. The platform gives you a lot if you let it.

  • A visible <label> for every input, tied to it with for and id. A placeholder is not a label; it disappears as soon as someone types.
  • The right type: email, tel, url, date. They bring the right mobile keyboard and built-in checks.
  • An autocomplete token such as email, username, current-password, new-password, one-time-code or postal-code. Password managers and autofill depend on them, and they save your users more time than any feature you'll build this month.
  • Native constraints such as required and minlength as a first line of feedback. The server's validation is the one that counts.
  • Errors next to the field, in words, connected with aria-describedby, and never by clearing what the user typed.

CSS layout: flexbox and grid

Set box-sizing: border-box everywhere, so padding and borders sit inside an element's width instead of adding to it. Then use two layout tools. Flexbox lays items out along one axis: a toolbar, a row of buttons, a label beside its value. Grid lays items out in two dimensions: page structure, card grids, forms with aligned columns. Positioning things with absolute offsets and magic numbers is almost always a sign one of these was the right tool.

Design for the smallest screen first, and let layouts grow. Container queries let a component respond to the space it's actually given rather than to the whole window, so the same invoice card works in a narrow sidebar and a wide list.

The DOM and events

The DOM is the live tree of objects the browser builds from your HTML, and every framework ultimately reads and writes it. Two event concepts are worth knowing cold. Events bubble from the element where they happened up through its ancestors, so one listener on a list can handle clicks on every row, including rows added later. That's event delegation. And event.target is where the event started, while event.currentTarget is the element whose listener is running.

The event loop

Each page runs its JavaScript on one main thread, which is also the thread that responds to input and paints the screen. Work arrives as tasks: a click handler, a timer, a network callback. After each task, the browser runs every queued microtask, which is where promise callbacks go, and then it may render. So a task that runs for 300 milliseconds freezes the page for 300 milliseconds: clicks wait, typing lags, nothing repaints. The browser calls anything over 50 milliseconds a long task, and long tasks are the main cause of poor responsiveness scores (chapter 11).

To keep the page responsive, break long work into chunks and yield to the browser between them, move heavy computation to a Web Worker, or do it on the server. Where it's supported, await scheduler.yield() is the cleanest way to give the browser a chance to handle input mid-task.

Progressive enhancement

Start with HTML that works on its own: a form that posts to the server and gets a page back. Then enhance it with JavaScript for a smoother experience. JavaScript fails more often than developers think: flaky networks, browser extensions, a script error on an old device, a corporate proxy. When it fails, an enhanced form still works, and a JavaScript-only form is a blank rectangle. Server-rendered forms with a layer of enhancement are also, very often, the fastest thing you can ship.

Common traps
  • Div soup. Clickable divs instead of buttons and links.
  • Placeholders as labels. Gone the moment someone types, and often too faint to read.
  • Blocking paste in password fields. It breaks password managers and pushes people towards weak passwords.
  • type="number" for things that aren't quantities. Card numbers and postcodes lose leading zeros and gain spinner arrows.
  • Layout by magic numbers. Absolute positioning that works on one screen size.
  • Long tasks on the main thread. The page looks loaded and ignores the user.

Chapter 09

Accessibility

7 min read3 exercises4 flashcards

Accessibility means people with disabilities can use what you build, whether by keyboard, screen reader, magnification or voice. Build it in from the first component, because retrofitting is expensive, and in more and more markets it's the law.

Why it matters

The World Health Organization estimates that about 1.3 billion people, one in six, live with a significant disability. Add temporary and situational limits, such as a broken wrist, a toddler on one arm, or sunlight on a screen, and accessibility stops being about a minority of users.

The web is still doing badly. WebAIM tests the home pages of the top million websites every year. In its 2026 report, 95.9% had detectable failures of the Web Content Accessibility Guidelines, an average of 56 errors per page and worse than the year before. The encouraging part is that six kinds of error account for 96% of everything found, and all six are straightforward to fix.

FailureHome pages affectedThe fix
Low-contrast text83.9%At least 4.5:1 for normal text, 3:1 for large text and interface parts
Images without alt text53.1%Describe what the image means; alt="" if it's purely decorative

Empty links46.3%Give icon-only links an accessible name
Empty buttons30.6%Give icon-only buttons an accessible name
No document language13.5%<html lang="en">

The law is catching up. The European Accessibility Act has applied since 28 June 2025 to e-commerce and many other consumer services sold in the EU, including by companies based elsewhere, and it measures conformance against a standard built on WCAG. In the United States, lawsuits over inaccessible websites run into the thousands every year. The usual target is WCAG 2.2, level AA.

The four principles

WCAG organises everything under four principles, known by the acronym POUR. Content must be perceivable: available to at least one sense a user has, so images have text alternatives and videos have captions. The interface must be operable: usable with a keyboard, with enough time, without triggering seizures. It must be understandable: predictable, readable, and helpful when mistakes happen. And it must be robust: built with standard markup that assistive technologies can interpret.

Accessible names

Every interactive element needs a name that a screen reader can announce. Text inside a button is its name. An icon has no name unless you give it one.

Note the specific name. A table with fifty rows, each with a button called "Delete", is fifty identical announcements. Including the invoice number tells a screen reader user which invoice they're about to delete.

Keyboard and focus

Everything must work with a keyboard alone: Tab to move, Enter and Space to activate, Escape to dismiss. The tab order follows the order of elements in the HTML, so keep the source order logical rather than rearranging things visually with CSS. Every focused element needs a clearly visible indicator. Never remove the outline without replacing it; :focus-visible lets you show it for keyboard users without showing it on every mouse click.

Single-page apps must manage focus themselves, because they change the page without the browser's usual navigation. After a route change, move focus to the new page's main heading. When a dialog opens, focus moves into it and stays there until it closes, and then returns to whatever opened it. The native <dialog> element, opened with showModal(), does most of this for you: it traps focus, closes on Escape, and makes the rest of the page inert.

ARIA: the first rule

ARIA attributes add roles, states and names that HTML can't express on its own. The W3C's first rule of ARIA is not to use it when a native element already does the job. WebAIM found that home pages using ARIA had noticeably more detected errors on average than those without it. That's a correlation, not proof of cause, but it matches experience: misapplied ARIA actively makes pages worse, because it overrides what the browser would have announced correctly. The ARIA Authoring Practices Guide puts it bluntly: no ARIA is better than bad ARIA.

Where ARIA earns its place: announcing changes that happen without a page load, such as "Invoice sent", through a live region; the state of disclosure buttons with aria-expanded; the current page in navigation with aria-current="page"; and linking inputs to their error messages with aria-describedby and aria-invalid.

What WCAG 2.2 added

The 2023 revision added criteria that catch common modern mistakes. Focused elements must not be completely hidden behind sticky headers or cookie banners. Click targets must be at least 24 by 24 CSS pixels, or spaced out enough to avoid mis-taps. Anything done by dragging needs a single-pointer alternative. Help must appear in a consistent place. Users shouldn't have to re-enter information they've already given. And sign-in must not depend on a cognitive test, such as retyping characters or solving a puzzle, without an alternative; allowing paste and password managers, as chapter 5 recommends, helps satisfy it.

Testing

Automated checkers such as axe-core and Lighthouse find the mechanical problems quickly, and they belong in your CI pipeline. They can't tell you whether alt text is meaningful, whether the focus order makes sense, or whether a flow is usable at all, so pair them with manual checks.

  • Put the mouse away and complete every key flow with the keyboard: sign up, create an invoice, send it, pay it.
  • Use a screen reader for a few minutes on each new component: VoiceOver on macOS and iOS, NVDA on Windows, TalkBack on Android.
  • Zoom to 200% and 400%, and check that nothing overlaps or disappears and that you rarely need to scroll sideways.
  • Turn on reduced motion and high contrast in the operating system, and check that your interface respects them.
Common traps
  • Accessibility as a final audit. By then, the inaccessible patterns are in every component.
  • Overlay widgets. Scripts that promise automatic compliance don't deliver it. In 2025 the US Federal Trade Commission fined one such vendor over claims that its tool made sites compliant.
  • Removing focus outlines without providing a replacement.
  • Colour as the only signal. A red dot for "overdue" says nothing to someone who can't distinguish red.
  • Custom widgets built from divs with no keyboard support.
  • ARIA sprinkled on to silence a checker rather than to describe real behaviour.

Chapter 10

Components, state and data fetching

7 min read3 exercises4 flashcards

Most frontend complexity comes from state kept in the wrong place. Treat server data as a cache of something you don't own, keep interface state as local as possible, put shareable state in the URL, and derive everything else.

Components

A component is a function from its inputs, called props, and its own state, to a piece of interface. The deep-module thinking of The Engineer's Craft applies directly: a good component does one job, exposes a small, clear set of props, hides its internals, and has no hidden dependencies on global variables. Compose small components through their children rather than building one component with thirty configuration flags.

TypeScript's Record<InvoiceStatus, string> is doing quiet work here. Add a new status to the union and this file stops compiling until it has a label, which is exactly the reminder you want.

Four kinds of state

KindExamples in the invoicing appWhere it belongs
Server stateInvoices, clients, the signed-in userA query cache such as TanStack Query, or your framework's data loaders
URL stateFilters, sort order, page, selected tab, the open invoiceThe path and query string
Local interface stateIs this menu open? What has been typed so far?The component itself, with useState
Global client stateTheme; a draft spanning several screens of a wizardA small store or context, and rarely needed

The React community's biggest shift of the last few years was recognising that server state and client state are different problems. Server data is a borrowed copy of something that lives elsewhere. It goes stale, other people change it, it must be refetched, deduplicated and invalidated. Putting it into a general-purpose global store means rebuilding a cache badly, by hand.

Derive, don't duplicate

If a value can be computed from other state, compute it. Every extra piece of state is something that can fall out of sync.

Server state in a query cache

Two components asking for the same invoices share one request. Data refreshes in the background when the window regains focus. Failed requests retry. After sending an invoice, every cached invoice list is marked stale and refetched. None of that is code you write.

Every view that shows data has four states, not one: loading, error, empty and data. Design all four. The empty state of a brand-new account is the first thing a new user sees, and a blank table with no guidance is a common reason people never come back.

URL state

Filters, sort order and the selected tab belong in the URL. Then a view can be bookmarked, shared with a colleague, survives a refresh, and the back button does what people expect.

Forms

Keep form fields local until submission, validate on the client for fast feedback, and treat the server's answer as final. Where you can, share one validation schema between client and server so the rules can't drift apart. Show server errors next to the right fields, using the field paths from the problem details of chapter 1. React 19 added Actions for form submissions, which track pending and error state for you and cooperate with server-side rendering.

Optimistic updates

For quick, low-risk, almost-always-successful actions, such as archiving an invoice or renaming a client, update the interface immediately and roll back if the server refuses. It makes a product feel instant. Never do it for anything irreversible or financial: a payment must show "processing" until the server confirms it.

Where rendering happens

React Server Components, now the default in frameworks such as Next.js, let some components run only on the server: they fetch data directly and send rendered output, and none of their code ships to the browser. Components that need interactivity are marked as client components. A common pattern is server components for the initial page, a query cache for data that changes while the page is open, and local state for the rest. Chapter 11 looks at what this does for performance.

Common traps
  • A global store used as a cache. Copying server data into it means hand-writing staleness, refetching and invalidation.
  • Derived values in state. They drift out of sync with their source.
  • Filters that live only in memory. Refresh the page and they're gone; share the link and they're gone.
  • Only designing the happy path. No loading, error or empty states.
  • Fetching in useEffect with no cache. Duplicate requests, and responses that arrive out of order.
  • Optimism about money. Optimistic updates on payments or sends that can't be undone.

Mix strategies within one product. Bytes are a budget

JavaScript is the most expensive thing you can send. After downloading, it must be parsed, compiled and run on the main thread, and on a mid-range phone that takes several times longer than on your laptop. Set a budget, such as a maximum compressed size of JavaScript for each route, and fail the build when a change exceeds it. Then keep under it.

  • Split code by route, so the dashboard doesn't download the settings page.
  • Load heavy, rarely used components on demand: charts, rich-text editors, PDF previews.
  • Audit dependencies with a bundle analyser. A date library imported for one format call can outweigh your whole application.
  • Prefer the platform. Intl.NumberFormat formats money in every locale, and <dialog> is a modal, without a single byte of library code.

Images and fonts

Images are usually the largest bytes on a page and often the Largest Contentful Paint element itself. Serve modern formats such as AVIF or WebP, offer several sizes with srcset, and always give width and height so the browser reserves space and nothing shifts. Lazy-load images below the fold, but never the main image at the top; mark that one fetchpriority="high" instead.

For fonts, use as few families and weights as you can, subset them to the characters you need, preload the main one, and use font-display: swap so text is readable before the font arrives.

Caching

Build tools put a content hash in each asset's file name, such as app.3f9a1c.js, which changes whenever the file does. That makes it safe to cache those files forever. The HTML that references them must never be cached like that, or users will keep loading old versions after every deploy.

A classic confusion: no-cache doesn't mean "don't cache". It means "check with the server before using the cached copy", which is exactly right for HTML. no-store is the one that means don't keep it at all.

Perceived performance

How fast something feels matters as much as how fast it is. Respond to every click within about 100 milliseconds, even if only by showing that something has started. Use skeletons that match the final layout. Prefetch the next likely page when the user hovers over a link. And use optimistic updates (chapter 10) for safe, reversible actions.

Common traps
  • Testing only on a fast laptop. Your users' median device is slower than yours, often by several times.
  • Lazy-loading the hero image. It delays exactly the element that decides Largest Contentful Paint.
  • A whole library for one feature. Check the cost of every dependency.
  • Images without dimensions. The page jumps as they load.
  • Hydrating everything for one interactive widget.
  • Long-lived caching on HTML. Users are stuck on old versions after you deploy.

Behind the request

Much of what makes a product work happens after the response is sent: the email that goes out, the PDF that renders, the file that uploads, the webhook that arrives at three in the morning, the payment that settles. Four chapters on that machinery.

Chapter 12

Background jobs and scheduled work

8 min read3 exercises4 flashcards

Anything slow, unreliable, or not needed for the response belongs in a background job. Jobs run at least once, sometimes twice, and sometimes out of order, so make every job idempotent, retry with backoff, and give failures somewhere visible to land.

What belongs in a job

Sending email, rendering PDFs, calling third-party APIs, resizing images, imports and exports, delivering webhooks: anything that takes more than a few hundred milliseconds, or that can fail for reasons outside your control. The request records what needs to happen and returns quickly, often with 202 Accepted (chapter 1). A worker process does the work. The user learns the outcome from a status in the interface, a server-sent event, or an email.

A job system has three parts: producers that enqueue jobs, a broker that stores them, and workers that run them. The broker might be Redis, RabbitMQ or a cloud queue, or it can simply be your PostgreSQL database, which is a very good choice for a young product for reasons that will become clear below.

How queues actually deliver

A worker takes a job and starts it. If the worker crashes before confirming it's finished, the broker assumes the job was lost and, after a timeout, hands it to another worker. That's the only safe behaviour, and it means a job can run twice: the first run may have done most of its work before dying. This is at-least-once delivery, and it's what every practical queue provides. Exactly-once delivery isn't really on offer. What you can have is exactly-once effects, by making jobs idempotent. Don't count on order, either: retries and parallel workers mean jobs can complete in any sequence.

Idempotent jobs

There's still a gap between sending and recording. If your email provider accepts an idempotency key, pass one and the gap closes. If it doesn't, you must choose which way to fail. Record first and you risk never sending: at most once. Send first and you risk sending twice: at least once. For a receipt, an occasional duplicate is far better than a missing one. For a charge, neither gap is acceptable, which is why payment APIs support idempotency keys (chapter 15).

Pass identifiers in job payloads, not whole objects. The worker should load the current invoice when it runs, not act on a snapshot from minutes ago, and payloads containing personal data end up copied into logs and dashboards.

Retries, backoff and dead letters

Retry transient failures with exponential backoff and jitter, as The Engineer's Craft describes, and cap the number of attempts. Don't retry permanent failures at all: an email address the provider rejects as invalid will be just as invalid in an hour. When a job exhausts its attempts or fails permanently, move it to a dead-letter queue with the error attached, alert someone, and provide a way to inspect it and run it again once the cause is fixed.

The dual-write problem, and the outbox

This innocent code has two different ways to go wrong.

If the process dies between the commit and the enqueue, the invoice says "sent" and no email ever goes. Swap the order and the job may run before the commit is visible, or the transaction may roll back after the job has been queued, emailing an invoice that was never sent. The database and the queue are two systems, and there's no transaction spanning both.

The transactional outbox fixes this. Write the job, or event, into an outbox table in the same database transaction as the business change, so both commit or neither does. A separate relay process reads new outbox rows, puts them on the queue, and marks them published.

FOR UPDATE SKIP LOCKED lets several relays run side by side, each claiming different rows. The relay can still publish a message and crash before marking it, so consumers see duplicates occasionally, and they must be idempotent. That's the point of the previous section. And if your job queue lives in the same PostgreSQL database, you get the same guarantee for free: enqueue the job inside the business transaction. That's a strong reason to start with a database-backed queue.

Scheduled work

Recurring work, such as "send reminders for overdue invoices every morning", brings three extra concerns. It must run once, not once per application server, so use a scheduler with unique jobs or take a database advisory lock. It must be idempotent over its window, so that running it twice on the same day sends each reminder once. And "every morning" raises the question of whose morning. Run the scheduler hourly and select the teams for whom it's now 9 a.m. locally.

Keep it visible

Queues fail quietly. Watch the depth of each queue, the failure rate, the size of the dead-letter queue, and above all the age of the oldest waiting job. A queue of 10,000 jobs moving quickly is healthy; a queue of 12 where the oldest has waited an hour is an incident. Break very long jobs into chunks, such as one job per thousand rows, so a crash doesn't restart from zero and a deploy doesn't have to wait an hour.

Common traps
  • Slow work inside the request. The user waits, and a timeout loses the work.
  • Jobs that aren't idempotent. Duplicate emails, fees and exports.
  • Retrying permanent failures until the heat death of the universe.
  • Enqueueing outside the transaction. Lost jobs, or jobs for changes that never happened.
  • A scheduler on every server. Every reminder goes out once per machine.
  • Whole objects in payloads. Stale data, and personal data spread through your queue.
  • No alert on job age. The queue stalls on Friday night; customers notice on Monday.

Chapter 13

Files, uploads and CDNs

7 min read3 exercises4 flashcards

Files are untrusted input with a size. Upload them straight to object storage with a narrow, short-lived permission, never trust their names or declared types, check them in the background, and serve them with the right access rules.

Keep file bytes away from your app servers

Streaming a 40 MB upload through your API ties up a worker for the whole transfer, uses memory, and runs into request timeouts on slow connections. Instead, let the browser upload directly to object storage, such as S3 or any compatible service. Your API's only job is to decide whether the upload is allowed and to sign a permission for exactly that upload.

The signed policy is enforced by the storage service itself: the exact key, the declared type, a size range, and a five-minute lifetime. The browser posts the file with the returned fields, then tells your API the upload is finished, or storage sends an event to a worker directly.

Never trust the file

  • The name is hostile. User-supplied file names can contain ../ path traversal, control characters, or markup that breaks your pages. Generate your own storage keys, as above. Keep the original name as metadata, cleaned up, only for display.
  • The type is a claim. A file's extension and its declared content type are whatever the uploader said. Check the actual bytes after upload: a PDF starts with %PDF-, a PNG with an eight-byte signature, a JPEG with FF D8 FF.
  • Files other people will open need scanning. Run a malware scanner in the processing job and quarantine files until they pass.
  • Re-encode images. Decoding and re-saving an image removes metadata, such as GPS coordinates in a phone photo, and neutralises many malformed-file exploits. Cap pixel dimensions first, to avoid decompression bombs that expand to gigabytes.
  • SVG is code. An SVG file is XML that can contain scripts. Don't serve users' SVGs from your own domain unless you've sanitised them; rasterising them is safer.

A processing pipeline

Give every upload a status the interface can show: pending while it's uploading, processing while a job checks the type, scans it and generates thumbnails, then ready or rejected with a reason a person can act on, such as "This file isn't a PDF". The job follows chapter 12: idempotent, retried on transient failures, and failing into a visible queue.

Serving files

Public files, such as product images and your own static assets, go through a CDN with content-hashed names and long cache lifetimes (chapter 11). Private files, such as invoice PDFs and receipts, stay in a private bucket. When a user asks for one, check authorisation (chapter 7), then redirect to a signed URL that expires within a minute or two.

Serve user-uploaded content from a separate domain, such as files.example-usercontent.com, so that even a file that slips through your checks can't run script with access to your application's cookies. Send X-Content-Type-Options: nosniff so browsers don't second-guess the type, and Content-Disposition: attachment for anything that should download rather than open.

Don't email signed storage URLs. They either expire before the recipient clicks, or live long enough to be forwarded, leaked and reused. Email a link to a page in your app, which checks access and then issues a fresh, short-lived URL.

Deleting and keeping

When a record is deleted, delete its files too. Orphaned files cost money, and under privacy laws such as the GDPR a user's right to erasure includes their files. Set lifecycle rules so abandoned uploads, which were signed but never completed, disappear after a day. Decide deliberately how long backups and object versions keep deleted files, and say so in your privacy policy.

Common traps
  • The user's file name as the storage key. Path traversal, collisions and overwrites.
  • Trusting the declared type. A script renamed to invoice.pdf is still a script.
  • Public buckets for private documents. One guessed or leaked URL exposes them for good.
  • Serving uploads from your app's own domain. A hostile file runs with your cookies.
  • Long-lived signed URLs in emails. Forwarded, indexed, and leaked.
  • Location data left in photos. A user's home address, shared with everyone who sees the image.
  • Orphaned files after records are deleted.

Chapter 14

Webhooks, integrations and email

8 min read3 exercises4 flashcards

Every integration is a distributed system you don't control. Verify what arrives, acknowledge it quickly, process it idempotently, and reconcile what you missed. When you send email, prove to the inbox that it really comes from you.

Receiving webhooks

A webhook is an HTTP request another service sends you when something happens: a payment succeeded, an email bounced, a subscription renewed. Your endpoint is on the public internet, so anyone can send it anything, and the sender will retry, duplicate and reorder deliveries. Seven rules cover it.

  1. Verify the signature over the raw request body, with the shared secret, using a constant-time comparison.
  2. Check the timestamp is recent, typically within five minutes, so a captured request can't be replayed later.
  3. Deduplicate by event id. Senders retry whenever they're unsure you received something, so the same event can arrive twice.
  4. Acknowledge fast. Store the event and return 2xx within a few seconds, then do the real work in a background job.
  5. Don't trust the payload for anything important. Fetch the current state of the object from the provider's API.
  6. Expect any order. "Updated" can arrive before "created". Compare timestamps or versions, or simply fetch the current state.
  7. Reconcile. Webhooks get lost, and a sender disables endpoints that keep failing; Stripe does so after three days of failed retries. A daily job that lists recent objects from the provider and fixes anything you missed turns a silent loss into a delay.

Many providers now follow the Standard Webhooks specification: three headers carry an event id, a Unix timestamp and a signature, and the signature is an HMAC-SHA256 of the id, the timestamp and the body joined by dots. During a secret rotation, the signature header can carry several signatures, and any one matching is enough.

Verify against the raw bytes, before any parsing. Many frameworks parse JSON automatically, and if you re-serialise the parsed object to check the signature, spacing and key order change, and every valid webhook fails verification.

Sending webhooks

If your own product sends webhooks to customers, you're now the sender, and the same rules apply in reverse. Sign every delivery. Give every event a unique id and a type. Retry failures with exponential backoff over a day or more, then disable the endpoint and tell the customer. Show customers a log of recent deliveries with a button to resend. Support secret rotation. And keep payloads small; many APIs send only the event type and object id, so the receiver fetches the current object and never acts on stale data.

One risk is specific to senders: customers choose the destination URL. Without checks, someone registers an internal address and your servers helpfully post to your own private network. Validate destinations as chapter 16 describes.

Calling third-party APIs

Everything from The Engineer's Craft applies. Put each provider behind an adapter you own. Set a timeout on every call. Retry only transient failures of idempotent operations, with backoff and jitter. Respect the provider's rate limits and its Retry-After header. Use its test mode or sandbox in development. Log enough about each call to debug it later, without logging secrets. And decide in advance what your product does while the provider is down: queue the work and retry, show a clear message, or fall back to a manual path.

Transactional email

Password resets, receipts, invoices and reminders are transactional email: expected, individual, and important. Send it through a dedicated email provider, never directly from your servers, and keep it separate from marketing email, on its own sending stream or subdomain. If a newsletter draws spam complaints, it mustn't drag your password resets into the spam folder with it.

Inbox providers need proof that mail claiming to be from your domain really is. Three DNS records provide it.

  • SPF lists the servers allowed to send mail for your domain.
  • DKIM signs each message cryptographically, with a public key published in DNS.
  • DMARC tells receivers what to do with mail that fails those checks, and where to send reports.

Since February 2024, Gmail and Yahoo have required these from anyone sending 5,000 or more messages a day to their users, along with one-click unsubscribe headers (RFC 8058) on marketing mail, and a spam-complaint rate kept below 0.3%, and ideally below 0.1%. Gmail moved to rejecting non-compliant mail in November 2025. Set them up before launch, even while you're small; retrofitting them after deliverability has collapsed is much harder.

Handle the feedback. Providers report bounces and complaints, usually by webhook. Stop sending to addresses that hard-bounce, honour every unsubscribe immediately, and watch your complaint rate. In the messages themselves, include a plain-text version, use real text rather than text baked into images, and link to pages in your app rather than to raw file URLs.

Never let a development or staging environment send email to real people. Use the provider's sandbox mode, or route every outgoing message to a catch-all inbox. Chapter 20 comes back to this, because it's one of the most common and most embarrassing launch mistakes.

Notifications in general

Let users choose which notifications they get, on which channel, per type. Batch noisy events into digests. Respect quiet hours and time zones. And don't notify people about their own actions: a freelancer who just paid their subscription doesn't need an email telling them a payment was made.

Common traps
  • Parsing before verifying. The signature covers raw bytes, not your re-serialised JSON.
  • Doing the work inside the webhook request. Slow responses cause retries, and retries cause duplicates.
  • No deduplication. Every retried delivery is processed again.
  • Trusting delivery order. The older event arrives last and overwrites the newer state.
  • No reconciliation. A lost webhook means a customer who paid but is marked unpaid, forever.
  • Marketing and transactional mail mixed together. A newsletter complaint breaks password resets.
  • Real email from staging. Your test invoices, delivered to real customers.

Chapter 15

Payments

7 min read3 exercises4 flashcards

Payments are where a bug costs real money the same day. Let a payment provider handle the card, never trust a price sent by the browser, treat the provider's webhooks as the source of truth, and make every call that moves money idempotent.

Don't touch card numbers

The Payment Card Industry Data Security Standard, PCI DSS, governs anyone who handles card data, and handling raw card numbers brings hundreds of requirements. Use your provider's hosted checkout page, or its embedded card fields, which send card details from the browser straight to the provider without passing through your servers. That puts most merchants in the lightest self-assessment category, called SAQ A.

It doesn't make you exempt. Since version 4.0.1 of the standard became fully mandatory in March 2025, SAQ A merchants must also confirm that their payment page isn't open to malicious scripts, because a script on your checkout page can read what the customer types even into a provider's fields. Following the provider's integration instructions covers much of this. The rest is on you: keep third-party scripts off pages that take payment.

The shape of a payment

Modern card payments are a small state machine, not a single call, because the customer's bank may ask them to confirm, usually through 3-D Secure. In Europe, Strong Customer Authentication rules make that step routine.

  1. Your server creates a payment for an amount it calculated, and gets back a client secret.
  2. The browser uses the provider's library and that secret to collect card details and confirm the payment, including any bank challenge.
  3. The provider tells your server the outcome by webhook: succeeded, failed, or still processing.
  4. Your server fulfils the order, here by marking the invoice paid, in response to that webhook.

Why fulfil from the webhook rather than from the browser returning to your "thank you" page? Because users close tabs, phones lose signal after paying, and a redirect URL can be visited by anyone. The webhook, verified and re-fetched, is the only reliable record that money moved.

Never trust the client with prices

The browser should send identifiers, such as which invoice or which plan, and never amounts, currencies, quantities or discounts. Anything in a request can be edited. If your server takes {"amount": 49.00} from the client, someone will send {"amount": 0.49}.

Money in code

Store money as an integer number of minor units with its currency, or as a decimal, never as a float (The Engineer's Craft explains why). The float bug is real and quiet: in Python, int(19.99 * 100) is 1998, because 19.99 × 100 is actually 1998.9999999999998. And "minor units" aren't always cents. Japanese yen has no minor unit, so 5,000 yen is sent as 5000, while the Kuwaiti dinar has three decimal places. Keep a table of each currency's exponent from the ISO 4217 standard, and convert with decimals.

Decide, and write down, when rounding happens and how: per line or on the total, half-up or half-even. Tax across many jurisdictions is a specialism of its own; use a tax calculation service rather than a table you maintain by hand.

Subscriptions

If the invoicing app charges freelancers monthly, you've entered the world of billing cycles, prorated plan changes, free trials, failed renewals and cancellations. Let your provider's billing product handle the mechanics, and keep a local copy of each subscription's state, updated by webhooks. Derive what a team is allowed to do, its entitlements, from that local copy; don't call the provider on every page load. Plan for dunning, the process of recovering failed renewals: retry the card on a schedule, email the customer, allow a grace period, and only then restrict the account.

Refunds, disputes and reconciliation

A refund is a new transaction, never a deletion; record who issued it and why. A dispute, or chargeback, is when the cardholder asks their bank to reverse a payment. It has deadlines, requires evidence, and costs a fee even if you win. And every day, reconcile: compare your record of payments, refunds and fees against the provider's balance transactions and payouts, and investigate every difference. Record money movements in an append-only ledger table; for anything beyond simple invoicing, learn double-entry bookkeeping, which accountants have been using to catch exactly these errors for five hundred years.

Testing payments

Every provider has a test mode with special card numbers that succeed, decline, or trigger a bank challenge; Stripe's classic success card is 4242 4242 4242 4242. Use its command-line tool to forward test webhooks to your laptop. Then test the unhappy paths deliberately, because that's where the money leaks: a declined card, an abandoned bank challenge, a webhook delivered late, the same webhook delivered twice, a refund, and a dispute.

Common traps
  • Amounts from the browser. Anything the client sends can be edited.
  • Fulfilling on the redirect. Tabs close, signals drop, and URLs can be typed.
  • Calls without idempotency keys. A retried timeout becomes a double charge.
  • Floats for money, and assuming every currency has two decimal places.
  • Deleting payment records. Refunds are new rows, not deletions.
  • Asking the provider on every request whether a team has paid.
  • Third-party scripts on the checkout page. They can read what customers type.

Protecting and releasing

Two chapters on the edges of a product: the abuse that arrives as soon as anything is public, and the discipline of shipping changes to real users without betting the company on every deploy.

Chapter 16

Abuse, rate limits and input validation

8 min read3 exercises4 flashcards

Anything public will be abused: scraped, brute-forced, spammed and fed inputs you never imagined. Limit rates, put a bound on every resource, validate at the edge, and never fetch a URL a user gave you without checking where it leads.

Rate limiting

Rate limits stop password guessing, scraping, runaway client bugs and single tenants starving everyone else, and they cap what an attacker can cost you. The OWASP API Security Top 10 lists the lack of them as unrestricted resource consumption.

AlgorithmHow it worksTrade-off
Fixed windowCount requests per clock minuteSimple, but allows double bursts across a window boundary
Sliding windowCount requests in the last 60 secondsAccurate; the exact version stores a timestamp per request
Token bucketTokens refill at a steady rate up to a maximum; each request spends oneAllows short bursts but enforces an average; the most common choice

This is the deep RateLimiter from The Engineer's Craft, made concrete: one method, allow, hides the algorithm, the clock and the storage. When a request is refused, return 429 Too Many Requests with a Retry-After header computed from the second value, so well-behaved clients know exactly how long to wait.

Choose keys to match the threat. Limit sign-in attempts per account and per IP address, because attackers rotate both. Limit API calls per key and per tenant. Be careful with IP-only limits: an office or a mobile carrier can put thousands of people behind one address. Put coarse limits at the edge, in your CDN or gateway, to absorb floods cheaply, and business-specific limits in the application, where you know who the user is.

Put a bound on everything

Every unbounded input is a way to make your servers do unbounded work. Set a maximum request body size, a maximum page size (chapter 2), a maximum number of items in a batch, a maximum upload size (chapter 13), a maximum length for every string, a timeout on every operation, and per-tenant quotas on expensive actions such as exports. Tie quotas to plans, so the limits are also part of your pricing.

Regular expressions deserve a special mention. A pattern with nested repetition, such as ^([a-z0-9]+)*@, can take exponential time on a crafted input like a long string of letters followed by an unexpected character. This is called ReDoS, regular expression denial of service. Limit the input's length before matching, and avoid nested quantifiers.

Validate at the edge, with allowlists

Parse every request into a strict, typed schema at the boundary, as in The Engineer's Craft's "parse, don't validate". Describe what is allowed, not what's forbidden: an allowlist of expected values is finite, while a blocklist of dangerous ones never is.

Validation isn't the only defence, because some dangerous input is perfectly valid. The name O'Brien must be accepted, so SQL must always use bound parameters. A note containing <script> may be legitimate text, so output must always be escaped for where it's shown. Modern frameworks escape by default; the danger zones are the escape hatches, such as dangerouslySetInnerHTML, innerHTML and href values built from user input. If you must render user-supplied HTML, run it through a maintained sanitiser such as DOMPurify, and add a Content Security Policy as a second layer.

When your server fetches a URL

Features that fetch a URL a user supplied, such as importing a logo from a link, sending a webhook to a customer's endpoint, or generating a link preview, turn your server into the user's proxy. Point it at http://169.254.169.254/, the address where cloud virtual machines publish their credentials, and it may fetch your cloud keys and hand them back. This is server-side request forgery, SSRF, and it was central to one of the largest bank data breaches of 2019.

Checking is necessary but not sufficient. An attacker's DNS can answer with a public address when you check and a private one when you connect, a trick called DNS rebinding, so connect to the exact address you checked. Don't follow redirects, or check each one the same way. Set a timeout and a maximum response size. And ideally, make these requests through an isolated outbound proxy with no route to your internal network at all.

Abuse of business flows

Some abuse uses your product exactly as designed. OWASP calls it unrestricted access to sensitive business flows. For the invoicing app, think like an abuser:

  • Card testing. Fraudsters use your payment page to check which stolen cards work, one small payment at a time. Use your provider's fraud tools, rate-limit payment attempts, and add a challenge after failures.
  • Phishing through your domain. A new account sends convincing "invoices" containing malicious links to thousands of strangers, from your reputable domain. Limit what new accounts can send, check links, and act on complaints quickly.
  • Sign-up and trial farming. Scripts create accounts to claim free trials or to send spam. Verify email addresses, limit sign-ups, and watch for patterns.
  • Coupon guessing. Short codes can be brute-forced. Make them long and rate-limit attempts.

Use challenges such as CAPTCHAs sparingly, only on risky actions, and choose ones with accessible alternatives: WCAG 2.2's accessible authentication criterion applies to them too.

Common traps
  • Rate limiting by IP alone. Attackers rotate addresses; offices share them.
  • Unbounded requests. No limit on body size, page size or batch size.
  • Nested quantifiers in regular expressions run on long input.
  • Fetching user URLs from inside your network. SSRF straight to your cloud credentials.
  • Blocklists. There's always one more dangerous input you didn't list.
  • Relying on the frontend's validation. The API is the real boundary.

Chapter 17

Releasing safely

7 min read3 exercises4 flashcards

Separate deploying from releasing. Roll out to a few users before all of them, change the database in steps that each work with both the old and the new code, and be able to undo any release in minutes.

Small and often beats big and rare

The Engineer's Craft covered feature flags and the difference between deploying code and releasing behaviour. Build on it with one principle, supported by a decade of DORA's research: small, frequent deployments are safer than large, rare ones. A deploy containing one change is easy to understand, easy to test and easy to reverse. A deploy containing a month of changes is none of those, so it fails more often and takes longer to recover.

Progressive delivery

Release new behaviour to a small group first, watch what happens, and widen gradually: your own team, then 1% of customers, then 5%, 25%, and everyone. Infrastructure can do the same for whole versions, sending a slice of traffic to a canary deployment and promoting it only if its error rate and latency match the current version.

Assign users to a rollout deterministically, so that the same person always gets the same answer. Someone whose editor changes between two page loads files a bug report. Hashing the flag name with a stable identifier gives every subject a fixed position between 0 and 100, and raising the percentage only ever adds people.

Including the flag's name in the hash means the first 5% of one rollout aren't also the first 5% of every other, so a few unlucky customers don't receive every experiment at once. In a business product, roll out per team rather than per person: two colleagues looking at different versions of the same screen is its own source of confusion.

What to watch during a rollout

Decide before starting what would make you stop. Watch technical signals: error rate, latency at the 95th and 99th percentiles, failed jobs. And watch business signals, which catch the bugs that technical ones miss: invoices sent per hour, payments completed, sign-ups finished, support tickets opened. Compare the group that has the change with the group that doesn't. Where you can, make the check automatic, so a bad canary rolls itself back before anyone wakes up.

Database changes: expand and contract

Schema changes are where releases most often go wrong, because code and schema change on different schedules. During a rolling deploy, old and new code run side by side against the same database. And if you roll back the code, you can't roll back a column you've dropped. The safe pattern is expand and contract, which Martin Fowler calls parallel change: every step must work with both the code before it and the code after it.

Suppose you're replacing a decimal total column with an integer total_minor.

ReleaseSchemaCode writesCode reads
1. ExpandAdd total_minor, nullabletotal and total_minortotal
2. BackfillFill total_minor for old rows, in batchesBothtotal
3. SwitchMake total_minor requiredBothtotal_minor
4. Stop writingNo changetotal_minortotal_minor
5. ContractDrop totaltotal_minortotal_minor

Every row can be deployed on its own, and every row except the last can be rolled back with nothing lost.

Other operations are dangerous on large tables because they take locks that block every read or write while they run. Build indexes with CREATE INDEX CONCURRENTLY, which can't run inside a transaction. Add foreign keys and checks as NOT VALID, then validate them in a separate step. Avoid changing a column's type in place, which rewrites the whole table; add a new column instead. And start every migration with a lock_timeout, so that if a lock isn't available quickly, the migration fails and can be retried, instead of queueing behind a long query while every other request queues behind it.

Rollback and roll forward

Keep the previous build and make reverting to it a single command. Keep migrations backward-compatible, as above, so that rolling back the code is always safe. Remember that turning a flag off is the fastest rollback of all. Sometimes rolling forward with a fix is safer than rolling back, for instance once data has been written in a new format, and that's a judgement to make calmly, not at 3 a.m. for the first time. So practise: roll back a harmless release on purpose, and time it.

Tell people what changed

Keep a "what's new" page for users, and give your support team release notes before customers see a change, not after. In a business product, announce significant changes to workflows in advance, and let customers opt in to a beta early. Nobody likes discovering on a Monday morning that the invoice editor moved.

Common traps
  • Big-bang releases straight to every user.
  • Schema and code changed in one step, so the release can't be rolled back.
  • Plain CREATE INDEX on a big table. Writes stop until it finishes.
  • Random assignment per request. Users flicker between versions.
  • Watching only error rates. A bug that stops payments may throw no errors at all.
  • A rollback nobody has tried. It will fail exactly when you need it.

Part VI

Product and launch

Software that works but that nobody needs is still a failure. The last three chapters are about deciding what to build, finding out whether it worked, and launching and running a product for real users.

Chapter 18

Product thinking

7 min read3 exercises4 flashcards

Your job isn't to build what's asked for. It's to solve the problem behind the request, with the smallest thing that could work, and to find out quickly whether it did. Engineers who understand the problem make better technical decisions at every level.

Problems before solutions

Requests usually arrive as solutions: "add a button to export invoices as CSV". Behind each one is a problem: "my accountant needs last quarter's invoices every three months". Once you know the problem, better solutions often appear. Here, it might be a read-only link the accountant can use whenever they like, or an integration with their accounting software, either of which removes the chore rather than making it slightly faster.

Clayton Christensen's jobs to be done gives this a shape: people "hire" a product to make progress in a particular situation. His best-known example found commuters buying milkshakes in the morning, not because they wanted a milkshake, but because they wanted something to make a long, boring drive more bearable, and a thick shake lasted the whole journey. Freelancers don't want to create invoices. They want to be paid on time without awkward conversations. Every feature of the invoicing app should serve that job.

Talking to users without fooling yourself

Rob Fitzpatrick's short book The Mom Test is named for a simple idea: ask questions that even your mother couldn't lie to you about. People are kind, and they'll tell you your idea is great. Compliments, and predictions like "I would definitely use that", are worthless. Evidence comes from what people have actually done.

  • Talk about their life, not your idea.
  • Ask about specific past events, not about hypothetical futures or general opinions.
  • Talk less and listen more. The moment you start pitching, the data stops.
Instead ofAsk
"Would you use an app that chases late invoices for you?""Tell me about the last time a client paid late. What did you do?"

The smallest thing that could work

A minimum viable product isn't a small version of the whole product. It's the smallest experiment that tests your riskiest assumption. For automatic payment reminders, the riskiest assumption isn't technical, it's this: do reminders actually get freelancers paid faster? You can test that before writing any scheduling code, by sending reminders by hand for five customers for two weeks and comparing how quickly they're paid. That's a concierge test, and it's often the fastest way to learn.

Basecamp's Shape Up adds a useful discipline: decide your appetite first, meaning how much time this problem is worth, such as two weeks, and shape a solution that fits it. Fixed time, variable scope, the same principle as the estimation chapter of The Engineer's Craft. It stops a modest idea from quietly turning into a quarter's work.

Write it down first

Before building anything substantial, write one page. It forces clarity, and it's far cheaper to argue with a page than with a pull request.

Amazon's version of this, "working backwards", goes further: write the press release announcing the finished feature, and the answers to customers' likely questions, before any work starts. If the press release isn't exciting, the feature probably isn't worth building.

Saying no

Every feature carries a cost long after it ships: code to maintain, tests to keep green, interface to explain, support questions, and one more thing for every user to understand. Most feature requests should be understood, recorded and declined or deferred, while you watch for the problems that many requests have in common. Say no well: show you understood the problem, explain the trade-off honestly, and offer a workaround where one exists.

Engineers and product

The engineers who have the most influence on a product aren't the ones who implement specifications fastest. They're the ones who understand the users and the business. They read support tickets every week. They sit in on sales and support calls now and then. They notice friction in their own product. They propose simpler alternatives, instrument what they ship, and know how the company makes money. Many companies now hire specifically for this, under the title "product engineer".

Common traps
  • Building exactly what was asked for. The request is a clue, not a specification.
  • Asking people to predict their own behaviour. "Would you use…" questions produce polite fiction.
  • MVPs that are just a buggy first version. An experiment has a hypothesis and a result.
  • Features with no measure of success. You'll never know whether to keep them.
  • Roadmaps of features rather than problems to solve.
  • Never removing anything. Unused features still cost you every day.

Chapter 19

Measuring what users do

7 min read3 exercises4 flashcards

Decide what success looks like before you ship, instrument the few events that measure it, and stay humble about what the numbers can tell you. Most dashboards are noise; a handful of well-defined metrics are gold.

Metrics that mean something

Measure outcomes, not output. "Features shipped" and "page views" describe your activity. "Invoices paid on time" describes whether the product is doing its job. Structure the metrics you care about in three layers.

  • One headline metric that captures the value customers get. For the invoicing app, perhaps the number of invoices paid within their terms each week.
  • A few input metrics that drive it, which teams can influence directly: sign-ups that send a first invoice, invoices sent per active team, the share of overdue invoices with reminders on.
  • Guardrails: things that must not get worse while you improve the others, such as error rates, unsubscribes from reminder emails, and support tickets.

Be wary of vanity metrics, numbers that only ever go up and make everyone feel good, like total sign-ups since launch. Prefer rates and cohorts, which can go down and so can tell you something.

Activation and retention

Activation is the moment a new user first gets real value. Define it by an action, not a visit: for the invoicing app, "sent a first invoice within seven days of signing up" is much better than "logged in twice". Then look at retention by cohort: group users by the week they signed up, and chart what share are still active one, two, four and eight weeks later. If each cohort's curve keeps falling towards zero, people try the product and leave. If the curves flatten out, a core of users has found lasting value, which is one of the clearest early signs of a product people need.

Design events like an API

An analytics event is a contract with everyone who builds a dashboard on it, so design events as carefully as endpoints. Use one naming convention, such as an object followed by a past-tense action: Invoice Sent, Payment Received, Client Created. Give properties consistent names and types. Keep a tracking plan, a short document listing each event, when it fires, its properties and its owner, and review changes to it the way you review code.

Send important events from the server. Browser analytics are blocked by many extensions and lost when tabs close, so anything you'll make decisions on, such as sign-ups, sends and payments, should be recorded where it happens. Browser events are fine for interface details, such as which tab people open.

Collect the minimum. No email addresses, names or free text in event properties. Get consent where the law requires it, which in Europe includes most non-essential tracking in the browser. Honour the Global Privacy Control signal, which some US states treat as a legally binding opt-out. Set a retention period. Analytics data is personal data, and it's copied to more tools, with weaker controls, than your database.

Funnels

A funnel follows users through the steps of a flow and shows where they drop out: signed up, added a client, created an invoice, sent it, got paid. The largest drop is usually the most valuable place to work. Then find out why people drop there, by watching session recordings with personal data masked, or by asking them, before deciding what to change.

Experiments

An A/B test shows two versions to randomly assigned groups and compares an outcome. Assign by team or user with the stable hashing from chapter 17, using a separate flag for the experiment. Then follow the rules that keep the answer honest.

  • Choose one primary metric and your guardrails before starting. Picking the metric that happened to move afterwards is how false discoveries are made.
  • Calculate the sample size in advance, from the current rate and the smallest change worth detecting.
  • Don't peek and stop early. Checking results daily and stopping the moment they look significant greatly increases the chance of declaring a winner that isn't real. Evan Miller's essay How Not To Run an A/B Test explains why.
  • Run whole weeks, because behaviour on Mondays differs from behaviour on Saturdays.

A rough guide to sample size is Lehr's rule: for 80% power at the usual 5% significance level, you need about 16 × p(1 − p) ÷ δ² subjects in each group, where p is the current rate and δ is the absolute change you want to detect. With a 20% conversion rate and a 2-point change to detect, that's 16 × 0.2 × 0.8 ÷ 0.02², which is 6,400 users per group.

That arithmetic has an important consequence for a young product: you probably don't have the traffic to run useful A/B tests yet. Early on, talk to users, watch them use the product, and make bigger, bolder changes whose effect you can see without statistics.

Numbers and stories

Quantitative data tells you what is happening; only people can tell you why. Read survey comments, not just scores. Watch a few recorded sessions every week. Keep a running list of recurring support questions. And be suspicious of averages: an overall conversion rate can rise while it falls in every single segment, if the mix of users shifts between segments. That's Simpson's paradox, and segmenting by plan, channel or cohort is the cure.

Common traps
  • Tracking everything. Thousands of events, no decisions.
  • No tracking plan. invoiceSent, Invoice sent and sent_invoice, all at once.
  • Personal data in analytics. Emails and names spread across third-party tools.
  • Peeking at experiments. Stopping when the result looks good produces false winners.
  • Optimising the metric instead of the goal. Goodhart's law, again.
  • Averages that hide segments. Simpson's paradox is common, not exotic.

Chapter 20

Launch and the first ninety days

8 min read3 exercises4 flashcards

Launching is the start of the work, not the end of it. Before real users arrive, make the product observable, recoverable and reachable. Then spend the first ninety days listening, fixing, and resisting the urge to add features.

Configuration and environments

The Twelve-Factor App, a methodology first published by Heroku's engineers in 2011, remains the clearest statement of how to make an application easy to deploy. Its core points for a first launch:

  • Configuration lives in the environment, not in code, so the same build runs everywhere with different settings.
  • Secrets come from a secret manager or the platform's encrypted settings, never from the repository, and the development secrets are never the production ones.
  • One build, promoted from environment to environment, rather than rebuilt for each.
  • Development and production as similar as possible: the same database engine and version, not SQLite on a laptop and PostgreSQL in production.
  • Logs written to standard output as a stream of events, collected by the platform.

Use at least three environments: your laptop; a staging environment that mirrors production, with made-up or anonymised data; and production. Preview deployments for every pull request are a luxury worth having when your platform makes them easy. And make sure only production can send real email and take real money. The defaults above do that: every other environment has to opt in explicitly.

The launch checklist

Go through this in the week before real users arrive. Each item is a sentence, but each has sunk a launch somewhere.

  • Security: sign-in and recovery reviewed against chapter 5; rate limits on sign-in, reset and sign-up; development secrets rotated out; HTTPS everywhere, with HSTS; security headers, including a Content Security Policy; dependencies scanned for known vulnerabilities.
  • Data: backups running and one restore tested; every migration reversible; users can export their data and delete their account.
  • Legal and trust: terms of service and a privacy policy; cookie consent if you use non-essential cookies; a data processing agreement ready for business customers; an accessibility statement if you sell in the EU.
  • Money: live payment keys configured; webhooks registered in live mode; one real payment made and refunded; tax settings checked.
  • Email: SPF, DKIM and DMARC in place; every non-production environment unable to email real people; every template read by a human.
  • Support: a monitored support address; help pages for the five most common tasks; a way to contact you from inside the app.
  • Observability: error tracking, uptime checks and alerts all tested by deliberately triggering them; a short runbook for your three most likely failures.
  • Performance: the key pages checked on a mid-range phone; the key endpoints load-tested at ten times your expected traffic.
  • Rollback: practised, and timed.

The first ninety days

The first week: watch everything. Read every error, every log of a failed payment, every support message. Fix bugs the same day where you can. Talk to every early user you can reach, and watch at least a few of them sign up and send their first invoice, silently, noting every hesitation.

The first month: hold a short weekly review of three things: the activation funnel, new errors, and the themes in support messages. Fix the biggest point of friction each week. Resist new features, however tempting; the product you have isn't finished until new users can succeed with it unaided.

Months two and three: look at retention by cohort. Decide what to double down on and what to remove. Pay down the shortcuts you took in launch week before they turn into incidents. Write a short postmortem for every incident, however small. And notice what maintaining a live product actually involves: dependency updates, security patches, a database that keeps growing, users who find paths you never imagined. That experience is the real deliverable of this stage.

Treat support as part of the product. Fast, human replies build more trust than any feature, and every repeated question is either a missing help page or, more often, a design problem worth fixing so the question never needs asking.

When something breaks

Something will. When it does: say so, on your status page or wherever your users will look. Mitigate before you diagnose, by rolling back, switching off a flag or scaling up, because restoring service matters more than understanding the cause in the moment. Then find the root cause, fix it properly, and write a blameless postmortem, as The Engineer's Craft describes: what happened, what the impact was, why it happened, what went well, and what will change, with an owner for each action.

Common traps
  • Backups never restored. The first restore attempt shouldn't be during a disaster.
  • Alerting on everything, or nothing. Both end with nobody responding.
  • Staging with production credentials. Test invoices emailed to real clients; test charges on real cards.
  • Secrets in the repository. Rotate anything that was ever committed, even if you deleted it later.
  • New features in week two while new users still can't finish onboarding.
  • No way to reach you. Unhappy users who can't complain just leave.

The twenty rules

One per chapter, each linked back to it. Read them before every launch, and against every pull request that touches one of these areas.

  1. Design from the client's side: nouns for resources, honest status codes, and errors that say how to fix them.
  2. Page with cursors over a total order, and make every write retryable with an idempotency key.
  3. Change APIs additively; when you can't, deprecate out loud, with dates, headers and brownouts.
  4. Pick the API style for your clients, and the simplest real-time channel that works.
  5. Hash passwords with a memory-hard algorithm, keep sessions in locked-down cookies, and make recovery as strong as login.
  6. Use the code flow with PKCE, key users by issuer and subject, and keep tokens out of the browser.
  7. Check every object on every request through one policy, and scope every query to its tenant.
  8. Use the native element for the job, label every input, and keep the main thread free.
  9. Make every flow work by keyboard and screen reader, and reach for ARIA only when HTML can't do it.
  10. Cache server state, put shareable state in the URL, and derive the rest.
  11. Choose rendering per page, measure real users at the 75th percentile, and budget your JavaScript.
  12. Move slow work into idempotent jobs, and write each change and its event in one transaction.
  13. Upload straight to storage, trust bytes rather than names, and serve private files through short-lived signatures.
  14. Verify, deduplicate, acknowledge fast and reconcile webhooks; authenticate every email you send.
  15. Never touch a card or trust a price from the browser; fulfil from verified webhooks, idempotently.
  16. Limit rates, bound every resource, validate at the edge, and check where a URL leads before fetching it.
  17. Release to a few before all, change schemas in compatible steps, and practise the rollback.
  18. Understand the problem behind the request, then ship the smallest test of your riskiest assumption.
  19. Define success before shipping, track a few events well, and never peek at an experiment.
  20. Launch observable, recoverable and reachable, then spend ninety days listening.
