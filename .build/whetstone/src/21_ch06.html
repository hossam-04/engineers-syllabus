Chapter 6

Permissions

{{RT}} min read{{EX}} exercises

Every file has an owner, a group, and nine permission bits: read, write and execute, for the owner, for the group, and for everyone else. On a file the bits mean what they say. On a folder they mean something different, and that's where the surprises live: deleting a file needs permission on its folder, not on the file itself. This chapter decodes the bits, tries what each one allows, and covers the commands that change them, the default that sets them, and the account that ignores them.

An owner, a group and nine bits

ls -l starts each line with ten characters, such as -rwxr-x---. The first is the type: - for a file, d for a folder, l for a symbolic link. The other nine are three groups of three, r for read, w for write and x for execute, with - for a missing permission. The first group applies to the file's owner, the second to members of its group, and the third to everyone else, called others. ls -l also shows the owner's and group's names, and id shows who you are and which groups you're in.

Each group of three is also a number from 0 to 7, adding 4 for r, 2 for w and 1 for x, so the whole mode is three digits: rwxr-x--- is 750. You'll meet a few constantly: 644 for ordinary files, 755 for programs and folders, 600 for private files and 700 for private folders. Exactly one group applies to you, checked in order: the owner's if you own the file, otherwise the group's if you're in its group, otherwise others'. So an owner with fewer rights than the group gets the owner's rights.

Changing them, and the default

chmod changes the bits, either with a number, chmod 640 plan.txt, or symbolically: u, g, o and a for user, group, others and all, then +, - or =, then the letters. So chmod u+x makes a file executable for its owner, and chmod go-r stops anyone else reading it. -R applies a change to a whole tree, and a capital X adds execute only to folders and to files that were already executable, which is usually what you want. chown changes the owner, which only the administrator can do, and chgrp the group.

New files get their bits from the umask, a mask of permissions to remove from everything a program creates. Programs ask for 666 for files and 777 for folders, and the umask takes bits away. The usual umask, 022, removes write for the group and others, giving 644 and 755. A umask of 077 makes everything private, 600 and 700, which section 2 of the example shows. umask with no argument prints yours; set it in your shell's startup file, as chapter 8 does, to change it everywhere.

The example sets bits with chmod and umask and reads them back, then tries real operations as an ordinary user and reports only whether each was allowed. The exact wording of "Permission denied" differs between systems, but the decisions don't.

What the example shows

On a file, the bits mean what they say. With mode --w-------, the owner couldn't read secret.txt; with r--r--r--, appending to fixed.txt was refused. ./hello.sh failed with status 126, chapter 2's "found but not executable", while bash hello.sh ran it, because then bash is the program and only needs to read the file. Execute permission is a statement of intent, not a security barrier. Anyone who can read a script can run it.

On a folder, they mean something else. r lets you read the folder's list of names, so echo box/* worked on rw-------, but without x nothing inside could be reached: cat box/note.txt was refused. On a Mac, even ls box complains in that state, because it tries to look at each entry, which needs x. With -wx, the opposite: the names can't be listed, but a file whose name you already know can be opened. w on a folder means changing its list of names: without it, rm box/note.txt was refused even though the file itself was fine. And the last line is the surprise: a read-only file was deleted, because its folder was writable. Deleting a file removes a name from a folder, as chapter 5 explained, so it's the folder's permission that counts. Plain rm would have asked first, at a terminal; -f skipped the question, not the rule.

The administrator, and three special bits

The administrator account, root, user number 0, bypasses almost all of these checks, which is why the example refuses to run as root: its results would be meaningless. sudo command runs one command as root, after asking for your password, and records that you did. Use it for system changes, installing a package or editing a file in /etc, and never to make an error in your own folders go away. sudo pip install or sudo npm install leaves root-owned files in your home folder that later commands, run as you, can't change, and the fix is to correct the ownership, not to use sudo again.

Three more bits exist. Setuid on a program makes it run as its owner: passwd is owned by root and setuid, so that you can change your own password in a file only root may write. Setgid on a folder, on Linux, makes new files inside it belong to the folder's group, which is how shared project folders work; macOS always does that, setgid or not. And the sticky bit on a folder, shown as a t in drwxrwxrwt, lets everyone create files there but each person delete only their own, which is what keeps /tmp civil. A Mac adds extended attributes, shown as @ after the mode, and access control lists, shown as +; xattr and ls -le show them.

Common traps
  • chmod -R 777 to make an error disappear, which lets every user on the machine change everything.
  • sudo on tools that write to your home folder, leaving files you can no longer change.
  • Forgetting x on a folder, so readable files inside it can't be reached.
  • Thinking a read-only file is safe from deletion: its folder decides.
  • Private keys and tokens readable by others, which SSH and many other programs refuse to use.
Exercises
Exercise 6.1Bits and numbers

(a) What number is rw-r-----? (b) What string is 755? (c) What does chmod u=rw,go= leave on a file that was 755? (d) With a umask of 027, what modes do new files and folders get?

Show solution

(a) 640: rw- is 4 + 2, r-- is 4, --- is 0. (b) rwxr-xr-x. (c) 600, rw-------: = sets a class's bits exactly, and go= with nothing after it removes all of them. (d) 640 for files and 750 for folders: 666 without the bits in 027 is 640, and 777 without them is 750. Running umask 027; touch f; mkdir d confirms it, and gives the group read access while shutting everyone else out, a common setting on shared servers. Note the umask can only remove bits: no umask makes new files executable, because programs don't ask for that bit when they create ordinary files.

Exercise 6.2The key that's too open

Running ssh server prints WARNING: UNPROTECTED PRIVATE KEY FILE! and Permissions 0644 for '/home/you/.ssh/id_ed25519' are too open, and then refuses to use the key. Why does SSH care, and what's the fix?

Show solution
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519          # private key: only you may read it
chmod 644 ~/.ssh/id_ed25519.pub      # public key: anyone may read it, that's its purpose

With 644, every user on the machine can read your private key, and anyone who has it can log in as you wherever the key is accepted. SSH refuses on principle rather than assume nobody else has an account. The fix is to remove every permission for the group and others. The folder should be 700 too, so others can't even see which keys you have. The same reasoning applies to any secret in a file, such as an API token, a .env file or a password store. Make them 600, and keep them out of repositories, as chapter 8 explains.

Exercise 6.3A folder for a team

On a Linux server, everyone in the group web should be able to create and edit files in /srv/site, including each other's, and nobody else should be able to change anything. Set it up.

Show solution
sudo chgrp -R web /srv/site
sudo chmod -R g+rwX,o-w /srv/site
sudo find /srv/site -type d -exec chmod g+s {} +    # new files inherit the group "web"
# and in each member's shell startup file:
umask 002                                          # new files are group-writable

The group gets read and write on everything, and execute on folders and on files that were already executable; that's what the capital X does, as running it confirms. Others lose write. Setgid on every folder makes new files belong to web rather than to their creator's own group, and the umask of 002 makes them group-writable when they're created, so a colleague can edit them without anyone running chmod. Without those two, the setup works for a day and then breaks file by file. For anything more detailed, such as one person who may read but not write, access control lists, through setfacl, are the next tool.
