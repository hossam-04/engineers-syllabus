The Engineer's Whetstone

A whetstone cuts nothing. It keeps every other blade sharp. This volume is about the tools you'll use every working day: the shell and the small programs it runs, the filesystem underneath them, Git, one editor, and the skill of learning itself. Each turns out to rest on a handful of ideas, and once you see them, commands you used to copy and paste become things you can reason about. Every chapter runs the real tools and shows exactly what they did.

How to use this volume

Almost nobody teaches this stage, and skipping it costs beginners hundreds of hours. The cost is spread thin: twenty minutes lost to a quoting mistake, an afternoon to a Git state nobody understands, a week of half-remembered tutorials. None of it feels like the thing holding you back, which is why it goes on for years. Sixty hours here pays for itself many times over, in every stage after it. The table shows where each of the stage's topics is taught, and what to read or practise alongside.

Four parts, one a week. At fifteen hours a week the stage takes a month. Spend the first week on the shell, the second on the machine underneath it, finishing with your dotfiles repository. Give the third, the longest, to Git, and the fourth to your editor, error messages and study habits, while you finish the deliverable. Chapter 16 is short and can be read at any point. If you're starting the whole syllabus here, read it first: it changes how you'll study everything else.

Predict, run, explain. Each chapter's example is a Python program that runs the real tools, bash, grep, sed, awk, find and Git, in a temporary folder, and shows exactly what they printed. Before you read an output, cover it and predict what it will be. Then run the example yourself and, when your prediction was wrong, find out why before going on. The examples give the same output on any Mac or Linux machine. They give every commit a fixed author and time, ignore your own Git settings, and sort anything whose order would otherwise depend on the filesystem. On Windows, use the Windows Subsystem for Linux: the stage is about the Unix tools that every server runs.

Type the commands as well. The examples show what happens; your fingers have to learn it. Keep a terminal open while you read, and try each command in a scratch folder, made with mkdir -p ~/scratch && cd ~/scratch, where nothing can be lost. MIT's The Missing Semester of Your CS Education covers the same ground as lectures with exercises, and is the best two weeks of free teaching in the syllabus. Do its exercises too.

The deliverable is two things you'll keep: a public repository of your dotfiles, the settings that make your tools yours, with a script that installs them on a new machine, and one shell script that automates a chore you genuinely repeat. Chapters 8 and 4 build a small working version of each, and the appendix lists what the full versions need. Write each README as if a stranger will use it, because one will: you, on a new laptop, in a year.

The one habit

The tools in this volume hide almost nothing; they just don't volunteer it. The shell will tell you exactly what a line expands to, Git will draw its whole graph, and every error message names what went wrong.

So look before you change anything. Run type before blaming PATH, git status and git log --graph --all before any Git command you're unsure of, and read the whole error message before searching for it. Most confusion ends the moment you look at the actual state instead of the one you imagined.
