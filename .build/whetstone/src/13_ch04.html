Chapter 4

Scripts that don't break

{{RT}} min read{{EX}} exercises

A shell script is the cheapest automation there is: the commands you'd type, saved in a file. It's also the easiest to get dangerously wrong, because the shell carries on after errors, splits what it shouldn't and deletes what it's told. A handful of habits make the difference. Stop at the first failure, check the arguments, show what you'd do before doing it, never overwrite or delete without checking, clean up however the script ends, and make it safe to run twice. This chapter writes the kind of script the stage asks for, one that tidies a downloads folder, and puts it through its paces.

A script is a file of commands

A script starts with a shebang line, #!/usr/bin/env bash, which tells the system which program runs the file. env finds bash on your PATH, which matters on a Mac. Its /bin/bash is version 3.2, first released in 2006, kept because later versions use a licence Apple won't ship, so a newer bash, if you install one, lives elsewhere. Make the file executable with chmod +x tidy, and run it as ./tidy, or put it in a folder on your PATH, such as ~/.local/bin, and run it by name. bash tidy works without the execute bit, because then bash only reads the file.

Inside, $1, $2 and so on are the arguments, $# is how many there are, and "$@" is all of them, each kept as a separate word: it's the only correct way to pass a script's arguments on to another command. shift drops the first. For options, the built-in getopts handles -n, combined flags like -nv and options with values. A function is a named group of commands, name() { ...; }, called like any command, with its own $1 and so on. A function's return sets its exit status, like a program's. To give back a value, it prints it, and the caller captures it with $(name args). local keeps a variable inside the function instead of overwriting one outside.

Strict mode

Put set -euo pipefail near the top of every script. -e exits at the first command that fails, with the exceptions chapter 2 listed, instead of carrying on with the next line. -u makes using an unset variable an error, which turns a typo like $flie, or chapter 1's empty $STEAMROOT, into a stop instead of an empty string. pipefail makes a pipeline fail when any part of it does. Together they mean a script that hits something unexpected stops, and stopping is almost always the right thing for a script that runs without anyone watching. When you expect a command might fail, say so explicitly, with || true or an if. And ${1:-} reads a possibly missing argument without upsetting -u.

Failing well, and never destroying data

A script should fail the way a good program does. Messages go to stderr, with >&2, so they don't mix with output. Wrong usage prints a usage line and exits with status 2. Any other failure exits non-zero with a message that names the problem and the value that caused it: tidy: no such folder: Nowhere, not error. Check everything the script relies on before it starts changing things.

Then make destruction hard. Offer a dry run that prints what would happen, and use it first. Move rather than delete, and never overwrite: mv -n refuses to replace an existing file, and choosing a free name first, as the example's free_name does, means the refusal never comes up. Write new files under a temporary name and rename them into place only when complete, so nothing ever sees half a file. Before anything like rm -rf "$dir", check that $dir is set, exists and is what you think it is. Finally, make the script idempotent, safe to run any number of times. Run twice, it should find nothing left to do rather than doing it all again or failing halfway.

Locks and cleanup

Two copies of a script working on the same files at once, perhaps from a timer and from you, will trip over each other. A lock prevents it, and mkdir makes a good one. Creating a folder either succeeds or fails, in one indivisible step, so exactly one copy can create .tidy.lock and the others see that it exists. The lock must be removed however the script ends, and that's what trap is for. trap 'rmdir "$lock"' EXIT runs its command when the script exits: normally, through set -e after an error, or after Ctrl-C. Only kill -9, which nothing can catch, skips it. The same pattern deletes temporary files made with mktemp.

The example writes tidy, a script that sorts the files at the top of a folder into images, documents, archives and other by their extension. Then it runs it on a downloads folder in every way that matters: wrongly, as a dry run, for real, a second time, on a missing folder, and while another run holds the lock. The script is written for bash 3.2, so it runs unchanged on a Mac and on Linux.

What the example shows

It stops before doing harm. With no folder, it printed its usage line to stderr and exited with status 2; with a missing folder, a precise message and status 1; with the lock already taken, it refused rather than racing the other run. None of those runs changed anything, because every check comes before the first move. ${1%/} removes a trailing slash, so tidy Downloads/ works too: the shell's Tab completion adds that slash, so users will type it.

The plan and the run agree, and nothing is lost. The dry run printed exactly the seven moves the real run then made. The report that was already in documents kept its name, and the new one became report (1).pdf. The subfolder projects was skipped because the loop only moves plain files. The order, capital letters first, is the C locale's byte order, the same everywhere. A second run found nothing to tidy, and no lock was left behind. Category names come from a case statement rather than an associative array, because those need bash 4.

Testing a script, and knowing when to stop

Test scripts like any program. bash -n script checks the syntax without running anything, and bash -x script traces every command, as chapter 1's set -x does. ShellCheck reads a script and points out unquoted variables, useless cats, cds without error handling and dozens of other known mistakes. Run it on everything you write. Tests can be shell scripts too, with a framework such as bats, or a Python program like the example, which builds a folder, runs the script and checks the result.

Shell is the right language for gluing programs together and the wrong one for nearly everything else. Google's style guide for shell puts the line at about a hundred lines, or any non-trivial control flow. Past that point, or once you need data structures, arithmetic on anything but whole numbers, JSON, or careful error handling, rewrite it in Python: its subprocess, pathlib and shutil modules do everything a script does, without the quoting.

Common traps
  • No set -u, so a misspelt variable silently expands to nothing.
  • cd somewhere without || exit, so the rest of the script runs in the wrong folder.
  • Parsing the output of ls instead of looping over a glob.
  • Results and messages on the same stream, so another program can't use the results.
  • Bash 4 features, like associative arrays and ${x,,}, in a script that must run on a Mac's bash 3.2.
Exercises
Exercise 4.1An undo

Make tidy keep a record of its moves, and write untidy FOLDER, which puts every file back where it came from, newest move first.

Show solution
# in tidy, after the mv:
printf '%s\t%s\n' "$dest/$target" "$name" >> "$folder/.tidy-log"

#!/usr/bin/env bash
# untidy: undo tidy's moves in FOLDER, newest first, using the log tidy kept.
set -euo pipefail
folder=${1:?usage: untidy FOLDER}
log="$folder/.tidy-log"
[ -f "$log" ] || { echo "untidy: nothing to undo in $folder" >&2; exit 1; }
awk '{ line[NR] = $0 } END { for (i = NR; i > 0; i--) print line[i] }' "$log" |
while IFS=$'\t' read -r moved original; do
  mv -n -- "$folder/$moved" "$folder/$original" && echo "restored: $original"
done
rm -- "$log"

Each line of the log holds the new and old names, separated by a tab, which file names almost never contain. The awk program reverses the lines, because GNU's tac and BSD's tail -r each exist on only one system. Undoing newest first matters when one name was used twice. IFS=$'\t' read -r splits each line at the tab only, and -r keeps backslashes as they are. Run on a folder with three files, tidy moved them, untidy restored all three, and a second untidy said there was nothing to undo. The empty images and documents folders stay behind; removing them only if they're empty, with rmdir, would be a careful improvement. A name containing a newline would still break the log, which is the honest limit of line-based records.

Exercise 4.2Find the bugs

List everything wrong with this script, which compresses old logs, and rewrite it.

#!/bin/bash
backup_dir=$1
cd $backup_dir
for f in $(ls *.log); do
  gzip $f
done
rm -rf $backup_dir/old/*
echo "done"
Show solution
#!/usr/bin/env bash
set -euo pipefail
[ "$#" -eq 1 ] || { echo "usage: compress-logs FOLDER" >&2; exit 2; }
backup_dir=$1
[ -d "$backup_dir/old" ] || { echo "compress-logs: no old/ in $backup_dir" >&2; exit 1; }
cd -- "$backup_dir"
for f in *.log; do
  [ -e "$f" ] || continue
  gzip -- "$f"
done
find old -mindepth 1 -delete      # empty old/, here and only here
echo "done" >&2

The original has no strict mode, so it carries on after any failure. With no argument, backup_dir is empty and cd $backup_dir goes to your home folder; with a missing folder, cd fails and the script continues in whatever folder it was started from. $(ls *.log) splits names at spaces, and the unquoted $f splits them again. Worst, with an empty backup_dir, the rm line becomes rm -rf /old/*, and with a relative path like logs it points at logs/old inside the folder it has already moved into. The rewrite checks its argument and the folder before changing anything, uses paths relative to the folder it has entered, quotes everything, and deletes with find old -mindepth 1 -delete, which can only touch old's contents. The message goes to stderr, and in a script run by a timer it could be dropped entirely.

Exercise 4.3Shell or Python?

For each task, decide whether to write a shell script or a Python program, and say why: (a) run the tests, then the linter, and deploy only if both pass; (b) rename photos to the date they were taken, read from inside each file; (c) call a web API every hour, retry when it fails, and save one field of the JSON reply.

Show solution

(a) Shell. It's pure glue: three programs in order, each decision made by an exit status. set -euo pipefail followed by the three commands, each on its own line, is the whole script, and anything else would be longer. (b) Python. The date is inside the image's metadata, which needs a library to read, and the renaming needs care with collisions and time zones that shell makes awkward. Shell could call a tool like exiftool, but by the time it handles a missing date and two photos taken in the same second, it's past the point where shell is clear. (c) Python, using the standard library's urllib and json, or requests. Retrying with a delay that grows, telling a timeout from an error, and reading JSON are all things shell does badly. curl and jq can do a simple version, but error handling is where the shell version always grows a hundred lines. The rule: when you find yourself fighting the shell's quoting or reaching for its arrays, switch.

Checklist
  • Can you write a script with a shebang, strict mode, a usage message and getopts?
  • Can you pass arguments on correctly with "$@", and return values from functions?
  • Can you add a dry run, avoid overwriting files, and make a script safe to run twice?
  • Can you take a lock with mkdir and clean up with trap ... EXIT?
  • Can you check a script with ShellCheck, bash -n and bash -x, and say when to switch to Python?
