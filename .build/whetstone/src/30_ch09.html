Part III

Git

Five chapters on the tool every software team runs on. Git has a reputation for confusing commands, and it earns it, but under the commands is a data structure small enough to draw on a napkin: objects named by their contents, and a few movable names pointing at them. The part builds that structure by hand, then uses it to explain branches, merges, rebases and conflicts. It turns history into a debugging tool, and ends with the workflow of forks and pull requests that collaboration on GitHub runs on. It's the longest part of the stage, so give it the most time.

Chapter 9

Git's objects

{{RT}} min read{{EX}} exercises

Git is a store of objects, each named by a hash of its own contents, plus a few names that point into it. A blob is a file's contents, a tree is a folder listing, and a commit is a tree together with its parent commits, an author and a message. Once you see that, Git's behaviour stops being arbitrary. A commit is a snapshot of the whole project, not a list of changes. Identical files are stored once. And changing anything in the past changes the name of every commit after it. This chapter builds all three kinds of object by hand, and gets exactly the names Git does.

Names made from contents

A hash function turns any amount of data into a short, fixed-size number, such that the same input always gives the same number, and the smallest change to the input gives a completely different one. Git uses SHA-1, whose numbers are written as 40 hexadecimal digits, and names every object by the hash of a short header, its type and size, then a zero byte, then its contents. So the name of an object is a summary of what's in it: two people who commit the same file get the same blob name without ever communicating, and if a single bit of a stored object changes, its name no longer matches and Git notices. This is called content addressing. Objects are kept compressed in .git/objects, in a folder named after the first two digits, and later packed together into packfiles to save space.

In 2017, researchers produced the first two different files with the same SHA-1 hash, at a cost of thousands of years of computing time. Git responded by using a hardened SHA-1 that detects that kind of attack, and it now also supports repositories that use SHA-256 throughout. New repositories still use SHA-1 by default.

Blobs, trees and commits

A blob holds a file's contents and nothing else: not its name, not its permissions. A tree holds a folder's listing, one entry per name. Each entry has a mode, 100644 for an ordinary file, 100755 for an executable one, 40000 for a subfolder and 120000 for a symbolic link, then the name, then the id of the blob or tree it refers to. A commit is a few lines of text: the id of the tree for the whole project, the ids of its parent commits, none for the first, two for a merge, then the author and committer with timestamps, a blank line, and the message. A fourth type, the annotated tag, names a commit and adds a message of its own.

Between your files and a commit sits the index, also called the staging area. git add stores the current contents of a file as a blob, and records its name and id in the index. git commit turns the index into trees, writes a commit pointing at the top tree, and moves the current branch to it, which chapter 10 covers. git status compares three things: the last commit's tree, the index, and the files in your folder, which is why a file can be "staged" and "modified" at once.

The example computes object names in Python the way Git does, with hashlib, and checks each one against Git's own answer. Every commit gets a fixed author and time, so the 40-digit names printed here are the ones you'll get on your machine.

What the example shows

Git's names are just hashes, and you can compute them. The blob for hello and a newline is ce0136... whether you compute it in Python or ask git hash-object, and the file Git stored, decompressed, is exactly the header, a zero byte and the contents. The tree computed by hand, two entries sorted by name with their modes and raw ids, matched git write-tree. The commit was simpler still: four lines of text and a message. Note that cat-file -p prints the folder's mode as 040000, padded for display, while the stored tree says 40000. Hashing the displayed form would give the wrong answer.

Snapshots share what didn't change. After the README changed, the second commit had a new top tree and a new README blob, but its src folder was the very same tree, 5234dadb27, as the first commit's, because nothing in it changed. Adding copy.py, an exact copy of app.py, didn't add an object at all: both names point to one blob. Nine objects hold two complete snapshots: four blobs, three trees and two commits.

What follows from the model

Several things that puzzle people about Git follow directly. A commit doesn't contain a diff; when you ask for one, Git computes it by comparing two trees. Packfiles do store objects as differences from similar objects, but that's a storage detail, invisible to everything else. Renames aren't recorded: a rename is a blob that disappears from one path and appears at another, and git log --follow and git diff detect it by similarity. Empty folders can't be committed, because a tree lists files and subfolders, and an empty one has nothing to list, which is why projects keep a placeholder file such as .gitkeep. And history can't be edited, only replaced. A commit's name depends on its parent's name, so changing an old commit gives it a new name, which changes its child, and so on to the end, as exercise 9.3 explains.

Common traps
  • Thinking a commit stores changes rather than a snapshot of every file.
  • Expecting Git to track renames or empty folders, which it records neither of.
  • Committing large binary files that change often: every version is kept for ever. Git LFS is the tool for those.
  • Expecting git add to stage later edits: it records the contents at that moment.
  • Editing files under .git by hand, instead of with the commands that keep it consistent.
Exercises
Exercise 9.1A hash by hand

Compute the blob id for a file containing hello with no newline at the end, without Git, then check it. Why does echo hello | git hash-object --stdin give a different answer?

Show solution
import hashlib
data = b"hello"
print(hashlib.sha1(b"blob %d\0" % len(data) + data).hexdigest())   # b6fc4c620b67d95f953a5c1c1230aaab5db5a1b0

The header is the type, a space, the size in bytes as decimal digits, and a zero byte; then come the contents. printf hello | git hash-object --stdin agrees: b6fc4c62.... echo adds a newline, so it hashes six bytes, not five, and gets the example's ce013625.... One invisible character changes the whole name, which is the point of a hash. It's also why a file whose only change is a newline at the end, or Windows line endings, counts as changed to Git.

Exercise 9.2What a rename costs

In a repository with one committed file, a.txt, you run git mv a.txt b.txt and commit. Which new objects does that create?

Show solution

Exactly two: a new tree, which lists b.txt instead of a.txt, and a new commit pointing at it. No new blob, because the contents didn't change, and a blob has no name in it. Listing every object before and after, with git cat-file --batch-all-objects --batch-check, shows one tree and one commit added. In a deep folder structure, a rename also creates new trees for each folder on the path from the file up to the top, since each of their listings changes. So does an edit, which is why a commit of a one-line change in a large project is still cheap.

Exercise 9.3Why history can't be changed

A branch has three commits, A, B and C. You fix a typo in A's message. What happens to B and C, and why does that matter if someone else already has them?

Show solution

A's message is part of A's contents, so the fixed commit has a new name, A'. B's contents include its parent's name, which is now A' instead of A, so B must be rewritten as B', with a new name, and C likewise as C'. Changing one commit renames every commit after it. That chain is what makes Git's history trustworthy: a commit's name vouches for the whole history behind it, so two repositories that agree on one name agree on everything before it. It's also what makes rewriting shared history disruptive. Anyone who already has A, B and C still has them, and from Git's point of view your A', B', C' are unrelated new commits. Their next merge will join both copies together, with the same changes appearing twice. Chapter 11's rule follows: rewrite only commits nobody else has.
