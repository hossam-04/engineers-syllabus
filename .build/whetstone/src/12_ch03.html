Chapter 3

Searching and transforming text

{{RT}} min read{{EX}} exercises

Most of what you'll want to ask a computer is already written down somewhere as text: in logs, configuration files, code and exported data. Four tools answer most of those questions. find chooses files, grep chooses lines, sed rewrites lines, and awk computes over the fields of each line. With sort, uniq, cut and head between them, a pipeline of five short commands answers questions that would take a page of code. A little knowledge of regular expressions makes all of them more precise. This chapter questions a web server's log and a project folder.

Regular expressions in ten minutes

A regular expression is a pattern that matches text. Most characters match themselves. A . matches any one character; [abc] matches one of a set, [^abc] anything outside it, and [0-9] a range. ^ and $ anchor the pattern to the start and end of the line. Repetition applies to the thing just before it: * means zero or more, + one or more, ? zero or one, and {2,4} between two and four. Parentheses group, and | means "or", so ^(GET|POST) /api/ matches lines that start with either word followed by /api/. A backslash makes a special character ordinary: \. is a real dot. Matching is greedy: ".*" on "a" and "b" matches the whole thing, not just "a", because .* takes as much as it can.

There are two dialects, and that causes confusion. Basic regular expressions, the default for grep and sed, treat +, ?, |, () and {} as ordinary characters unless they have a backslash. Extended regular expressions, which you get with grep -E and sed -E and which awk always uses, give them their special meaning directly. Use -E everywhere and you only have to remember one. Named classes like [[:digit:]] and [[:space:]] work in both, and in every locale. Chapter 1's globs are a different language: there * means "anything" by itself.

grep chooses lines, find chooses files

grep pattern file prints the lines that match. The options you'll use constantly are -i to ignore case, -v for lines that don't match, -c to count them, -n to show line numbers, -o to print only the matching part, -w to match whole words, -F to treat the pattern as plain text, and -r to search a whole folder, with -l to list only the files. Like every good tool it reports through its exit status too: 0 if something matched, 1 if nothing did, 2 for an error, which is what makes grep -q useful in conditions.

find walks a folder tree and tests each file against an expression. -name '*.py' matches names by glob, and must be quoted, or the shell expands it first. -type f chooses files and -type d folders. -mtime +30 means last modified more than 30 days ago, and -size +10M bigger than ten megabytes. Tests are combined with an implied "and", or with -o for "or". -prune stops find from going into a folder, which is how you skip node_modules or .git. The default action is to print the path. -exec command {} + runs a command on the files it found, with as many names per run as fit, and -delete deletes them.

sed rewrites lines, awk computes over fields

sed, the stream editor, applies editing commands to each line as it passes through. Almost all of its use is substitution: s/old/new/ replaces the first match on each line, s/old/new/g every match, and parentheses in the pattern capture text that \1, \2 put back in the replacement. A command can be limited to some lines by number, 3,5s/a/b/, or by pattern, /ERROR/s/a/b/. With -n, sed prints nothing unless told to with p, so sed -n '/404/p' behaves like grep.

awk is a small programming language for tables of text. It splits each line into fields, $1, $2 and so on to $NF, the last one, at runs of spaces or at the separator given with -F. A program is a list of pattern {action} rules: the action runs on lines that match the pattern, and a missing pattern matches every line. BEGIN and END rules run before the first line and after the last. Variables need no declaring, start at zero or empty, and can be associative arrays, so {n[$1]++} counts lines by their first field. awk was written in 1977 by Aho, Weinberger and Kernighan, whose initials give it its name, and their book about it was updated in 2023.

The example builds a web server's access log of 48 requests, each line holding the client's address, the time, the request, the status, the bytes sent and the milliseconds taken, plus a small project folder. Then it answers questions with one pipeline each.

What the example shows

Each tool does one job, and the pipeline does the rest. cut -d ' ' -f 1,7,9,11 picks fields by number from lines separated by single spaces, which is how it pulled the address, path, status and time from each server error. grep -o printed just the /api/... part of each line, ready for counting. uniq -c counts runs of identical adjacent lines, which is why it always follows a sort. It also pads its counts differently on macOS and Linux, so the example passes them through awk '{print $1, $2}' to print the same everywhere. That's a habit worth having for any output another program will read.

awk does the arithmetic. n[$1]++ counted requests per address, and the END rule printed the totals, in an order awk doesn't promise, so sort -k1,1nr -k2,2 put them in order: numerically by count, highest first, and by address when counts tie, so the result never depends on chance. In $NF + 0 > 1400, adding zero turned 1698ms into the number 1698, because awk reads the leading digits of a string as its numeric value. The averages per status class came from two arrays and a printf, which formats numbers exactly as C's printf does.

Names with spaces need care. xargs reads names from its input and runs a command on them, but by default it splits its input at spaces, so ./old notes.tmp became two names, ./old and notes.tmp, neither of which exists. The file survived. find -print0 ends each name with a zero byte, the one character a file name can't contain, and xargs -0 splits only there. find . -name '*.tmp' -exec rm {} + avoids the problem entirely, by never turning names into text.

GNU, BSD and portability

Linux comes with the GNU versions of these tools, and macOS with the BSD ones. They agree on everything in this chapter's example, and differ in the corners. sed -i edits a file in place on Linux, while macOS needs sed -i ''. grep -P, for Perl-style patterns, is GNU-only, as are many long options. stat and date take completely different flags. Scripts that must run on both should stick to the options POSIX defines, the standard both follow, or check which system they're on. On a Mac, Homebrew's coreutils, gnu-sed and grep packages install the GNU versions with a g in front, gsed and ggrep, if you want Linux behaviour. Two modern tools are worth installing anywhere: rg (ripgrep), a much faster grep -r that skips files ignored by Git, and jq, which does for JSON what awk does for columns.

Common traps
  • find . -name *.py unquoted, which the shell expands before find sees it.
  • uniq without sort, which only merges duplicates that happen to be adjacent.
  • An unescaped . in a pattern, matching any character: grep 2026.03 also matches 2026503.
  • sed -i in a script that must run on both macOS and Linux.
  • Feeding names to plain xargs or to for f in $(find ...), which split them at spaces.
Exercises
Exercise 3.1Six commands

In 1986, Jon Bentley asked Donald Knuth to write a program that prints the most common words in a text, and Doug McIlroy reviewed the result. Knuth's answer was ten pages of carefully documented Pascal; McIlroy's review included a six-command pipeline that did the same job. Write that pipeline: print the ten most frequent words in story.txt, ignoring case and punctuation, and explain each stage.

Show solution
tr -cs 'A-Za-z' '\n' < story.txt |   # every run of non-letters becomes one newline: a word per line
  tr 'A-Z' 'a-z' |                     # lower case, so "The" and "the" are the same word
  sort |                               # identical words become adjacent
  uniq -c |                            # count each run of identical lines
  sort -rn |                           # highest count first
  head -n 10                           # keep the top ten

-c makes tr act on characters not in the set, and -s squeezes each run of them into a single newline. On the two sentences "The cat sat on the mat. The dog sat on the log. A cat and a dog: the best of friends, or the worst? The end." it puts the first with 7, then a five-way tie at 2. Ties come out in reverse alphabetical order, sat, on, dog, cat, a, because -r also reverses sort's final whole-line comparison. McIlroy's point wasn't that Knuth's program was bad. It was that reusable tools, composed, solve most such problems in minutes, and that the pipeline is easy to change: sort -rn to sort -n gives the rarest words instead.

Exercise 3.2A pattern that means what it says

A file contains the lines 2026-03-14, 2026503914, 2026.03.14 and meeting 2026-03-14 at 9. How many lines does grep -c '2026.03' count? Write patterns that match lines consisting of exactly one date in the form 2026-03-14, and lines that contain one anywhere.

Show solution
grep -c '2026.03' dates.txt                          # 4: the dot matches any character
grep -cE '^[0-9]{4}-[0-9]{2}-[0-9]{2}$' dates.txt    # 1: a whole line that is just a date
grep -cE '[0-9]{4}-[0-9]{2}-[0-9]{2}' dates.txt      # 2: a date anywhere in the line

All four lines match the first pattern: the dot matched a -, a 5 and a ., and the fourth line contains 2026-03. To match a literal dot, write \., or use grep -F for plain text. The anchors make the second pattern describe the whole line. Without them, as in the third, the pattern can match anywhere, so it also finds the date inside the meeting line. Neither pattern checks that the date is real: 2026-13-99 matches too. Regular expressions are good at shape and bad at meaning, so once you've found candidates, check them with a real date parser.

Exercise 3.3Rename a whole tree

Rename every .jpeg file under pics, in any subfolder, to .jpg, without breaking on names with spaces and without overwriting a file that already exists.

Show solution
find pics -type f -name '*.jpeg' -exec sh -c '
  for f do
    mv -n -- "$f" "${f%.jpeg}.jpg"
  done' sh {} +

find hands the names straight to a small shell script, never as text to be split, so spaces are safe; {} + passes as many as fit at once, and the sh after the script fills $0, so the names arrive as "$@", which for f do loops over. ${f%.jpeg} removes the suffix, mv -n refuses to overwrite, and -- protects names that start with a dash. Run on a tree with a.jpeg, 2025 trip/beach day.jpeg, 2025 trip/b.JPEG and c.jpg, it renamed the first two and left b.JPEG alone: -name is case-sensitive. -iname would find it, but then the suffix to strip could be any mix of cases. Try such a command with echo in front of mv first, and look at the list before letting it run.

Checklist
  • Can you write an extended regular expression with classes, anchors, groups and repetition?
  • Can you find files by name, type, size and age, skipping folders you don't want?
  • Can you count, rank and summarise a log with sort, uniq and awk?
  • Can you rewrite text with sed substitutions and capture groups?
  • Can you process file names safely with -print0, xargs -0 or -exec ... {} +?
