Chapter 12

History as a debugging tool

{{RT}} min read{{EX}} exercises

A repository's history isn't just a backup. It's the best debugging tool you have for the bug that begins "it used to work". git bisect searches history for the commit that broke something, automatically if you give it a test, and finds it among a thousand commits in ten steps. git log -S finds the commits that added or removed a piece of text, and git blame says which commit last changed each line, which leads to why. All three are only as good as the history they search: small commits, with messages that explain why.

Reading history

git log shows commits newest first, and a handful of options turn it into a query. --oneline gives one line per commit, --graph --all draws every branch, -p adds each commit's changes, and --stat lists the files each touched. -n 5, --since=2.weeks and --author=Ada limit it, and -- path at the end limits it to commits that changed one file or folder. git log main..feature lists commits on feature that aren't on main, which is what a pull request contains, and git show displays one commit in full. Put a lg alias for log --graph --oneline --all in your dotfiles and you'll use it every day.

Bisect: binary search over history

When something worked at an old commit and doesn't now, the commit that broke it is somewhere in between, and checking every one would take as long as there are commits. git bisect does a binary search instead. You mark one commit good and one bad, and Git checks out the commit halfway between them, on a detached HEAD. You test it and say git bisect good or git bisect bad, which throws away half the suspects. Repeat, and after about log2 of the number of commits, Git names the first bad one: ten steps for a thousand commits, twenty for a million. git bisect reset returns you to where you started.

Better still, give bisect a command and let it do the testing: git bisect run ./check.sh. Its exit status decides. 0 means good, 125 means "this commit can't be tested, skip it", and any other status from 1 to 127 means bad. Recent versions of Git also stop with an error if the test can't even run, status 126 or 127, on the commit you marked good. That catches a missing or non-executable script before it can blame an innocent commit. But nothing can catch a test that runs and checks the wrong thing.

The example builds a small repository with forty commits. The first adds a slug() function that turns a recipe's title into a web address, and commit 27, "Simplify slug()", quietly breaks it for accented letters. A test script checks one title. The example lets bisect run find the culprit, then asks log -S and blame the same question, and undoes the damage with revert.

What the example shows

Bisect needed five tests. It tried commit 20, which was good, then 30, bad, 25, good, 27, bad, and 26, good, and concluded that 27 was the first bad commit. That's every possible culprit among 39 suspects, commits 2 to 40, settled in five runs of the test, with no human involved. On a real project, with a test suite that takes minutes, this is the difference between a ten-minute search and an afternoon.

Text search and blame answer different questions. git log -S normalize listed the two commits that changed how many times the word normalize appeared: the one that added it and the one that removed it. Without knowing where the bug was, that found it from a guess about what had changed. git blame on the function gave each line's last commit: the first two lines date from the original, and the broken return line from "Simplify slug()". The example reads blame's machine-readable --line-porcelain output, the right choice for scripts; at a terminal, plain git blame marks lines from the very first commit with a ^. Finally, git revert made a new commit that applies the opposite of the bad one, and the test passed again. History wasn't rewritten, so it's safe even after the bad commit has been shared.

Searching and blaming well

-S text, the "pickaxe", finds commits that change the number of occurrences of the text, so it finds where a function was added or deleted, but not where an existing call was edited. For that, -G regex finds commits whose changed lines match. git blame -w ignores changes of whitespace, and -C follows lines that were moved or copied from other files. Large reformatting commits make blame useless for every line they touched. List them in a .git-blame-ignore-revs file, and git blame --ignore-revs-file, or GitHub's blame view, will look past them. Remember what blame is for: a line's commit leads to its message, its pull request and its discussion. That's why the line is the way it is, which is far more useful than who typed it.

History worth searching

Each of these tools depends on how history was written. When bisect finds a five-line commit that does one thing, the bug is obvious. When it finds a two-thousand-line commit titled "updates", you've learned little. So make small commits that do one thing each, and make sure each one builds and passes the tests, so bisect can test any of them. Write messages that explain why. The first line is a short summary in the imperative, around fifty characters, as in "Simplify slug()", then a blank line, then whatever a reader will need in a year: the reason for the change, what you considered, what it fixes. git commit without -m opens your editor so there's room for that, which is one reason chapter 14 matters.

Common traps
  • Huge commits that mix unrelated changes, which bisect can only point at, not explain.
  • Messages like "fix" or "wip", which tell blame's reader nothing.
  • Forgetting git bisect reset, and carrying on work on a detached HEAD.
  • A bisect test that checks the wrong thing, which makes bisect blame an innocent commit.
  • Undoing a shared commit with reset instead of revert.
Exercises
Exercise 12.1A thousand commits

A bug appeared somewhere in the last 1,000 commits. About how many tests will bisect need? Some old commits don't build at all; write a bisect run script for a project tested with make test that copes with them.

Show solution
#!/bin/sh
# check.sh: tell git bisect whether this commit is good (0), bad (1) or untestable (125)
make > /dev/null 2>&1 || exit 125      # doesn't build: neither good nor bad, so skip it
make test > /dev/null 2>&1 || exit 1   # builds, tests fail: bad
exit 0                                 # builds and passes: good

About 10, since 210 is 1,024: each test halves the suspects. The script turns a build failure into 125, so bisect skips that commit and tests a neighbour instead, rather than wrongly blaming a commit that only failed to build. In a test with a skipped commit in the middle of the range, bisect still named the right first bad commit. Keep the script outside the repository, or untracked, so it doesn't change as bisect checks out old commits, and make it exit 1 for a real failure rather than any status above 127, which would stop the search.

Exercise 12.2A message for the future

A commit changes the API client's timeout from timeout=30 to timeout=30_000, because the library it uses changed from seconds to milliseconds in version 4. Its message is "fixed stuff". Write a better one.

Show solution
Give the API client's timeout in milliseconds

Version 4 of the HTTP library takes timeouts in milliseconds instead of
seconds, so after the upgrade our 30-second timeout became 30 ms, and
every request to the slower reports endpoint timed out.

Keep the same 30-second timeout, now written as 30_000.

The summary says what the commit does, in the imperative, short enough to read in git log --oneline. The body explains what nobody can recover from the change itself: why 30 became 30_000, which would otherwise look like a typo someone might "fix" back. The symptom it cured is there for whoever searches for it, and the last line records that the behaviour was meant to stay the same. Someone who finds this line with blame next year will know not to touch it, which is the point.

Exercise 12.3Which undo?

Choose the command for each: (a) you've edited a file and want it back as it was in the last commit; (b) your last commit, not yet pushed, has a typo in its message; (c) a commit from last week, already on main, broke production; (d) your last three local commits should have been one.

Show solution

(a) git restore file, which throws away the uncommitted edits in that file, for good, so be sure. (b) git commit --amend, which replaces the last commit with a corrected one, fine because nobody else has it yet. (c) git revert <commit>, which adds a new commit that undoes it and changes no existing history, the only safe choice for a commit others have. (d) git reset --soft HEAD~3 then git commit, which moves the branch back three commits while keeping all their changes staged, ready to commit as one; git rebase -i HEAD~3 does the same with more control. The test in each case is chapter 11's rule: has anyone else got the commit? If so, add a commit; if not, you may replace it.

Checklist
  • Can you query history by file, author, date and branch with git log?
  • Can you find the commit that introduced a bug with git bisect, by hand and with run?
  • Can you find when a piece of code appeared or disappeared with git log -S?
  • Can you use git blame to find why a line is the way it is?
  • Can you choose between restore, amend, reset and revert?
