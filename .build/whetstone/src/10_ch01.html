Part I

The shell

Four chapters on the program you'll type into for the rest of your career. The shell is a small programming language whose real job is starting other programs and connecting them together. First, how it turns a line you type into a list of arguments, which explains almost every quoting bug. Then the streams and exit codes that let programs cooperate, the four tools that answer most questions about text, and the habits that make a shell script safe to run while you sleep. By the end of this part you can automate a chore and trust the result.

Chapter 1

The shell as a language

{{RT}} min read{{EX}} exercises

The shell is a programming language whose main job is starting other programs. Before it runs a line, it rewrites it: it replaces variables, expands patterns into file names, splits the result into words, and only then hands the program a list of arguments. The program never sees your quotes, your $ signs or your *. Almost every surprise in the shell is a surprise about that rewriting, so this chapter shows exactly which list a program receives for each kind of line.

A command is a list of words

Three things are easy to confuse. The terminal is the window: it draws characters and sends your key presses on. The shell is the program running inside it, usually bash or zsh, which reads each line you type and decides what to do with it. And the commands are ordinary programs, ls, grep, git, which the shell starts. When you type ls -l Documents, the shell finds a program called ls, which chapter 7 explains, and starts it with a list of three strings: ls, -l and Documents. That list, called argv in C and sys.argv in Python, is everything the program gets from the line. What -l means is entirely up to ls.

Programs mostly follow the same conventions for their arguments. Single letters after one dash are options, and can often be combined: ls -l -a is ls -la. Long names take two dashes, as in ls --all. Some options take a value, like head -n 5, and a lone -- means "no more options", so rm -- -notes.txt deletes a file whose name begins with a dash. These are conventions, not rules the shell enforces. The shell's own job ends at producing the list.

Quoting

The shell gives special meaning to a few characters: spaces separate words, $ starts a variable or substitution, *, ? and [ make patterns, and |, >, <, & and ; connect or separate commands. Quoting turns those meanings off. Inside single quotes, everything is literal: '$HOME *' is exactly those seven characters. Inside double quotes, spaces and pattern characters are literal, but $, backquotes and backslash still work, so "$HOME" becomes your home folder as one word, however many spaces it contains. A backslash outside quotes makes the next character literal: it\'s. Quotes can be mixed within one word: 'single'"double" is one argument, singledouble. The quotes themselves are removed before the program starts, which is why it never sees them.

The expansions, in order

Before running a line, bash performs a fixed sequence of expansions, and the order explains the surprises. Brace expansion comes first, turning file{1..3}.log into three words. Tilde expansion turns ~ at the start of a word into your home folder. Then, from left to right, parameter expansion replaces $name and ${name} with variables' values, arithmetic expansion computes $((2 + 3 * 4)), and command substitution runs $(command) and puts its output in its place. Only then does word splitting break the results of those three, wherever they weren't in double quotes, at spaces, tabs and newlines. Pathname expansion, usually called globbing, then replaces each word containing *, ? or [ with the matching file names. Finally, quote removal deletes the quotes.

The best way to learn this is to watch it. The example creates a tiny program, showargs, which prints its arguments one per bracket, so you can see exactly where each word begins and ends. It then runs it through bash in a folder holding a.txt, b c.txt and notes.md, with a variable f holding my notes.txt and another, empty, holding nothing.

What the example shows

Unquoted expansions are split, and quoted ones aren't. showargs $f receives two arguments, my and notes.txt, because the value was split at its space. A program given those would look for two files that don't exist. "$f" keeps it whole. An empty variable unquoted disappears altogether, leaving zero arguments, while "$empty" is one empty argument. That difference is why [ $answer = yes ] fails with a strange error when answer is empty: the test receives = yes. The rule that prevents most shell bugs is simple: put double quotes around every expansion, "$var", "$(command)", "$@", unless you can say why you want it split.

Globs match file names, and are expanded after splitting. *.txt became a.txt and b c.txt, sorted, with the space intact: names produced by globbing are never split again. A glob that matches nothing is passed on unchanged, so showargs *.csv received the literal *.csv; that's bash's default, and zsh's default is different: it stops with "no matches found". Quoted, "*.txt" is just text. Section 5 shows the order's sharpest edge: the output of $(printf '*.txt') is the text *.txt, and because substitution happens before globbing, it is then expanded into file names. Command output containing a *, a space or a newline is rewritten unless it's quoted.

Assignments have no spaces. x=5 sets a variable. x = 5 runs a program called x with arguments = and 5, and fails with status 127, "command not found". Putting an assignment before a command, as in x=5 y="a b" showargs, sets them for that one command only, which chapter 7 uses. And the last line shows the other side: when Python's subprocess.run is given a list, there's no shell, so nothing is expanded. *.txt and $HOME arrive exactly as written. When you start programs from your own code, pass a list rather than a string to a shell, and the quoting problems disappear.

Globs are not regular expressions

Glob patterns look like the regular expressions of chapter 3, and mean different things. In a glob, * matches any run of characters, ? exactly one, and [abc] one of a set; the pattern must match the whole name. A * doesn't match a leading dot, so * skips hidden files like .bashrc, and it doesn't cross /, so src/*.py looks in one folder only. To match in every subfolder, zsh understands **/*.py by default, and bash does after shopt -s globstar, which needs bash 4; for anything more, use find, in chapter 3. In a regular expression, by contrast, * means "the previous thing, any number of times", and . means any character.

Seeing what the shell will run

You never have to guess what a line expands to. set -x makes bash print each command, after expansion, before running it, with a + in front; set +x turns it off. It's the most useful debugging tool the shell has, and it works in scripts too. For a single line, put echo or printf '[%s]\n' in front of a command to see its arguments without running it. Two keyboard habits save hours as well: Tab completes commands and file names, and quotes awkward names for you, and Ctrl-R searches back through the commands you've run before. History is kept in a file, usually ~/.bash_history or ~/.zsh_history.

Common traps
  • Unquoted variables, which break on the first file name with a space and vanish when empty.
  • for f in $(ls), which splits names at spaces; loop over a glob, for f in *, instead.
  • Spaces around = in an assignment, which turn it into a command.
  • Expecting * to match hidden files, or an unmatched glob to vanish: bash passes it on unchanged.
  • Curly quotes pasted from a web page or word processor: “ and ” are ordinary characters to the shell, not quotes.
Exercises
Exercise 1.1Predict the list

After a="1 2"; b="", in a folder with no files whose names start with 1, predict what showargs receives from each line: showargs $a$b, showargs "$a""$b", showargs $b $a, showargs '$a' "\$a", showargs {x,y}{1,2} and showargs "$a"*.

Show solution
showargs $a$b          2 argument(s): [1] [2]
showargs "$a""$b"      1 argument(s): [1 2]
showargs $b $a         2 argument(s): [1] [2]
showargs '$a' "\$a"    2 argument(s): [$a] [$a]
showargs {x,y}{1,2}    4 argument(s): [x1] [x2] [y1] [y2]
showargs "$a"*         1 argument(s): [1 2*]

$a$b is 1 2 followed by nothing, split into two words. Quoted, "$a""$b" is one word, and the empty "$b" adds nothing to it because it's part of the same word. In $b $a the unquoted empty $b disappears. Single quotes and a backslash both stop expansion. Two brace expressions in one word multiply, giving every combination. In the last line the quoted part isn't split, so the glob is the single pattern 1 2*, which matches nothing and is passed on unchanged. Each answer was produced by running the line in bash.

Exercise 1.2The loop that breaks on spaces

In a folder holding my notes.txt and todo.txt, this loop prints three lines instead of two: for f in $(ls *.txt); do echo "loop got [$f]"; done. Explain why, and write a loop that's correct for any file name, including when there are no matching files.

Show solution
for f in *.txt; do
  [ -e "$f" ] || continue        # no match: bash leaves the literal "*.txt"
  echo "loop got [$f]"
done

The glob *.txt is expanded into two names for ls, which prints them, one per line. But the output of $(ls *.txt) is then split at every space and newline, so my notes.txt becomes two words, and the loop runs three times, with my, notes.txt and todo.txt. Looping over the glob itself gives each name as one word, spaces and all, because names produced by globbing are never split. The [ -e "$f" ] test handles the empty case: with no .txt files, the loop would otherwise run once with the literal *.txt. In bash, shopt -s nullglob makes an unmatched glob expand to nothing instead. And inside the loop, "$f" stays quoted wherever it's used.

Exercise 1.3The empty variable

In 2015, Steam's installer for Linux ran a line like rm -rf "$STEAMROOT/"*. On some machines STEAMROOT turned out to be empty. What did the line expand to, and how should it have been written?

Show solution

With STEAMROOT empty, "$STEAMROOT/"* is the glob /*, every entry at the top of the filesystem. With showargs in place of rm, on the Mac this volume was written on, the line expands to seventeen arguments: -rf, then /Applications, /Library, /System, /Users and every other top-level folder. For an ordinary user, that deleted every file they owned, on every mounted drive, which is what the bug report described. The defences, in order of importance: ${STEAMROOT:?} makes the shell stop with an error if the variable is unset or empty, instead of expanding to nothing; set -u at the top of a script makes any unset variable an error, which chapter 4 recommends; and checking a value before using it to delete anything, [ -d "$STEAMROOT" ] || exit 1, catches values that are set but wrong. Running a destructive line with echo in front first would have shown the problem on the developer's machine.
