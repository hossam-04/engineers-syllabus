Chapter 10

Refs, branches and HEAD

{{RT}} min read{{EX}} exercises

A branch is a small file that holds one commit's name, and HEAD is a file that holds the name of the current branch. Committing writes a new commit whose parent is the current one, then moves the current branch forward to it. Almost every other command that seems to rearrange history only moves these names around: switching branches, detaching HEAD, resetting. And nothing you've committed is lost when a name moves, because the reflog remembers everywhere each name has been.

Names for commits

Forty-digit names are for machines. People use refs, named pointers to commits. A branch called main is the file .git/refs/heads/main, which contains one commit's name and a newline: that's all a branch is. Tags live in refs/tags, and chapter 13's remote-tracking branches, like origin/main, in refs/remotes. Git sometimes packs many refs into one file, .git/packed-refs, for speed, and newer versions can store them in a different format altogether. So read refs with git rev-parse main rather than by opening files, as the example does only to show what's there.

Git understands a small language for naming commits relative to others. HEAD~1 is the current commit's parent, and HEAD~3 its great-grandparent, following first parents. HEAD^2 is a merge's second parent. main@{1} is where main pointed before its last move, from the reflog. Any unambiguous prefix of a commit's name works too, so the seven-digit abbreviations Git prints are enough to type.

Committing moves a branch

HEAD normally contains ref: refs/heads/main, meaning "the current branch is main". When you commit, Git writes a commit whose parent is the commit main points to, then rewrites the file refs/heads/main to hold the new commit's name. No other branch changes. That's the whole of "being on a branch": your next commit will move that name. Making a branch writes one tiny file, so branches cost nothing, and it's normal to make one for every piece of work, however small. git switch name moves HEAD to another branch and updates your files to match its commit. The older git checkout does that too, along with several unrelated things, which is why newer versions of Git split it into switch and restore.

Detached HEAD

HEAD can also hold a commit's name directly, which Git calls a detached HEAD. You get one when you switch to a commit rather than a branch, to look at an old version, and Git puts you in one during a rebase or a bisect. You can commit there, but no branch moves, so the new commits are known only to HEAD. Switch to a branch, and they're no longer reachable from any name. They're not deleted, but they're easy to lose track of, which is why Git warns you when you leave. git switch -c name gives the commits a branch and makes them safe.

The example makes the files visible. It prints the contents of HEAD and of the branch files as it creates a branch, commits on it, detaches HEAD, commits there and switches away, then finds the "lost" commit in the reflog and gives it a name. Last, it moves a branch with reset and moves it back.

What the example shows

A branch is the name of one commit, and it moves. refs/heads/main held c7ebc43f...; making feature wrote a file with the same contents; committing C on feature changed that file and left main's alone. The graph's labels, (HEAD -> feature) and (main), are exactly those files drawn on the commits they name.

Unlabelled commits fall out of view, not out of the repository. After detaching at B and committing D, switching back to main left D on no branch, and git log --all, which starts from every ref, no longer showed it. But the reflog for HEAD records each move with the reason, commit: D: an experiment and checkout: moving from ..., and one git branch made D reachable again, joining the graph as a fork from B. Finally, reset --hard moved main back to A, which made B unreachable too. main's own reflog, 87b02ea, c7ebc43, 87b02ea, showed where it had been, and main@{1} put it back.

reset, and what really can be lost

git reset target moves the current branch, along with HEAD, to another commit, and its three modes say what happens to your files. --soft moves only the branch: the undone commit's changes stay staged, ready to be committed again, which is a way to squash several commits into one. --mixed, the default, also resets the index, so the changes stay in your files but unstaged. --hard also overwrites your files to match. That's the one dangerous command in this chapter, because changes you never committed aren't in any object, so no reflog can bring them back. Before a --hard reset, git stash saves uncommitted work as a commit you can restore. For files alone, git restore file discards a file's unstaged changes, and git restore --staged file unstages it.

Commits themselves are very hard to lose. They stay in the repository as long as a ref or a reflog entry leads to them. Reflog entries are kept for 90 days by default, or 30 for commits that are no longer reachable, and only after that can Git's garbage collection delete them. In practice, if you committed it in the last month, it's still there.

Common traps
  • Committing on a detached HEAD and switching away without making a branch.
  • git reset --hard with uncommitted changes, the one loss no reflog can undo.
  • Using reset on commits already pushed; chapter 12's revert undoes them without rewriting history.
  • Thinking git branch -D deletes the commits; it deletes a name, and prints the commit it pointed to.
  • Reading .git/refs in scripts instead of asking git rev-parse.
Exercises
Exercise 10.1Three kinds of reset

Your last commit added line 2 to f.txt. For each of git reset --soft HEAD~1, git reset HEAD~1 and git reset --hard HEAD~1, say where the branch points afterwards, what git status shows, and what f.txt contains.

Show solution
reset --soft HEAD~1    branch at the first commit   status: M  f.txt (staged)     f.txt: line 1, line 2
reset HEAD~1           branch at the first commit   status:  M f.txt (unstaged)   f.txt: line 1, line 2
reset --hard HEAD~1    branch at the first commit   status: clean                 f.txt: line 1

All three move the branch identically; they differ in how much else they reset. In git status --short, the first column is the index and the second your files: an M in the first column means the change is staged, and in the second, that it's only in your folder. Each line was checked on a fresh repository. In all three cases the undone commit is still reachable through the reflog, so even the --hard reset here could be undone with git reset --hard HEAD@{1}. What it would destroy for good is any edit to f.txt that hadn't been committed.

Exercise 10.2The deleted branch

You ran git branch -D feature on the wrong branch, which had a week of unmerged commits. Get it back.

Show solution
git branch -D feature
# Deleted branch feature (was 6f8d2ca).     <- the commit it pointed to
git branch feature 6f8d2ca                  # recreate the name; the commits were never deleted

# if that message has scrolled away, the reflog of HEAD remembers being on the branch:
git reflog | grep -m 1 'moving from feature'
git log -1 HEAD@{3}                         # inspect a candidate before recreating the branch

Deleting a branch deletes the 41-byte file, nothing else. Git even prints the commit it pointed to, so the quickest fix is to recreate the name at that commit. If the message is gone, HEAD's reflog has an entry from each time you switched away from the branch, and the commit you were on at that moment is the branch's tip, or close to it. Inspect the candidate with git log before recreating the branch.

Exercise 10.3Tildes and carets

On main, commits A then B; a branch side starts at A and adds S; then side is merged into main. Name the commits that HEAD^, HEAD^2, HEAD~1, HEAD~2 and HEAD^2~1 refer to.

Show solution
HEAD^      B    the merge's first parent: what main pointed to before the merge
HEAD^2     S    the merge's second parent: the branch that was merged in
HEAD~1     B    one step back, following first parents
HEAD~2     A    two steps back, following first parents
HEAD^2~1   A    the second parent, then one step back from it

^ chooses among a commit's parents; ~ walks back through first parents. They only differ at merges, which have two. The first parent is always the branch you were on when you merged, so following ~ from the tip of main walks main's own history and skips the details of every merged branch. That's what git log --first-parent shows, and why merge commits, chapter 11's subject, keep a readable summary of a project. Running git log -1 --format=%s on each of the five confirms the answers.

Checklist
  • Can you say what a branch, a tag and HEAD each contain?
  • Can you explain what moves when you commit, and what doesn't?
  • Can you recognise a detached HEAD, and keep commits made there?
  • Can you find and rescue an unreachable commit with the reflog?
  • Can you choose between reset --soft, --mixed, --hard and restore?
