Chapter 7

Processes, the environment and PATH

{{RT}} min read{{EX}} exercises

Every command runs as a process, started by the shell, and each process gets its own copy of the environment, a list of NAME=value strings inherited from its parent. Copies flow down to children and never back up. That's why cd and export must be part of the shell itself, and why a script can't change the folder you're in. PATH is one of those variables: a list of folders searched in order. It explains every "command not found", and every time the wrong version of a program runs.

Processes

A process is a running program: its code, its memory, its open files, its current folder, and a number, the process ID, that names it. Every process except the first has a parent, the process that started it, and ps, top or the friendlier htop show them all. When you type a command, the shell makes a copy of itself, and the copy replaces its own program with the one you asked for, keeping its open files, its folder and its environment. That is how a child inherits everything from chapter 2's redirections. When the child exits, the shell receives its exit status, and shows the prompt again.

A command ending in & runs in the background while you carry on; jobs lists them, fg brings one back, and Ctrl-Z pauses the current one so that bg can continue it in the background. Processes are stopped with signals. Ctrl-C sends SIGINT, kill 1234 sends SIGTERM, a polite request to exit that a program can catch to clean up, as chapter 4's trap did. kill -9 1234 sends SIGKILL, which can't be caught and leaves no chance to clean up, so it's the last resort, not the first.

Variables and the environment

x=1 makes a shell variable, which only this shell can see. export x, or export x=1 in one go, marks it to be copied into the environment of every program the shell starts from then on. env or printenv lists the current environment, and unset x removes a variable. Putting assignments before a command, LANG=C sort names.txt, sets them in that one command's environment and nowhere else. By convention, environment variables have upper-case names. Some are shared by everything: HOME, PATH, EDITOR, LANG and TZ. Others belong to one program, like the GIT_ variables the Git examples use to fix names and dates.

Down, never up

A child gets a copy of its parent's environment, at the moment it starts. Whatever it changes afterwards, in its variables or its current folder, changes only its copy, and disappears when it exits. Nothing in the system lets a child reach back into its parent. So cd can't be an ordinary program. A cd program would change its own folder and then exit, leaving yours exactly where it was. That's why cd, export, source and a few others are builtins, commands the shell runs itself. type name says what a name is: a builtin, an alias, a shell function, or a program and where it is.

The same rule decides what a script can do to your shell. Running bash setup.sh, or ./setup.sh, starts a child, so its cd and export vanish with it. Sourcing it, source setup.sh or . setup.sh, runs its lines in your current shell, as if you'd typed them, so their effects stay. Startup files, and virtual environments' activate scripts, are sourced for exactly this reason.

PATH

When you type a command name without a / in it, the shell looks in each folder listed in PATH, separated by colons, in order, and runs the first executable file with that name. A name containing a slash, like ./tidy or /usr/bin/python3, is used as given, with no search. type -a name lists every match in search order, and command -v name prints the one that would run, which makes it the reliable check in scripts. which is a separate program on many systems and can disagree, because it doesn't know about your aliases and functions. To add a folder, put it at the front, where it wins, in the startup file chapter 8 sets up: export PATH="$HOME/.local/bin:$PATH". Never add ., the current folder: any folder you cd into could then supply a fake ls.

Bash also remembers where it last found each command, so as not to search every time. If you install a program into a folder that comes earlier in PATH than the version you've been running, bash keeps running the old one until you type hash -r (in zsh, rehash) or open a new shell. Changing PATH itself clears that memory. Version managers for Python, Node and the rest, and Python's virtual environments, all work the same way: they put their own folder at the front of PATH.

The example builds two folders, bin1 and bin2, each with its own program called greet. It runs them with PATH in each order, passes variables to child shells, runs and sources a script, and finally starts bash in four ways, with startup files that announce themselves.

What the example shows

The first match wins, and builtins aren't on PATH at all. With bin1 first, greet ran bin1's program; reversed, bin2's, and type -a listed both in order. With neither folder on PATH, status 127. type called cd and export builtins, which is why no PATH change can ever break them.

Only exported variables reach a child, and nothing comes back. The unexported x was invisible to the child bash; exported, it arrived. x=2 bash -c ... gave the child a value the parent never had. The child's x=99 and cd / changed its copy only. Running setup.sh left GREETING empty and the folder unchanged, and sourcing it did both.

Startup files depend on how the shell started. A script reads no startup files. A login shell, which is what you get when you log in, read ~/.bash_profile; an interactive shell, one you type into, read ~/.bashrc. And an interactive login shell read only ~/.bash_profile, which is the surprise. Terminal on a Mac starts a login shell in every window, so settings put only in .bashrc seem to be ignored there, while most Linux terminals start non-login shells, which read only .bashrc. The usual fix is a line in ~/.bash_profile that sources ~/.bashrc. Zsh, the default on Macs since 2019, has its own set: ~/.zshenv always, ~/.zprofile for login shells, and ~/.zshrc for interactive ones. Put environment settings such as PATH in the login file, and interactive ones, aliases and the prompt, in the rc file.

Common traps
  • Expecting a script to change your shell's folder or variables: source it, or make it a function.
  • Setting a variable without export and wondering why a program can't see it.
  • Adding to PATH in a file that every nested shell reads, so it grows each time.
  • Trusting which over type -a, which knows about aliases, functions and order.
  • A stale command after installing a new version: hash -r or a new shell.
Exercises
Exercise 7.1The wrong Python

You installed Python 3.13, but python3 --version still says 3.9. How do you find out why, and fix it?

Show solution
type -a python3            # every python3 on PATH, in the order they're searched
echo "$PATH" | tr ':' '\n' # the folders, one per line
hash -r                    # forget remembered locations, then try again
# if the new folder is after the old one, put it first, in ~/.zprofile or ~/.bash_profile:
export PATH="/opt/homebrew/bin:$PATH"

Either the new Python's folder comes later in PATH than the old one's, so the old one wins, or bash remembered the old location. type -a tells you which. In a test with an old python3 already found once, and a new one then installed into a folder earlier on PATH, the shell kept running the old one, and type said python3 is hashed with the old path, until hash -r. If the order is the problem, change PATH in your login startup file and open a new terminal. Don't fix it by deleting or renaming the system's Python, which other programs rely on. For projects, a virtual environment, from chapter 16 of The Engineer's Primer, puts the right Python first automatically.

Exercise 7.2The script that wouldn't move

A script called proj contains cd ~/code/"$1". Running proj shop prints nothing, and leaves you where you were. Why, and what should it be instead?

Show solution
# in ~/.zshrc or ~/.bashrc
proj() {
  cd ~/code/"$1" || return
}

The script ran as a child process. It changed its own folder, which it's allowed to do, then exited, and its folder went with it. Your shell's folder was never touched, because a child can't change its parent. A function defined in your startup file runs inside your shell, so its cd is your cd. || return makes it stop with a failure status if the folder doesn't exist. An alias would work for a fixed folder, but can't take an argument in the middle. The same reasoning explains why tools that change your environment, from nvm to Python's activate, are shell functions or sourced scripts, never ordinary programs.

Exercise 7.3The PATH that grew

Your ~/.zshrc has export PATH="$HOME/bin:$PATH". After a while you notice $HOME/bin appears in PATH several times. Why, how can you check, and what are two fixes?

Show solution
echo "$PATH" | tr ':' '\n' | sort | uniq -d     # print any folder that appears twice

# fix 1: in zsh, make the path array keep only the first copy of each entry
typeset -U path

# fix 2, for bash or any shell: only add the folder if it's missing
add_path() { case ":$PATH:" in *":$1:"*) ;; *) PATH="$1:$PATH" ;; esac; }
add_path "$HOME/bin"

.zshrc runs for every interactive shell, and each one inherits the PATH its parent already extended. So a shell started inside another one, in a terminal multiplexer, in an editor's terminal, or by typing zsh, adds the folder again. The duplicates are mostly harmless, but they make PATH hard to read and slow every failed lookup. The check prints each folder that appears more than once. In zsh, path is an array linked to PATH, and typeset -U makes it unique. The case pattern works in any shell: called three times, it added the folder once. Better still, set PATH in the login file, ~/.zprofile, which runs once per login rather than once per shell.
