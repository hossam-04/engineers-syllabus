Chapter 11

Merging, rebasing and conflicts

{{RT}} min read{{EX}} exercises

Merging combines two lines of work by comparing each with the last commit they share, the merge base. A change made on only one side is taken. A place changed on both sides, in different ways, is a conflict: Git can't know which you meant, so it marks the spot and asks you. Rebasing does something else: it replays your commits on top of the other line of work, as new commits with new names. Both can produce the same files. They differ in the history they leave behind, and in who gets hurt when they're used on commits other people already have.

Two lines of work

Two branches that have each gained commits since they last agreed have diverged. The commit they last agreed on is their merge base, which git merge-base main lunch finds by walking back through both histories. If one side has no commits of its own, there's nothing to combine: merging just moves the branch forward to the other's tip, a fast-forward, and no merge commit is made. Otherwise Git performs a three-way merge and records the result in a merge commit, which has two parents and so keeps both histories.

The three-way merge

For each part of each file, Git looks at three versions: the merge base, ours (the branch you're on) and theirs (the one being merged in). The rule is simple. If neither side changed it, keep it. If only one side changed it, take that side's version: the other side's version is just the old one. If both sides made the same change, take it once. If both changed it differently, it's a conflict. Comparing with the base is what makes this work. With only the two tips, Git couldn't tell "I changed this line" from "you changed it", and every difference would be a question. Git first lines the versions up with a diff, so it works on hunks, runs of changed lines, rather than line numbers, and inserted or deleted lines don't throw it off. Changes that touch or sit right next to each other count as the same hunk, so two edits on neighbouring lines conflict even though they don't overlap.

The example works on a seven-line menu. Two branches change different lines and merge cleanly, then a third changes the same line as one of them and conflicts. A fourth moves forward without a merge commit, and two last commits are rebased onto main. Each command happens a minute after the last, so every id is reproducible.

What the example shows

The rule, line by line. The table in section 1 is the three-way merge made visible. Line 2 changed only on lunch, so it was taken from lunch; line 5 changed only on main, so it stayed; everything else agreed. Git's merged file matched the rule on every line, and Git asked nothing.

A conflict is a question Git leaves in the file. Since the merge base, main had changed line 2 to Sourdough, and dinner had changed it to Garlic bread. git merge exited with status 1 and listed menu.txt as unmerged. In the file, between <<<<<<< HEAD and ======= is our version, and between that and >>>>>>> dinner theirs; everything outside the markers merged normally. Resolving means editing the file into what it should be, here a line that keeps both ideas, then git add and git commit, which made the merge commit. The graph shows both merges, each with two parents.

A rebase makes new commits. tea was made from main's tip, so merging it was a fast-forward: main moved to the same commit, with no merge commit. drinks had been started from the very first commit. Rebasing it onto main replayed its two commits on top of main's tip. Each came out with a new id, because its parent and its tree changed, as chapter 9 predicted, but the lines each one added and removed were exactly the same. The old commits still exist, unreferenced, until the reflog lets them go. Afterwards main fast-forwarded to drinks, and the newest part of history is a straight line.

Resolving conflicts well

A conflict means two people had different intentions for the same lines, so resolve it by understanding both, not by picking a side. git log --merge -p file shows the commits on each side that touched the file. Setting merge.conflictStyle to zdiff3 adds a third section to each conflict, the base version, so you can see what each side changed rather than just what each side ended with. It's the most useful Git setting few people know, and belongs in your dotfiles. Once the file is right, run the tests before committing, because a merge can be textually clean and still wrong: one side renames a function while the other adds a new call to it. If it gets confusing, git merge --abort or git rebase --abort puts everything back as it was. git diff --check catches leftover markers before you commit them.

Merge or rebase?

Both are good tools for different jobs. Rebase your own work to keep it current and tidy before you share it. Replaying your unpushed commits on top of the latest main means your eventual merge is simple, and an interactive rebase, git rebase -i, lets you reorder, combine and reword them first. Merge to combine shared work, because a merge adds a commit and changes none. And follow the one rule that matters: never rebase commits that other people already have. To them, your rebased commits are new and unrelated, and their next pull brings in both versions. git pull --rebase is safe, because it only replays the local commits you haven't pushed.

Common traps
  • Committing conflict markers; git diff --check finds them.
  • Rebasing a branch that others have pulled, which duplicates its commits for everyone.
  • Resolving by taking one side wholesale without reading what the other side changed.
  • Long-lived branches that drift until merging them takes days; integrate often.
  • Forgetting that --abort exists, and improvising in the middle of a merge.
Exercises
Exercise 11.1Apply the rule

For each of five lines, far enough apart that their changes don't touch, give the merged result or say it conflicts: (1) base a, ours a, theirs b; (2) base x, ours y, theirs y; (3) base p, ours q, theirs r; (4) all three m; (5) base k, ours deleted the line, theirs k.

Show solution

(1) b: only theirs changed it. (2) y: both made the same change, which is taken once. (3) A conflict: both changed it, differently. (4) m: nobody changed it. (5) The line is deleted: only ours changed it, and a deletion is a change like any other. git merge-file, which runs Git's three-way merge on three files, agrees on all five, with a single conflict on line 3. Case 5 surprises people. If theirs had edited line k while ours deleted it, that would be a conflict, because Git can't know whether the edit matters more than the deletion.

Exercise 11.2The rebase that hurt

You pushed a branch, a colleague pulled it and built on it, and then you rebased the branch onto the latest main and force-pushed. What happens when your colleague next pulls, and how should each of you recover?

Show solution

Your colleague's commits sit on top of your old commits, A, B and C, while the branch on the server now holds new ones, A', B' and C', with the same changes and different ids. A plain git pull merges the two histories, so their branch now contains every change twice, once in each set of commits. Any of them that touched the same lines conflicts with its own copy. To recover, your colleague should replay only their own commits onto the new branch: git pull --rebase usually manages that by itself, because it recognises commits whose changes are already upstream and skips them; failing that, git rebase --onto origin/branch C moves exactly the commits after your old C. The lesson for you is the rule: once a branch is shared, add commits to it, or ask first. If you do need to replace a shared branch's history, push with --force-with-lease, chapter 13's safer force, and tell everyone who has it.

Exercise 11.3Three buttons

A pull request has three commits. GitHub offers to merge it with a merge commit, to squash and merge, or to rebase and merge. What does main's history look like after each?

Show solution

Create a merge commit: the three commits, unchanged and with their ids, plus a merge commit whose second parent is the last of them. git log --first-parent main shows one entry for the whole pull request, and the details are one level down. Squash and merge: one new commit on main containing all three commits' changes together, with the pull request's title as its message; the original three aren't in main's history at all. Rebase and merge: the three commits replayed onto main as new commits with new ids, in a straight line, with no merge commit. Squashing gives the tidiest history and loses the steps, which matters to chapter 12's bisect if a pull request was large. Merging keeps everything, and rebasing keeps the steps without the merge. Teams pick one and say so in their contributing guide.

Checklist
  • Can you find the merge base of two branches, and say when a merge will fast-forward?
  • Can you apply the three-way rule to predict a merge's result?
  • Can you read conflict markers, resolve them by understanding both sides, and finish or abort the merge?
  • Can you explain why a rebased commit has a new id but the same change?
  • Can you say when to merge, when to rebase, and which commits must never be rebased?
