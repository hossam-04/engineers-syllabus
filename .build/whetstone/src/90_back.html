The deliverable

The stage asks for two things, both public and both with a README written for a stranger: a repository of your dotfiles, and one shell script that automates a chore you genuinely repeat. Chapters 8 and 4 build a small working version of each; the lists below say what the full versions need. Both will outlive the stage. You'll install the first on every machine you use, and the second is the start of a habit of automating what bores you.

1. A public dotfiles repository

Your settings for the tools you use every day, in a repository anyone can read, with a script that installs them. Chapter 8 is the model.

  1. Settings for your shell, Git and editor, grown a line at a time, each with a comment saying why it's there.
  2. An install script that links every file into place, backs up anything it would replace, never deletes, and is safe to run again, plus an uninstall that reverses it.
  3. Per-machine and private settings in local files that the shared ones include, ignored by Git, and no secret anywhere in the history: check with git grep or a scanner before you publish.
  4. Tested on a clean account or a fresh container, with anything specific to macOS or Linux behind a check of uname.
  5. A README that says what each file configures, gives the one command that installs it, says what that command changes and how to undo it, and lists the systems you've tried it on.

2. A script for a chore you repeat

Pick something you really do by hand every week: tidying downloads, backing up a folder, renaming photos, cleaning old branches, starting your day's tools. Chapter 4 is the model.

  1. Strict mode, a usage message for -h and for wrong arguments, options parsed with getopts, exit statuses 0, 1 and 2, and every message on stderr.
  2. A dry run that shows exactly what would happen; nothing overwritten or deleted without a check; safe to run twice; and a lock and a trap if two runs could ever overlap.
  3. Every expansion quoted, no warnings from ShellCheck, and either bash 3.2 compatible or a clear statement of the version it needs.
  4. Tests that run it in a temporary folder and check the results, including what happens with bad arguments, a missing folder and names with spaces.
  5. Installed as a command through your dotfiles, documented in a README, and if the chore is regular, run on a schedule with cron on Linux or launchd on a Mac.

For both: keep them under Git from the first day, with small commits and messages that explain why, as chapter 12 describes. Make at least one change through a pull request, from a branch, even in your own repository, so chapter 13's workflow is something you've done rather than read about. Then ask someone else to install your dotfiles and run your script from the README alone, and fix whatever confused them.

The sixteen rules

One per chapter, each linked back to it. Read them before you start a new script or a new repository, and again when a tool surprises you.

  1. Quote every expansion, and know exactly which list of arguments a line becomes.
  2. Results to stdout, messages to stderr, and check the status of every step, including inside a pipeline.
  3. Ask questions of text with small tools in a pipeline: quote the patterns, and sort before you count.
  4. Strict mode, a dry run, and never overwrite: a script must be safe to run twice.
  5. A name points to an inode, and a symbolic link points to a name.
  6. The folder decides who may delete; never fix a permission error with 777 or sudo.
  7. The environment flows down, never up; ask type -a what a name will run.
  8. Keep your settings in a public repository, linked into place, and your secrets out of it.
  9. A commit is a snapshot named by its contents; changing the past renames everything after it.
  10. Branches are labels and the reflog remembers them; only uncommitted work can really be lost.
  11. Merge shared work; rebase only commits nobody else has.
  12. Make small commits that explain why, and bisect whatever used to work.
  13. Work on branches, push with a lease, and keep pull requests small and explained.
  14. Learn one editor deeply, and rename with a tool that understands the code.
  15. Read the whole message, from the bottom, and ask with a minimal reproduction.
  16. Test yourself, space your reviews, and practise at the edge of your ability.

Tools are described as of late 2026.

Every example was executed before publication with Python 3.14 on macOS 26, whose shell tools are bash 3.2, BSD's versions of the text tools, and Git 2.50. They're written for Python 3.12 or later and to print the same output on Linux with the GNU tools: they sort whatever the filesystem would order arbitrarily, avoid output whose spacing differs between systems, give every commit a fixed author and time, ignore your own Git settings, and use only features shared by bash 3.2 and bash 5. They were not run on Linux for this edition, so a difference there is a bug worth reporting. Each was also run a second time in a deliberately hostile environment, with a different time zone and temporary folder, a home folder with its own Git and shell settings, and BASH_ENV and CDPATH set, and printed exactly the same. Tested here: how bash turns a line into arguments; redirections, pipes, exit statuses and set -e; questions answered from a web server's log; a tidying script with a dry run, a lock and a trap; hard links, symbolic links and a deleted file still open; permission bits tried one at a time; PATH, exported variables and bash's startup files; a dotfiles repository installed twice; Git's objects built by hand; refs, a detached HEAD and the reflog; a clean merge, a conflict and a rebase; a bug found by bisect, log -S and blame; a contribution through a fork; a fuzzy finder and a scope-aware rename; a traceback read and an input shrunk by delta debugging; and a model of forgetting.
