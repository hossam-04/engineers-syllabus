The Engineer's Mill

Charles Babbage's Analytical Engine, designed in the 1830s, had two parts: the Store, which held numbers, and the Mill, which worked on them. Every computer since has kept that split. This volume builds a machine from a single kind of logic gate upward, through adders, an ALU, registers and a CPU that runs real programs. It then follows a program from source text to a running process, and explains the memory hierarchy, pipelines and parallel hardware that decide how fast it runs. Every circuit and mechanism is simulated in Python you can run.

The one habit

Every question about speed has an arithmetic answer: how many instructions, how many cycles each, how many trips to memory, and how far away the memory is.

An L1 cache hit costs about a nanosecond and a trip to main memory about a hundred. A mispredicted branch costs a dozen or more cycles, and a disk seek costs millions. So estimate the cost before you measure it, and measure before you optimise. When the estimate and the measurement disagree, one of your models is wrong, and finding out which is how you learn the machine.

Part I

Bits

Two chapters on how numbers live in hardware: integers as fixed-width patterns of bits, with the wrap-around that comes with them, and real numbers as binary scientific notation, with the rounding that comes with that. Every later chapter computes with these representations, and many famous bugs live in them.

Chapter 01

Binary, hex and two's complement

11 min read3 exercises

Everything in a computer is a pattern of bits, and a type is just an agreement about how to read one. The same eight bits are 255 or −1 depending on who's asking. Two's complement, the representation every modern processor uses for signed integers, lets one adder serve both readings. That convenience comes at a price: integers have a fixed width, and when a result doesn't fit, most languages wrap around silently. This chapter covers the representations, the arithmetic, and the overflow bugs that have shipped in real software.

Bases, bits and bytes

A number written in base b has digits worth powers of b, so 2026 is 2⋅103+0⋅102+2⋅10+6 in decimal and 11111101010 in binary. Hardware uses base 2 because a wire is easiest to read as one of two states. People write binary in hexadecimal, base 16, because each hex digit stands for exactly four bits, a nibble, so 0x7EA is 0111 1110 1010 at a glance. Eight bits make a byte, the smallest unit memory is addressed in, and a word is the natural width of the processor's registers, now almost always 64 bits.

With n bits there are 2n patterns. Read as unsigned integers they stand for 0 to 2n−1, and arithmetic on them is arithmetic modulo 2n: add 1 to the largest value and you get 0, exactly the clock arithmetic of The Engineer's Compass, chapter 5.

Two's complement

For signed integers, every modern processor uses two's complement. The top bit's weight is negative: in n bits it's worth −2n−1 instead of +2n−1, and the other bits keep their usual positive weights. In 8 bits, 10000000 is −128, 11111111 is −128 + 127 = −1, and 01111111 is +127. The range is −2n−1 to 2n−1−1, one more negative number than positive. Equivalently, the pattern for −x is the unsigned number 2n−x, which is why the representation lines up so neatly with modular arithmetic.

To negate a two's complement number, invert every bit and add 1: inverting gives (2n−1)−x, and adding 1 gives 2n−x (exercise 1.2). There's one zero, unlike older sign-and-magnitude schemes with a +0 and a −0. Most importantly, the hardware that adds unsigned numbers adds signed ones correctly too, because both are arithmetic modulo 2n. The processor doesn't need to know which reading you intend. Only comparisons, division, widening and overflow detection differ. The asymmetry has one sharp edge: the most negative number has no positive partner, so negating −128 in 8 bits gives −128 again, and abs(INT_MIN) in C is negative.

Overflow

An unsigned sum overflows when it carries out of the top bit. A signed sum overflows when two operands of the same sign produce a result of the other sign. In 8 bits, 100 + 50 gives the pattern 10010110, which is 150 unsigned and −106 signed. Languages disagree about what to do. C and C++ make signed overflow undefined behaviour, so compilers may assume it never happens and delete checks that rely on it, while unsigned overflow wraps by definition. Java and Go wrap signed integers silently. Rust panics in debug builds and wraps in release builds unless you ask for checked arithmetic. Python's integers grow without limit, so the only overflow is running out of memory.

Wrap-around has caused famous failures. In 2006 Joshua Bloch reported that the binary search in Java's standard library, and in many textbooks, computed its midpoint as (low + high) / 2. With arrays of over a billion elements, the sum overflows 32 bits and becomes negative. The fix is low + (high - low) / 2, and the example reproduces both. Systems that store time as a signed 32-bit count of seconds since 1970 run out on 19 January 2038 at 03:14:07 UTC, one second before they jump back to December 1901. And in 1996 the first Ariane 5 rocket was lost about forty seconds after launch, when a conversion of a 64-bit floating-point value into a 16-bit signed integer overflowed in software reused from Ariane 4, whose slower trajectory had never produced values that large.

Shifts, widening and division

Shifting left by k multiplies by 2k, dropping bits that fall off the top. Shifting right comes in two kinds. A logical shift fills with zeros, which suits unsigned values. An arithmetic shift copies the sign bit, so −20 >> 2 is −5, which suits signed values. Widening a signed value to more bits needs sign extension, copying the top bit into the new bits, so that −1 in 8 bits stays −1 in 32. Integer division of negative numbers differs too. Python's // and >> round down, so −7 // 2 is −4, while C, Java and Go round integer division towards zero, giving −3. Ported code that relies on either behaviour breaks quietly.

Byte order

A 32-bit value occupies four bytes, and machines disagree about their order. Little-endian machines, which include x86 and almost all ARM systems, store the least significant byte first, so 0x12345678 sits in memory as 78 56 34 12. Big-endian order, 12 34 56 78, is the convention for network protocols, where it's called network byte order, and for many file formats. Byte order never matters inside a program's own arithmetic. It matters the moment bytes cross a boundary: written to a file, sent over a network, or read from a memory dump. Then the format, not the machine, must say which order it uses, and code must convert explicitly, as Python's struct and int.from_bytes do.

Bits, run

The example converts between bases, encodes and decodes 8-bit two's complement, detects overflow, compares shifts and division rules, shows both byte orders, reproduces the midpoint and 2038 bugs in 32-bit arithmetic, and counts set bits with a classic trick.

The last line uses the identity that x & (x - 1) clears the lowest set bit of x. Subtracting 1 turns the lowest 1 into 0 and the zeros below it into ones, and the & then erases all of them. Repeating it until x is zero counts the set bits, and x is a power of two exactly when one application gives zero. Bit tricks like these are the vocabulary of hash functions, compression and the flags fields of network headers. Processors also offer them as single instructions such as popcnt.

Common traps
  • Mixing signed and unsigned in a comparison. In C, -1 < 0u is false, because −1 is converted to the largest unsigned value.
  • Assuming overflow raises an error. In most languages it wraps, and in C it's undefined.
  • Taking the absolute value of the most negative integer, which overflows back to itself.
  • Right-shifting a negative number and expecting a logical shift, or the reverse.
  • Writing binary data without stating its byte order, then reading it on a machine with the other one.
  • Storing timestamps or counters in 32 bits that will outgrow them during the system's lifetime.
Exercises
Exercise 1.1Subtraction is addition

Write −37 in 8-bit two's complement, then compute 100 + (−37) in binary, ignoring any carry out of the top bit. Check the result.

Show solution

37 is 00100101. Inverting gives 11011010 and adding 1 gives 11011011, which is 219 as an unsigned number, and 256 − 37 = 219, as it should be. Adding 100 = 01100100 gives 1 00111111. Drop the carry out of bit 8 and the result is 00111111 = 63 = 100 − 37. The carry out of the top bit doesn't indicate signed overflow: the operands had different signs, so overflow was impossible. This is how processors subtract, by adding the two's complement, so a single adder circuit does both (chapter 4).

Exercise 1.2Why invert-and-add-one negates

Prove that for an n-bit pattern x, inverting every bit and adding 1 gives the two's complement representation of −x.

Show solution

Inverting every bit of x gives the pattern whose bits are 1 exactly where x's are 0, so x and its inverse add to 11…1, which is 2n−1. The inverse is therefore (2n−1)−x, and adding 1 gives 2n−x. Working modulo 2n, that's congruent to −x, and the two's complement pattern of −x is by definition 2n−x. ∎ For x = 0 the result is 2n, which wraps to 0, so zero is its own negation. For x=2n−1, the most negative number, it gives 2n−1 again, which is the asymmetry described above.

Exercise 1.3An overflow check the compiler deletes

In C, if (a + b < a) is a correct test for overflow when a and b are unsigned, and b is at most the maximum value. Why does it work for unsigned integers, and why can a compiler legally delete it when they're signed?

Show solution

Unsigned arithmetic wraps modulo 2n by definition. If a + b fits, the result is at least a. If it doesn't, the true sum is less than a+2n, so the wrapped result a+b−2n is less than a. So the test fires exactly on overflow. For signed integers, overflow is undefined behaviour, so the compiler may assume it never happens. Under that assumption, a + b < a can only be true when b < 0, and for a known non-negative b the compiler may conclude the condition is always false and remove it. Correct signed checks test before adding, for example b > 0 && a > INT_MAX - b, or use the __builtin_add_overflow intrinsic in GCC and Clang.

Chapter 02

Floating point, and why 0.1 + 0.2 isn't 0.3

10 min read3 exercises

Floating point is scientific notation in binary, with a fixed number of significant bits. Most decimal fractions, 0.1 among them, have no exact binary form, so they're rounded the moment they're written down. Every operation rounds again. The gaps between representable numbers grow with their size, addition stops being associative, and subtracting two nearly equal numbers can wipe out every correct digit. None of this is a bug. IEEE 754 specifies it exactly, and it's what makes floating point fast and predictable. This chapter shows the layout, the rounding and the special values, then the habits that keep numerical code correct.

The layout

The IEEE 754 double, Python's float and JavaScript's only number type, packs a number into 64 bits: a sign bit s, an 11-bit exponent e and a 52-bit fraction f. For normal numbers the value is

(−1)s×1.f×2e−1023.

The leading 1 before the binary point isn't stored, since every normal number has one, so the 52 stored bits give 53 bits of precision. The exponent is stored with a bias of 1023 so that it can be compared as an unsigned number. The 32-bit single format has 8 exponent bits and 23 fraction bits, about 7 significant decimal digits against the double's 15 to 17.

Why 0.1 + 0.2 isn't 0.3

The double stored for 0.1 is exactly 0.1000000000000000055511151231257827…, slightly too large, and the ones for 0.2 and 0.3 are rounded too. IEEE 754 guarantees that each basic operation is correctly rounded: the result is the exact result of the stored inputs, rounded to the nearest double, with ties going to the even neighbour. The sum of the stored 0.1 and 0.2 rounds to a double one step above the double stored for 0.3, so they differ by 2−54, and Python prints 0.30000000000000004. The arithmetic was as accurate as it could be. The inputs weren't the numbers you typed. So never compare floating-point results with ==. Compare with a tolerance suited to the problem, as math.isclose does with a relative tolerance by default.

Precision, and gaps that grow

The distance from a double to the next one is its unit in the last place, or ulp. Near 1 it's 2−52≈2.2×10−16, the machine epsilon. Near a million it's about 10−10, and above 253≈9×1015 it's 2 or more, so doubles stop representing every integer. The example shows 253+1 rounding to 253. That matters outside numerical code. JavaScript stores every number as a double, so 64-bit identifiers sent as JSON numbers lose their low digits in a browser, which is why APIs send large IDs as strings. Single precision runs out of integers at 224=16,777,216, which is why games with large worlds see objects jitter far from the origin.

Rounding accumulates, and order matters

Each operation rounds, and errors build up over many operations. Addition isn't associative: (1016+1)−1016 is 0, because adding 1 to 1016 falls within half an ulp and is rounded away, while (1016−1016)+1 is 1. Adding 0.1 ten million times in a loop gives 999,999.99984, off by about 1.6×10−4, because each small addend loses its low bits against the growing total. Kahan summation carries the lost low-order bits in a separate correction variable and adds them back, and Python's math.fsum goes further, tracking partial sums exactly and rounding once at the end. Both give 1,000,000.0. Order dependence has a practical consequence: a parallel sum, which adds in whatever order the threads finish, can give slightly different results on every run.

Special values

An exponent of all ones encodes infinity, when the fraction is zero, or NaN, "not a number", when it isn't. Overflow produces ±∞, and invalid operations such as ∞ − ∞ or 0/0 produce NaN, which then propagates through every later operation. NaN is unequal to everything, including itself, which breaks sorting and hash tables (The Engineer's Compass, chapter 4). There are two zeros, +0 and −0, equal under == but distinguishable by their sign, so 1/−0 is −∞. An exponent of all zeros encodes subnormal numbers, which fill the gap between the smallest normal double, about 2.2×10−308, and zero. That's gradual underflow, and on some processors arithmetic on subnormals is much slower than normal arithmetic.

Catastrophic cancellation

Subtracting two nearly equal numbers cancels their shared leading digits and leaves only the low digits, which are the ones carrying rounding error. For small x, cos x is very close to 1, so 1−cosx keeps hardly any correct digits. At x = 10−8, cos x rounds to exactly 1 and (1−cosx)/x2 comes out as 0 instead of 0.5. The identity 1−cosx=2sin2(x/2) computes the same quantity without subtracting, and stays accurate. The same issue makes the textbook formula for variance, the mean of the squares minus the square of the mean, useless for data with a large mean and a small spread (exercise 2.3). The general cure is algebraic: rearrange the formula so it doesn't subtract nearly equal quantities.

Floats, measured

The example decodes the fields of three doubles, shows the exact stored value of 0.1, measures the gaps between doubles at four magnitudes, compares three ways of summing, exercises the special values, and computes (1−cosx)/x2 both ways.

The fields line up with the formula. 1.0 has exponent field 1023, meaning 20, and fraction 0. −2.5 is −1.25×21, with fraction 0x4000000000000, binary .01. 0.1 is 1.6×2−4, whose fraction 0x999999999999A is the repeating pattern 1001 1001… ending in a rounded-up 1010. For money, use integers counting the smallest unit, or a decimal type such as Python's Decimal. Binary floating point can't hold 0.10 exactly, and an accounting system can't round away a cent.

Common traps
  • Comparing floats with ==, including loop conditions like while x != 1.0.
  • Storing money in binary floating point. Use integer cents or a decimal type.
  • Sending 64-bit integers to JavaScript as numbers, which silently rounds them above 253.
  • Summing many small values into a large total without Kahan summation or math.fsum.
  • Subtracting nearly equal quantities, as in naive variance formulas.
  • Expecting identical results everywhere. Fused multiply–add, compiler flags such as -ffast-math and parallel reduction order all change the last bits.
Exercises
Exercise 2.1Decode a float by hand

Decode the 32-bit single-precision pattern 0xC0490FDB. Single precision has 1 sign bit, 8 exponent bits with bias 127, and 23 fraction bits.

Show solution

In binary, 0xC0490FDB is 1100 0000 0100 1001 0000 1111 1101 1011. The sign bit is 1, so the number is negative. The next 8 bits, 1000 0000, give exponent field 128, so the scale is 2128−127=2. The remaining 23 bits are the fraction .1001001 0000 1111 1101 1011, so the significand is 1.10010010000111111011012 ≈ 1.5707964. The value is −1.5707964×2≈−3.1415927: it's −π, rounded to single precision. The digits after the seventh are wrong, since π=3.14159265…, which is what about 24 bits of precision buys.

Exercise 2.2A loop that never ends

Why might for (float f = 0.0f; f != 1.0f; f += 0.1f) never terminate? How should the loop be written?

Show solution

0.1f isn't exactly one tenth, and each addition rounds. After ten steps, f is 1.0000001192… in single precision, one ulp above 1.0f, so f != 1.0f stays true and the loop runs past 1 for ever, or until something else stops it. Loop over an integer counter, and compute the float from it: for (int i = 0; i < 10; i++) { float f = i * 0.1f; … }. Computing each value from the counter also prevents error from accumulating across iterations, since each value is rounded once instead of ten times.

Exercise 2.3The variance formula that fails

The population variance equals x2‾−x¯2, the mean of the squares minus the square of the mean. For the values 109+4, 109+7, 109+13 and 109+16, this formula in double precision gives 0, while the true variance is 22.5. Explain why, and give a formula that works.

Show solution

Each square is about 1018, where the gap between doubles is 128, so the squares are stored with an error of up to 64 each. The mean of the squares and the square of the mean are both about 1018 and agree in their first 16 digits, and the variance, 22.5, is far smaller than the rounding error in either. Subtracting them cancels everything except noise, which here happens to be 0. The fix is to subtract the mean before squaring: 1n∑(xi−x¯)2 works with numbers like 4.5 and 2.5 instead of 1018. For data arriving one value at a time, Welford's algorithm updates the mean and the sum of squared deviations incrementally with the same stability. Python's statistics.pvariance returns 22.5 for this data.

Chapter 03

Logic gates, from a single NAND

9 min read3 exercises

A logic gate computes a boolean function of its inputs, and one gate is enough to build all the others. NAND, "not and", is functionally complete: Not, And, Or, Xor, the multiplexers that choose between signals and, eventually, a whole computer can be built from NAND gates alone. That's where Nand2Tetris starts. This chapter builds the basic gates, counts what each one costs in NANDs and in delay, turns any truth table into a circuit, and shows why the shape of a circuit matters as much as its size.

Gates are functions, and wires are variables

A combinational circuit has no memory. Its outputs depend only on its current inputs, so it computes a function, and its truth table describes it completely. Physically, a gate is a handful of transistors, and a modern processor contains billions of them. Two costs matter. Size is the number of gates, which costs chip area and power. Depth is the longest chain of gates from any input to the output. Each gate takes time to settle, so depth sets how long the circuit needs before its output is valid, and therefore, in chapter 5, how fast the clock can tick.

Everything from NAND

NAND is 0 only when both inputs are 1. The Engineer's Compass, exercise 1.3, proved that it can express any boolean function. Here are the constructions, built up so that each gate uses the ones before:

  • Not(a) = Nand(a, a), one gate;
  • And(a, b) = Not(Nand(a, b)), two gates;
  • Or(a, b) = Nand(Not a, Not b), three gates, by De Morgan's law;
  • Xor(a, b): with t = Nand(a, b), the result is Nand(Nand(a, t), Nand(b, t)), four gates.

The multiplexer, or Mux, is the gate that makes computers programmable. It takes two data inputs and a selector, and passes through one input or the other: Mux(a, b, sel) = sel ? b : a, four NANDs. Its mirror image, the demultiplexer, routes one input to one of two outputs. Wider versions select among 4, 8 or more inputs and handle whole 16- or 64-bit words at once. A 16-bit And is just 16 Ands side by side: 32 NANDs, still depth 2, because the bits don't interact. Multiplexers are how a CPU chooses which register to read, which ALU function to apply and where the next instruction comes from.

From any truth table to a circuit

Every truth table has a circuit. For each input row where the output is 1, build an And of the inputs, negated where that row has a 0, and Or all of these terms together. This sum of products is correct by construction, and it's how logic synthesis starts, but it's rarely efficient. For the majority function, which is 1 when at least two of three inputs are 1, the sum of products uses 28 NANDs at depth 11, while a hand-designed version uses 6 NANDs at depth 4. Turning a specification into a small, shallow circuit is the job of synthesis tools. Like an optimising compiler, they apply algebraic identities until nothing more can be saved.

Shape matters as much as size. An 8-way Or, which is 1 if any of eight inputs is 1, can be a chain of seven Ors or a balanced tree of seven Ors. Both use 21 NANDs, but the chain is 14 gates deep and the tree only 6. Depth grows linearly in the chain and logarithmically in the tree. The same choice, at the scale of 64-bit additions, decides how fast a processor can add (chapter 4).

Built and checked

The example builds every gate above from a single nand function. Each signal carries its value and its depth, and a counter tracks how many NANDs each evaluation used. Every gate is checked against its full truth table.

Common traps
  • Counting gates and forgetting depth. A small, deep circuit can be slower than a larger, shallow one.
  • Confusing a Mux with a DMux: a Mux chooses one of several inputs, a DMux sends one input to one of several outputs.
  • Trusting a hand-optimised circuit without checking its whole truth table. With n inputs there are only 2n rows, so check them all.
  • Assuming a sum of products is a good circuit. It's a correct starting point, not an efficient one.
  • Thinking of gates as instantaneous. Every gate delays its output, and chapter 5's clock exists because of that.
Exercises
Exercise 3.1A 4-way multiplexer

Build a Mux4Way, which selects one of four inputs a, b, c, d using a 2-bit selector s1s0, from the 2-way Mux. How many NANDs does it use, and what's its depth?

Show solution

Use s0 to choose within each pair, then s1 to choose between the pairs: ab = Mux(a, b, s0), cd = Mux(c, d, s0), out = Mux(ab, cd, s1). That's 3 Muxes, so 12 NANDs. A Mux is 2 gates deep from its data inputs and 3 from its selector, which first goes through a Not. The selector s0 reaches the output through the first Mux's selector and then the last Mux's data input, so the depth is 3 + 2 = 5. In general an n-way Mux built as a tree of 2-way Muxes uses n − 1 of them and has depth proportional to log n. Nand2Tetris asks you to build Mux4Way16 and Mux8Way16 exactly this way, 16 bits at a time.

Exercise 3.2Why Or needs three NANDs

Prove that Or(a, b) = Nand(Not a, Not b). Can Or be built from fewer than three 2-input NANDs?

Show solution

By De Morgan, ¬(¬a∧¬b)=a∨b, and Nand(x, y) is ¬(x∧y), so Nand(Not a, Not b) = a ∨ b. For the lower bound, any circuit with one NAND computes a NAND of two of its inputs or constants, which isn't Or. With two NANDs, the output gate is a NAND whose inputs are a, b, or the output of the first gate. Checking the few possibilities shows none of them is Or. For example, Nand(Nand(a, b), x) is 1 whenever a and b are both 1, regardless of x, and also whenever x is 0, so it can't match Or in every row. So three is the minimum. Proving minimality is usually much harder than this, and synthesis tools rely on heuristics rather than proofs.

Exercise 3.3A comparator

Design a circuit that outputs 1 when two 4-bit numbers are equal. How many NANDs does your design use, and what's its depth?

Show solution

Two bits are equal exactly when their Xor is 0. So compute di=Xor(ai,bi) for the four bit positions, 16 NANDs at depth 3, then output 1 if no di is 1: out = Not(Or(Or(d_0, d_1), Or(d_2, d_3))). Two levels of Or form a balanced tree, 3 Ors for 9 NANDs adding depth 4, and the final Not adds 1. That's 26 NANDs at depth 8. You can save the final Not by building the last Or as a Nor directly, which shows how much room there is between a correct circuit and a minimal one. Comparators like this one decide branches, as in chapter 4's ALU, whose zero flag zr tests whether a 16-bit result is all zeros.

Chapter 04

Adders and the ALU

10 min read3 exercises

Arithmetic is just more gates. A full adder adds three bits, a chain of them adds whole words, and subtraction reuses the same chain through two's complement. The simple chain is slow, because each bit waits for the carry from the bit below it, and the fix is the most important idea in fast arithmetic: compute all the carries in parallel. The arithmetic logic unit then wraps an adder in a few multiplexers, so that six control bits choose among eighteen functions. That's the Hack ALU, the heart of the Nand2Tetris computer, built and checked in this chapter.

Adding bits

Adding two bits gives a sum bit and a carry: 1 + 1 = 10 in binary, sum 0 carry 1. The sum is a + b mod 2, which is Xor, and the carry is And. That's a half adder. Adding a column of a long sum needs three inputs, the two bits plus the carry from the column to the right, and a full adder does that with two half adders and an Or:

s=a⊕b⊕cin,cout=ab∨(a⊕b)cin.

Built from this chapter's gates, a full adder takes 15 NANDs; a hand-optimised one takes 9.

The ripple-carry adder

To add two n-bit numbers, chain n full adders, feeding each one's carry out into the next one's carry in. This ripple-carry adder is exactly schoolbook addition, done in binary.

The example builds an 8-bit ripple adder from NAND gates and checks it on all 65,536 pairs of inputs. Its weakness is depth. Each full adder adds four gates to the carry path, so an 8-bit adder is 34 gates deep and a 64-bit adder 258. Chapter 5 shows that the clock can tick no faster than the slowest such path allows, so a 64-bit ripple adder would cap a processor at a few hundred megahertz.

Computing every carry at once

The way out is to notice when a column decides its carry on its own. A column generates a carry if both its bits are 1, gi=aibi, and propagates an incoming carry if exactly one bit is 1, pi=ai⊕bi. Then ci+1=gi∨pici. Unrolling this shows that every carry is a function of the bits below it, and nothing forces the computation to go column by column:

c4=g3∨p3g2∨p3p2g1∨p3p2p1g0∨p3p2p1p0c0.

The pairs (g, p) for adjacent spans of columns combine with an associative operation: a span generates a carry if its upper half generates one, or its upper half propagates and its lower half generates. Associativity means all the prefixes can be computed in a balanced tree, in log2n levels, the same trick as chapter 3's balanced Or. That's a parallel-prefix adder, here the Kogge–Stone design from 1973. The example's table shows the trade. At 64 bits the prefix adder is 28 gates deep against the ripple adder's 258, and it uses three times as many gates, 2,883 against 960. Real processors use prefix adders of various shapes that balance gate count, wiring and depth.

Subtraction for free

Chapter 1 showed that −y is the bitwise inverse of y plus 1, so x−y=x+y‾+1. A subtractor is therefore an adder with a row of Xor gates that invert y on demand, and a carry-in of 1 that supplies the "+ 1". One circuit adds and subtracts, signed or unsigned. Comparisons come free too: x < y exactly when x − y is negative, ignoring overflow, so the sign bit of the difference answers the question.

The ALU

An arithmetic logic unit computes one of several functions of its inputs, chosen by control bits. The Hack ALU, designed for Nand2Tetris, does it with six bits applied in order:

  • zx zeroes x, and nx then inverts it;
  • zy zeroes y, and ny then inverts it;
  • f chooses between x + y and x & y;
  • no inverts the output.

Two status outputs report whether the result is zero (zr) and whether it's negative (ng). Those few operations produce eighteen useful functions, because inversion and addition combine in clever ways. With v‾=−v−1 in two's complement, setting nx, f and no computes x‾+y‾=−(−x−1+y)−1=x−y. The example implements the ALU at the word level, runs all 18 control codes from the Nand2Tetris specification on 2,000 random pairs of 16-bit inputs, and checks every result against Python's arithmetic.

The status flags are how a computer decides anything. Every conditional branch in chapter 7 is a jump taken or not according to zr and ng, the results of an ALU operation such as x − y. Real ALUs add shifts, rotations and comparisons, and processors pair them with separate units for multiplication and division. Multiplying 64-bit integers takes a few cycles on a modern core, using trees of adders working in parallel. Division is iterative and takes tens of cycles, which is why compilers turn division by a constant into a multiplication and a shift whenever they can.

Common traps
  • Forgetting the carry-in of 1 when subtracting by inverting.
  • Reading the carry out as signed overflow. Signed overflow is when the carries into and out of the sign bit differ (exercise 4.3).
  • Treating every arithmetic operation as equally cheap. Addition takes one cycle, multiplication a few, division tens.
  • Judging an adder by gate count alone. The carry chain decides its speed.
  • Hand-optimising multiplication by constants into shifts. Compilers already do it, and do it correctly.

Exercise 4.2How deep is a lookahead carry?

Using the expansion of c4 above, how deep is a 4-bit carry-lookahead unit built from 2-input gates, and why doesn't the same flat expansion work for 64 bits?

Show solution

The g and p signals take one gate level each, roughly, and each term of c4 is an And of up to five signals and the result an Or of five terms. With 2-input gates, a 5-input And or Or is a balanced tree of depth 3, so c4 is about 1 + 3 + 3 = 7 gate levels, against 4 × 4 = 16 levels of carry path in a 4-bit ripple chain. Flattened for 64 bits, the last carry would be an Or of 65 terms, some of them Ands of 65 signals. The fan-in and the wiring explode, and the gate count grows quadratically. Prefix adders keep the logarithmic depth while reusing partial results, which is why they, rather than flat lookahead, are what wide adders use.

Exercise 4.3The overflow flag

Show that a signed addition overflows exactly when the carry into the sign bit differs from the carry out of it. Check the rule on 100 + 50 and on −100 + −50 in 8 bits.

Show solution

Let a and b be the sign bits and c the carry into the sign position. The sign of the result is a⊕b⊕c and the carry out is the majority of a, b and c. If a and b differ, the result can't overflow, and the carry out equals c. If a = b = 0, overflow means the result's sign is 1, which happens exactly when c = 1, and the carry out is then 0, so they differ. If a = b = 1, overflow means the sign is 0, which happens exactly when c = 0, and the carry out is 1. So overflow happens exactly when c ≠ carry out. ∎ For 100 + 50 = 01100100 + 00110010, there's a carry into bit 7 and none out: overflow. For −100 + −50 = 10011100 + 11001110, there's a carry out of bit 7 and none into it: overflow again, matching chapter 1. Processors compute this Xor as the V, or OF, flag after every addition.

Chapter 05

Flip-flops, registers and the clock

11 min read3 exercises

Combinational circuits forget their inputs the moment those inputs change. Memory needs feedback, a circuit whose output loops back into its own input. Two NAND gates wired to each other remember one bit. Add a clock, and you get a flip-flop that changes only at the instant the clock ticks, which turns the messy physics of gate delays into a simple rule: everything between two ticks has one clock period to settle. Registers, RAM and the program counter are flip-flops plus the multiplexers of chapter 3, and the slowest path between two flip-flops sets the processor's clock speed.

Feedback and the latch

Wire two NAND gates so that each one's output is one of the other's inputs, and leave one input on each free. Call the free inputs S‾ and R‾; they're active-low, meaning a 0 does something. Pulling S‾ to 0 forces the output Q to 1, and the cross-connection then holds it there after S‾ returns to 1. Pulling R‾ to 0 forces Q to 0, which is also held. With both inputs at 1 the circuit just remembers its last state. That's an SR latch, one bit of memory made of two gates.

The forbidden input is both at 0, which forces both outputs to 1, breaking the rule that they're opposites. Releasing both at once creates a race, and the example's simulation, which updates both gates in lockstep, oscillates for ever. Real gates are never perfectly matched, so the latch eventually falls one way or the other, but it may hover between the two for an unpredictable time first, a condition called metastability. Designs avoid the forbidden input, and synchronise any signal arriving from outside the clock's control.

The clock and the D flip-flop

A latch changes whenever its inputs change, and signals in a real circuit change at different times as they ripple through gates of different depths. The solution is a clock, a signal that alternates between 0 and 1 at a fixed rate, and a D flip-flop that copies its input D to its output Q only at the clock's rising edge. Internally it's two latches in a row, master and slave, alternately enabled by the clock, so the input can never race straight through. Nand2Tetris treats the flip-flop as a primitive with a simple rule: out(t) = in(t − 1), the output during each clock cycle is what the input was during the previous one.

For the sampling to work, D must be stable for a short setup time before the edge and a hold time after it. Meeting those two constraints everywhere on a chip is what timing analysis tools check, and violating them is how metastability gets in.

Registers, RAM and the program counter

A 1-bit register is a flip-flop with a Mux in front. When the load bit is 1 the Mux passes in the new value, and when it's 0 it feeds the flip-flop's own output back, so the bit is kept (exercise 5.1). Sixteen of them side by side make a 16-bit register. A RAM is many registers plus addressing. A DMux routes the load bit to the one register selected by the address, and a Mux selects that register's output. Nand2Tetris builds RAM8 from 8 registers, then RAM64 from 8 RAM8s, and so on up to the 16K-word RAM of the Hack computer, each level using three more address bits. Real memories aren't built from flip-flops. Static RAM, used for caches, takes six transistors per bit, and dynamic RAM, used for main memory, stores each bit as charge on a tiny capacitor with one transistor. That's dense and cheap, but the charge leaks away, so every row must be read and rewritten every few tens of milliseconds, and it's slow to read (chapter 9).

The program counter holds the address of the next instruction. On each cycle it does one of four things, in priority order: reset to 0, load a new address for a jump, increment to the next instruction, or hold. In the example it counts 0, 1, 2, 3, jumps to 100, counts on, and resets. That one register is the whole of a computer's control flow: chapter 7's CPU decides each cycle whether to increment it or load it.

Simulated

The example simulates the SR latch gate by gate, then models flip-flops, a register, an 8-word RAM and the program counter cycle by cycle, and finally turns chapter 4's adder depths into maximum clock rates.

How fast can the clock tick?

In a synchronous design every flip-flop updates at the same clock edge, and between edges the combinational logic computes the next values. Those values must settle before the next edge, so the clock period must exceed the delay of the slowest path from one flip-flop to the next, the critical path, plus the setup time. With an illustrative 15 picoseconds per gate, the 64-bit ripple adder's 258-gate path allows at most 258 MHz, while the prefix adder's 28 gates allow about 2.4 GHz. That's why chapter 4's carry trick matters. Designers shorten critical paths with faster circuits, and by splitting long paths into stages separated by registers, which is pipelining (chapter 12).

Clock rates rose for decades and then stopped near 4 to 5 GHz around 2005. The power a chip burns switching its transistors grows with the clock rate and with the square of the supply voltage. Voltages could no longer fall fast enough to compensate, and chips would have melted. Since then, more performance has come from doing more per cycle and from more cores (chapter 15), not from a faster clock.

Common traps
  • Expecting a register to show a value in the same cycle it's written. It appears in the next cycle.
  • Creating feedback through combinational logic by accident, which makes a circuit oscillate or latch unpredictably.
  • Feeding an unsynchronised external signal straight into clocked logic, inviting metastability.
  • Thinking of RAM as fast. Main memory is DRAM, and reading it takes hundreds of clock cycles.
  • Assuming clock speed is the measure of performance. Work per cycle matters as much.

Exercise 5.2The size of the Hack RAM

The Hack computer's data memory, RAM16K, holds 16,384 words of 16 bits, built as RAM8 → RAM64 → RAM512 → RAM4K → RAM16K. How many flip-flops does it contain, how many address bits does each level use, and how does an address split across the levels?

Show solution

16,384 × 16 = 262,144 flip-flops. Each of the first four levels multiplies the size by 8, using 3 more address bits: RAM8 needs 3 bits, RAM64 6, RAM512 9, RAM4K 12. RAM16K is four RAM4Ks rather than eight, so it adds 2 bits, for 14 in total (214=16,384). In a 14-bit address, the top 2 bits choose a RAM4K, the next 3 a RAM512 inside it, and so on down to the lowest 3 bits, which choose a register within a RAM8. Each level is a DMux on the load bit and a Mux on the outputs, driven by its share of the address. Real memory chips decode addresses the same way, in rows and columns.

Exercise 5.3Splitting the critical path

A circuit's critical path is 258 gates long, at 15 ps per gate. If you split it into four equal stages with registers between them, and each register adds the equivalent of 3 gate delays, what clock rate becomes possible? Why isn't the speed-up exactly 4?

Show solution

Each stage has 258 / 4 = 64.5 gates of logic plus 3 of register overhead, 67.5 gate delays, or about 1.01 ns, so the clock can run at about 988 MHz instead of 258 MHz. That's 3.8 times faster, not 4, because the register overhead is paid once per stage, and it grows relative to the logic as the stages get shorter. Splitting into 100 stages would leave 2.6 gates of logic and 3 of overhead per stage, so the overhead would dominate. This is one reason pipelines stopped getting deeper, which chapter 12 takes up. Another is that a result needed by the next instruction then takes more stages to come back.

Chapter 06

Instruction sets and machine code

8 min read3 exercises

The instruction set architecture is the contract between hardware and software. It fixes the registers, the instructions and their binary encodings, and exactly what each instruction does. A program compiled for an instruction set runs on every processor that implements it, however different those processors are inside. This chapter compares the two main design philosophies, RISC and CISC, encodes and decodes real RISC-V instructions bit by bit, and encodes the two instruction types of the Hack computer that Nand2Tetris builds.

What an instruction set promises

An instruction set architecture (ISA) specifies the programmer-visible state, meaning the registers, the program counter and memory, and every instruction's effect on it. RISC-V, for example, has 32 integer registers of 32 or 64 bits, named x0 to x31, where x0 always reads as zero. Memory is a large array of bytes, stored little-endian. Everything else is microarchitecture: how many instructions run at once, how big the caches are, how branches are predicted. A cheap microcontroller and a server processor can implement the same ISA and run the same binary, one at a millionth of the other's speed. Three ISAs dominate today: x86-64 in most PCs and servers, ARM64 in phones and Apple's computers, and RISC-V, an open standard designed at Berkeley in 2010 that anyone can implement without a licence.

RISC and CISC

The x86 family is the classic CISC, complex instruction set computer. Its instructions vary from 1 to 15 bytes, and many can read memory, compute and write memory in a single instruction. ret is the single byte C3, mov eax, 1 is 5 bytes, and loading a 64-bit constant takes 10. RISC designs such as ARM64 and RISC-V, reduced instruction set computers, use fixed-size instructions, 4 bytes in RISC-V, and a load/store architecture: only loads and stores touch memory, and arithmetic works only on registers. Fixed sizes make decoding simple, since the processor knows where every instruction starts, and that matters when it wants to decode several per cycle (chapter 14). The old trade-off has mostly dissolved. Modern x86 processors translate each instruction into RISC-like micro-operations internally, while RISC designs added compressed 2-byte forms to recover CISC's code density.

Encoding RISC-V

Every RV32I instruction is 32 bits, in one of six formats. The lowest 7 bits, the opcode, say which format applies, and the fields that name registers sit at the same positions in every format.

Immediates are two's complement and sign-extended to the register width, so addi x6, x0, -1 stores the 12-bit pattern 0xFFF and loads −1. Branch offsets count bytes from the branch itself and are always even, so the lowest bit isn't stored, which lets a 12-bit field reach ±4 KiB. The B-format's odd-looking bit shuffle keeps each immediate bit at the same position as in the S-format, so the hardware needs fewer multiplexers to assemble it.

Encoded and decoded

The example encodes nine RISC-V instructions into machine code, shows each one's fields, and decodes the binary back into assembly. It then encodes some Hack instructions.

Read the binary column against the figure. add x7, x5, x6 has funct7 0, rs2 = 6, rs1 = 5, funct3 0, rd = 7 and opcode 0110011, and sub differs only in funct7, 0100000. The ALU's subtract control comes straight from that one bit. lui x10, 0x12345 loads a 20-bit immediate into the upper bits of a register, and an addi fills in the low 12, which is how RISC-V builds 32-bit constants (exercise 6.2).

The Hack instruction set

The Hack computer has 16-bit instructions of just two kinds. An A-instruction, a 0 followed by 15 bits, loads a constant into the A register, as in @21. A C-instruction, 111 followed by 13 bits, computes something with the ALU, stores it, and maybe jumps. The bits are the control signals: one bit chooses whether the ALU's second input is A or M, the memory word at address A; six bits are the ALU's zx, nx, zy, ny, f and no from chapter 4; three bits say which of A, D and M receive the result; and three bits say whether to jump if the result is negative, zero or positive. D=D+A is 1110000010010000, and 0;JMP, an unconditional jump to the address in A, is 1110101010000111. Hack has no call or return instructions and no stack. Nand2Tetris adds those in software, with a virtual machine (chapter 8).

Common traps
  • Confusing the ISA with performance. The same instructions run at very different speeds on different implementations.
  • Forgetting that immediates are sign-extended, so a 12-bit field holding 0xFFF means −1, not 4,095.
  • Computing branch offsets in instructions instead of bytes, or from the wrong starting address.
  • Building a 32-bit constant with lui and addi without correcting for the sign of the low part (exercise 6.2).
  • Decoding x86 at an arbitrary byte. With variable-length instructions, you must know where one starts.

Exercise 6.2Loading 0xDEADBEEF

Load the 32-bit constant 0xDEADBEEF into x5 using lui and addi. Why is lui x5, 0xDEADB followed by addi x5, x5, 0xEEF wrong?

addi sign-extends its 12-bit immediate, and 0xEEF has its top bit set, so it means 0xEEF − 0x1000 = −273, not +3823. The sequence above would give 0xDEADB000 − 273 = 0xDEADAEEF. Exercise 6.3Why the fields don't move

RISC-V keeps rs1, rs2 and rd at the same bit positions in every format, and the immediate's sign bit always at bit 31. What does that buy a hardware designer?

Show solution

Speed and simplicity in decoding. Because rs1 and rs2 are always in the same place, the processor can start reading both registers from the register file in the same cycle the instruction arrives, before it has worked out which format the instruction is. If the instruction turns out not to use them, the values are simply ignored. Fixed positions also mean fewer multiplexers in front of the register file. Keeping the sign bit at bit 31 means the sign extension of any immediate can begin immediately, in parallel with decoding, instead of waiting to find out where the immediate's top bit is. Both decisions shorten the critical path of chapter 5, which helps the clock rate, at the cost of immediates whose bits look scrambled to humans.

Chapter 07

The CPU: fetch, decode, execute

10 min read3 exercises

A CPU is a loop. Fetch the instruction the program counter points to, decode its bits into control signals, execute it on the datapath of registers, ALU and memory, and decide where the next instruction is. Everything built so far fits together here: the ALU of chapter 4, the registers and program counter of chapter 5, and the instruction encoding of chapter 6. This chapter assembles the Hack CPU's datapath, writes a two-pass assembler, and runs real programs on an emulator cycle by cycle, counting exactly what they cost.

The datapath and the control unit

A processor has two parts. The datapath holds and transforms data: registers, the ALU, memory, and multiplexers that route values between them. The control unit decodes each instruction into the signals that drive the datapath: which inputs the multiplexers select, what the ALU computes, which registers load a new value, and whether the program counter jumps. In most processors the control unit is a substantial circuit. In Hack it's almost nothing, because the C-instruction's bits already are the control signals.

Fetch, decode, execute

Each clock cycle, the Hack CPU does all of the following:

  • Fetch: read the instruction at ROM[PC].
  • Decode: if the top bit is 0, it's an A-instruction; otherwise split it into the a bit, the six ALU control bits, three destination bits and three jump bits.
  • Execute: for an A-instruction, load the constant into A. For a C-instruction, run the ALU on D and either A or M, and store the result in whichever of A, D and M the destination bits name.
  • Next: if the jump bits match the ALU's zero and negative flags, load PC from A; otherwise increment it.

Hack is a single-cycle design: one instruction per cycle, and the clock period long enough for the slowest instruction to finish. It's also a Harvard architecture, with separate memories for instructions and data, so fetching and loading never compete. Most computers are von Neumann machines, with one memory holding both, which is what lets a program load another program, or a compiler write machine code. Modern processors are von Neumann outside and split again inside, with separate level-1 caches for instructions and data. Real CPUs also don't finish one instruction before starting the next. They overlap many, which Part IV explains, but the logical cycle stays the same.

An assembler in two passes

Programs are written in assembly, with names instead of numbers, and an assembler translates them into machine code. The difficulty is forward references: @END refers to a label defined later. The standard solution is two passes. The first pass walks the program counting instructions and records the ROM address of every label, which don't take up ROM themselves. The second pass translates each instruction, replacing labels with their addresses and giving every other new symbol, a variable, the next free RAM address from 16 upward. The example's assembler does exactly this in about thirty lines, which is Nand2Tetris project 6.

Programs, run

The example assembles a program that adds the numbers 1 to 100, shows its first machine words and the first eight cycles of execution, and runs it to completion. It then runs a multiplication program, which multiplies by repeated addition because Hack has no multiply instruction, on three pairs of inputs.

The trace shows the machine working at the lowest level. Cycles 1 to 4 set i = 1 and sum = 0. In cycle 5, @i puts i's address, 16, into A; in cycle 6, D=M reads RAM[16] into D; and by cycle 8, D holds i − 100 = −99, ready for the jump test. Each loop iteration costs 14 instructions, so the program takes 14 × 100 + 16 = 1,416 cycles (exercise 7.2). The multiplication results show how much an algorithm depends on its inputs: 2 × 1000 takes 12,008 cycles, because the loop counts down the second operand. Swapping the operands would take 32.

Memory-mapped I/O

The Hack computer has no input or output instructions. Instead, part of the data memory is wired to devices. RAM[16384] to RAM[24575] are the 512 × 256 screen, one bit per pixel, so writing a word there turns 16 pixels on or off. RAM[24576] holds the code of the key currently pressed. Reading and writing devices with ordinary loads and stores is called memory-mapped I/O, and real computers use it extensively, as chapter 19 explains.

Common traps
  • Using the new value of A in the same instruction that changes it. M and the jump target use the value A had at the start.
  • Counting labels as instructions. They mark addresses and occupy no ROM.
  • Assuming one instruction takes one cycle on real processors. Some take one, some dozens, and many overlap.
  • Forgetting to end a Hack program with an infinite loop. Otherwise the CPU runs on into whatever ROM holds next.
  • Ignoring the inputs' effect on running time, as with multiplication by repeated addition.

Show solution

Compute RAM[0] − RAM[1] and jump on its sign: @R0, D=M, @R1, D=D-M, @FIRST, D;JGT, then @R1, D=M, @STORE, 0;JMP, then (FIRST) @R0, D=M, then (STORE) @R2, M=D, and finally (HALT) @HALT, 0;JMP. Every if/else compiles to this shape: compute a value, jump on a flag, and jump over the other branch. One subtlety: D − M can overflow for very large values of opposite sign, which a careful version handles by comparing signs first.

Exercise 7.2Counting cycles

Show that the sum program takes 14n + 16 cycles to add up 1 to n, which is 1,416 for n = 100.

Show solution

The setup, @i, M=1, @sum, M=0, takes 4 cycles. Each of the n iterations runs all 14 instructions from (LOOP) to 0;JMP. The final test, when i = n + 1, runs the first 6 instructions of the loop and jumps to END. The END block takes 4 cycles, and the halt loop's two instructions are counted once by the emulator before it stops. That's 4 + 14n + 6 + 4 + 2 = 14n + 16. Counting like this is exactly the analysis of algorithms, at the level of machine instructions instead of abstract steps. Chapter 20's iron law of performance multiplies such counts by cycles per instruction and seconds per cycle.

Exercise 7.3Faster multiplication

The multiplication program takes 12y + 8 cycles to compute x × y. How would you make it fast for all inputs, without hardware support?

Show solution

First, loop over the smaller operand, which needs a comparison at the start and costs at most 12 min(x, y) + a few cycles. Better, use shift-and-add, binary long multiplication: for each bit of y, if the bit is 1 add the current shifted copy of x to the result, then double x. With 16-bit numbers that's at most 16 iterations whatever the values, a few hundred cycles instead of up to hundreds of thousands. Hack can double a number with D=D+M on itself, and test a bit by Anding with a mask held in memory. Hardware multipliers do the same thing in parallel, adding all the partial products at once in a tree of adders, which is why real multiplication takes a few cycles (chapter 4).

Chapter 08

Reading assembly, and stack machines

10 min read3 exercises

Compilers turn source code into assembly, and reading it is how you find out what a program really does: which values stay in registers, which go to memory, where the loops and calls are, and whether the compiler did what you hoped. This chapter reads and runs a RISC-V function, names the patterns every compiled program is made of, and then meets the other way to design an instruction set, the stack machine. Stack machines run Java, Python and WebAssembly, and the Nand2Tetris virtual machine is one.

Reading a function

The example's RISC-V program has a main that calls a function sum(array, n). Reading it needs three pieces of vocabulary. The first is the calling convention, the agreement about registers that lets separately compiled functions call each other. In RISC-V, arguments arrive in a0 to a7 and the result returns in a0. The return address is in ra. The t registers are temporaries a function may overwrite, and the s registers must be preserved. The second is the shape of a loop: a test at the top that branches forward out of the loop, a body, and a jump backwards to the test. The third is address arithmetic. Element i of an array of 4-byte words lives at base + 4i, which the code computes with a shift, slli t2, t1, 2, because shifting left by 2 multiplies by 4.

Calls are two instructions. jal ra, sum jumps to sum and stores the address of the next instruction in ra, and jalr zero, 0(ra) jumps back to it. The example's final register dump shows ra = 12, the byte address of the instruction after the call, since main's instructions sit at addresses 0, 4 and 8.

Patterns to recognise

Compiled code is built from a small set of shapes. Once you know them, a listing reads like a structured program:

  • if/else: a compare and a branch forward over the "then" block, and a jump over the "else";
  • loops: a backward branch, often with the test moved to the bottom so each iteration takes one branch;
  • function prologue and epilogue: lowering sp to make room on the stack, saving ra and any s registers, and restoring them before returning (chapter 18);
  • switch: a bounds check and an indirect jump through a table of addresses;
  • optimisations: multiplications turned into shifts and adds, loop bodies duplicated (unrolling), and several elements processed per instruction (vectorisation, chapter 15).

Optimisation level changes everything. At -O0 a compiler keeps every variable in memory and reloads it at each use, which is easy to follow and slow. At -O2 variables live in registers, code is reordered and duplicated, and parts of the program disappear because the compiler proved them unnecessary. Read optimised code to learn about performance. Compiler Explorer, at godbolt.org, shows the assembly for any snippet in dozens of languages and compilers side by side, and objdump -d disassembles any binary on your own machine.

Stack machines

A register machine names its operands: add t0, t0, t3 says exactly which registers to use. A stack machine names none. Its instructions take operands from the top of a stack and push results back. To compute (a + b) × c it pushes a and b, adds, which pops two values and pushes their sum, then pushes c and multiplies.

Stack code is compact and easy to generate: a compiler emits it by walking the expression tree in post-order, operands before operators. That's why most virtual machines use it, including the Java Virtual Machine, CPython's bytecode interpreter, WebAssembly, and the Nand2Tetris VM, whose 20-odd commands, push, pop, add, sub, neg, eq, gt, lt, and, or, not, label, goto, if-goto, function, call and return, are what the course's Jack compiler produces. A VM translator, Nand2Tetris projects 7 and 8, turns each VM command into a handful of Hack instructions, and a JIT compiler does the same for the JVM at run time, mapping the top of the stack onto real registers.

Three machines, one loop

The example runs the RISC-V function in a small interpreter, prints the bytecode that CPython compiles the same loop into, and runs a sum of 1 to 100 on a stack VM in the style of Nand2Tetris.

The CPython bytecode is a stack program. LOAD_FAST pushes a local variable, BINARY_OP pops two values and pushes the result, and STORE_FAST pops into a local. FOR_ITER and JUMP_BACKWARD are the loop's top and bottom. The exact instruction names change between Python versions, and this listing is from version 3.14. The stack VM takes 1,411 commands for the sum, where the hand-written Hack program of chapter 7 took 1,416 instructions. Translated into Hack, each VM command becomes several Hack instructions, so the VM version would run several times slower. That's the cost of a convenient abstraction, and recovering it is what optimising compilers and JITs are for.

Common traps
  • Reading unoptimised code as representative of what runs in production.
  • Expecting assembly to mirror the source line by line. Optimisers reorder, merge and delete.
  • Mixing up AT&T and Intel syntax for x86, which put operands in opposite orders.
  • Depending on bytecode details, which change between interpreter versions.
  • Forgetting which registers a call may overwrite, the t and a registers in RISC-V.

Exercise 8.2Walk a pointer

Chapter 09

The memory hierarchy and its real latencies

8 min read3 exercises

Fast memory is small and expensive, and big memory is slow, so computers stack several kinds in a hierarchy. Registers and caches sit next to the processor, main memory sits further off, and storage further still, with each level roughly ten times larger and several times slower than the one above. The hierarchy works because programs have locality: they reuse what they used recently and touch what's next to it. This chapter gives the real numbers, measures the gap between cache and main memory on real hardware, and introduces the two quantities every performance argument needs, latency and bandwidth.

Why a hierarchy

Processor speed grew far faster than memory speed for decades. A modern core can execute several instructions per nanosecond, but a read from main memory, which is DRAM (chapter 5), takes around 100 nanoseconds. That's hundreds of instructions' worth of waiting, a gap often called the memory wall. Caches bridge it by keeping copies of recently used data in small, fast static RAM next to the core. A typical modern processor has a level-1 cache of 32 to 128 KiB per core, a level-2 cache of a few MiB, a level-3 cache of tens of MiB shared between cores, and then many gigabytes of DRAM.

Below memory comes storage. An NVMe solid-state drive answers a random read in tens of microseconds, and a spinning disk needs milliseconds to move its head. Networks add their own scale: a round trip inside a data centre takes about half a millisecond, and one across a continent tens of milliseconds. Jeff Dean's list of "latency numbers every programmer should know" made these numbers famous, and their ratios matter more than their exact values, which keep changing.

Locality

The hierarchy works because real programs have locality. Temporal locality means that data used recently is likely to be used again soon, like a loop counter or the top of the stack. Spatial locality means that data near recently used data is likely to be used soon, like the next element of an array. Caches exploit both. They keep recently used data, and they move memory in fixed-size blocks called cache lines, 64 bytes on most x86 and ARM processors and 128 bytes on Apple's M-series chips, so one miss brings in the neighbours too. Hardware prefetchers watch the stream of misses, recognise sequential and strided patterns, and fetch lines before they're asked for. A program that walks memory in order gets almost every access from cache. A program that jumps around a large data set at random defeats all of it.

Measured on real hardware

The example performs the same work, 4 million reads of 8-byte integers, from arrays of growing size, once in sequential order and once in random order. The work per access is identical. Only where the data sits in the hierarchy changes. Unlike most examples in this volume it measures time, so its output depends on the machine: the run shown was recorded on an Apple M1 Pro laptop, and your numbers will differ.

Python's interpreter adds about 19 ns to every access, which hides the difference between L1 and L2 entirely: at 16 KiB and 256 KiB both orders cost the same. At 4 MiB, random access starts to cost more, as the data spills out of the closest caches. At 64 MiB and 256 MiB the array no longer fits in any cache, and random access costs about 4 times as much as sequential, adding roughly 50 to 60 ns to each read, most of a trip to DRAM. Sequential access stays at 19 ns even for 256 MiB, because each 128-byte line serves 16 consecutive reads and the prefetcher fetches the next lines ahead of time. In a compiled language, without the interpreter's overhead, the same experiment shows a ratio of tens rather than 4.

Latency and bandwidth

Latency is how long one access takes. Bandwidth is how much data per second the memory system can deliver when many accesses are in flight. They're different limits. A laptop's DRAM delivers tens to hundreds of gigabytes per second, yet any single read still takes around 100 ns. Little's law connects them: the number of requests in flight equals throughput times latency. To use the bandwidth, the processor must keep many misses outstanding at once, which out-of-order cores do (chapter 14), and which a linked-list traversal prevents, because the address of the next node isn't known until the current load finishes. Workloads are accordingly latency-bound, waiting on one access after another, or bandwidth-bound, streaming more data than the memory can deliver. The cures differ, and chapter 20's roofline model tells them apart.

One more cache stands between a program and its data. Programs use virtual addresses, which the hardware translates to physical addresses through page tables kept by the operating system, and a small cache of recent translations, the TLB, makes that fast. Random access across hundreds of megabytes misses in the TLB as well as in the data caches, part of what the example's last rows measure. Stage 05 covers virtual memory in full.

Common traps
  • Optimising arithmetic in a program that's waiting for memory. Find out which one it's bound by first.
  • Benchmarking with data that fits in cache and extrapolating to data that doesn't.
  • Treating big-O as the whole story. An O(log n) tree of scattered nodes can lose to an O(n) scan of an array.
  • Pointer-heavy data structures in hot paths, where every hop is a potential trip to DRAM.
  • Mixing cold and warm measurements: the first run fills the caches, and later runs reuse them.

Chapter 10

Caches: lines, sets, ways and misses

11 min read3 exercises

A cache keeps copies of recently used memory lines, and four design choices decide which access patterns it rewards: the line size, the number of sets, the number of ways in each set, and the rule for what to evict. Every miss falls into one of three kinds. Compulsory misses happen on first touch, capacity misses because the working set is too big, and conflict misses because too many lines compete for the same set. This chapter explains the organisation, then runs a cache simulator that sorts misses into these three kinds. It reproduces a classic trap, a matrix whose power-of-two row length makes a column walk thrash, along with its one-line fix.

Lines, sets and ways

A cache is divided into lines of, say, 64 bytes, and memory is moved in and out whole lines at a time. To find whether an address is cached, the hardware splits it into three fields. The lowest bits are the offset within the line, 6 bits for 64-byte lines. The next bits, the index, choose a set. The remaining high bits, the tag, identify which of the many memory lines that map to that set is actually there. A set holds several lines, its ways, and the hardware compares the tag against all of them at once.

Associativity is a trade-off. A direct-mapped cache, with one way per set, is fast and simple but suffers when two frequently used addresses map to the same set. A fully associative cache, where any line can go anywhere, avoids that, but comparing every tag at once is too expensive for anything but small structures such as TLBs. Level-1 caches are typically 8- to 12-way, and level-3 caches 12- to 16-way.

The three Cs

Mark Hill's classic classification sorts misses by cause, which tells you how to fix them:

  • Compulsory, or cold, misses: the first access to a line can only miss. Prefetching hides them, and larger lines reduce their number.
  • Capacity misses: the program's working set is bigger than the cache, so lines are evicted before they're reused. The fix is to use less data at a time, which is what chapter 11's blocking does.
  • Conflict misses: the working set would fit, but too many of its lines map to the same set. The fix is to change the addresses, by padding data or changing strides, or to add associativity.

The simulator classifies each miss by also running a fully associative cache of the same size alongside. A miss that the fully associative cache would also have taken, on a line seen before, is capacity. A miss it would have avoided is conflict.

Replacement and the LRU cliff

When a set is full, a new line evicts one of the old ones. Least recently used (LRU) replacement evicts the line untouched for longest, a good bet under temporal locality. It has one pathological case: a loop over data slightly bigger than the cache. Each line is evicted just before the loop comes back for it, so the miss rate jumps from almost nothing to 100% as the array grows past the cache size. In the example, scanning a 32 KiB array repeatedly through a 32 KiB cache misses only on the first pass, 5%, while a 36 KiB array misses on every access. Real caches approximate LRU cheaply with pseudo-LRU bits, and recent designs use adaptive policies that resist such scans.

Writes

A write-back cache updates only its own copy and marks the line dirty, writing it to the next level when it's evicted. A write-through cache sends every write onward immediately. Almost all modern CPU caches are write-back and write-allocate, fetching a line on a write miss so it can be modified in place. With several cores, each with its own caches, a coherence protocol such as MESI keeps the copies consistent. A core that writes a line must first invalidate everyone else's copy. That's invisible to correct programs, but it costs time when two cores keep writing the same line, which is false sharing (chapter 11).

Simulated

The example's cache is set-associative with LRU replacement, 64-byte lines and configurable size and ways. It runs four experiments: a sequential scan, three ways of walking a 512 × 512 matrix, eight addresses that collide in one set, and repeated scans of arrays around the cache size.

The sequential scan misses once per 64-byte line, 1 access in 16, and all of those misses are compulsory. Walking the matrix row by row does the same. Walking it column by column misses on every access, and the simulator calls these misses conflict, not capacity. The 512 lines a column walk touches would fit in the cache's 512 lines. But each row is 512 × 4 = 2,048 bytes, exactly 32 lines, so consecutive elements of a column are 32 lines apart, and with 64 sets they fall into only 2 of them. Sixteen slots for 512 lines means constant eviction. Padding each row to 528 integers makes the stride 33 lines, and since 33 shares no factor with 64, the column now spreads over all 64 sets and the miss rate drops back to 6.2%. The 8-way cache shrugs off eight addresses 32 KiB apart that a direct-mapped cache thrashes on, which is the case for associativity in one line.

Common traps
  • Arrays whose rows, or strides, are large powers of two, which map many hot lines into the same few sets.
  • Loops over data just larger than the cache, where LRU replacement fails completely.
  • Assuming 64-byte lines everywhere. Apple's M-series chips use 128 bytes.
  • Benchmarking a data structure that fits in cache and expecting the same speed at full size.
  • Two threads writing neighbouring variables, which share a line and fight over it.

Exercise 10.2Why padding works

In the column walk, row i starts at line 32i with no padding and at line 33i with padding. Show which sets are used in each case for a cache with 64 sets, and explain why 33 works but 34 wouldn't work as well.

Show solution

Element (i, j) of a column lies in line 32i + c for a fixed c, so its set is (32i + c) mod 64, which takes only 2 values as i varies. With padding the set is (33i + c) mod 64, and since gcd(33, 64) = 1, the multiples of 33 run through every residue mod 64 before repeating, so 64 consecutive rows land in 64 different sets and 512 rows fill each set with exactly 8 lines, matching its 8 ways. With a stride of 34 lines, gcd(34, 64) = 2, so only the 32 even-numbered sets are used, 16 lines each, twice the associativity, and the cache thrashes again. The rule: choose a pitch whose number of lines is odd.

Exercise 10.3Line size and a sequential sum

Summing an array of 8-byte integers in order, what's the miss rate with 64-byte lines, and with 128-byte lines? Why does a sequential sum still run near full speed when a quarter or more of its time would otherwise be spent on misses?

A 64-byte line holds 8 integers, so 1 access in 8 misses, 12.5%. With 128-byte lines it's 1 in 16, 6.25%, all compulsory. If each miss cost a full trip to DRAM, the misses would dominate. The hardware prefetcher sees the sequential stream after a few misses and starts fetching lines ahead of the loop, so by the time an access arrives its line is already in cache, and the memory system works at its bandwidth instead of its latency. Compulsory misses are unavoidable, but predictable ones are free. That's why the example in chapter 9 found sequential access equally fast at 16 KiB and at 256 MiB.

Chapter 11

Cache-friendly code and data layout

11 min read3 exercises

The same computation can run ten times faster or slower depending only on the order in which it touches memory and how its data is laid out. The techniques are few and powerful. Walk memory in the order it's stored. Block a computation into tiles that fit in cache. Store the fields you scan together contiguously. Prefer arrays to pointers, and keep threads from writing to the same cache line. This chapter applies each one in the cache simulator. Blocking a matrix multiplication cuts its misses by a factor of 46, which is the stage's second deliverable in miniature: making a program several times faster through locality alone.

Walk memory in the order it's stored

C, C++, Rust, Go, NumPy's default and Python's lists of lists store two-dimensional arrays row-major: each row is contiguous, and moving along a row moves through memory one element at a time. Fortran, MATLAB, Julia and R store them column-major. A loop whose innermost index moves along the contiguous direction uses every byte of every cache line it fetches. A loop whose innermost index moves the other way strides through memory and may use 8 bytes of each 64-byte line. Fixing it is often a matter of swapping two loops, loop interchange, which compilers do automatically only when they can prove it's safe.

Matrix multiplication shows the effect. The textbook loop order, i-j-k, computes each Cij as a dot product of row i of A with column j of B, so its innermost loop walks down a column of B. The order i-k-j instead adds Aik times row k of B into row i of C, so its innermost loop walks along rows of both. Same arithmetic, same result, different access pattern.

Blocking

Even with the right loop order, a large matrix multiplication streams all of B through the cache once for every row of A, because B is too big to stay cached. Blocking, also called tiling, restructures the loops to work on small square tiles. Take a tile of A, a tile of B and a tile of C that fit in cache together, do all the work those three tiles allow, and only then move on.

Inside a tile, every loaded line is reused many times before it's evicted. That's the principle behind every fast linear algebra library. BLAS implementations such as OpenBLAS and Intel's MKL block at several levels at once, for registers, L1, L2 and L3, and add SIMD instructions (chapter 15), which is how they reach close to the processor's peak while a naive triple loop reaches a few percent of it.

Data layout: arrays of structures and structures of arrays

A particle system might store each particle as a record with position, velocity, mass and charge, and keep an array of these records, an array of structures (AoS). A loop that updates every field of one particle at a time likes that layout. A loop that sums just one field over all particles fetches a 64-byte line for each 8-byte value it needs, wasting seven-eighths of the bandwidth. Storing each field in its own array, a structure of arrays (SoA), packs the values the loop needs together. In the example the scan drops from 100,000 misses to 12,500. Game engines built on entity-component systems, and the columnar databases described in The Engineer's Ledger, use the same idea at larger scale.

Pointer chasing

A linked list, a tree of small nodes, or a hash table whose buckets point to chains scatters its data wherever the allocator put it. Every step follows a pointer, the address of the next access isn't known until the current one completes, and the prefetcher can't help. In the example, traversing 100,000 values through a list whose nodes sit at random addresses misses 99,651 times, against 12,500 for an array of the same values. Under a simple model of 1 ns per hit and 100 ns per miss, that's about 100 ns per element against 13. Prefer contiguous containers: arrays and vectors, B-trees with wide nodes, hash tables with open addressing (The Engineer's Workbench, chapter 2), and nodes allocated together from an arena.

False sharing

Caches keep copies coherent a line at a time (chapter 10). If two threads on different cores write to different variables that happen to share a cache line, each write invalidates the other core's copy, and the line bounces between cores, every write costing a coherence round trip. That's false sharing: no data is shared, only the line. Per-thread counters stored next to each other in an array are the classic case. The fix is to pad or align each thread's data to its own line, 64 bytes on most machines and 128 on Apple's, using alignas(64) in C++ or Java's @Contended.

Simulated

The example uses chapter 10's cache to compare three versions of a 96 × 96 matrix multiplication, two layouts for a particle array, and a scattered linked list against an array. A small 8 KiB cache keeps the matrix simulation quick, standing in for a real 32 to 64 KiB level-1 cache facing proportionally larger matrices. Interchanging the loops cuts the misses from 923,520 to 112,896, and blocking cuts them to 20,022, 46 times fewer than the textbook order, with exactly the same arithmetic. Measured speed-ups for blocking large matrix multiplications in compiled code are still typically several-fold, which is the size of the stage's goal. The method generalises. Measure where the misses are, find the loop whose accesses stride or scatter, and change the order or the layout until each fetched line is used fully, and used again before it's evicted.

Common traps
  • Traversing in the wrong order for the language's layout, especially when porting between C and Fortran or MATLAB.
  • Choosing tiles that don't fit in cache together, or that are so small the loop overhead dominates.
  • Using AoS for data that's scanned one field at a time, or SoA for data that's always used whole.
  • Optimising without measuring misses. Use perf stat -e cache-misses, Instruments or VTune.
  • Per-thread counters packed side by side, the textbook false-sharing bug.
  • Hand-blocking matrix code that a BLAS library already does better. Call the library.

Exercise 11.2Where i-k-j's misses come from

In the i-k-j order, the example counted 112,896 misses for n = 96. Show that streaming B accounts for almost all of them.

B is 72 KiB and the cache is 8 KiB, so nothing survives until the next i, and every line misses again: 96 × 1,152 = 110,592 misses. Rows of A and C are reused within each i and miss only once per i, adding 96 × (12 + 12) = 2,304. Together that's 112,896, exactly the simulator's count. Exercise 11.3A cache-friendly transpose

Transposing a large matrix, B[j][i] = A[i][j], reads A row by row but writes B column by column. Why is that slow, and how do you fix it?

Show solution

Every write to B lands in a different row, a full row length further along in memory, so each write touches a different cache line, and with large matrices each line is evicted before its neighbours are written. You can't make both the reads and the writes sequential, because a transpose inherently swaps the two directions. Blocking solves it. Transpose one b × b tile at a time, so the tile of A and the tile of B both fit in cache, and each line fetched is fully used: the reads cover b consecutive elements of each row of A, and the writes b consecutive elements of each row of B. Tiles of 8 to 32 elements on a side typically give several times the speed of the naive loop, and they're the same technique used for blocked matrix multiplication.

Chapter 12

Pipelining and hazards

10 min read3 exercises

A laundry with a washer and a dryer doesn't wait for one load to dry before washing the next. Pipelining does the same with instructions. Split each one into stages, fetch, decode, execute, memory and write back, and work on five instructions at once, one in each stage. In the ideal case the processor finishes one instruction per cycle, even though each takes five. Hazards spoil the ideal: an instruction needs a result that isn't ready yet, or the pipeline doesn't know which instruction comes next. Forwarding, stalls, careful instruction order and branch prediction are how processors recover. This chapter simulates a five-stage pipeline and measures each one.

Five stages

The classic RISC pipeline has five stages, each with a register between it and the next:

  • IF, instruction fetch, reads the instruction at PC;
  • ID, instruction decode, decodes it and reads its source registers;
  • EX, execute, runs the ALU, or computes an address for a load or store;
  • MEM accesses data memory, for loads and stores;
  • WB, write back, writes the result into the destination register.

Each stage does about a fifth of the work, so the clock can run roughly five times faster than a single-cycle design (chapter 5's exercise 5.3). Every instruction still takes five cycles from start to finish, its latency, but a new one can start every cycle, its throughput. The figure shows a loop's instructions overlapping in a staircase.

Data hazards: forwarding and stalls

A data hazard occurs when an instruction needs a result that an earlier instruction hasn't written back yet. add x6, x6, x5 needs x5 from the load just before it, but the load only writes x5 in its WB stage. The simplest fix is to stall: hold the dependent instruction in decode, inserting bubbles, until the value is in the register file. Without anything better, the example's loop runs at 2.2 cycles per instruction, CPI 2.20, instead of 1.

The better fix is forwarding, or bypassing. The value exists as soon as the ALU computes it, at the end of EX, so wires carry it straight from the pipeline register back to the ALU's input for the next instruction, without waiting for write back. With forwarding, ALU-to-ALU dependences cost nothing. Loads are the exception: a loaded value arrives only at the end of MEM, too late for an instruction in EX the very next cycle, so a load-use dependence still costs one bubble, the one in the figure. The fix for that is software. Move an independent instruction between the load and its use, as the example's reordered loop does, and the bubble disappears. Compilers schedule instructions this way automatically.

Control hazards

A branch decides which instruction comes next, but the pipeline must fetch the next instruction before the branch has been decided, which in this pipeline happens in EX, two stages after fetch. If the processor simply waits, or always fetches the next instruction in memory, every taken branch wastes two cycles. In the example's loop, where 1 instruction in 5 is a taken branch, that costs 0.4 cycles per instruction. The fix is to predict the branch and fetch from the predicted target immediately, discarding the wrong-path instructions if the guess was wrong. Chapter 13 shows how predictors get it right well over 90% of the time.

A third kind, structural hazards, happens when two instructions need the same hardware in the same cycle, for example a single memory port for both fetching instructions and loading data. Separate instruction and data caches and duplicated functional units remove most of them.

Simulated

The example schedules the loop on a five-stage pipeline under four assumptions, prints the pipeline diagram for two of them, and counts cycles over 1,000 iterations.

Each improvement removes one source of lost cycles. Forwarding removes the waits for write back, from CPI 2.20 to 1.60. Predicting the branch removes the two wasted fetches per iteration, giving 1.20. Moving the add away from the load removes the last bubble, giving the ideal CPI of 1.00. In the diagrams, the gaps before a stalled instruction's EX stage are its bubbles. Real hardware holds the stalled instruction in its stage rather than fetching it late, but the cycles lost are the same.

Deeper pipelines

More, shorter stages allow a faster clock, and in the early 2000s Intel's Pentium 4 used around 20 to 31 stages to reach high clock rates. The costs grow with depth. Forwarding paths multiply, every register between stages adds overhead (exercise 5.3), and a mispredicted branch throws away more work, because more instructions are in flight when the mistake is discovered. Designs settled at around 14 to 20 stages, with performance coming instead from issuing several instructions per cycle, which is chapter 14's subject.

Common traps
  • Confusing latency and throughput. A pipelined instruction still takes five cycles; the pipeline finishes one per cycle.
  • Using a loaded value in the very next instruction in hand-written assembly for a simple in-order core.
  • Expecting deeper pipelines to be faster without limit. Overhead and misprediction cost grow with depth.
  • Ignoring that results depend on instruction order when timing tight loops on in-order processors.
  • Forgetting that every taken branch disturbs the fetch stream, even when it's predicted.

Exercise 12.2Count the stalls

Without forwarding, how many bubbles does the example's loop suffer per iteration, and from which dependences? Check your answer against the CPI of 2.20.

Exercise 12.3Schedule it yourself

Chapter 13

Branch prediction and speculative execution

9 min read3 exercises

A modern core has well over a hundred instructions in flight, and a branch turns up every five or six of them, so waiting to learn which way each branch goes would leave most of the machine idle. Instead the processor predicts, runs ahead down the predicted path, and throws the work away if it guessed wrong. Predictors are right far more than 90% of the time on typical code, but a branch that depends on random data defeats them, and the difference can make the same loop several times slower. This chapter builds three predictors, measures them on four kinds of branch, and explains how speculation became the basis of the Spectre attacks.

Why predict

Chapter 12's five-stage pipeline lost two cycles on every taken branch. A real core loses far more. It fetches several instructions per cycle into a pipeline 15 or more stages deep, so by the time a branch is resolved, dozens of later instructions have already been fetched. Stalling at every branch would waste most of that capacity. Predicting the branch and fetching from the guessed target keeps the pipeline full, and as long as the guesses are right the branches cost nearly nothing.

Predictors, from simple to clever

The simplest static rule predicts backward branches taken and forward branches not taken, which suits loops: the branch at the bottom of a loop jumps backwards and is usually taken. Dynamic predictors learn from history. A 1-bit predictor remembers each branch's last outcome and predicts the same again. A 2-bit saturating counter needs two mistakes in a row to change its mind, so the single not-taken exit at the end of a loop doesn't spoil the prediction for the next time the loop runs.

Counters indexed by the branch address alone can't learn patterns such as "taken, not taken, taken, not taken", or "the inner loop exits every tenth time". Global history predictors also look at the outcomes of the last several branches. Gshare, from Scott McFarling in 1993, indexes its counters by the branch address XORed with a register of recent outcomes, so the same branch gets different counters in different contexts. Modern predictors such as TAGE combine several history lengths and reach over 95% accuracy on typical programs. A branch target buffer separately predicts where a taken branch goes, and a small return address stack predicts the targets of function returns.

Measured

The example implements a 1-bit predictor, a 2-bit predictor and gshare with 10 bits of history, and runs each on four branches: a loop that iterates 10 times, entered 1,000 times; an if-test on random bytes; the same test on the same bytes sorted; and a branch that alternates. It then turns accuracy into cycles per instruction for a 4-wide core with a 15-cycle misprediction penalty.

Each result has a simple explanation. On the loop, the 1-bit predictor misses twice per entry, at the exit and again at the first iteration of the next entry, for 80%. The 2-bit counter misses only at the exit, for 90%. Gshare sees the history of the last ten outcomes and learns exactly where the exit comes, reaching 99.8%. On random data every predictor scores about 50%, because there's no pattern to learn. On the same data sorted, the branch is not taken for the first half and taken for the second, which every predictor gets almost entirely right. The alternating branch is the 2-bit counter's worst case, always one step behind, at 0%, while gshare's history makes it trivial.

What a misprediction costs

A wrong guess means flushing every instruction fetched after the branch and restarting from the right target, typically 15 to 20 cycles on a modern core. With 1 instruction in 5 a branch, a 50% miss rate costs 0.2 × 0.5 × 15 = 1.5 cycles per instruction, so the example's loop over random data runs at a CPI of 1.75 against 0.25 for sorted data, seven times slower for identical work. In 2012 this became one of Stack Overflow's most famous questions, "Why is processing a sorted array faster than processing an unsorted array?", with exactly this explanation.

The cure for an unpredictable branch is not to branch. Compute the condition as a number and use it arithmetically, as the example's x * (x >= 128) does. Alternatively, use a conditional move, an instruction that selects between two values without changing the flow of control, which compilers emit when they judge a branch unpredictable. Branch-free code always does the work of both sides, so it's slower when the branch would have been predictable. Measure before choosing.

Speculation, and Spectre

Running ahead on a prediction is speculative execution. Instructions on the predicted path execute fully, and their results are kept in the pipeline until the branch is confirmed, then either committed or discarded. Architecturally the discarded work leaves no trace, but microarchitecturally it can: a speculative load still brings its line into the cache. In 2018 Paul Kocher, Jann Horn and colleagues published Spectre. An attacker trains a bounds-check branch to predict "in bounds", then supplies an out-of-bounds index. The processor speculatively reads secret memory and uses it to touch one of 256 cache lines before discovering the mistake, and timing which line is now cached reveals the secret byte. Meltdown, announced at the same time, let unprivileged code read kernel memory through speculative loads past a permission check on many Intel processors.

The defences cost performance and live at every level: speculation barriers and index masking in sensitive code, hardware fixes in new processors, operating-system changes such as separating kernel and user page tables, and browsers isolating each site in its own process. The Engineer's Citadel covers side channels in more depth. The lesson for this chapter is that performance tricks invisible to a program's results can still be visible to an attacker who measures time.

Common traps
  • Unpredictable branches in hot loops, such as tests on random or hashed data.
  • Benchmarking with sorted or regular test data and deploying on real, messy data.
  • Rewriting predictable branches as branch-free code, which makes them slower.
  • Branching on secret data in cryptographic code, which leaks it through timing; such code must be constant-time.
  • Assuming discarded speculative work leaves no trace. Caches remember it.

A branch repeats the pattern taken, taken, not taken. What steady-state accuracy do a 1-bit predictor and a 2-bit counter achieve?

Exercise 13.2The price of a miss rate

Chapter 14

Instruction-level parallelism and out-of-order execution

9 min read3 exercises

A modern core decodes several instructions per cycle, looks hundreds of instructions ahead, and executes each one as soon as its inputs are ready, in whatever order that turns out to be. It still commits results in program order, so the program can't tell. Three things limit how much it finds to do. Dependency chains force waiting, the number of functional units caps throughput, and the size of the instruction window limits how far ahead it can look. This chapter simulates an idealised out-of-order core and shows how to write code with more independent work in it: several accumulators instead of one, registers that don't create false dependences, and data that isn't reached by chasing pointers.

Superscalar, out of order, in-order commit

A superscalar processor issues more than one instruction per cycle. Today's large cores decode 6 to 8 or more per cycle and have several integer ALUs, two or more load and store units, and several floating-point and vector units. An out-of-order core fetches and decodes instructions in program order and places them in a large window, often called the reorder buffer, holding several hundred instructions. Any instruction whose operands are ready goes to a free unit, regardless of where it sits in the program. Finished instructions then retire in program order, which keeps exceptions precise: if an instruction faults, everything before it has completed and nothing after it has changed the architectural state. That in-order retirement is also what makes speculation, chapter 13, safe to undo.

Dependences, true and false

A true dependence, or read-after-write, means an instruction needs a value another computes, and nothing can avoid waiting for it. False dependences come from reusing register names. A write-after-read means an instruction overwrites a register an earlier one still has to read; a write-after-write means two instructions write the same register and the later value must win. Compilers reuse registers constantly, because there are only 32 names, so false dependences are everywhere. Register renaming removes them. The core has a much larger physical register file, often a few hundred registers, and gives every new result a fresh physical register, mapping the architectural name to whichever physical register holds its latest value. In the example, 64 independent load–multiply–add steps that all reuse x5 and x6 take 449 cycles in order and 260 out of order without renaming, but only 71 with it.

Latency, throughput and how many chains

Summing an array with one running total is a single chain of dependent additions, each waiting for the last. With a floating-point add latency of 4 cycles, the core manages one add every 4 cycles however many adders it has. Split the sum into k independent totals that are combined at the end, and k chains run side by side.

How many chains are enough? To keep every adder busy, you need as many additions in flight as latency times throughput, here 4 cycles × 2 adders = 8. That's Little's law again, the same rule as chapter 9's outstanding cache misses. The example's sums of 1,024 floats run at 0.25, 0.5, 1 and then 1.9 adds per cycle for 1, 2, 4 and 8 accumulators, close to the 2-per-cycle limit. Sixteen accumulators are slightly slower, because combining them at the end takes a chain of 15 more adds. Combining them as a tree would fix that (exercise 14.2). Compilers make this transformation for integer sums, but not for floating point without permission such as -ffast-math, because floating-point addition isn't associative (chapter 2), and reordering a sum changes its last bits.

Simulated

The example's core starts each instruction as soon as its inputs are ready and a functional unit of the right kind is free, with 2 floating-point adders, 2 load units, 4 integer ALUs and 1 multiplier. Its window is unlimited, which makes it an upper bound on what real hardware finds.

The last two lines measure memory-level parallelism. A thousand loads from independent addresses overlap almost completely: 503 cycles from L1, and only 599 from DRAM, because in this idealised model all of them can be outstanding at once. A real core tracks a few dozen outstanding misses, so independent DRAM loads take longer than that, but still far less than one by one. A thousand dependent loads, each needing the previous one's result as its address, can't overlap at all: 100,000 cycles from DRAM. Out-of-order hardware is powerless against a dependency chain through memory, which is why chapter 11's linked list is slow on every processor ever built.

Common traps
  • Reductions with a single accumulator in hot floating-point loops.
  • Expecting the compiler to reassociate floating-point arithmetic without being allowed to.
  • Long dependency chains through memory, such as linked structures, which no hardware can overlap.
  • Judging code by instruction count. Cycles depend on dependences and units, not just on how many instructions there are.
  • Assuming a wider core always helps. Without independent work, extra units sit idle.

Exercise 14.1Enough chains for an FMA unit

Exercise 14.3Why integers but not floats

Compilers happily split an integer sum into several accumulators, but not a floating-point sum. Why is the transformation exact for integers?

Show solution

Integer addition, including its wrap-around on overflow, is arithmetic modulo 2n (chapter 1), which is associative and commutative: any grouping and order gives exactly the same bits. Splitting a sum into partial sums and combining them regroups the additions, so the result is identical. Floating-point addition rounds after every operation, so regrouping changes the rounding errors and can change the result, as chapter 2's non-associativity examples showed. Languages promise a specific order of evaluation for floating point, so a compiler may reorder it only with an explicit flag, or when the programmer writes the multiple accumulators by hand and accepts the slightly different result.

Chapter 15

SIMD, multicore and the limits of parallelism

9 min read3 exercises

When clock rates stopped rising around 2005, performance had to come from doing more at once. SIMD instructions apply one operation to a whole vector of values. Multicore chips run several instruction streams side by side, and GPUs push the SIMD idea to thousands of lanes. Each pays off only when the work has the right shape: data laid out contiguously, iterations that don't depend on each other, and threads that don't fight over the same cache lines. Amdahl's law sets the ceiling, because whatever part of a program stays serial decides how much faster the rest can make it.

SIMD: one instruction, many lanes

A SIMD instruction, single instruction, multiple data, operates on a wide register holding several values, called lanes, at once. A 128-bit register holds four 32-bit floats, and one instruction adds four pairs. x86 has had 128-bit SSE since 1999, 256-bit AVX2 since 2013, and 512-bit AVX-512 on some processors. ARM has 128-bit NEON and the scalable SVE, whose vector length the hardware chooses. Adding two arrays of 1,024 floats takes 1,024 scalar adds, 256 with 128-bit vectors and 64 with 512-bit ones.

SIMD has three requirements. The data must be contiguous, so a vector load can fetch several elements at once, which is another reason for chapter 11's structure-of-arrays layout. The iterations must be independent: a[i] = a[i-1] + b[i] can't run four lanes at once, because each lane needs the previous one's result. And branches become masks. Each lane computes both possibilities and a mask selects the result, so lanes whose condition is false do wasted work, as in the example, where 5 of 8 lanes are useful. Compilers auto-vectorise simple loops that meet these conditions, and libraries such as NumPy, BLAS and image codecs use SIMD intrinsics written by hand.

GPUs

A GPU takes the same idea to an extreme. Thousands of simple lanes are grouped into units of 32 or so, called warps on NVIDIA hardware, which execute the same instruction in lockstep on different data, a model NVIDIA calls SIMT. A GPU keeps tens of thousands of threads in flight to hide memory latency, the throughput strategy of chapter 9 taken as far as it goes, and pairs them with very high memory bandwidth. It excels at large, regular, data-parallel work such as graphics, matrix multiplication and the training of neural networks. It suffers when threads in a warp take different branches, because the warp must run both paths with half its lanes masked off each time.

Multicore

A multicore chip puts several complete cores on one die, sharing the last-level cache and memory. Threads on different cores share memory, and the coherence protocol of chapter 10 keeps their caches consistent, which costs time whenever cores write to the same line. False sharing makes that cost appear where no data is actually shared. In the example's model, two cores each incrementing their own counter cause 200,000 line transfers when the counters sit on one cache line, and 2 when they sit on separate lines. Beyond coherence, parallel programs pay for creating and synchronising threads and for contention on shared locks, so splitting small tasks across cores often makes them slower. Stage 05 covers threads, locks and their bugs.

Amdahl's law

If a fraction p of a program's work can be parallelised perfectly over n processors and the rest stays serial, the speed-up is

S(n)=1(1−p)+p/n,

which can never exceed 1/(1−p), however many processors there are. Gene Amdahl made the argument in 1967. With 90% of the work parallel, 16 cores give a speed-up of 6.4 and no number of cores gives more than 10. The serial part, such as reading input, combining results or a lock everyone needs, dominates as soon as the parallel part has been divided up. Gustafson's law gives the optimistic counterpart: people use more processors to solve bigger problems, and if the parallel part grows with the problem, the serial fraction shrinks, which is how supercomputers stay useful.

Counted

The example counts instructions for SIMD addition at four vector widths, applies a mask in place of a branch, tabulates Amdahl's law, and counts the coherence traffic that false sharing causes.

Common traps
  • Data layouts that defeat vector loads, such as arrays of structures scanned one field at a time.
  • Loop-carried dependences that silently prevent vectorisation.
  • Expecting linear speed-up from more cores. Measure the serial fraction first.
  • Parallelising tiny tasks, where thread start-up and synchronisation cost more than the work.
  • Per-thread data packed into one cache line, the false-sharing trap.
  • Adding cores to a memory-bound program, which saturates bandwidth and stops scaling (chapter 20).

Exercise 15.1Amdahl in practice

A batch job spends 20% of its time in a serial setup phase and the rest in work that parallelises perfectly. What's its speed-up on 16 cores, and what's the limit? How much faster would 16 cores be if you also halved the setup time?

Show solution

Exercise 15.2A loop that won't vectorise

Why can't for i in 1..n: a[i] = a[i-1] + b[i], a running sum, be vectorised directly? How can a running sum still be computed in parallel?

Show solution

Each element depends on the one computed just before it, a loop-carried dependence, so four lanes can't start four iterations at once: lane 2 would need lane 1's result in the same instruction. But a running sum is a prefix sum, or scan, and addition is associative (for integers), so it can be restructured. Within a vector of 4, add each element to its neighbour one place to the left, then to the element two places to the left, which gives 4 prefix sums in 2 steps, log2 4. Then add the running total from the previous vector to all four lanes. Parallel prefix algorithms do the same at larger scale in log n steps, the same associativity trick as chapter 4's prefix adder.

Exercise 15.3Vectorising a memory-bound loop

A loop adds two large arrays of floats that don't fit in cache, c[i] = a[i] + b[i]. Switching from scalar code to 8-lane SIMD makes it barely faster. Why?

Show solution

Each element needs 12 bytes of memory traffic, two 4-byte loads and one 4-byte store, for a single addition. A core can do billions of additions per second even without SIMD, but DRAM delivers perhaps 20 to 100 GB/s, so at 12 bytes per element the memory system supplies only a few billion elements per second. That's already about what scalar code achieves, so the loop is bandwidth-bound and the arithmetic was never the bottleneck. SIMD helps loops that do a lot of arithmetic per byte, or whose data is in cache. Chapter 20's roofline model makes this calculation routine: compare the arithmetic per byte with the machine's ratio of compute to bandwidth.

From source to process

Three chapters on how a program written as text becomes a running process: compiling it in stages to lower-level code and finally machine code; linking separately compiled pieces into one executable and loading it into memory; and the call stack that every running function uses, along with the overflow bugs that have made it the most attacked structure in computing.

Chapter 16

Compiling and assembling

8 min read3 exercises

A compiler is a pipeline of simple translations. Lexing turns characters into tokens, parsing turns tokens into a tree, analysis and optimisation transform the tree, and code generation turns it into instructions for some target machine. Each stage is a short program, and the tree in the middle is what makes compilers manageable. This chapter builds all four stages for a small language in about a hundred lines of Python, compiles a loop into chapter 8's stack VM, and runs it. That's the shape of Nand2Tetris projects 10 and 11, and of every real compiler.

The pipeline

Translation from source to machine happens in several steps, and Nand2Tetris builds every one of them. Each stage consumes the previous one's output and produces something closer to the machine.

Lexing and parsing

The lexer, or tokenizer, groups characters into tokens: names, numbers, operators and punctuation, discarding whitespace and comments. A regular expression is often enough, as in the example. The parser checks that the tokens follow the language's grammar and builds an abstract syntax tree (AST), a tree whose nodes are operations and whose leaves are names and constants. Recursive descent is the simplest parsing method: write one function per grammar rule, each calling the functions for the rules it contains. Operator precedence falls out of the structure. An expression is a sum of terms and a term is a product of factors, so expr calls term, which calls factor, and multiplication binds tighter than addition without any special handling. The tree for x = (2 + 3) * y - 4 * 2 is ('-', ('*', ('+', 2, 3), 'y'), ('*', 4, 2)), which makes the order of evaluation explicit.

Analysis and optimisation

Between parsing and code generation, a compiler builds symbol tables, mapping each name to its type and its storage location, such as the example's local slots. It checks types, and transforms the tree. Constant folding evaluates operations whose operands are known at compile time, so (2 + 3) * y - 4 * 2 becomes 5 * y - 8, and the generated code shrinks from 10 VM commands to 6. Real optimisers apply dozens of passes. They remove dead code, reuse common subexpressions, inline small functions, move work out of loops, and turn multiplication by a constant into shifts (chapter 4). They also assign variables to registers, which is graph colouring (The Engineer's Workbench, chapter 8), and schedule instructions around pipeline stalls (chapter 12). Most of a modern compiler is its optimiser, and most of that works on an intermediate representation such as LLVM's IR rather than on the source tree.

Code generation

For a stack machine, code generation is a post-order walk of the tree: emit code for the left operand, then for the right, then the operator. That's exactly the order a stack machine needs, operands pushed before the operation pops them. Control flow becomes labels and jumps. A while loop compiles to a label at the top, the condition, a jump to the end if it's false, the body, and a jump back to the top. Generating code for a register machine adds two harder problems, choosing instructions and allocating registers, which is why many compilers, and Nand2Tetris, first target a stack VM and translate from there.

Compiled and run

The example lexes and parses an assignment, folds its constants and generates VM code before and after folding. It then compiles a while loop that sums 1 to 100 and runs the result on a stack VM.

The compiled loop runs 1,511 VM commands, where chapter 8's hand-written version ran 1,411. The difference is the not the code generator emits before every loop test, 101 times, because it compiles "jump to the end if the condition is false" literally. A slightly smarter generator would test the inverse condition directly (exercise 16.3). Compilers are full of small decisions like that, and their accumulated effect is the difference between naive and optimised code.

Assembling, and beyond

Below the compiler, the VM translator turns each VM command into a fixed sequence of assembly instructions (chapter 8, exercise 8.3), and the assembler turns assembly into machine code with chapter 7's two passes. Real toolchains split the same work across separate programs. clang -S stops after code generation and shows the assembly, clang -c runs the assembler too and produces an object file, and the linker (chapter 17) finishes the job. Just-in-time compilers, in the JVM, in JavaScript engines such as V8, and in PyPy, run this pipeline while the program executes, compiling the hottest code using the types and values they actually observe.

Common traps
  • Left recursion in a recursive-descent parser, which recurses for ever; use a loop, as the example's expr does.
  • Getting associativity wrong, so that a − b − c parses as a − (b − c).
  • Ambiguous grammars, such as the dangling else, resolved silently in a way the programmer didn't expect.
  • Optimisations that change meaning, usually because the program relied on undefined behaviour.
  • Treating every layer as free. Each translation adds instructions unless something optimises them away.

Exercise 16.1Left associativity

The example's expr parses with a loop: a term, then repeatedly an operator and another term. Why not write it as the recursive rule expr → term "−" expr? Work through 10 − 4 − 3 both ways.

Show solution

The recursive rule groups to the right: it parses 10, then "−", then the whole rest as an expression, giving 10 − (4 − 3) = 9. Subtraction is left-associative, so the right answer is (10 − 4) − 3 = 3. The loop builds the tree from the left, wrapping the tree so far as the left child of each new operator, which gives ('−', ('−', 10, 4), 3). The left-recursive rule expr → expr "−" term would describe the right grouping, but a recursive-descent parser can't use it directly, because expr would call itself before consuming anything and never stop. The loop is the standard fix.

Exercise 16.2Generate by hand

Write the VM code the example's generator produces for y = a * (b + c);, with a, b and c in local slots 0, 1 and 2 and y in slot 3. How deep does the stack get?

A post-order walk gives: push local 0, push local 1, push local 2, add, mul, pop local 3. The stack reaches depth 3, just before the add, holding a, b and c. In general the depth needed for an expression tree is bounded by its height. Evaluating the deeper subtree first minimises it, a choice register allocators make too, because each stack slot corresponds to a register in compiled code.

Chapter 17

Linking and loading

9 min read3 exercises

Real programs are compiled in pieces: one object file per source file, plus libraries compiled by someone else, years earlier. The linker combines them. It decides where every function and variable will live, matches each reference to exactly one definition, and patches the machine code with the final addresses. The loader then maps the result into memory and starts it. This chapter builds a toy linker that does all three steps and reports the two classic errors, then explains static and dynamic linking, how a process is laid out in memory, and why addresses are randomised on every run.

Object files

A compiler and assembler turn each source file into an object file: machine code that isn't yet runnable, because it refers to things whose addresses aren't known. An object file contains sections. .text holds the code, .data initialised global variables, .rodata constants, and .bss zero-initialised globals, which take no space in the file, only a size. It has a symbol table listing the names it defines and the names it uses but doesn't define, and relocation entries marking each place in the code that refers to a symbol and must be patched once its address is known. The formats differ by platform: ELF on Linux, Mach-O on macOS and PE/COFF on Windows. The tools to inspect them, nm, objdump and readelf, are worth learning.

What the linker does

Linking happens in two steps, much like chapter 7's assembler. Symbol resolution matches every undefined symbol in every input to exactly one definition elsewhere. Relocation lays the sections out at final addresses, computes every symbol's address, and patches each relocation entry with the right value.

The two classic errors fall out of resolution. "Undefined reference" means some symbol has no definition in any input, usually a missing library on the command line, such as forgetting -lm for sqrt. "Duplicate symbol" or "multiple definition" means two inputs define the same name, often because a variable was defined, rather than declared, in a header included by several files. Static libraries, .a archives, are searched only for symbols still undefined at that point, which is why the order of libraries on a Unix linker command line matters.

Linked, by hand

The example's object files are lists of pseudo-instructions with symbol tables and relocation entries. The linker places the text sections from address 0x1000 and the data from 0x8000, resolves every reference, and patches the code. It then fails twice on purpose, and finally loads the result at three random base addresses.

Static and dynamic linking

Static linking copies the library code a program uses into the executable. The result is self-contained and starts fast, but every program carries its own copy, and fixing a bug in the library means relinking every program. Dynamic linking leaves library references unresolved until the program runs. Shared libraries, .so on Linux, .dylib on macOS and .dll on Windows, are loaded at run time and their code pages shared between all the processes that use them. A security fix to a shared library reaches every program at once. The costs are a little indirection on every call, through a procedure linkage table (PLT) and a global offset table (GOT) that the dynamic linker fills in, some start-up work, and a class of version-mismatch problems known on Windows as "DLL hell". Go and Rust link their own code statically by default, while most C and C++ programs link the system's C library dynamically.

Loading

To start a program, the operating system creates a fresh virtual address space and maps the executable's segments into it: code as read-only and executable, data as read-write. It reserves the bss and a stack, places the arguments and environment variables on the stack, and, for a dynamically linked program, maps the dynamic linker, ld.so on Linux, which loads the shared libraries and resolves their symbols. Control finally passes to the entry point, usually _start in the C runtime, which initialises the library and calls main. The resulting layout has code and data at the bottom, the heap above them growing upward as the program allocates, shared libraries and other mappings in the middle, and the stack near the top growing downward (chapter 18).

Address randomisation

If code always loads at the same address, an attacker who can overwrite a return address (chapter 18) knows exactly where to jump. Address space layout randomisation (ASLR) loads the executable, libraries, heap and stack at random addresses on every run, so a hard-coded address works only by luck. It requires position-independent code, which refers to its own functions and data relative to the current instruction's address rather than by absolute address. In the example, the base address changes on each run while the distance from main's call site to add stays +16, so an instruction that encodes "call the function 16 bytes ahead" works wherever the code is loaded. Modern compilers produce position-independent executables (PIE) by default for exactly this reason.

Common traps
  • Putting libraries before the objects that use them on a Unix linker command line.
  • Defining variables in headers, which produces duplicate symbols when the header is included twice.
  • Mixing library versions between build and deployment machines with dynamic linking.
  • Assuming fixed addresses for code, data or the stack. ASLR moves them every run.
  • Relying on the order of static initialisers across files in C++, which the language doesn't define.

Exercise 17.1Where does .bss go?

A program declares static char buffer[100000000]; at file scope. Why doesn't the executable grow by 100 MB, and what happens when it runs?

Show solution

An uninitialised, or zero-initialised, global goes into .bss, and the object file records only its size, not 100 MB of zeros. When the program is loaded, the operating system reserves that much address space and maps it to zero-filled pages on demand. A page of physical memory is allocated only when the program first touches it. So the file stays small and the process uses memory only for the parts of the buffer it actually writes. Initialising the array with any non-zero value would move it to .data and put all 100 MB in the file.

Exercise 17.2Read the error

Diagnose each linker error: "undefined reference to `sqrt'" when building a C program with gcc main.c, and "multiple definition of `counter'" in a program where counter.h contains int counter = 0;.

Fix it with gcc main.c -lm, with the library after the files that use it. The second: every file that includes counter.h gets its own definition of counter, so the linker sees several. Put extern int counter;, a declaration, in the header, and the definition int counter = 0; in exactly one source file. Both errors are about the difference between a declaration, which says a name exists, and a definition, which creates it.

Exercise 17.3Why relative addressing survives relocation

Explain why an instruction that says "call the address 16 bytes after this one" needs no relocation when a library is loaded at a different base address, while "call address 0x1018" does. What does position-independent code do about global variables?

Show solution

Moving the whole library by some offset moves the calling instruction and the called function by the same amount, so the distance between them is unchanged and a PC-relative call stays correct, as the example's constant +16 shows. An absolute address names one fixed location, so it's wrong as soon as the code moves, and the loader would have to patch it, which would also make the page private to one process instead of shareable. For data whose address isn't known until load time, such as a variable in another shared library, position-independent code loads the address from the global offset table, which sits at a fixed distance from the code and which the dynamic linker fills in. One table entry per symbol is patched, rather than every instruction that uses it.

Chapter 18

The stack and overflows

8 min read3 exercises

Every function call gets a frame on the stack: the address to return to, some saved registers, and the function's local variables. The stack is just memory and a pointer, which is why it's both fast and dangerous. Allocating a frame is one subtraction, but a local array sits a few bytes below the return address, and C's string functions don't check lengths. This chapter lays out a frame byte by byte, overflows it to take over the return address, watches a stack canary catch the same attack, and works out how deep recursion can go before the stack runs out.

Calls and frames

A call has to remember where to come back to. On x86 the call instruction pushes the return address onto the stack. On RISC-V, jal puts it in the register ra (chapter 6), and a function that makes calls of its own saves ra to the stack first. The function's prologue then saves the caller's frame pointer and any registers it promised to preserve, and allocates space for its locals by subtracting from the stack pointer. The epilogue undoes all of that, and ret jumps to the saved address. The rules for which registers hold arguments, which hold the return value, and which a function must preserve make up the calling convention. RISC-V passes the first eight arguments in a0 to a7 and returns in a0; on Linux and macOS, x86-64 uses rdi, rsi, rdx, rcx, r8 and r9, and returns in rax. Further arguments go on the stack.

Two consequences follow. Stack allocation is almost free compared with the heap, where malloc has to search for a free block, which is one reason short-lived locals are fast. And a local variable stops existing when its function returns. Its bytes stay in memory until the next call reuses them, so a pointer to a local that outlives the call reads whatever the next frame put there.

Overflowing a buffer

In C, strcpy(buf, input) copies until it finds the terminating zero byte, however big buf is. So do gets, which can't be used safely at all and was removed from C11, and sprintf. If the input comes from outside the program, its author decides what lands past the end of the buffer, and the return address starts only 8 bytes past its end. The example simulates a 64 KiB machine and runs the vulnerable function three times. A 5-byte input and a 16-byte one leave the frame intact. A 32-byte input fills the buffer, overwrites the saved frame pointer with the bytes BBBBBBBB, and replaces the return address with a value the attacker chose.

In a real attack, the chosen address points at code the attacker supplied in the same input, or at existing code that does what they want. This is the oldest exploit technique in computing that still works. The Morris worm used it in 1988 against a gets call in the finger daemon, and Aleph One's 1996 article "Smashing the Stack for Fun and Profit" taught it to a generation.

Defences

A stack canary is a random value the prologue places between the locals and the saved registers, and that the epilogue checks before returning. An overflow from a buffer must pass through it to reach the return address, and the attacker doesn't know its value, so the check fails and the program aborts instead of jumping. GCC and Clang insert canaries with -fstack-protector, on by default in most Linux distributions. A non-executable stack, also called NX, DEP or W^X, makes the processor refuse to run instructions from stack pages, so injected code can't run. Attackers answered with return-oriented programming: chaining short fragments of the program's existing code, each ending in ret. That's where ASLR (chapter 17) comes in, since the fragments' addresses are no longer known in advance. The newest defences are in hardware. Intel's CET keeps a shadow stack of return addresses that ordinary stores can't write, and ARM's pointer authentication, used on Apple silicon, signs return addresses with a key held in the processor.

Each defence raises the cost of an attack, and none removes the bug. Microsoft and the Chromium project have each reported that about 70% of their serious security bugs are memory-safety errors. The lasting fix is code that can't write past the end of a buffer: bounds-checked languages such as Rust, Go, Java and Python, and in C and C++, functions that take the destination's size, such as snprintf, used correctly.

How deep can recursion go?

Each nested call adds a frame, and the stack has a fixed size. The main thread's default is 8 MiB on Linux and macOS, other threads often get less (512 KiB for secondary threads on macOS), and Windows defaults to 1 MiB. The example's last lines divide 8 MiB by the frame size: about 175,000 calls for a small 48-byte frame, but only 2,048 for a function with a 4 KiB local array. Below the stack sits an unmapped guard page, so running out is a crash, a segmentation fault, rather than silent corruption of the heap. Python sets its own recursion limit, 1,000 by default, well below the point where its interpreter's C stack would overflow. Recursion whose depth depends on the input, such as walking a long linked list or parsing deeply nested JSON, should be rewritten as a loop with an explicit stack on the heap.

Common traps
  • Returning a pointer to a local variable. Its frame is gone as soon as the function returns.
  • Using gets, strcpy or sprintf on input whose length you don't control.
  • Forgetting the terminating zero byte when sizing a buffer for a string.
  • Putting large arrays on the stack, especially in threads with small stacks.
  • Recursing to a depth the input controls.
  • Assuming canaries and ASLR make an overflow harmless. They make it harder to exploit.

Exercise 18.1The off-by-one

In the example, a 16-byte input returned safely. Explain why strcpy with a 16-character string is still an overflow of buf[16] in C, and what it damages on this little-endian machine.

Show solution

strcpy also copies the terminating zero byte, so a 16-character string writes 17 bytes. The 17th lands at 0xFFF0, the first byte of the saved frame pointer. On a little-endian machine that's its lowest byte, so the saved value 0xFFF0 becomes 0xFF00. The function itself returns normally. But when the caller restores its frame pointer, it points 240 bytes too low, and the caller then reads its locals, and possibly its own return address, from the wrong place. One-byte zero overwrites like this have been exploited in practice. The fix is to size buffers for the string plus its terminator, and to copy with functions that take the destination's size.

Exercise 18.2Will it fit?

A recursive function with a 256-byte frame walks a linked list of 100,000 nodes, one call per node. Does it fit in an 8 MiB stack? In a 512 KiB thread stack? What should the function do instead?

Exercise 18.3What a canary misses

The example's canary has a zero lowest byte. Why does that help against strcpy overflows? Name two kinds of attack a canary doesn't stop.

Show solution

On a little-endian machine the lowest byte is stored first, so it's the first byte of the canary an overflow from the buffer reaches. To get past the canary without changing it, the input would have to contain a zero byte at that point, and strcpy stops copying at a zero byte. Canaries don't stop overflows that change other locals, such as a function pointer or a length, between the buffer and the canary; compilers reduce this by placing arrays directly below the canary. They don't stop writes that skip over it, such as buf[i] = x with an index the attacker controls, or overflows on the heap. And if a separate bug leaks the canary's value, for instance a format-string bug, the attacker can write it back unchanged.

The machine at work

Two chapters on the machine as a whole: how the processor exchanges data with the devices around it, from keyboards to network cards and SSDs, without spending all its time waiting for them; and how to predict a program's performance with a few lines of arithmetic, and so know which optimisation is worth making before you make it.

Chapter 19

I/O, interrupts and DMA

10 min read3 exercises

A processor talks to a device by reading and writing the device's registers. The hard part is knowing when something has happened. The processor can keep asking, which is polling. The device can interrupt it. Or the device can copy its data into memory by itself, which is direct memory access (DMA), and interrupt only when a batch is done. This chapter prices all three for a keyboard, a mouse, a 10 Gb/s network card and an NVMe SSD. It shows why fast devices need DMA, and why at the highest rates the answer turns back to polling.

Talking to devices

Most devices are reached by memory-mapped I/O. Their control and status registers appear at physical addresses, and ordinary loads and stores to those addresses go to the device instead of memory, just as the Hack computer's screen and keyboard did in chapter 7. A store to a network card's register might mean "send the packet described here", and a load from its status register reports whether one has arrived. Those addresses must never be cached, and accesses to them must not be reordered or optimised away, so the page tables mark them uncached and drivers access them through volatile pointers or helpers such as Linux's readl and writel. In a modern computer most devices sit on PCI Express, and the code that knows a particular device's registers is its driver.

Polling and interrupts

Polling means reading the status register in a loop until it says data is ready. Each check costs only tens of cycles, but the core does nothing else, so polling a keyboard that produces ten events a second wastes a whole core. With interrupts, the device raises a signal when it needs attention. The processor finishes its current instruction, saves the program counter and some state, switches to kernel mode, and jumps to the handler registered for that interrupt in a table of handlers, the interrupt vector table. The handler acknowledges the device, does the minimum, schedules any longer work for later, and returns, and the interrupted program continues as if nothing had happened. The same mechanism handles exceptions, such as a page fault or a division by zero, and system calls, where a program deliberately traps into the kernel. A timer interrupt, a few hundred or a thousand times a second, is what lets the operating system take the processor back from a running program and schedule another.

An interrupt isn't free. Saving state, switching modes and running the handler costs around a microsecond, roughly 3,000 cycles, and the handler's code and data push the program's out of the caches. Even with interrupts, if the processor copies every byte from the device itself, a fast device keeps it busy.

Direct memory access

With DMA, the device copies the data itself. The driver sets up a ring of descriptors in memory, each pointing at an empty buffer. The device writes each incoming packet or disk block into the next buffer, marks the descriptor as filled, and raises an interrupt only after a batch of them, or after a short timeout. This is interrupt coalescing. The processor never touches the data until it's ready to use it. Two practical details matter. On x86 machines, DMA is cache-coherent: the hardware makes sure the caches don't hold stale copies of buffers a device has written. On many ARM systems the driver must flush or invalidate the caches itself. And because a device that can write anywhere in memory can also overwrite the kernel, an IOMMU translates and restricts the addresses each device may use, the way page tables restrict programs.

The example prices one second of each device. Busy polling costs a whole core whatever the device, which is why it's worth it only when events never stop. With interrupts, the keyboard and mouse cost almost nothing, and their DMA column shows only that at low rates the choice doesn't matter; nobody batches keystrokes. The network card, with an interrupt and a copy per packet, takes 94% of a core. The SSD would need more than a whole core. DMA with one interrupt per 32 events brings both down to about 3%.

When interrupts are too many

The last lines of the output show the failure that made networking engineers rethink interrupts. At a million packets a second with one interrupt each, handling interrupts takes the whole core. The handler runs, receives the packet, and before the program can process it the next interrupt arrives. The machine is fully busy and gets nothing done. This is receive livelock, described by Mogul and Ramakrishnan in 1996. The answer was to go back to polling, but polling memory rather than device registers. Linux's NAPI takes one interrupt, switches it off, and polls the DMA ring until it's empty, switching interrupts back on only when traffic falls. Frameworks such as DPDK, for networking, and SPDK, for storage, go further: they give a device to a user-space program that polls its rings on dedicated cores and never takes an interrupt. Interrupts are best when events are rare, and polling a DMA ring is best when they never stop.

Coalescing trades latency for throughput. An interrupt per batch of 32 means the first packet waits for 31 more, or for the timeout. Network cards and storage drivers let the timeout and batch size be tuned, and latency-sensitive systems such as trading platforms set them low or poll.

Common traps
  • Reading a device register through an ordinary pointer. The compiler may read it once and loop forever on the cached value.
  • Doing slow work in an interrupt handler. Acknowledge the device and defer the rest.
  • Assuming DMA buffers are coherent with the caches on every platform.
  • One interrupt per event at high rates, which ends in livelock.
  • Tuning coalescing for throughput on a system that needs low latency, or the reverse.

Exercise 19.2The loop that never ends

A driver waits for a device with while (*status == 0) {}, where status is an ordinary uint32_t * pointing at the device's status register. Give two reasons it might loop forever after the device sets the register to 1.

Show solution

First, the compiler sees no store to *status inside the loop, so it may load the value once and test the same register copy forever. Declaring the pointer volatile, or using the kernel's readl, forces a real load on every iteration. Second, if the register's address were mapped as ordinary cacheable memory, the loads would hit the cache and never reach the device. Device memory must be mapped uncached, which the operating system's functions for mapping device registers, such as Linux's ioremap, do. A related rule applies to writes: when a driver fills in a descriptor and then writes a "go" register, a barrier must make sure the descriptor reaches memory before the device is told to read it.

Chapter 20

Performance as arithmetic

10 min read3 exercises

Most performance questions can be answered, or at least bounded, before any code is written, with three formulas and a handful of numbers. The iron law splits running time into instruction count, cycles per instruction and clock period, and so says which of the earlier chapters' techniques can help. The roofline says whether a loop is limited by arithmetic or by memory, and how fast it can possibly go. Amdahl's law, applied to a profile, says which part is worth speeding up. This chapter applies all three, then turns to measurement, which checks the arithmetic.

The iron law

A program's running time is the product of three factors:

time=instructions×cyclesinstruction×secondscycle.

Different things change each factor. The instruction count depends on the algorithm, the compiler and the instruction set; SIMD (chapter 15) cuts it by doing several operations per instruction. Cycles per instruction, or CPI, depends on how well the program suits the microarchitecture: cache misses (chapters 9 to 11), branch mispredictions (chapter 13) and dependency chains (chapter 14) all raise it. The clock period is set by circuit design and power (chapters 3 and 12). The factors interact, which is why the law is worth writing down. In the example, a better compiler removes 20% of the instructions, but the remaining ones are slower on average, and the gain is 1.18 times rather than 1.25. A cache-friendly data layout that leaves the instruction count alone but cuts CPI from 1.6 to 0.9 gains 1.78 times, much more than a 20% faster clock.

Hardware people often quote the inverse, instructions per cycle or IPC. A wide out-of-order core running well-behaved code retires three or four instructions per cycle, and the same core chasing pointers through memory retires a fraction of one. On Linux, perf stat reports a program's IPC along with its cache and branch misses, and is the quickest way to see which factor is the problem. Comparing CPI or clock rates between different instruction sets or different programs says little, because the instruction counts differ.

The roofline

A loop needs both arithmetic and data. Its arithmetic intensity I is the number of floating-point operations it does per byte it moves to or from main memory. A machine has a peak arithmetic rate Ppeak and a memory bandwidth B, and the loop can go no faster than whichever limit it hits first:

P=min(Ppeak,I×B).

Plotted on log-log axes, that's a sloped line, the bandwidth limit, meeting a flat one, the peak, at the ridge point Ppeak/B. The example's machine, with 200 GFLOP/s and 50 GB/s, has its ridge at 4 FLOP per byte. Real CPUs have ridges between roughly 5 and 15, and GPUs often higher still, so most simple loops are on the slope. A vector add does one addition per 12 bytes moved, three 4-byte floats, and can't exceed 4.2 GFLOP/s on a machine that could do 200. Wider SIMD or more cores make no difference to a loop on the slope. Only reducing its memory traffic does: blocking (chapter 11), smaller data types, or fusing loops so that data is used several times while it's in the cache.

Matrix multiplication is the chapter 11 result seen on the roofline. The naive loop loads two values for every multiply-add, an intensity of 0.125. Blocking reuses each loaded value 64 times, which raises the intensity to 8 and moves the loop past the ridge, where it's limited by arithmetic. That's also why matrix multiplication is the workload GPUs and AI accelerators are built around: it's one of the few important computations with enough reuse to use all their arithmetic.

Numbers to know

Estimates need a few numbers, known to within a factor of two: chapter 9's latencies, and the bandwidths in the example's third section. Reading a gigabyte takes about 20 ms from memory, 200 ms from an NVMe SSD, 5 s from a hard disk and 8 s over a 1 Gb/s network. Multiplying such numbers out answers design questions in a minute. A request that must read 1 GB from memory can't be served more than about 50 times a second per memory system, and a full scan of a 1 TB table on one SSD takes over three minutes however clever the query is. Throughput and latency connect through Little's law (chapters 9 and 14): the number of operations in flight equals throughput times latency, so a disk with a 100 µs latency needs 100 outstanding requests to deliver a million operations a second.

Amdahl on a profile

Before speeding anything up, find out where the time goes. A sampling profiler such as perf record on Linux, Instruments on macOS or py-spy for Python interrupts the program thousands of times a second and records what it was running, which gives each function's share of the time with little overhead. Amdahl's law (chapter 15) then gives the ceiling. In the example's profile, computing takes 70% of the time. Making it four times faster speeds the whole program up 2.11 times, and making it infinitely fast only 3.33 times, 1/(1−0.7). Making parsing, 15% of the time, four times faster gains 1.13 times. Effort spent on a small part of the profile is mostly wasted, however good the optimisation.

Measurement has its own traps. Run several times and report the median, since the first run pays for cold caches and the rest vary with whatever else the machine is doing. Clock rates change with temperature and power: a laptop on battery or a core that has been busy for a minute runs slower than one that just woke up. Measure the work you care about at a realistic size, because a benchmark that fits in the cache tells you nothing about one that doesn't. The method that works is to estimate the bound first, measure, and compare. A loop running at 10% of its roofline has a problem worth finding, while one at 80% needs a different algorithm or a different machine, not more tuning.

Common traps
  • Optimising before profiling, and so speeding up a part that takes 5% of the time.
  • Measuring once, with cold caches, on a machine whose clock rate is changing.
  • Comparing CPI or GHz across instruction sets or across programs.
  • Adding SIMD or cores to a memory-bound loop. Reduce its traffic instead.
  • Treating spec-sheet peaks as achievable. Measure sustained bandwidth, for example with the STREAM benchmark.

An optimisation removes 30% of a program's instructions but raises its CPI from 1.2 to 1.5. The clock rate is unchanged. Is the program faster or slower, and by how much?

Exercise 20.2A roofline for daxpy

On the example's machine, a loop computes y[i] = a * x[i] + y[i] for 108 doubles. What's its arithmetic intensity, the fastest it can run, and the minimum time? Would 512-bit SIMD help? What would?

Show solution

Each element does 2 FLOPs, a multiply and an add, and moves 24 bytes: it reads x[i] and y[i] and writes y[i], 8 bytes each. The intensity is 2/24≈0.083 FLOP per byte, far below the ridge at 4, so the loop is memory-bound at 0.083×50=4.2 GFLOP/s. The minimum time is the traffic over the bandwidth: 2.4 GB at 50 GB/s, 48 ms. Wider SIMD doesn't help, because arithmetic was never the limit. What helps is moving fewer bytes: single precision halves the traffic and the time, and fusing this loop with the next one that reads y avoids writing it out and reading it back.

Exercise 20.3Find the bottleneck

A nightly job reads a 500 GB log from an NVMe SSD at 5 GB/s, parses it at 1 GB/s per core on 8 cores, and sends 50 GB of results over a 1 Gb/s network. The three stages can overlap. What's the shortest possible running time, and what would you change first?

Show solution

Reading takes 500/5 = 100 s. Parsing runs at 8 GB/s, so it takes 62.5 s. Sending 50 GB at 125 MB/s takes 400 s. With the stages overlapped, the job can't finish faster than its slowest stage, so the minimum is 400 s, and the network is the bottleneck. Buying faster SSDs or more cores would change nothing. Change the network first: compressing the output four times brings it to 100 s, and a 10 Gb/s link to 40 s. Either way, reading at 100 s becomes the new bottleneck. That's Amdahl's law again: once one stage is fixed, the next slowest sets the time.

The twenty rules

One per chapter, each linked back to it. Read them before you choose a data type, trust a benchmark, or decide what to optimise.

  1. Know the width and signedness of every integer, and decide in advance what happens when it overflows.
  2. Never compare floats with ==, never store money in them, and sum carefully when the terms differ in size.
  3. Any logic can be built from NAND alone; judge a circuit by its depth as well as its gate count.
  4. An adder is as fast as its carry chain, and subtraction is addition of the inverted operand plus one.
  5. State changes only on the clock edge, and the slowest path between two registers sets the clock.
  6. An instruction set is a contract, not a speed; know its formats, and remember that immediates are sign-extended.
  7. A CPU is fetch, decode and execute in a loop, and an assembler is two passes and a symbol table.
  8. Read the optimised assembly before believing anything about what the machine does.
  9. Ask how far away the data is: a nanosecond in L1, a hundred in main memory, millions on a disk.
  10. Know your cache's line size and sets, and keep hot data off large power-of-two strides.
  11. Walk memory in the order it's stored, block what you reuse, and lay data out the way it's read.
  12. A pipeline overlaps instructions but doesn't shorten them; dependences and taken branches cost stalls.
  13. Make hot branches predictable or remove them, and remember that speculation leaves traces in the cache.
  14. Speed comes from independent work, so split long dependency chains into several shorter ones.
  15. Parallel hardware pays only for parallel work; measure the serial fraction before adding lanes or cores.
  16. A compiler is a pipeline of small translations through a tree; check what it produced before optimising by hand.
  17. Every reference needs exactly one definition: declare in headers, define once, and put libraries after their users.
  18. Never copy into a buffer without knowing its size; defences slow attackers down, but only bounds checks stop them.
  19. Use interrupts for rare events and DMA for bulk data, and poll a ring when the events never stop.
  20. Estimate the bound, measure, and compare; optimise only what the profile and the roofline say matters.
