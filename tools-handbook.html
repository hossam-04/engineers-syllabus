A whetstone cuts nothing. It keeps every other blade sharp. This volume is about the tools you'll use every working day: the shell and the small programs it runs, the filesystem underneath them, Git, one editor, and the skill of learning itself. The one habit

The tools in this volume hide almost nothing; they just don't volunteer it. The shell will tell you exactly what a line expands to, Git will draw its whole graph, and every error message names what went wrong.

So look before you change anything. Run type before blaming PATH, git status and git log --graph --all before any Git command you're unsure of, and read the whole error message before searching for it. Most confusion ends the moment you look at the actual state instead of the one you imagined.

Part I

The shell

Four chapters on the program you'll type into for the rest of your career. The shell is a small programming language whose real job is starting other programs and connecting them together. First, how it turns a line you type into a list of arguments, which explains almost every quoting bug. Then the streams and exit codes that let programs cooperate, the four tools that answer most questions about text, and the habits that make a shell script safe to run while you sleep. By the end of this part you can automate a chore and trust the result.

Chapter 1

The shell as a language

13 min read3 exercises

The shell is a programming language whose main job is starting other programs. Before it runs a line, it rewrites it: it replaces variables, expands patterns into file names, splits the result into words, and only then hands the program a list of arguments. The program never sees your quotes, your $ signs or your *. Almost every surprise in the shell is a surprise about that rewriting, so this chapter shows exactly which list a program receives for each kind of line.

A command is a list of words

Three things are easy to confuse. The terminal is the window: it draws characters and sends your key presses on. The shell is the program running inside it, usually bash or zsh, which reads each line you type and decides what to do with it. And the commands are ordinary programs, ls, grep, git, which the shell starts. When you type ls -l Documents, the shell finds a program called ls, which chapter 7 explains, and starts it with a list of three strings: ls, -l and Documents. That list, called argv in C and sys.argv in Python, is everything the program gets from the line. What -l means is entirely up to ls.

Programs mostly follow the same conventions for their arguments. Single letters after one dash are options, and can often be combined: ls -l -a is ls -la. Long names take two dashes, as in ls --all. Some options take a value, like head -n 5, and a lone -- means "no more options", so rm -- -notes.txt deletes a file whose name begins with a dash. These are conventions, not rules the shell enforces. The shell's own job ends at producing the list.

Quoting

The shell gives special meaning to a few characters: spaces separate words, $ starts a variable or substitution, *, ? and [ make patterns, and |, >, <, & and ; connect or separate commands. Quoting turns those meanings off. Inside single quotes, everything is literal: '$HOME *' is exactly those seven characters. Inside double quotes, spaces and pattern characters are literal, but $, backquotes and backslash still work, so "$HOME" becomes your home folder as one word, however many spaces it contains. A backslash outside quotes makes the next character literal: it\'s. Quotes can be mixed within one word: 'single'"double" is one argument, singledouble. The quotes themselves are removed before the program starts, which is why it never sees them.

The expansions, in order

Before running a line, bash performs a fixed sequence of expansions, and the order explains the surprises. Brace expansion comes first, turning file{1..3}.log into three words. Tilde expansion turns ~ at the start of a word into your home folder. Then, from left to right, parameter expansion replaces $name and ${name} with variables' values, arithmetic expansion computes $((2 + 3 * 4)), and command substitution runs $(command) and puts its output in its place. Only then does word splitting break the results of those three, wherever they weren't in double quotes, at spaces, tabs and newlines. Pathname expansion, usually called globbing, then replaces each word containing *, ? or [ with the matching file names. Finally, quote removal deletes the quotes.

The best way to learn this is to watch it. The example creates a tiny program, showargs, which prints its arguments one per bracket, so you can see exactly where each word begins and ends. It then runs it through bash in a folder holding a.txt, b c.txt and notes.md, with a variable f holding my notes.txt and another, empty, holding nothing.

What the example shows

Unquoted expansions are split, and quoted ones aren't. showargs $f receives two arguments, my and notes.txt, because the value was split at its space. A program given those would look for two files that don't exist. "$f" keeps it whole. An empty variable unquoted disappears altogether, leaving zero arguments, while "$empty" is one empty argument. That difference is why [ $answer = yes ] fails with a strange error when answer is empty: the test receives = yes. The rule that prevents most shell bugs is simple: put double quotes around every expansion, "$var", "$(command)", "$@", unless you can say why you want it split.

Globs match file names, and are expanded after splitting. *.txt became a.txt and b c.txt, sorted, with the space intact: names produced by globbing are never split again. A glob that matches nothing is passed on unchanged, so showargs *.csv received the literal *.csv; that's bash's default, and zsh's default is different: it stops with "no matches found". Quoted, "*.txt" is just text. Section 5 shows the order's sharpest edge: the output of $(printf '*.txt') is the text *.txt, and because substitution happens before globbing, it is then expanded into file names. Command output containing a *, a space or a newline is rewritten unless it's quoted.

Assignments have no spaces. x=5 sets a variable. x = 5 runs a program called x with arguments = and 5, and fails with status 127, "command not found". Putting an assignment before a command, as in x=5 y="a b" showargs, sets them for that one command only, which chapter 7 uses. And the last line shows the other side: when Python's subprocess.run is given a list, there's no shell, so nothing is expanded. *.txt and $HOME arrive exactly as written. When you start programs from your own code, pass a list rather than a string to a shell, and the quoting problems disappear.

Globs are not regular expressions

Glob patterns look like the regular expressions of chapter 3, and mean different things. In a glob, * matches any run of characters, ? exactly one, and [abc] one of a set; the pattern must match the whole name. A * doesn't match a leading dot, so * skips hidden files like .bashrc, and it doesn't cross /, so src/*.py looks in one folder only. To match in every subfolder, zsh understands **/*.py by default, and bash does after shopt -s globstar, which needs bash 4; for anything more, use find, in chapter 3. In a regular expression, by contrast, * means "the previous thing, any number of times", and . means any character.

Seeing what the shell will run

You never have to guess what a line expands to. set -x makes bash print each command, after expansion, before running it, with a + in front; set +x turns it off. It's the most useful debugging tool the shell has, and it works in scripts too. For a single line, put echo or printf '[%s]\n' in front of a command to see its arguments without running it. Two keyboard habits save hours as well: Tab completes commands and file names, and quotes awkward names for you, and Ctrl-R searches back through the commands you've run before. History is kept in a file, usually ~/.bash_history or ~/.zsh_history.

Common traps
  • Unquoted variables, which break on the first file name with a space and vanish when empty.
  • for f in $(ls), which splits names at spaces; loop over a glob, for f in *, instead.
  • Spaces around = in an assignment, which turn it into a command.
  • Expecting * to match hidden files, or an unmatched glob to vanish: bash passes it on unchanged.
  • Curly quotes pasted from a web page or word processor: “ and ” are ordinary characters to the shell, not quotes.

Exercise 1.1Predict the list

After a="1 2"; b="", in a folder with no files whose names start with 1, predict what showargs receives from each line: showargs $a$b, showargs "$a""$b", showargs $b $a, showargs '$a' "\$a", showargs {x,y}{1,2} and showargs "$a"*.

Show solution
showargs $a$b          2 argument(s): [1] [2]
showargs "$a""$b"      1 argument(s): [1 2]
showargs $b $a         2 argument(s): [1] [2]
showargs '$a' "\$a"    2 argument(s): [$a] [$a]
showargs {x,y}{1,2}    4 argument(s): [x1] [x2] [y1] [y2]
showargs "$a"*         1 argument(s): [1 2*]

$a$b is 1 2 followed by nothing, split into two words. Quoted, "$a""$b" is one word, and the empty "$b" adds nothing to it because it's part of the same word. In $b $a the unquoted empty $b disappears. Single quotes and a backslash both stop expansion. Two brace expressions in one word multiply, giving every combination. In the last line the quoted part isn't split, so the glob is the single pattern 1 2*, which matches nothing and is passed on unchanged. Each answer was produced by running the line in bash.

Exercise 1.2The loop that breaks on spaces

In a folder holding my notes.txt and todo.txt, this loop prints three lines instead of two: for f in $(ls *.txt); do echo "loop got [$f]"; done. Explain why, and write a loop that's correct for any file name, including when there are no matching files.

Show solution
for f in *.txt; do
  [ -e "$f" ] || continue        # no match: bash leaves the literal "*.txt"
  echo "loop got [$f]"
done

The glob *.txt is expanded into two names for ls, which prints them, one per line. But the output of $(ls *.txt) is then split at every space and newline, so my notes.txt becomes two words, and the loop runs three times, with my, notes.txt and todo.txt. Looping over the glob itself gives each name as one word, spaces and all, because names produced by globbing are never split. The [ -e "$f" ] test handles the empty case: with no .txt files, the loop would otherwise run once with the literal *.txt. In bash, shopt -s nullglob makes an unmatched glob expand to nothing instead. And inside the loop, "$f" stays quoted wherever it's used.

Exercise 1.3The empty variable

In 2015, Steam's installer for Linux ran a line like rm -rf "$STEAMROOT/"*. On some machines STEAMROOT turned out to be empty. What did the line expand to, and how should it have been written?

Show solution

With STEAMROOT empty, "$STEAMROOT/"* is the glob /*, every entry at the top of the filesystem. With showargs in place of rm, on the Mac this volume was written on, the line expands to seventeen arguments: -rf, then /Applications, /Library, /System, /Users and every other top-level folder. For an ordinary user, that deleted every file they owned, on every mounted drive, which is what the bug report described. The defences, in order of importance: ${STEAMROOT:?} makes the shell stop with an error if the variable is unset or empty, instead of expanding to nothing; set -u at the top of a script makes any unset variable an error, which chapter 4 recommends; and checking a value before using it to delete anything, [ -d "$STEAMROOT" ] || exit 1, catches values that are set but wrong. Running a destructive line with echo in front first would have shown the problem on the developer's machine.

Chapter 2

Streams, pipes and exit codes

12 min read3 exercises

Every program starts with three open streams, for its input, its output and its error messages, and finishes by returning a small number that says whether it worked. Redirection points those streams at files. A pipe connects one program's output to the next program's input, and the exit status lets the shell decide what to run next. Small programs that each do one thing become powerful through these three mechanisms. Two details cause most of the bugs: redirections are applied from left to right, and a pipeline reports only its last command's status.

Three streams and a number

When a program starts, it inherits three open file descriptors, small numbers that stand for open files: 0 is standard input, 1 standard output and 2 standard error. In a terminal all three are the terminal itself, which is why both output and error messages appear on screen. They're separate so that a program's results and its complaints can go to different places: results into a file or the next program, errors to a person. A well-behaved program writes what it computed to stdout and anything meant for a human, warnings, progress, errors, to stderr.

When it finishes, every program returns an exit status between 0 and 255. Zero means success, and every other value is some kind of failure; the shell keeps the last one in $?. A few values have conventional meanings: 1 for a general failure, 2 for misuse such as a bad option, 126 for a file that was found but isn't executable, 127 for a command that wasn't found, and 128 plus a signal's number for a program that was killed. That makes 130 a program stopped by Ctrl-C, signal 2, and 141 one killed by SIGPIPE, signal 13, which the example shows. The exit status is the only result every caller checks without reading anything.

Redirection

> file sends stdout to a file, creating it or emptying it first; >> file appends instead; < file reads stdin from a file; and putting a number in front picks the descriptor, so 2> errors.txt redirects stderr. 2>&1 means "make descriptor 2 point wherever descriptor 1 points now". That last word is the whole difficulty. The shell processes redirections from left to right, each one changing a table of where the descriptors point. So > out.txt 2>&1 first points 1 at the file, then points 2 at the same place: both go to the file. But 2>&1 > out.txt first points 2 at the terminal, where 1 still points, and only then moves 1 to the file: errors stay on the screen. Bash's &> file is shorthand for the first form. /dev/null is a file that discards whatever is written to it.

The example uses a tiny program, talk, that writes one line to stdout, one to stderr, and exits with whatever status it's given. For each line, it reports which text reached the terminal's stdout, which reached its stderr, and what ended up in any file.

Pipes

A pipe, a | b, connects a's stdout to b's stdin. Only stdout: in section 3, talk | tr a-z A-Z uppercased the stdout line, while the stderr line went around the pipe to the terminal, unchanged. To send both through, redirect first: talk 2>&1 | tr a-z A-Z. tee file copies its input to a file and passes it on, so you can save a stream and keep processing it. Both programs in a pipeline run at the same time, the second reading as the first writes, which is why a pipeline can process a file far larger than memory. It's also why yes | head -n 2 finishes: yes prints y for ever, head exits after two lines, and the next write by yes finds no reader and kills it with SIGPIPE. Its status, 141, is in section 5.

Exit statuses, conditions and pipefail

The shell's conditions are built on exit statuses, not on true and false values. a && b runs b only if a succeeded, a || b only if it failed, and if command; then runs the branch when the command's status is 0. The [ in if [ -f notes.txt ] is itself a command, also called test, which exits 0 or 1. Programs like grep -q exist to be used as conditions: they print nothing and exit 0 if a line matched. One caution: a && b || c isn't if-then-else, because c also runs when b fails.

A pipeline's status is the status of its last command. false | true succeeds, which means a failure early in a pipeline, a download that broke halfway, a program that crashed, is silently ignored. set -o pipefail changes the rule: the pipeline fails if any command in it failed. And bash keeps every status from the last pipeline in the array PIPESTATUS: 1 0 2 in section 5 are the statuses of false, true and talk 2. Like $?, it's overwritten by the next command, so read it immediately.

set -e makes a script exit when a command fails, and it has surprising exceptions. It doesn't apply to commands whose status is being tested, in an if, a while, or on the left of && or ||. And the exemption reaches into functions: in section 6, check was called on the left of ||, so inside it false failed and the function carried on as if nothing had happened. set -e is still worth using, as chapter 4 does, but as a safety net. When a failure matters, check it explicitly: cd "$dir" || exit 1.

Here-documents

A here-document feeds the lines between <<EOF and a line containing just EOF to a command's stdin, which is the cleanest way to write a file or a block of text from a script. Variables and substitutions are expanded inside it, unless the marker is quoted, <<'EOF', which section 7 shows. Bash also has the here-string, grep x <<< "$text", which feeds one string as input. Any word can be the marker, and EOF is only a habit.

Common traps
  • cmd 2>&1 > file when you meant both streams in the file: put 2>&1 last.
  • sort data.txt > data.txt, which empties the file: the shell truncates it before sort starts.
  • Reading $? too late, after another command, even an echo, has replaced it.
  • Pipelines without pipefail, where an early failure disappears behind a successful last command.
  • Trusting set -e inside functions that are called from a condition.

Exercise 2.1Where does each line go?

For the example's talk, say what reaches the terminal and what ends up in which file for: talk > log 2>&1, talk 2>&1 > log, talk &> log and talk 2> err > out.

Show solution
talk > log 2>&1      terminal: nothing          log: to stdout, to stderr
talk 2>&1 > log      terminal: to stderr        log: to stdout

talk 2> err > out    terminal: nothing          out: to stdout   err: to stderr

In the second line, 2>&1 runs while 1 still points at the terminal, so 2 is pointed at the terminal, and the later > log moves only 1. &> is bash's shorthand for > log 2>&1; it doesn't exist in plain sh, so scripts meant for any shell spell it out. Exercise 2.2The file that emptied itself

Someone sorts a list in place with sort names.txt > names.txt, and finds names.txt empty afterwards. Explain what happened, and give two correct ways to do it.

Show solution
sort -o names.txt names.txt                          # sort can write over its own input
sort names.txt > names.txt.new && mv names.txt.new names.txt   # works for any command

Redirections are set up by the shell before the command starts, and > empties its file. So by the time sort opened names.txt to read it, it was already empty, and sorting nothing produced nothing: running the line leaves the file at 0 bytes. sort -o is safe because sort reads all its input before it opens the output. The general pattern, writing to a new file and renaming it over the old one only if the command succeeded, works for any program, and the && means a failed command leaves the original untouched. The rename is atomic, as chapter 5 explains, so nothing ever sees a half-written file.

Exercise 2.3The failure that disappeared

A build script runs make 2>&1 | tee build.log, and the job is marked successful even when make fails. Explain why, and fix it two ways: for the whole script, and for this one line.

Show solution
set -o pipefail                      # for the whole script: any failure fails the pipeline
make 2>&1 | tee build.log

make 2>&1 | tee build.log            # for one line: check make's own status
status=${PIPESTATUS[0]}
[ "$status" -eq 0 ] || { echo "build failed with status $status" >&2; exit "$status"; }

The pipeline's status is tee's, and tee succeeds whenever it can write the log, so make's failure is lost. With pipefail, the pipeline fails if any part fails: running false | wc -l gives status 0 normally and 1 with pipefail. PIPESTATUS gives each command's status separately, so the script can report make's own code. It has to be copied straight away, as here, because the next command replaces it. GitHub Actions adds -o pipefail for exactly this reason when a step names bash as its shell, but not when the shell is left to its default; a script shouldn't depend on where it's run.

Chapter 3

Searching and transforming text

14 min read3 exercises

Most of what you'll want to ask a computer is already written down somewhere as text: in logs, configuration files, code and exported data. Four tools answer most of those questions. find chooses files, grep chooses lines, sed rewrites lines, and awk computes over the fields of each line. With sort, uniq, cut and head between them, a pipeline of five short commands answers questions that would take a page of code. A little knowledge of regular expressions makes all of them more precise. This chapter questions a web server's log and a project folder.

Regular expressions in ten minutes

A regular expression is a pattern that matches text. Most characters match themselves. A . matches any one character; [abc] matches one of a set, [^abc] anything outside it, and [0-9] a range. ^ and $ anchor the pattern to the start and end of the line. Repetition applies to the thing just before it: * means zero or more, + one or more, ? zero or one, and {2,4} between two and four. Parentheses group, and | means "or", so ^(GET|POST) /api/ matches lines that start with either word followed by /api/. A backslash makes a special character ordinary: \. is a real dot. Matching is greedy: ".*" on "a" and "b" matches the whole thing, not just "a", because .* takes as much as it can.

There are two dialects, and that causes confusion. Basic regular expressions, the default for grep and sed, treat +, ?, |, () and {} as ordinary characters unless they have a backslash. Extended regular expressions, which you get with grep -E and sed -E and which awk always uses, give them their special meaning directly. Use -E everywhere and you only have to remember one. Named classes like [[:digit:]] and [[:space:]] work in both, and in every locale. Chapter 1's globs are a different language: there * means "anything" by itself.

grep chooses lines, find chooses files

grep pattern file prints the lines that match. The options you'll use constantly are -i to ignore case, -v for lines that don't match, -c to count them, -n to show line numbers, -o to print only the matching part, -w to match whole words, -F to treat the pattern as plain text, and -r to search a whole folder, with -l to list only the files. Like every good tool it reports through its exit status too: 0 if something matched, 1 if nothing did, 2 for an error, which is what makes grep -q useful in conditions.

find walks a folder tree and tests each file against an expression. -name '*.py' matches names by glob, and must be quoted, or the shell expands it first. -type f chooses files and -type d folders. -mtime +30 means last modified more than 30 days ago, and -size +10M bigger than ten megabytes. Tests are combined with an implied "and", or with -o for "or". -prune stops find from going into a folder, which is how you skip node_modules or .git. The default action is to print the path. -exec command {} + runs a command on the files it found, with as many names per run as fit, and -delete deletes them.

sed rewrites lines, awk computes over fields

sed, the stream editor, applies editing commands to each line as it passes through. Almost all of its use is substitution: s/old/new/ replaces the first match on each line, s/old/new/g every match, and parentheses in the pattern capture text that \1, \2 put back in the replacement. A command can be limited to some lines by number, 3,5s/a/b/, or by pattern, /ERROR/s/a/b/. With -n, sed prints nothing unless told to with p, so sed -n '/404/p' behaves like grep.

awk is a small programming language for tables of text. It splits each line into fields, $1, $2 and so on to $NF, the last one, at runs of spaces or at the separator given with -F. A program is a list of pattern {action} rules: the action runs on lines that match the pattern, and a missing pattern matches every line. BEGIN and END rules run before the first line and after the last. Variables need no declaring, start at zero or empty, and can be associative arrays, so {n[$1]++} counts lines by their first field. awk was written in 1977 by Aho, Weinberger and Kernighan, whose initials give it its name, and their book about it was updated in 2023.

The example builds a web server's access log of 48 requests, each line holding the client's address, the time, the request, the status, the bytes sent and the milliseconds taken, plus a small project folder. Then it answers questions with one pipeline each.

What the example shows

Each tool does one job, and the pipeline does the rest. cut -d ' ' -f 1,7,9,11 picks fields by number from lines separated by single spaces, which is how it pulled the address, path, status and time from each server error. grep -o printed just the /api/... part of each line, ready for counting. uniq -c counts runs of identical adjacent lines, which is why it always follows a sort. It also pads its counts differently on macOS and Linux, so the example passes them through awk '{print $1, $2}' to print the same everywhere. That's a habit worth having for any output another program will read.

awk does the arithmetic. n[$1]++ counted requests per address, and the END rule printed the totals, in an order awk doesn't promise, so sort -k1,1nr -k2,2 put them in order: numerically by count, highest first, and by address when counts tie, so the result never depends on chance. In $NF + 0 > 1400, adding zero turned 1698ms into the number 1698, because awk reads the leading digits of a string as its numeric value. The averages per status class came from two arrays and a printf, which formats numbers exactly as C's printf does.

Names with spaces need care. xargs reads names from its input and runs a command on them, but by default it splits its input at spaces, so ./old notes.tmp became two names, ./old and notes.tmp, neither of which exists. The file survived. find -print0 ends each name with a zero byte, the one character a file name can't contain, and xargs -0 splits only there. find . -name '*.tmp' -exec rm {} + avoids the problem entirely, by never turning names into text.

GNU, BSD and portability

Linux comes with the GNU versions of these tools, and macOS with the BSD ones. They agree on everything in this chapter's example, and differ in the corners. sed -i edits a file in place on Linux, while macOS needs sed -i ''. grep -P, for Perl-style patterns, is GNU-only, as are many long options. stat and date take completely different flags. Scripts that must run on both should stick to the options POSIX defines, the standard both follow, or check which system they're on. On a Mac, Homebrew's coreutils, gnu-sed and grep packages install the GNU versions with a g in front, gsed and ggrep, if you want Linux behaviour. Two modern tools are worth installing anywhere: rg (ripgrep), a much faster grep -r that skips files ignored by Git, and jq, which does for JSON what awk does for columns.

Common traps
  • find . -name *.py unquoted, which the shell expands before find sees it.
  • uniq without sort, which only merges duplicates that happen to be adjacent.
  • An unescaped . in a pattern, matching any character: grep 2026.03 also matches 2026503.
  • sed -i in a script that must run on both macOS and Linux.
  • Feeding names to plain xargs or to for f in $(find ...), which split them at spaces.

Exercise 3.1Six commands

In 1986, Jon Bentley asked Donald Knuth to write a program that prints the most common words in a text, and Doug McIlroy reviewed the result. Show solution
tr -cs 'A-Za-z' '\n' < story.txt |   # every run of non-letters becomes one newline: a word per line
  tr 'A-Z' 'a-z' |                     # lower case, so "The" and "the" are the same word

  uniq -c |                            # count each run of identical lines
  sort -rn |                           # highest count first
  head -n 10                           # keep the top ten

-c makes tr act on characters not in the set, and -s squeezes each run of them into a single newline. On the two sentences "The cat sat on the mat. The dog sat on the log. A cat and a dog: the best of friends, or the worst? The end." it puts the first with 7, then a five-way tie at 2. Ties come out in reverse alphabetical order, sat, on, dog, cat, a, because -r also reverses sort's final whole-line comparison. McIlroy's point wasn't that Knuth's program was bad. It was that reusable tools, composed, solve most such problems in minutes, and that the pipeline is easy to change: sort -rn to sort -n gives the rarest words instead.

Chapter 4

Scripts that don't break

13 min read3 exercises

A shell script is the cheapest automation there is: the commands you'd type, saved in a file. It's also the easiest to get dangerously wrong, because the shell carries on after errors, splits what it shouldn't and deletes what it's told. A handful of habits make the difference. Stop at the first failure, check the arguments, show what you'd do before doing it, never overwrite or delete without checking, clean up however the script ends, and make it safe to run twice. This chapter writes the kind of script the stage asks for, one that tidies a downloads folder, and puts it through its paces.

A script is a file of commands

A script starts with a shebang line, #!/usr/bin/env bash, which tells the system which program runs the file. env finds bash on your PATH, which matters on a Mac. Its /bin/bash is version 3.2, first released in 2006, kept because later versions use a licence Apple won't ship, so a newer bash, if you install one, lives elsewhere. Make the file executable with chmod +x tidy, and run it as ./tidy, or put it in a folder on your PATH, such as ~/.local/bin, and run it by name. bash tidy works without the execute bit, because then bash only reads the file.

Inside, $1, $2 and so on are the arguments, $# is how many there are, and "$@" is all of them, each kept as a separate word: it's the only correct way to pass a script's arguments on to another command. shift drops the first. For options, the built-in getopts handles -n, combined flags like -nv and options with values. A function is a named group of commands, name() { ...; }, called like any command, with its own $1 and so on. A function's return sets its exit status, like a program's. To give back a value, it prints it, and the caller captures it with $(name args). local keeps a variable inside the function instead of overwriting one outside.

Strict mode

Put set -euo pipefail near the top of every script. -e exits at the first command that fails, with the exceptions chapter 2 listed, instead of carrying on with the next line. -u makes using an unset variable an error, which turns a typo like $flie, or chapter 1's empty $STEAMROOT, into a stop instead of an empty string. pipefail makes a pipeline fail when any part of it does. Together they mean a script that hits something unexpected stops, and stopping is almost always the right thing for a script that runs without anyone watching. When you expect a command might fail, say so explicitly, with || true or an if. And ${1:-} reads a possibly missing argument without upsetting -u.

Failing well, and never destroying data

A script should fail the way a good program does. Messages go to stderr, with >&2, so they don't mix with output. Wrong usage prints a usage line and exits with status 2. Any other failure exits non-zero with a message that names the problem and the value that caused it: tidy: no such folder: Nowhere, not error. Check everything the script relies on before it starts changing things.

Then make destruction hard. Offer a dry run that prints what would happen, and use it first. Move rather than delete, and never overwrite: mv -n refuses to replace an existing file, and choosing a free name first, as the example's free_name does, means the refusal never comes up. Write new files under a temporary name and rename them into place only when complete, so nothing ever sees half a file. Before anything like rm -rf "$dir", check that $dir is set, exists and is what you think it is. Finally, make the script idempotent, safe to run any number of times. Run twice, it should find nothing left to do rather than doing it all again or failing halfway.

Locks and cleanup

Two copies of a script working on the same files at once, perhaps from a timer and from you, will trip over each other. A lock prevents it, and mkdir makes a good one. Creating a folder either succeeds or fails, in one indivisible step, so exactly one copy can create .tidy.lock and the others see that it exists. The lock must be removed however the script ends, and that's what trap is for. trap 'rmdir "$lock"' EXIT runs its command when the script exits: normally, through set -e after an error, or after Ctrl-C. Only kill -9, which nothing can catch, skips it. The same pattern deletes temporary files made with mktemp.

The example writes tidy, a script that sorts the files at the top of a folder into images, documents, archives and other by their extension. Then it runs it on a downloads folder in every way that matters: wrongly, as a dry run, for real, a second time, on a missing folder, and while another run holds the lock. The script is written for bash 3.2, so it runs unchanged on a Mac and on Linux.

What the example shows

It stops before doing harm. With no folder, it printed its usage line to stderr and exited with status 2; with a missing folder, a precise message and status 1; with the lock already taken, it refused rather than racing the other run. None of those runs changed anything, because every check comes before the first move. ${1%/} removes a trailing slash, so tidy Downloads/ works too: the shell's Tab completion adds that slash, so users will type it.

The plan and the run agree, and nothing is lost. The dry run printed exactly the seven moves the real run then made. The report that was already in documents kept its name, and the new one became report (1).pdf. The subfolder projects was skipped because the loop only moves plain files. The order, capital letters first, is the C locale's byte order, the same everywhere. A second run found nothing to tidy, and no lock was left behind. Category names come from a case statement rather than an associative array, because those need bash 4.

Testing a script, and knowing when to stop

Test scripts like any program. bash -n script checks the syntax without running anything, and bash -x script traces every command, as chapter 1's set -x does. ShellCheck reads a script and points out unquoted variables, useless cats, cds without error handling and dozens of other known mistakes. Run it on everything you write. Tests can be shell scripts too, with a framework such as bats, or a Python program like the example, which builds a folder, runs the script and checks the result.

Shell is the right language for gluing programs together and the wrong one for nearly everything else. Google's style guide for shell puts the line at about a hundred lines, or any non-trivial control flow. Past that point, or once you need data structures, arithmetic on anything but whole numbers, JSON, or careful error handling, rewrite it in Python: its subprocess, pathlib and shutil modules do everything a script does, without the quoting.

Common traps
  • No set -u, so a misspelt variable silently expands to nothing.
  • cd somewhere without || exit, so the rest of the script runs in the wrong folder.
  • Parsing the output of ls instead of looping over a glob.
  • Results and messages on the same stream, so another program can't use the results.
  • Bash 4 features, like associative arrays and ${x,,}, in a script that must run on a Mac's bash 3.2.

Chapter 5

Files, paths and links

12 min read3 exercises

A filesystem is a tree of names, and each name points to an inode, the record that holds a file's data, size, owner and permissions, but not its name. A path is directions through the tree. A hard link is a second name for the same inode, and a symbolic link is a small file that holds a path. Keeping those apart explains several everyday puzzles: why renaming a huge file is instant, why a symbolic link can break when nothing it points to was touched, and why deleting a log file doesn't always free the space.

One tree, and directions through it

On Linux and macOS every file is somewhere in a single tree whose root is /. Other disks don't get letters as on Windows; they're mounted into the tree at a folder, such as /Volumes/Backup on a Mac or /mnt/data on Linux. A path that starts with / is absolute: directions from the root. Any other path is relative: directions from the current working directory, which pwd prints and cd changes. Every folder contains two special entries: ., the folder itself, and .., its parent. Section 1 of the example resolves a few paths the way the system does: ../data/./in.csv from /home/learner/project is /home/learner/data/in.csv. cd - returns to the previous folder, and ~ is your home folder.

Names starting with a dot are hidden from ls and from *, which is all "hidden" means. Linux treats README.md and readme.md as different names. A Mac's disk, by default, does not: it remembers the case you typed, but finds the file whatever case you ask for. So a Git repository containing both names, which is fine on Linux, breaks on a Mac, where only one of them can exist.

Names and inodes

A folder is a table that maps names to inode numbers, and the inode holds everything else about the file. ls -i shows the numbers, and stat shows the rest. Because the name isn't part of the file, renaming a file within one filesystem only rewrites an entry in a folder's table, which is why mv renames a ten-gigabyte video instantly. Moving it to another disk copies all the data and then deletes the original, because inode numbers only mean something within one filesystem. The rename is also atomic: anyone looking sees either the old name or the new one, never something in between. That's why "write a new file, then rename it over the old one" is the safe way to replace a file, as chapter 2 used.

Hard links and symbolic links

ln existing newname makes a hard link: another entry, in the same or another folder, pointing at the same inode. Both names are equally real; neither is the original. The inode keeps a link count, the number of names pointing at it, and the file's data is freed only when that reaches zero. Hard links can't cross filesystems, and you can't make them to folders.

ln -s target linkname makes a symbolic link, or symlink: a tiny file whose contents are a path. Whenever something opens the link, the system reads that path and follows it, so a symlink can point at a folder, at another disk, or at nothing at all, in which case it's broken, or dangling. ls -l shows a symlink as name -> target, and readlink prints the stored path. A relative target is resolved from the folder the link is in, not from wherever you were when you made it, which is the most common way dotfile links go wrong.

The example makes the commands' effects visible. It runs each command in bash, then inspects the results with Python's os module, labelling inodes A, B and so on, because the real numbers differ on every machine.

What the example shows

A hard link is the same file. After ln notes.txt hard.txt, both names showed inode A and two names; writing version 2 through hard.txt changed what notes.txt contains, because there's only one file. Renaming notes.txt left inode A and its contents exactly as they were. Deleting renamed.txt dropped the count to one name, and hard.txt still holds the data. The symlink went the other way. It held the path notes.txt all along, so the moment that name stopped existing, the link broke, though nothing it once reached had been deleted at the time.

A relative link is read from where it lives. In section 4, both links were made from the same folder, but stored different text. home/.zshrc holds dotfiles/zshrc, which, read from inside home, means home/dotfiles/zshrc, which doesn't exist. ../dotfiles/zshrc climbs out of home first, and works. And section 5 showed the reason a full disk can survive a cleanup. After rm big.log the name was gone, but the program that had the file open could still use all million bytes, and the inode had zero names. The space returns only when that program closes the file or exits.

Where things live

The layout of the tree is conventional, and knowing it saves searching. Programs live in /usr/bin and /bin, and ones you install yourself in /usr/local/bin; on Apple silicon Macs, Homebrew uses /opt/homebrew. System configuration lives in /etc, logs in /var/log, temporary files in /tmp. Your own files and settings are under your home folder, /Users/you on a Mac and /home/you on Linux, and many programs keep their settings in ~/.config, which chapter 8 uses. df -h shows how full each mounted filesystem is, and du -sh folder how much a folder uses; when they disagree, a deleted file that's still open is the usual reason.

Common traps
  • A relative symlink whose target was written relative to the wrong folder.
  • Deleting a big log file that a running program still has open, and expecting the space back.
  • Two names that differ only in case, which are one file on a Mac.
  • Assuming mv is instant and safe everywhere: across disks it copies, and can be interrupted halfway.
  • Editing a file through a hard link and forgetting the other name changes too.

Chapter 6

Permissions

11 min read3 exercises

Every file has an owner, a group, and nine permission bits: read, write and execute, for the owner, for the group, and for everyone else. On a file the bits mean what they say. On a folder they mean something different, and that's where the surprises live: deleting a file needs permission on its folder, not on the file itself. This chapter decodes the bits, tries what each one allows, and covers the commands that change them, the default that sets them, and the account that ignores them.

An owner, a group and nine bits

ls -l starts each line with ten characters, such as -rwxr-x---. The first is the type: - for a file, d for a folder, l for a symbolic link. The other nine are three groups of three, r for read, w for write and x for execute, with - for a missing permission. The first group applies to the file's owner, the second to members of its group, and the third to everyone else, called others. ls -l also shows the owner's and group's names, and id shows who you are and which groups you're in.

Each group of three is also a number from 0 to 7, adding 4 for r, 2 for w and 1 for x, so the whole mode is three digits: rwxr-x--- is 750. You'll meet a few constantly: 644 for ordinary files, 755 for programs and folders, 600 for private files and 700 for private folders. Exactly one group applies to you, checked in order: the owner's if you own the file, otherwise the group's if you're in its group, otherwise others'. So an owner with fewer rights than the group gets the owner's rights.

Changing them, and the default

chmod changes the bits, either with a number, chmod 640 plan.txt, or symbolically: u, g, o and a for user, group, others and all, then +, - or =, then the letters. So chmod u+x makes a file executable for its owner, and chmod go-r stops anyone else reading it. -R applies a change to a whole tree, and a capital X adds execute only to folders and to files that were already executable, which is usually what you want. chown changes the owner, which only the administrator can do, and chgrp the group.

New files get their bits from the umask, a mask of permissions to remove from everything a program creates. Programs ask for 666 for files and 777 for folders, and the umask takes bits away. The usual umask, 022, removes write for the group and others, giving 644 and 755. A umask of 077 makes everything private, 600 and 700, which section 2 of the example shows. umask with no argument prints yours; set it in your shell's startup file, as chapter 8 does, to change it everywhere.

The example sets bits with chmod and umask and reads them back, then tries real operations as an ordinary user and reports only whether each was allowed. The exact wording of "Permission denied" differs between systems, but the decisions don't.

What the example shows

On a file, the bits mean what they say. With mode --w-------, the owner couldn't read secret.txt; with r--r--r--, appending to fixed.txt was refused. ./hello.sh failed with status 126, chapter 2's "found but not executable", while bash hello.sh ran it, because then bash is the program and only needs to read the file. Execute permission is a statement of intent, not a security barrier. Anyone who can read a script can run it.

On a folder, they mean something else. r lets you read the folder's list of names, so echo box/* worked on rw-------, but without x nothing inside could be reached: cat box/note.txt was refused. On a Mac, even ls box complains in that state, because it tries to look at each entry, which needs x. With -wx, the opposite: the names can't be listed, but a file whose name you already know can be opened. w on a folder means changing its list of names: without it, rm box/note.txt was refused even though the file itself was fine. And the last line is the surprise: a read-only file was deleted, because its folder was writable. Deleting a file removes a name from a folder, as chapter 5 explained, so it's the folder's permission that counts. Plain rm would have asked first, at a terminal; -f skipped the question, not the rule.

The administrator, and three special bits

The administrator account, root, user number 0, bypasses almost all of these checks, which is why the example refuses to run as root: its results would be meaningless. sudo command runs one command as root, after asking for your password, and records that you did. Use it for system changes, installing a package or editing a file in /etc, and never to make an error in your own folders go away. sudo pip install or sudo npm install leaves root-owned files in your home folder that later commands, run as you, can't change, and the fix is to correct the ownership, not to use sudo again.

Three more bits exist. Setuid on a program makes it run as its owner: passwd is owned by root and setuid, so that you can change your own password in a file only root may write. Setgid on a folder, on Linux, makes new files inside it belong to the folder's group, which is how shared project folders work; macOS always does that, setgid or not. And the sticky bit on a folder, shown as a t in drwxrwxrwt, lets everyone create files there but each person delete only their own, which is what keeps /tmp civil. A Mac adds extended attributes, shown as @ after the mode, and access control lists, shown as +; xattr and ls -le show them.

Common traps
  • chmod -R 777 to make an error disappear, which lets every user on the machine change everything.
  • sudo on tools that write to your home folder, leaving files you can no longer change.
  • Forgetting x on a folder, so readable files inside it can't be reached.
  • Thinking a read-only file is safe from deletion: its folder decides.
  • Private keys and tokens readable by others, which SSH and many other programs refuse to use.

Chapter 7

Processes, the environment and PATH

12 min read3 exercises

Every command runs as a process, started by the shell, and each process gets its own copy of the environment, a list of NAME=value strings inherited from its parent. Copies flow down to children and never back up. That's why cd and export must be part of the shell itself, and why a script can't change the folder you're in. PATH is one of those variables: a list of folders searched in order. It explains every "command not found", and every time the wrong version of a program runs.

Processes

A process is a running program: its code, its memory, its open files, its current folder, and a number, the process ID, that names it. Every process except the first has a parent, the process that started it, and ps, top or the friendlier htop show them all. When you type a command, the shell makes a copy of itself, and the copy replaces its own program with the one you asked for, keeping its open files, its folder and its environment. That is how a child inherits everything from chapter 2's redirections. When the child exits, the shell receives its exit status, and shows the prompt again.

A command ending in & runs in the background while you carry on; jobs lists them, fg brings one back, and Ctrl-Z pauses the current one so that bg can continue it in the background. Processes are stopped with signals. Ctrl-C sends SIGINT, kill 1234 sends SIGTERM, a polite request to exit that a program can catch to clean up, as chapter 4's trap did. kill -9 1234 sends SIGKILL, which can't be caught and leaves no chance to clean up, so it's the last resort, not the first.

Variables and the environment

x=1 makes a shell variable, which only this shell can see. export x, or export x=1 in one go, marks it to be copied into the environment of every program the shell starts from then on. env or printenv lists the current environment, and unset x removes a variable. Putting assignments before a command, LANG=C sort names.txt, sets them in that one command's environment and nowhere else. By convention, environment variables have upper-case names. Some are shared by everything: HOME, PATH, EDITOR, LANG and TZ. Others belong to one program, like the GIT_ variables the Git examples use to fix names and dates.

Down, never up

A child gets a copy of its parent's environment, at the moment it starts. Whatever it changes afterwards, in its variables or its current folder, changes only its copy, and disappears when it exits. Nothing in the system lets a child reach back into its parent. So cd can't be an ordinary program. A cd program would change its own folder and then exit, leaving yours exactly where it was. That's why cd, export, source and a few others are builtins, commands the shell runs itself. type name says what a name is: a builtin, an alias, a shell function, or a program and where it is.

The same rule decides what a script can do to your shell. Running bash setup.sh, or ./setup.sh, starts a child, so its cd and export vanish with it. Sourcing it, source setup.sh or . setup.sh, runs its lines in your current shell, as if you'd typed them, so their effects stay. Startup files, and virtual environments' activate scripts, are sourced for exactly this reason.

PATH

When you type a command name without a / in it, the shell looks in each folder listed in PATH, separated by colons, in order, and runs the first executable file with that name. A name containing a slash, like ./tidy or /usr/bin/python3, is used as given, with no search. type -a name lists every match in search order, and command -v name prints the one that would run, which makes it the reliable check in scripts. which is a separate program on many systems and can disagree, because it doesn't know about your aliases and functions. To add a folder, put it at the front, where it wins, in the startup file chapter 8 sets up: export PATH="$HOME/.local/bin:$PATH". Never add ., the current folder: any folder you cd into could then supply a fake ls.

Bash also remembers where it last found each command, so as not to search every time. If you install a program into a folder that comes earlier in PATH than the version you've been running, bash keeps running the old one until you type hash -r (in zsh, rehash) or open a new shell. Changing PATH itself clears that memory. Version managers for Python, Node and the rest, and Python's virtual environments, all work the same way: they put their own folder at the front of PATH.

The example builds two folders, bin1 and bin2, each with its own program called greet. It runs them with PATH in each order, passes variables to child shells, runs and sources a script, and finally starts bash in four ways, with startup files that announce themselves.

What the example shows

The first match wins, and builtins aren't on PATH at all. With bin1 first, greet ran bin1's program; reversed, bin2's, and type -a listed both in order. With neither folder on PATH, status 127. type called cd and export builtins, which is why no PATH change can ever break them.

Only exported variables reach a child, and nothing comes back. The unexported x was invisible to the child bash; exported, it arrived. x=2 bash -c ... gave the child a value the parent never had. The child's x=99 and cd / changed its copy only. Running setup.sh left GREETING empty and the folder unchanged, and sourcing it did both.

Startup files depend on how the shell started. A script reads no startup files. A login shell, which is what you get when you log in, read ~/.bash_profile; an interactive shell, one you type into, read ~/.bashrc. And an interactive login shell read only ~/.bash_profile, which is the surprise. Terminal on a Mac starts a login shell in every window, so settings put only in .bashrc seem to be ignored there, while most Linux terminals start non-login shells, which read only .bashrc. The usual fix is a line in ~/.bash_profile that sources ~/.bashrc. Zsh, the default on Macs since 2019, has its own set: ~/.zshenv always, ~/.zprofile for login shells, and ~/.zshrc for interactive ones. Put environment settings such as PATH in the login file, and interactive ones, aliases and the prompt, in the rc file.

Common traps
  • Expecting a script to change your shell's folder or variables: source it, or make it a function.
  • Setting a variable without export and wondering why a program can't see it.
  • Adding to PATH in a file that every nested shell reads, so it grows each time.
  • Trusting which over type -a, which knows about aliases, functions and order.
  • A stale command after installing a new version: hash -r or a new shell.

proj() {
  cd ~/code/"$1" || return
}

The script ran as a child process. It changed its own folder, which it's allowed to do, then exited, and its folder went with it. Your shell's folder was never touched, because a child can't change its parent. A function defined in your startup file runs inside your shell, so its cd is your cd. || return makes it stop with a failure status if the folder doesn't exist. An alias would work for a fixed folder, but can't take an argument in the middle. The same reasoning explains why tools that change your environment, from nvm to Python's activate, are shell functions or sourced scripts, never ordinary programs.

Exercise 7.3The PATH that grew

# fix 2, for bash or any shell: only add the folder if it's missing
add_path() { case ":$PATH:" in *":$1:"*) ;; *) PATH="$1:$PATH" ;; esac; }
add_path "$HOME/bin"

.zshrc runs for every interactive shell, and each one inherits the PATH its parent already extended. So a shell started inside another one, in a terminal multiplexer, in an editor's terminal, or by typing zsh, adds the folder again. The duplicates are mostly harmless, but they make PATH hard to read and slow every failed lookup. The check prints each folder that appears more than once. In zsh, path is an array linked to PATH, and typeset -U makes it unique. The case pattern works in any shell: called three times, it added the folder once. Better still, set PATH in the login file, ~/.zprofile, which runs once per login rather than once per shell.

Chapter 8

Dotfiles

10 min read3 exercises

Your tools read their settings from small text files in your home folder, named with a leading dot so they stay out of the way. Kept in a Git repository, with a script that links each one into place, they turn setting up a new laptop from a lost day into ten minutes, and they're the first half of this stage's deliverable. The script has to be safe to run twice, must never destroy what's already there, and the repository, which you'll make public, must never contain a secret.

What dotfiles are

Each program decides where it looks for its settings, and most look in your home folder: ~/.zshrc and ~/.bashrc for the shells, ~/.gitconfig for Git, ~/.vimrc for Vim, ~/.ssh/config for SSH. Newer programs follow the XDG convention and keep their files under ~/.config, so Git also reads ~/.config/git/config and ~/.config/git/ignore, and Neovim reads ~/.config/nvim. A program's manual page lists its files, usually in a section called FILES, which is the place to look when you don't know where a setting lives.

What to put in them

Start small and grow the files by noticing. Each time you type something long twice, or fix the same annoyance again, add a line, with a comment saying why. A useful first set covers three files. In the shell's: a PATH that includes ~/.local/bin, from chapter 7; EDITOR; a long history that's shared between terminals; a few aliases, such as ll for ls -lah; chapter 7's proj function; and a prompt that shows the current Git branch. In Git's: your name, init.defaultBranch, pull.ff only, and an alias like lg = log --graph --oneline --all, which you'll type a thousand times in Part III. In your editor's: whatever you've changed from its defaults. Reading other people's dotfiles on GitHub is a good source of ideas, and copying a stranger's five-hundred-line configuration whole is how you end up with a shell you can't explain.

A repository, and links into it

Keep the files in one folder, such as ~/dotfiles, under Git, named without their dots so they're visible: zshrc, gitconfig. Then make the real locations symbolic links into the repository, as chapter 5 described. Every program reads the repository's file through its link, so editing ~/.zshrc edits the tracked file, and git diff shows what you changed. Copying the files into place instead works once, and then the copies and the repository drift apart. An install script makes the links. Tools such as GNU Stow, chezmoi and yadm do the same job with more features. Write your own first, because it's twenty lines and you'll understand every one.

The example builds a small repository with an install script and three settings files, and a home folder that already has an old .zshrc. It installs twice, then checks the result the only way that matters: by asking Git what it now reads.

What the example shows

The script is safe to run any number of times. On the first run it found a real file at ~/.zshrc, moved it into ~/.dotfiles-backup and linked the repository's version in its place. The second run found every link already pointing at the right file and changed nothing. That's the check [ "$(readlink "$dst")" = "$src" ]. ${2//\//_} replaces each slash in a path with an underscore, so a backup of .config/git/ignore gets a flat, unambiguous name. And the first line, built from BASH_SOURCE and pwd -P, finds the repository's absolute location wherever the script is run from, which exercise 8.1 explains.

Shared settings and private ones stay apart. git config --show-origin showed the name coming from the linked ~/.gitconfig and the email from ~/.gitconfig.local, which the shared file pulls in with an [include] but which isn't in the repository. That's the pattern for anything that differs between machines or shouldn't be public: a work email, a signing key, a company's proxy. The shell's version is a last line in zshrc, [ -f ~/.zshrc.local ] && source ~/.zshrc.local. The global ignore file kept .DS_Store out of a brand-new repository without any setup there. In the dotfiles repository itself, *.local in .gitignore kept a stray secrets.local out of the commit.

Secrets, and the README

A dotfiles repository is meant to be public, so treat everything in it as published. Never commit API tokens, passwords, private SSH keys, ~/.netrc or a shell history; keep them in local files, as above, or in your system's keychain or a password manager. Before your first push, and from time to time after, search for anything that looks like a secret, with git grep -iE 'token|secret|passw|api_?key' or a scanner such as gitleaks. Bots search public repositories for keys within minutes of a push, so a leaked key has to be treated as stolen at once, which is what exercise 8.2 is about.

Then write the README for a stranger who has just cloned it. Say what's in the repository and what each file configures. Give the one command that installs it, say exactly what that command changes and how to undo it, and list the systems you've tried it on. Your future self, setting up a new machine in a hurry, is the stranger.

Common traps
  • A token, key or private detail committed to a public repository.
  • Copying someone's entire configuration instead of growing your own a line at a time.
  • An install script that overwrites existing files instead of backing them up.
  • Links that store a relative path that only works from one folder.
  • Settings for one system only, such as Homebrew's paths, applied unconditionally on another; check with uname.

#!/usr/bin/env bash
# uninstall.sh: remove the links install.sh made, and put back what it backed up.
set -euo pipefail
repo=$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd -P)
backup="$HOME/.dotfiles-backup"
unlink_one() {   # unlink_one FILE-IN-REPO PATH-UNDER-HOME
  local src="$repo/$1" dst="$HOME/$2" saved="$backup/${2//\//_}"
  if [ -L "$dst" ] && [ "$(readlink "$dst")" = "$src" ]; then
    rm -- "$dst"; echo "removed     ~/$2"
  else
    echo "left alone  ~/$2 (not our link)"; return
  fi
  if [ -e "$saved" ] || [ -L "$saved" ]; then mv -- "$saved" "$dst"; echo "restored    ~/$2"; fi
}

Chapter 9

Git's objects

11 min read3 exercises

Git is a store of objects, each named by a hash of its own contents, plus a few names that point into it. A blob is a file's contents, a tree is a folder listing, and a commit is a tree together with its parent commits, an author and a message. Once you see that, Git's behaviour stops being arbitrary. A commit is a snapshot of the whole project, not a list of changes. Identical files are stored once. And changing anything in the past changes the name of every commit after it. This chapter builds all three kinds of object by hand, and gets exactly the names Git does.

Names made from contents

A hash function turns any amount of data into a short, fixed-size number, such that the same input always gives the same number, and the smallest change to the input gives a completely different one. Git uses SHA-1, whose numbers are written as 40 hexadecimal digits, and names every object by the hash of a short header, its type and size, then a zero byte, then its contents. So the name of an object is a summary of what's in it: two people who commit the same file get the same blob name without ever communicating, and if a single bit of a stored object changes, its name no longer matches and Git notices. This is called content addressing. Objects are kept compressed in .git/objects, in a folder named after the first two digits, and later packed together into packfiles to save space.

In 2017, researchers produced the first two different files with the same SHA-1 hash, at a cost of thousands of years of computing time. Git responded by using a hardened SHA-1 that detects that kind of attack, and it now also supports repositories that use SHA-256 throughout. New repositories still use SHA-1 by default.

Blobs, trees and commits

A blob holds a file's contents and nothing else: not its name, not its permissions. A tree holds a folder's listing, one entry per name. Each entry has a mode, 100644 for an ordinary file, 100755 for an executable one, 40000 for a subfolder and 120000 for a symbolic link, then the name, then the id of the blob or tree it refers to. A commit is a few lines of text: the id of the tree for the whole project, the ids of its parent commits, none for the first, two for a merge, then the author and committer with timestamps, a blank line, and the message. A fourth type, the annotated tag, names a commit and adds a message of its own.

Between your files and a commit sits the index, also called the staging area. git add stores the current contents of a file as a blob, and records its name and id in the index. git commit turns the index into trees, writes a commit pointing at the top tree, and moves the current branch to it, which chapter 10 covers. git status compares three things: the last commit's tree, the index, and the files in your folder, which is why a file can be "staged" and "modified" at once.

The example computes object names in Python the way Git does, with hashlib, and checks each one against Git's own answer. Every commit gets a fixed author and time, so the 40-digit names printed here are the ones you'll get on your machine.

What the example shows

Git's names are just hashes, and you can compute them. The blob for hello and a newline is ce0136... whether you compute it in Python or ask git hash-object, and the file Git stored, decompressed, is exactly the header, a zero byte and the contents. The tree computed by hand, two entries sorted by name with their modes and raw ids, matched git write-tree. The commit was simpler still: four lines of text and a message. Note that cat-file -p prints the folder's mode as 040000, padded for display, while the stored tree says 40000. Hashing the displayed form would give the wrong answer.

Snapshots share what didn't change. After the README changed, the second commit had a new top tree and a new README blob, but its src folder was the very same tree, 5234dadb27, as the first commit's, because nothing in it changed. Adding copy.py, an exact copy of app.py, didn't add an object at all: both names point to one blob. Nine objects hold two complete snapshots: four blobs, three trees and two commits.

What follows from the model

Several things that puzzle people about Git follow directly. A commit doesn't contain a diff; when you ask for one, Git computes it by comparing two trees. Packfiles do store objects as differences from similar objects, but that's a storage detail, invisible to everything else. Renames aren't recorded: a rename is a blob that disappears from one path and appears at another, and git log --follow and git diff detect it by similarity. Empty folders can't be committed, because a tree lists files and subfolders, and an empty one has nothing to list, which is why projects keep a placeholder file such as .gitkeep. And history can't be edited, only replaced. A commit's name depends on its parent's name, so changing an old commit gives it a new name, which changes its child, and so on to the end, as exercise 9.3 explains.

Common traps
  • Thinking a commit stores changes rather than a snapshot of every file.
  • Expecting Git to track renames or empty folders, which it records neither of.
  • Committing large binary files that change often: every version is kept for ever. Git LFS is the tool for those.
  • Expecting git add to stage later edits: it records the contents at that moment.
  • Editing files under .git by hand, instead of with the commands that keep it consistent.

Exercise 9.3Why history can't be changed

A branch has three commits, A, B and C. You fix a typo in A's message. What happens to B and C, and why does that matter if someone else already has them?

Show solution

A's message is part of A's contents, so the fixed commit has a new name, A'. B's contents include its parent's name, which is now A' instead of A, so B must be rewritten as B', with a new name, and C likewise as C'. Changing one commit renames every commit after it. That chain is what makes Git's history trustworthy: a commit's name vouches for the whole history behind it, so two repositories that agree on one name agree on everything before it. It's also what makes rewriting shared history disruptive. Anyone who already has A, B and C still has them, and from Git's point of view your A', B', C' are unrelated new commits. Their next merge will join both copies together, with the same changes appearing twice. Chapter 11's rule follows: rewrite only commits nobody else has.

Chapter 10

Refs, branches and HEAD

10 min read3 exercises

A branch is a small file that holds one commit's name, and HEAD is a file that holds the name of the current branch. Committing writes a new commit whose parent is the current one, then moves the current branch forward to it. Almost every other command that seems to rearrange history only moves these names around: switching branches, detaching HEAD, resetting. And nothing you've committed is lost when a name moves, because the reflog remembers everywhere each name has been.

Names for commits

Forty-digit names are for machines. People use refs, named pointers to commits. A branch called main is the file .git/refs/heads/main, which contains one commit's name and a newline: that's all a branch is. Tags live in refs/tags, and chapter 13's remote-tracking branches, like origin/main, in refs/remotes. Git sometimes packs many refs into one file, .git/packed-refs, for speed, and newer versions can store them in a different format altogether. So read refs with git rev-parse main rather than by opening files, as the example does only to show what's there.

Git understands a small language for naming commits relative to others. HEAD~1 is the current commit's parent, and HEAD~3 its great-grandparent, following first parents. HEAD^2 is a merge's second parent. main@{1} is where main pointed before its last move, from the reflog. Any unambiguous prefix of a commit's name works too, so the seven-digit abbreviations Git prints are enough to type.

Committing moves a branch

HEAD normally contains ref: refs/heads/main, meaning "the current branch is main". When you commit, Git writes a commit whose parent is the commit main points to, then rewrites the file refs/heads/main to hold the new commit's name. No other branch changes. That's the whole of "being on a branch": your next commit will move that name. Making a branch writes one tiny file, so branches cost nothing, and it's normal to make one for every piece of work, however small. git switch name moves HEAD to another branch and updates your files to match its commit. The older git checkout does that too, along with several unrelated things, which is why newer versions of Git split it into switch and restore.

Detached HEAD

HEAD can also hold a commit's name directly, which Git calls a detached HEAD. You get one when you switch to a commit rather than a branch, to look at an old version, and Git puts you in one during a rebase or a bisect. You can commit there, but no branch moves, so the new commits are known only to HEAD. Switch to a branch, and they're no longer reachable from any name. They're not deleted, but they're easy to lose track of, which is why Git warns you when you leave. git switch -c name gives the commits a branch and makes them safe.

The example makes the files visible. It prints the contents of HEAD and of the branch files as it creates a branch, commits on it, detaches HEAD, commits there and switches away, then finds the "lost" commit in the reflog and gives it a name. Last, it moves a branch with reset and moves it back.

What the example shows

A branch is the name of one commit, and it moves. refs/heads/main held c7ebc43f...; making feature wrote a file with the same contents; committing C on feature changed that file and left main's alone. The graph's labels, (HEAD -> feature) and (main), are exactly those files drawn on the commits they name.

Unlabelled commits fall out of view, not out of the repository. After detaching at B and committing D, switching back to main left D on no branch, and git log --all, which starts from every ref, no longer showed it. But the reflog for HEAD records each move with the reason, commit: D: an experiment and checkout: moving from ..., and one git branch made D reachable again, joining the graph as a fork from B. Finally, reset --hard moved main back to A, which made B unreachable too. main's own reflog, 87b02ea, c7ebc43, 87b02ea, showed where it had been, and main@{1} put it back.

reset, and what really can be lost

git reset target moves the current branch, along with HEAD, to another commit, and its three modes say what happens to your files. --soft moves only the branch: the undone commit's changes stay staged, ready to be committed again, which is a way to squash several commits into one. --mixed, the default, also resets the index, so the changes stay in your files but unstaged. --hard also overwrites your files to match. That's the one dangerous command in this chapter, because changes you never committed aren't in any object, so no reflog can bring them back. Before a --hard reset, git stash saves uncommitted work as a commit you can restore. For files alone, git restore file discards a file's unstaged changes, and git restore --staged file unstages it.

Commits themselves are very hard to lose. They stay in the repository as long as a ref or a reflog entry leads to them. Reflog entries are kept for 90 days by default, or 30 for commits that are no longer reachable, and only after that can Git's garbage collection delete them. In practice, if you committed it in the last month, it's still there.

Common traps
  • Committing on a detached HEAD and switching away without making a branch.
  • git reset --hard with uncommitted changes, the one loss no reflog can undo.
  • Using reset on commits already pushed; chapter 12's revert undoes them without rewriting history.
  • Thinking git branch -D deletes the commits; it deletes a name, and prints the commit it pointed to.
  • Reading .git/refs in scripts instead of asking git rev-parse.

Chapter 11

Merging, rebasing and conflicts

11 min read3 exercises

Merging combines two lines of work by comparing each with the last commit they share, the merge base. A change made on only one side is taken. A place changed on both sides, in different ways, is a conflict: Git can't know which you meant, so it marks the spot and asks you. Rebasing does something else: it replays your commits on top of the other line of work, as new commits with new names. Both can produce the same files. They differ in the history they leave behind, and in who gets hurt when they're used on commits other people already have.

Two lines of work

Two branches that have each gained commits since they last agreed have diverged. The commit they last agreed on is their merge base, which git merge-base main lunch finds by walking back through both histories. If one side has no commits of its own, there's nothing to combine: merging just moves the branch forward to the other's tip, a fast-forward, and no merge commit is made. Otherwise Git performs a three-way merge and records the result in a merge commit, which has two parents and so keeps both histories.

The three-way merge

For each part of each file, Git looks at three versions: the merge base, ours (the branch you're on) and theirs (the one being merged in). The rule is simple. If neither side changed it, keep it. If only one side changed it, take that side's version: the other side's version is just the old one. If both sides made the same change, take it once. If both changed it differently, it's a conflict. Comparing with the base is what makes this work. With only the two tips, Git couldn't tell "I changed this line" from "you changed it", and every difference would be a question. Git first lines the versions up with a diff, so it works on hunks, runs of changed lines, rather than line numbers, and inserted or deleted lines don't throw it off. Changes that touch or sit right next to each other count as the same hunk, so two edits on neighbouring lines conflict even though they don't overlap.

The example works on a seven-line menu. Two branches change different lines and merge cleanly, then a third changes the same line as one of them and conflicts. A fourth moves forward without a merge commit, and two last commits are rebased onto main. Each command happens a minute after the last, so every id is reproducible.

What the example shows

The rule, line by line. The table in section 1 is the three-way merge made visible. Line 2 changed only on lunch, so it was taken from lunch; line 5 changed only on main, so it stayed; everything else agreed. Git's merged file matched the rule on every line, and Git asked nothing.

A conflict is a question Git leaves in the file. Since the merge base, main had changed line 2 to Sourdough, and dinner had changed it to Garlic bread. git merge exited with status 1 and listed menu.txt as unmerged. In the file, between <<<<<<< HEAD and ======= is our version, and between that and >>>>>>> dinner theirs; everything outside the markers merged normally. Resolving means editing the file into what it should be, here a line that keeps both ideas, then git add and git commit, which made the merge commit. The graph shows both merges, each with two parents.

A rebase makes new commits. tea was made from main's tip, so merging it was a fast-forward: main moved to the same commit, with no merge commit. drinks had been started from the very first commit. Rebasing it onto main replayed its two commits on top of main's tip. Each came out with a new id, because its parent and its tree changed, as chapter 9 predicted, but the lines each one added and removed were exactly the same. The old commits still exist, unreferenced, until the reflog lets them go. Afterwards main fast-forwarded to drinks, and the newest part of history is a straight line.

Resolving conflicts well

A conflict means two people had different intentions for the same lines, so resolve it by understanding both, not by picking a side. git log --merge -p file shows the commits on each side that touched the file. Setting merge.conflictStyle to zdiff3 adds a third section to each conflict, the base version, so you can see what each side changed rather than just what each side ended with. It's the most useful Git setting few people know, and belongs in your dotfiles. Once the file is right, run the tests before committing, because a merge can be textually clean and still wrong: one side renames a function while the other adds a new call to it. If it gets confusing, git merge --abort or git rebase --abort puts everything back as it was. git diff --check catches leftover markers before you commit them.

Merge or rebase?

Both are good tools for different jobs. Rebase your own work to keep it current and tidy before you share it. Replaying your unpushed commits on top of the latest main means your eventual merge is simple, and an interactive rebase, git rebase -i, lets you reorder, combine and reword them first. Merge to combine shared work, because a merge adds a commit and changes none. And follow the one rule that matters: never rebase commits that other people already have. To them, your rebased commits are new and unrelated, and their next pull brings in both versions. git pull --rebase is safe, because it only replays the local commits you haven't pushed.

Common traps
  • Committing conflict markers; git diff --check finds them.
  • Rebasing a branch that others have pulled, which duplicates its commits for everyone.
  • Resolving by taking one side wholesale without reading what the other side changed.
  • Long-lived branches that drift until merging them takes days; integrate often.
  • Forgetting that --abort exists, and improvising in the middle of a merge.

Your colleague's commits sit on top of your old commits, A, B and C, while the branch on the server now holds new ones, A', B' and C', with the same changes and different ids. Chapter 12

History as a debugging tool

11 min read3 exercises

A repository's history isn't just a backup. It's the best debugging tool you have for the bug that begins "it used to work". git bisect searches history for the commit that broke something, automatically if you give it a test, and finds it among a thousand commits in ten steps. git log -S finds the commits that added or removed a piece of text, and git blame says which commit last changed each line, which leads to why. All three are only as good as the history they search: small commits, with messages that explain why.

Reading history

git log shows commits newest first, and a handful of options turn it into a query. --oneline gives one line per commit, --graph --all draws every branch, -p adds each commit's changes, and --stat lists the files each touched. -n 5, --since=2.weeks and --author=Ada limit it, and -- path at the end limits it to commits that changed one file or folder. git log main..feature lists commits on feature that aren't on main, which is what a pull request contains, and git show displays one commit in full. Put a lg alias for log --graph --oneline --all in your dotfiles and you'll use it every day.

Bisect: binary search over history

When something worked at an old commit and doesn't now, the commit that broke it is somewhere in between, and checking every one would take as long as there are commits. git bisect does a binary search instead. You mark one commit good and one bad, and Git checks out the commit halfway between them, on a detached HEAD. You test it and say git bisect good or git bisect bad, which throws away half the suspects. Repeat, and after about log2 of the number of commits, Git names the first bad one: ten steps for a thousand commits, twenty for a million. git bisect reset returns you to where you started.

Better still, give bisect a command and let it do the testing: git bisect run ./check.sh. Its exit status decides. 0 means good, 125 means "this commit can't be tested, skip it", and any other status from 1 to 127 means bad. Recent versions of Git also stop with an error if the test can't even run, status 126 or 127, on the commit you marked good. That catches a missing or non-executable script before it can blame an innocent commit. But nothing can catch a test that runs and checks the wrong thing.

The example builds a small repository with forty commits. The first adds a slug() function that turns a recipe's title into a web address, and commit 27, "Simplify slug()", quietly breaks it for accented letters. A test script checks one title. The example lets bisect run find the culprit, then asks log -S and blame the same question, and undoes the damage with revert.

What the example shows

Bisect needed five tests. It tried commit 20, which was good, then 30, bad, 25, good, 27, bad, and 26, good, and concluded that 27 was the first bad commit. That's every possible culprit among 39 suspects, commits 2 to 40, settled in five runs of the test, with no human involved. On a real project, with a test suite that takes minutes, this is the difference between a ten-minute search and an afternoon.

Text search and blame answer different questions. git log -S normalize listed the two commits that changed how many times the word normalize appeared: the one that added it and the one that removed it. Without knowing where the bug was, that found it from a guess about what had changed. git blame on the function gave each line's last commit: the first two lines date from the original, and the broken return line from "Simplify slug()". The example reads blame's machine-readable --line-porcelain output, the right choice for scripts; at a terminal, plain git blame marks lines from the very first commit with a ^. Finally, git revert made a new commit that applies the opposite of the bad one, and the test passed again. History wasn't rewritten, so it's safe even after the bad commit has been shared.

Searching and blaming well

-S text, the "pickaxe", finds commits that change the number of occurrences of the text, so it finds where a function was added or deleted, but not where an existing call was edited. For that, -G regex finds commits whose changed lines match. git blame -w ignores changes of whitespace, and -C follows lines that were moved or copied from other files. Large reformatting commits make blame useless for every line they touched. List them in a .git-blame-ignore-revs file, and git blame --ignore-revs-file, or GitHub's blame view, will look past them. Remember what blame is for: a line's commit leads to its message, its pull request and its discussion. That's why the line is the way it is, which is far more useful than who typed it.

History worth searching

Each of these tools depends on how history was written. When bisect finds a five-line commit that does one thing, the bug is obvious. When it finds a two-thousand-line commit titled "updates", you've learned little. So make small commits that do one thing each, and make sure each one builds and passes the tests, so bisect can test any of them. Write messages that explain why. The first line is a short summary in the imperative, around fifty characters, as in "Simplify slug()", then a blank line, then whatever a reader will need in a year: the reason for the change, what you considered, what it fixes. git commit without -m opens your editor so there's room for that, which is one reason chapter 14 matters.

Common traps
  • Huge commits that mix unrelated changes, which bisect can only point at, not explain.
  • Messages like "fix" or "wip", which tell blame's reader nothing.
  • Forgetting git bisect reset, and carrying on work on a detached HEAD.
  • A bisect test that checks the wrong thing, which makes bisect blame an innocent commit.
  • Undoing a shared commit with reset instead of revert.

Chapter 13

Remotes, forks and pull requests

12 min read3 exercises

A remote is another copy of the repository, usually on a server. git fetch copies the commits you don't have and moves your record of the remote's branches. git push sends your commits and asks the other side to move one of its branches, which it agrees to only if nothing would be lost. GitHub builds a way of working on top of that: forks, pull requests, review and issues. This chapter simulates GitHub with plain repositories in a folder, and follows one contribution from the first commit to the merge.

Remotes, fetch and push

When you clone a repository, Git records where it came from as a remote called origin, and git remote -v lists your remotes and their addresses. For each branch on a remote, Git keeps a remote-tracking branch, such as origin/main: a ref recording where that branch was the last time you talked to the server. git fetch downloads any commits you're missing and updates those refs; it never touches your own branches. So origin/main is a snapshot, possibly hours old, and comparisons with it are only as fresh as your last fetch. git pull is a fetch followed by a merge of the remote branch into yours, or a rebase onto it if you've configured that.

git push origin feature sends your commits and asks the remote to move its feature to match yours. The remote refuses unless the move is a fast-forward, meaning your branch already contains everything it has. Otherwise, commits someone else pushed would be lost. When the push is refused, fetch, combine their work with yours, and push again. git push -u origin feature also sets origin/feature as your branch's upstream, after which plain git push and git pull know where to go, and git status says how many commits you're ahead or behind.

Forks and pull requests

On GitHub, you usually can't push to a project you don't maintain. So you fork it, which makes your own copy of the repository on GitHub's servers, clone your fork, and push branches there. A pull request asks the project's maintainers to merge one of your fork's branches into their repository. Around it, GitHub runs the conversation. Reviewers comment on lines, ask for changes or approve; automated checks run the tests; and every new commit you push to the branch updates the pull request. When it's ready, a maintainer merges it with one of chapter 11's three buttons. Inside a team with write access, people skip the fork and push branches to the main repository directly, but the pull request, the review and the checks are the same. Issues are GitHub's bug reports and discussions. A pull request whose description says Fixes #12 closes issue 12 when it's merged.

The example plays both parts. Bare repositories in a temporary folder stand in for GitHub: upstream.git is the project, and fork.git Ada's copy of it, made the way the Fork button does, with a server-side clone. Grace maintains the project; Ada contributes a small fix. Each person has their own name and email, and the clock is fixed, so the commit ids are reproducible.

What the example shows

Two remotes, two roles. Ada's clone has origin, her fork, where she can push, and upstream, the project, which she reads from. After push -u, git status -sb showed fix-typo...origin/fix-typo: the branch and its upstream, with nothing ahead or behind.

Pushes that would lose work are refused. While Ada worked, Grace pushed a commit to the project. Ada then tried to push a stray commit on main straight to upstream, and was refused with [rejected] (fetch first): the remote had a commit she'd never seen, and accepting her push would have discarded it. The example uses --porcelain to print that refusal in a stable, machine-readable form. Ada threw the stray commit away with reset --hard origin/main. To bring her branch up to date, she fetched upstream and rebased fix-typo onto upstream/main. Rebasing rewrote her one commit, so the push to her fork needed --force-with-lease, as exercise 13.2 explains.

The merge and the sync. Grace fetched the branch from Ada's fork, merged it with --no-ff, which always makes a merge commit, and used the message GitHub writes, Merge pull request #1 from ada/fix-typo. Then Ada updated her own main with pull --ff-only, pushed it to her fork, and deleted the merged branch there with the refspec :fix-typo, the same as git push origin --delete fix-typo. All four copies of main ended on the same commit.

A good pull request

Pull requests are read by busy people, so make them easy to review. Keep each one small and about one thing: a reviewer can check two hundred lines carefully, and two thousand only superficially. Write a description that says what changed and why, how you tested it, and what you're unsure about, with a screenshot for anything visible and a link to the issue it fixes. Open it as a draft when you want early feedback. When reviews come, answer every comment, either with a change or with a reason, and push fixes as new commits so reviewers can see what changed since they last looked. When you review someone else's, be specific and kind, and say which comments must be addressed and which are suggestions.

To talk to GitHub at all, you need to authenticate. Over SSH, make a key with ssh-keygen -t ed25519 and add the public half to your GitHub account; chapter 6 explained the permissions the private half needs. Over HTTPS, use a credential manager or a token, never your password. GitHub's command-line tool, gh, does all of this and more: gh auth login, gh repo fork, gh pr create and gh pr checkout turn most of this chapter into single commands.

Common traps
  • git push --force over commits someone else added; use --force-with-lease.
  • Working on your fork's main instead of a branch, so it drifts from the project's.
  • One enormous pull request that mixes a refactoring, a feature and a fix.
  • Treating origin/main as current without fetching first.
  • Pulling with a merge by habit, filling history with "Merge branch 'main'" commits; set pull.ff only or pull.rebase true.

Chapter 14

One editor, to fluency

11 min read3 exercises

Your editor is where you'll spend more working hours than anywhere else, so learning one deeply pays back every day. Fluency means moving without the mouse, opening any file or symbol in a keystroke, editing many places at once, and letting the editor understand your code well enough to rename a function safely. Pick one editor and practise it deliberately, the way chapter 16 describes. Under its best features are simple algorithms, and this chapter builds three of them: fuzzy file finding, search across files, and a rename that knows what each name refers to.

Pick one, and go deep

The choice matters much less than the depth. Visual Studio Code is the most widely used, free, and extensible for any language. JetBrains' editors, such as PyCharm, understand code most deeply out of the box. Vim and its descendant Neovim are modal editors, controlled entirely from the keyboard, steep to learn and very fast once learned, and available on every server. Emacs is a world of its own. Choose one, use it for everything, and give it a year. Whatever you choose, learn enough Vim to survive: it's what opens when Git wants a commit message on a machine you've never configured. i starts typing, Escape stops, :wq saves and quits, :q! quits without saving. Then set EDITOR in your dotfiles to the editor you chose.

What fluency means

Fluency is a list of things you can do without thinking. You can open any file by typing a few letters of its name, jump to any function or class by name, go to a definition and back again, and list every reference to a name. You can search the whole project, with a regular expression and a filter by file type, and replace across it after reviewing each change. You can put a cursor on many lines at once, or select every occurrence of a word and type once, rename a symbol everywhere it's used, and format a file on save. You can use the built-in terminal, the Git view to stage single hunks and see blame, and the debugger. The command palette, which finds any command by typing part of its name and shows its shortcut, is the key that unlocks the rest: when you don't know how to do something, ask the palette, and note the shortcut it shows you.

Learn the actions in small batches, by practice, not by reading lists. Each week, choose three to five things you do often and slowly, learn their keys, and make yourself use them even when it's slower at first; after a week they're habits. Vim has a built-in thirty-minute course, vimtutor. VS Code publishes a one-page shortcut reference for each system. Time a common task, such as finding and renaming a function, before and after a week of practice, and you'll see why the investment pays.

Under the features

Fuzzy finding scores every file path against the letters you've typed, in order, with gaps allowed, and shows the best first. Letters that start a word, after a /, _, - or ., are worth most, letters right after the previous match a lot, and letters in the file name rather than the folders a little more; letters skipped in between cost a little. The example finds the best alignment of the query in each path, the way fzf and VS Code do. Search across files is a scan of every line of every file, as chapter 3's grep -rn; ripgrep and the editors that use it make it fast by searching files in parallel and skipping those Git ignores. Rename is the one that needs real understanding. To rename a function, an editor has to know which uses of the name refer to that function, and which are a different variable, a string, or an attribute that happens to share it.

What the example shows

Initials find files. mdl picked src/shop/models/data_loader.py because its three letters start three words; the same letters in the middle of test_models.py scored about half as much. tmod found the one test file with t, m, o, d at word starts. And ord gave a near tie between three files, which is the honest answer to an ambiguous query: type one more letter. Exercise 14.3 tunes the scorer to break that tie the way most people would want.

Text replacement doesn't understand code. Replacing every total with grand_total changed all four lines that contain it, so it renamed the class attribute Receipt.total, which is a different thing. It also turned the variable totals into grand_totals and changed the printed text "total:". Whole-word replacement, \btotal\b, spared totals but still broke the other two. The rename that walked Python's syntax tree changed exactly three places: the definition and the two calls. It knew that total = 0 inside the class body defines something new, and that a string is not a name. Every version still compiles, which is the danger: the wrong renames produce working code that does the wrong thing.

Language servers

Editors used to need separate support for every language. The Language Server Protocol, published by Microsoft in 2016, split the job in two. A language server, such as pyright or basedpyright for Python, rust-analyzer for Rust or gopls for Go, understands one language: it parses your project, resolves names, and answers questions. Any editor that speaks the protocol can ask them: complete this, where is this defined, what refers to it, rename it, what's wrong with this line. That's why Neovim and VS Code can offer the same rename, and why setting up the language server is the most valuable configuration step for any language you use. Add a formatter, such as ruff or black for Python or Prettier for the web, and a linter that runs as you type, and the editor catches whole classes of mistakes before you run anything. Put the project's settings in the repository, for instance in an .editorconfig file for indentation and line endings, so everyone's editor agrees.

Common traps
  • Switching editors every few months, and never getting past the basics of any.
  • Renaming with find-and-replace across a project, instead of the editor's rename.
  • Hunting through menus instead of asking the command palette.
  • Not knowing how to leave Vim when Git opens it for a commit message.
  • Installing dozens of extensions at once; add one when you've felt the need for it.

Chapter 15

Error messages, docs and good questions

12 min read3 exercises

Most answers are already in front of you: in the error message you skimmed, the manual page, the --help output and the project's documentation. Reading them is a skill. Read tracebacks from the bottom up, decode a synopsis, and search the documentation before the web. When you do need help, a minimal reproduction does half the work: making one often reveals the bug, and when it doesn't, it gets your question answered fast. This chapter reads a traceback properly, then shrinks a failing input automatically to the two lines that matter.

Read the whole message

An error message is a program's best attempt to tell you what went wrong and where, and it's usually right. Read it slowly, all of it, before doing anything else. It names a file, a line, a value, or the thing it expected and what it found instead. When there are many errors, start with the first: compilers and test runners often report one real problem followed by a cascade of consequences. If you search for a message, search for the exact words in quotes, without the parts that are yours, such as your file names, paths and values, which nobody else's copy of the message contains.

Tracebacks, from the bottom

When a Python program fails, it prints a traceback: the chain of calls that was in progress, with the outermost first and the innermost, where the error happened, last, followed by a final line naming the exception and its message. So read it from the bottom. The last line says what went wrong. The frame just above it says where: the file, line number and function, and the line of code itself. The frames above that say how the program got there. The bug is usually in the lowest frame that belongs to your own code rather than to a library, because libraries mostly fail when given something they shouldn't have been. A traceback containing "During handling of the above exception, another exception occurred" shows two errors, and the first is usually the cause. Other languages differ in layout: Java, for one, prints the exception first and then the frames, innermost first. Learn your language's convention once.

Manuals, help and documentation

Every command-line tool documents itself. man ls opens the manual page. Its sections are always in the same order: NAME, SYNOPSIS, DESCRIPTION and the options, then often EXAMPLES, FILES, ENVIRONMENT and SEE ALSO. Search inside it with /, press n for the next match, and q to quit. man -k word searches the one-line descriptions of every page. Manuals are grouped in numbered sections, so man 1 crontab is the command and man 5 crontab the file format. Most programs also answer --help with a summary, and the community tldr pages give the five commands people actually type. For languages and libraries, read the official documentation, for the version you have. Python's is excellent, and help(thing) shows it from inside Python.

A synopsis is a compact grammar for a command's arguments. Square brackets mark something optional, a bar separates alternatives, and an ellipsis means "one or more". cp [-R [-H | -L | -P]] [-f | -i | -n] source_file ... target_directory says that -R is optional, and that -H, -L or -P may follow it. It also says that at most one of -f, -i and -n belongs in a command, and that copying several files requires a folder at the end.

The example takes a short function that averages prices by category from a menu file, and a real menu of about a hundred lines on which it crashes. It reads the traceback from structured data rather than printing it, because the exact layout of tracebacks changes between versions of Python. Then it hands the failing input to delta debugging, Andreas Zeller's algorithm for shrinking a failing input automatically. The algorithm repeatedly removes chunks of the input and keeps any smaller version that still fails, until removing anything at all makes the failure go away.

What the example shows

The traceback pointed straight at the cause. Its last line said ZeroDivisionError: division by zero; the frame above, line 20 in average(), showed the division by len(numbers), so the list was empty. The frame above that, line 11 in average_prices(), showed when average is called: when a new category starts and the previous one is finished. Together they say "a category had no items". Reading only the first line of the traceback would have told you nothing.

Shrinking found the real conditions. Delta debugging needed 30 runs to cut 104 lines down to two, [specials] and [sides]. Neither line fails alone: an empty category followed by another category is the bug, while an empty category at the very end is handled correctly. That's a fact you'd likely never have found by staring at the hundred-line menu, and it's exactly what the fix needs. The bug report in section 3 says in five lines what a confused paragraph and an attached file would otherwise have left the reader to work out. You can shrink by hand the same way, deleting halves of the input or the code and keeping the failure, as exercise 15.3 does.

Asking a good question

When you've read the message and the documentation and you're still stuck, ask, and make the question easy to answer. Give a minimal, reproducible example: the smallest complete program and input that show the problem, which someone else can run and see fail. Say what you expected and what happened instead, with the exact error copied as text, never a screenshot. Name the versions of everything involved, and list what you've already tried and ruled out. Making that example is itself a debugging technique: in shrinking the problem, you'll often find it. So will explaining it out loud to anyone, or anything, which is why programmers talk of rubber-duck debugging. The same rules apply when the one you ask is an AI assistant. Give it the minimal example and the exact error, and then check its answer, because you have to be able to explain every line you ship.

Common traps
  • Reading the first line of a traceback instead of the last.
  • Searching for an error with your own paths and names in it, which no one else's copy contains.
  • Screenshots of code or errors, which can't be searched, copied or run.
  • "It doesn't work", without what you expected, what happened, and what you tried.
  • Asking before reading, when the answer is in the message or the manual.

Chapter 16

How to learn

11 min read3 exercises

How you study matters as much as how long. Rereading and highlighting feel productive and produce little. Decades of experiments point to three things that work far better. Testing yourself beats reviewing. Spreading reviews out over days and weeks beats massing them. And practising a skill at the edge of your ability, with feedback, beats repeating what you can already do. This chapter explains why, uses a small model of forgetting to show what spacing buys, and builds the scheduler flashcard programs use.

Why rereading fails

Reading a chapter a second time feels like learning, because everything is familiar: you recognise each idea as it comes. But recognising is not recalling. The test that matters is whether you can produce the idea when you need it, with the book closed, and familiarity says little about that. Psychologists call the mistake an illusion of fluency, and it's why students who reread and highlight are often confident and wrong about what they know. The remedy is to make study feel more like the test. That's harder, and the difficulty is the point: the effort of retrieving something is what strengthens it.

Retrieval practice

In a well-known experiment by Henry Roediger and Jeffrey Karpicke, published in 2006, students studied short prose passages. Some reread a passage several times; others read it once and then tried to write down what they remembered. Five minutes later, the rereaders remembered slightly more. Two days and a week later, the students who had tested themselves remembered much more. Later experiments found retrieval practice beating rereading, note-taking and concept mapping across subjects and ages. The practical forms are simple. Close the book and write what you remember, then check. Use flashcards that ask a question. Explain an idea aloud as if teaching it. And, throughout this volume, predict what a command will print before you run it, which is retrieval with immediate feedback.

Spacing

In the 1880s, Hermann Ebbinghaus learned lists of nonsense syllables and measured how much he'd forgotten after various delays. The result was the first forgetting curve: steep at first, then flattening. He also found that reviewing a list again, after a delay, made the next curve shallower. A century of later work confirmed it as the spacing effect. A 2006 review by Nicholas Cepeda and colleagues, pooling hundreds of experiments, found that the same total study time, spread over separate sessions, is remembered far better than when it's massed into one. The best gap grows with how long you want to remember. To keep something for a year, review it at intervals of weeks, not minutes. Cramming works, after a fashion, for tomorrow's test, and leaves almost nothing a month later.

The example turns those findings into a small model. Its forgetting curve has the shape modern schedulers use, and a review strengthens a memory more the closer it was to being forgotten. It compares five plans for 200 facts learned on the same day, each reviewed only during the first month, and then follows one fact under the scheduling rule that flashcard programs use. Its numbers come from invented constants, so read them for their shape, not as measurements.

What the example shows

Cramming adds almost nothing. Four more passes on the evening of learning raised recall two months later from 13% to 15%. In the model, as in life, reviewing what you can recall easily barely strengthens it, because there's no effort of retrieval. The same number of reviews spread across the month, on days 1, 3, 7, 14 and 28, raised it to 81%.

Scheduling by need does slightly better, with less work. Leitner boxes, Sebastian Leitner's 1970s system of moving cards between boxes reviewed at doubling intervals, gave 83% from 4.9 reviews per fact. Reviewing each fact just as its predicted recall falls to 90%, which is what modern schedulers do, gave 86% from 4.8. They spend reviews where they're needed, often on facts about to be forgotten and rarely on secure ones. Under that rule, one fact's gaps between reviews grew from one day to three, six, fifteen, thirty-nine and ninety-eight: six reviews in half a year left it stable for the best part of a year. This is the real promise of spaced repetition: remembering something for years costs a few minutes in total.

Flashcards that work

A spaced-repetition program does the scheduling for you. Anki is free, open source and runs everywhere, and since 2023 includes the FSRS scheduler, which fits a memory model to your own review history and targets 90% recall by default, the rule the example used. The program is the easy part; the cards decide whether it works. Make each card ask one thing, as a question you have to answer from memory, in your own words. Ask why and when, not just what: "Why must cd be a shell builtin?" teaches more than "What is cd?". Use cloze deletions, blanks in a sentence, for syntax, such as "find . -name '*.py' -____ rm {} +". Add cards as you learn, review every day, about fifteen minutes, and delete cards that annoy you. For this stage, good material is anything you've looked up twice: options, Git concepts, regular-expression syntax, exit statuses.

Deliberate practice

Facts are only part of it; most of this stage is skills, and skills are learned by practice of a particular kind. Anders Ericsson's studies of expert performers, beginning with violinists in 1993, distinguished deliberate practice from doing the activity. It has a specific goal just beyond what you can do now, immediate feedback, full attention, and repetition with refinement. Playing through pieces you already know isn't it, and neither is typing commands you already know. Learn Git Branching is deliberate practice for Git: each level is a precise goal, the graph shows you instantly whether you reached it, and you can repeat a level until it's fluent. So is solving an exercise in this volume a second time, a week later, from memory.

Two more findings are worth knowing. Interleaving, mixing different kinds of problems in one session instead of practising one kind at a time, feels worse and works better, because each problem makes you first decide which tool it needs. Doug Rohrer and Kelli Taylor showed it with mathematics problems in 2007. And Robert Bjork's desirable difficulties sums up the chapter: the conditions that make practice feel harder, testing, spacing, interleaving, are the ones that make learning last. If studying feels easy, check that you're not just rereading.

Common traps
  • Rereading and highlighting as the main way of studying.
  • Cramming, which serves tomorrow and forgets next month.
  • Watching tutorials without doing the exercises, which builds recognition, not skill.
  • Flashcards that are too big, "Explain Git", or that only ask you to recognise an answer.
  • Practising only what you're already good at, because it feels like progress.

Exercise 16.1Ten cards

Write ten flashcards for chapters 1 to 3 of this volume, and say what makes each a good card.

Show solution
Q: What does a program receive from the line  showargs $f  when f="my notes.txt"?
A: Two arguments, "my" and "notes.txt": the unquoted expansion is split.
Q: Why does  sort data.txt > data.txt  leave an empty file?
A: The shell truncates data.txt for the redirection before sort starts reading it.
Q: In what order are these applied:  cmd > out.txt 2>&1 ?   Where does stderr go?
A: Left to right: 1 to out.txt, then 2 to where 1 points: both go to out.txt.
Q: What's a pipeline's exit status by default, and what changes it?
A: The last command's; set -o pipefail makes it fail if any command failed.
Q: What does exit status 127 mean? And 126? And 130?
A: Command not found; found but not executable; killed by SIGINT (128 + 2).
Q: Why does uniq need sorted input?
A: It only merges duplicate lines that are adjacent.
Q: Fill in:  find . -name '*.tmp' -____ | xargs -0 rm
A: print0
Q: In a regular expression, what does . match? How do you match a real dot?
A: Any one character; \. (or grep -F for plain text).
Q: In awk, what are $1, $NF and NR?
A: The first field, the last field, and the current line's number.
Q: When does set -e not stop a script after a failing command?
A: When the command's status is being tested: in an if, a while, or beside && or ||.

Each card asks one thing, and most ask why or when, not just what, so that recalling the answer exercises understanding. They're questions you must answer from memory, not statements to recognise. The answers are short enough to check in a second. The fill-in card trains a detail that's easy to forget and expensive to get wrong. Write your own cards in your own words, rather than copying these: making the card is the first act of retrieval, and you'll remember your phrasing better than anyone else's.

Exercise 16.2A week of deliberate practice

Plan a week of deliberate practice to make Part III's Git operations fluent, at about thirty minutes a day.

Show solution

Day 1: Learn Git Branching's introduction levels, then repeat any level you needed hints for until you can do it without them. Day 2: in a scratch repository, recreate from memory the graph in chapter 10's example, a branch, a detached commit, a rescue from the reflog, checking with git log --graph --all after each step. Day 3: the "moving work around" levels, rebase and cherry-pick, and then make a conflict on purpose and resolve it twice, once by merging and once by rebasing. Day 4: interleave, with a mixed set of five small tasks, such as undoing a pushed commit, splitting a commit, recovering a deleted branch, bisecting a planted bug and fixing a commit message. Choosing the right command for each is half the exercise. Day 5: time yourself on day 4's set, then do it again without looking anything up. Each session has a specific goal, immediate feedback from the graph or the test, and a difficulty just past where you are. When a task becomes easy, replace it with a harder one. And put the facts you had to look up on flashcards.

The deliverable

The stage asks for two things, both public and both with a README written for a stranger: a repository of your dotfiles, and one shell script that automates a chore you genuinely repeat. Chapters 8 and 4 build a small working version of each; the lists below say what the full versions need. Both will outlive the stage. You'll install the first on every machine you use, and the second is the start of a habit of automating what bores you.

1. A public dotfiles repository

Your settings for the tools you use every day, in a repository anyone can read, with a script that installs them. Chapter 8 is the model.

  1. Settings for your shell, Git and editor, grown a line at a time, each with a comment saying why it's there.
  2. An install script that links every file into place, backs up anything it would replace, never deletes, and is safe to run again, plus an uninstall that reverses it.
  3. Per-machine and private settings in local files that the shared ones include, ignored by Git, and no secret anywhere in the history: check with git grep or a scanner before you publish.
  4. Tested on a clean account or a fresh container, with anything specific to macOS or Linux behind a check of uname.
  5. A README that says what each file configures, gives the one command that installs it, says what that command changes and how to undo it, and lists the systems you've tried it on.

2. A script for a chore you repeat

Pick something you really do by hand every week: tidying downloads, backing up a folder, renaming photos, cleaning old branches, starting your day's tools. Chapter 4 is the model.

  1. Strict mode, a usage message for -h and for wrong arguments, options parsed with getopts, exit statuses 0, 1 and 2, and every message on stderr.
  2. A dry run that shows exactly what would happen; nothing overwritten or deleted without a check; safe to run twice; and a lock and a trap if two runs could ever overlap.
  3. Every expansion quoted, no warnings from ShellCheck, and either bash 3.2 compatible or a clear statement of the version it needs.
  4. Tests that run it in a temporary folder and check the results, including what happens with bad arguments, a missing folder and names with spaces.
  5. Installed as a command through your dotfiles, documented in a README, and if the chore is regular, run on a schedule with cron on Linux or launchd on a Mac.

For both: keep them under Git from the first day, with small commits and messages that explain why, as chapter 12 describes. Make at least one change through a pull request, from a branch, even in your own repository, so chapter 13's workflow is something you've done rather than read about. Then ask someone else to install your dotfiles and run your script from the README alone, and fix whatever confused them.

The sixteen rules

One per chapter, each linked back to it. Read them before you start a new script or a new repository, and again when a tool surprises you.

  1. Quote every expansion, and know exactly which list of arguments a line becomes.
  2. Results to stdout, messages to stderr, and check the status of every step, including inside a pipeline.
  3. Ask questions of text with small tools in a pipeline: quote the patterns, and sort before you count.
  4. Strict mode, a dry run, and never overwrite: a script must be safe to run twice.
  5. A name points to an inode, and a symbolic link points to a name.
  6. The folder decides who may delete; never fix a permission error with 777 or sudo.
  7. The environment flows down, never up; ask type -a what a name will run.
  8. Keep your settings in a public repository, linked into place, and your secrets out of it.
  9. A commit is a snapshot named by its contents; changing the past renames everything after it.
  10. Branches are labels and the reflog remembers them; only uncommitted work can really be lost.
  11. Merge shared work; rebase only commits nobody else has.
  12. Make small commits that explain why, and bisect whatever used to work.
  13. Work on branches, push with a lease, and keep pull requests small and explained.
  14. Learn one editor deeply, and rename with a tool that understands the code.
  15. Read the whole message, from the bottom, and ask with a minimal reproduction.
  16. Test yourself, space your reviews, and practise at the edge of your ability.
